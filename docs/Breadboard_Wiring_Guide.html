Breadboard wiring guide

nRF9160 DK + Adafruit breakouts · Phase 1 bring-up · no custom PCB

Before you plug anything in: find the VDD selector switch on the DK (marked 1.8V / 3V) and make sure it's on 3V. At 1.8 V the haptic driver and the microSD breakout won't work, and the amp's logic thresholds get marginal. Also confirm the header's 5V pin actually reads ~5 V with a multimeter before you hang the amp off it.

What's already taken on the DK

The Arduino headers look like 20 free pins. They aren't. This is what's already wired to something:

Disabling uart1 is what makes this fit. It's the "Arduino serial" port, which you have no use for — your console is uart0 on completely different pins and stays untouched.

4. LSM6DSOX IMU I²C, optional

Same bus as the haptic driver — VIN→VDD, GND→GND, SDA→SDA, SCL→SCL. Different I²C address (0x6A), so they coexist fine. Fully solderless via STEMMA QT. Skip it until everything else works; the DK already has an accelerometer.

6. Notification LED

Don't wire one. The DK has four, and they're already in devicetree as led0–led3. Save the GPIO.

7. ESP32 Feather

Keep this off the breadboard for now. It's a separate test rig for the AirPods/A2DP experiment and for WiFi-based server testing — it isn't part of the nRF9160 signal chain. Wiring it in now just adds variables. Bring it up on its own once the DK peripherals work.

Devicetree overlay

Create boards/nrf9160dk_nrf9160.overlay in your app folder:

/* Free P0.00, P0.01, P0.14, P0.15 — we don't use the Arduino UART */
&uart1 {
	status = "disabled";
};

&pinctrl {
	i2s0_default_alt: i2s0_default_alt {
		group1 {
			psels = <NRF_PSEL(I2S_SCK_M, 0, 14)>,   /* BCLK -> amp BCLK */
				<NRF_PSEL(I2S_LRCK_M, 0, 15)>,  /* LRC  -> amp LRC  */
				<NRF_PSEL(I2S_SDOUT, 0, 16)>;   /* DIN  -> amp DIN  */
		};
	};

	pdm0_default_alt: pdm0_default_alt {
		group1 {
			psels = <NRF_PSEL(PDM_CLK, 0, 0)>,      /* -> mic CLK */
				<NRF_PSEL(PDM_DIN, 0, 1)>;      /* -> mic DAT */
		};
	};
};

&i2s0 {
	status = "okay";
	pinctrl-0 = <&i2s0_default_alt>;
	pinctrl-names = "default";
	clock-source = "PCLK32M_HFXO";
};

&pdm0 {
	status = "okay";
	pinctrl-0 = <&pdm0_default_alt>;
	pinctrl-names = "default";
	clock-source = "PCLK32M_HFXO";
};

/* microSD on the Arduino SPI header */
&arduino_spi {
	status = "okay";
	cs-gpios = <&arduino_header 16 GPIO_ACTIVE_LOW>;  /* 16 = D10 */

	sdhc0: sdhc@0 {
		compatible = "zephyr,sdhc-spi-slot";
		reg = <0>;
		status = "okay";
		spi-max-frequency = <8000000>;

		mmc {
			compatible = "zephyr,sdmmc-disk";
			disk-name = "SD";
			status = "okay";
		};
	};
};

And in prj.conf, enable only what you're testing at the time:

# speaker (I2S)

Bring-up order

Wire and prove one at a time. Do not build the whole breadboard and then flash — if three things are wrong at once you'll never find any of them.

  1. Haptic driver first. Four wires, no soldering. Run an I²C scan and confirm 0x5A shows up. This proves your I²C, your overlay workflow, and your wiring habits with the lowest possible stakes.
  2. Speaker. Solder the amp header, wire I²S, play a 440 Hz sine from a buffer. Hearing a tone is the single most motivating milestone in this whole phase.
  3. Microphone. Capture a second of PDM audio, dump the samples over serial, plot them in Python. Confirms the mic works before you try to stream it anywhere.
  4. Loopback. Mic → buffer → speaker, on-device. No network, no server. If this works you have a working audio path end to end.
  5. microSD. Mount FAT, write a file, read it back.
  6. Then the network layer.

Gotchas

Secure vs non-secure build target. You're building for nrf9160dk/nrf9160, which is fine for all of the above. But the LTE modem library requires the non-secure target nrf9160dk/nrf9160/ns (it needs TF-M). When you switch, do a pristine build — peripherals get reassigned to the non-secure domain and a stale build directory will produce confusing errors.
Common grounds. Every breakout's GND must connect back to the DK's GND. On a breadboard this means running a ground rail, not one wire per board daisy-chained. Floating grounds on I²S produce noise that looks exactly like a firmware bug.
I²C pull-ups. Both Adafruit boards have them on-board. With two devices you'll have two sets in parallel — still fine. Add a third I²C device and you may need to cut one set.
If the mic reads silence, check SEL is actually grounded before you touch the code. Floating SEL is the number one cause.
