Slide 4 -- RAM and Bandwidth Constraints
-----------------------------------------
Communication job: Make the embedded resource ceiling feel concrete, then show why
audio compression is an enabling design decision for a conversational pendant.

Current layout / visual inventory: Title plus two bullets in the full content placeholder;
blank lower half; no visual asset. There is enough width for copy at left and a visual at
right, or enough lower-body area for a wide flow after a one-line claim.

Proposed visual: a single "audio budget" signal-path diagram, not a generic RAM icon.
Show a pendant microphone at left feeding a small local-memory chip labeled "available
RAM (verify)", then a waveform that visibly narrows into a compact packet stream after
an "Opus encode" step, ending at a cloud conversation endpoint. Above the compressed
stream, show a simple, source-backed bitrate comparison (e.g., uncompressed PCM ->
Opus) with the actual tested settings; use an annotated "up to 20x smaller in this
configuration" callout only if verified. This both explains bandwidth and leaves RAM as
the device constraint rather than implying that Opus reduces RAM.

Suggested on-slide copy: "A tiny memory and link budget makes every audio byte count."
Support line: "Encode on-device; stream compact audio frames as they are captured."

Accuracy care:
* "256 KB of RAM" must name the exact usable memory pool, MCU / core, firmware build,
  and whether buffers and runtime allocations are included. The visible exploded view
  names an nRF5340, so do not present 256 KB as the device's total RAM without checking
  the chip and memory partitioning.
* "256 KBps data" is ambiguous (kilobytes/s versus kilobits/s, uplink versus total link,
  sustained versus peak). State its measured/assumed transport constraint and units.
* A "20x" Opus reduction needs input format, sample rate, channel count, packet loss
  assumptions, and target bitrate. It is a configuration-dependent compression ratio,
  not a universal Opus property.
* "real-time conversations possible" needs an end-to-end latency / reliability test;
  avoid treating compression alone as proof.

Slide 5 -- Reducing Latency
---------------------------
Communication job: Explain how three pipeline choices remove wait time from a spoken
request, instead of making an unmeasured claim that the experience is "dramatically"
faster.

Current layout / visual inventory: Title and three large bullets occupy the upper body;
lower-body whitespace; no visual asset. Best refit: concise three-line copy in the left
third and a wide left-to-right workflow across the rest of the body.

Proposed visual: an end-to-end latency waterfall / overlapping-timeline diagram. Stack
three lanes: capture, upload, and model response. A faint "wait until recording ends /
transcribe / request" baseline sits above, while the emphasized path starts streaming
audio chunks during speech, sends those chunks immediately, and lets a realtime
multimodal model respond without a separate speech-to-text stage. Add KV cache only at
the model-context stage with a small label "reuses prior context". The key visual effect
is overlap, not a decorative speedometer.

Suggested on-slide copy: "Start work while the user is still speaking."
Support line: "Streaming audio + native audio input remove serial handoffs; context
caching reduces repeated model work."

Accuracy care:
* KV caching reduces repeated attention/context computation when cache reuse is valid;
  it does not by itself make arbitrary "computer actions" faster. Tie any speed claim to
  a measured workload and cache-hit conditions.
* "real-time models" and native-audio input are provider/model-specific capabilities.
  Name the model/API or phrase as a design choice rather than a universal capability.
* Avoid implying that eliminating transcription eliminates all latency, cost, or errors.
  Compare measured p50/p95 turn latency (with network conditions) if a numeric claim is
  desired.

Slide 6 -- System prompt
------------------------
Communication job: Show the prompt-design principle: give an agent a compact map of the
distributed system, then enable progressive tool discovery rather than dumping a long
tool catalog into every context.

Current layout / visual inventory: Title and two long bullets, with a large blank lower
body; no visual asset. Use the entire content region for the visual; retain at most one
short explanatory sentence above or below it.

Proposed visual: a split "context budget" architecture illustration. On the left, a
thin system-prompt document contains a small topology map: Pendant, Phone, Desktop,
Browser, Cloud. On the right, show a deliberately crossed-out dense tool list contrasted
with a compact "tool categories" index (for example: Files, Browser, Computer, Tasks).
An agent queries a category, discovers only relevant tools, and invokes a specific tool.
Use arrows labeled "describe nodes" and "discover on demand"; do not fabricate a real
terminal or product screenshot.

Suggested on-slide copy: "Keep coordination context compact; discover capabilities only
when a task needs them."

Accuracy care:
* "wastes too many tokens" is directionally plausible but needs a token-budget comparison
  if it is presented quantitatively. Prompt tokens can also trade off with tool-selection
  reliability and extra discovery calls.
* "could get agents off track" is a behavioral hypothesis. Support it with evaluation
  results or phrase it as a design rationale / observed failure mode.
* The system prompt should not imply tool availability or authorization; discovery must
  remain constrained by the current node, user permissions, and policy.

Slide 7 -- Deterministic vs. LLMs
---------------------------------
Communication job: Establish a routing policy: handle known, local, low-risk commands
deterministically; escalate the remaining requests through a capability/cost ladder.

Current layout / visual inventory: Title plus three very dense bullets extend through
the body; no visual asset. This is the most text-crowded slide. Replace the body with a
full-width decision flow and only 2--3 short labels; do not retain the paragraph.

Proposed visual: a decision-routing flowchart with a central spoken-request waveform.
First diamond: "wake word / known offline intent?" Yes -> local deterministic action
(alarm, timer) -> done. No -> "simple, permitted request?" -> economical cloud model.
The remaining branch goes to a more capable model. Add small, distinct captions beneath
the outcomes: "fast / private / low power", "lower cost", and "complex reasoning".
Arrows should show the decision, not make the three options look interchangeable.

Suggested on-slide copy: "Use deterministic code for the predictable; spend model
capacity only when the request warrants it."

Accuracy care:
* Use the conventional plural "LLMs" in the title.
* Offline wake-word RAM use varies substantially by model, feature set, quantization,
  MCU, and runtime. "Tens of KB" needs a named implementation and measured flash/RAM
  footprint; otherwise say "can fit within a small embedded memory budget."
* Wake-word success does not establish full offline voice-command capability; intent
  recognition, false accepts/rejects, and noisy-environment performance need separate
  evidence.
* "Cheaper" and "more expensive" models need a routing criterion, privacy/consent guard,
  and a failure/approval path for actions. Avoid a simplistic claim that the inexpensive
  model is always suitable for easy questions.

Slide 8 -- The Hivemind
-----------------------
Communication job: Make the distributed product architecture legible: five nodes bring
their own context and tools, while tasks and memory can move through a shared relay.

Current layout / visual inventory: Title and three bullets; no visual asset. The body is
ideal for a full-width architecture map with the text replaced by short labels.

Proposed visual: a hub-and-spoke architecture diagram. Place a small pendant, phone,
desktop, browser extension, and cloud relay as five labeled nodes around a center labeled
"shared task + memory coordination." Draw solid bidirectional paths from each node to
the center. Inside each outer node, show only one environment-specific tool cue (for
example: microphone, mobile context, terminal/computer control, current webpage,
server-side execution). Use a distinct dashed arrow to demonstrate one example handoff:
"Phone request -> Desktop agent." This is a real system diagram, not an illustration of
a generic AI brain.

Suggested on-slide copy: "Each node acts locally; tasks and memory keep the system
coordinated."

Accuracy care:
* "Memories and tasks are shared between all nodes" should specify the synchronization
  model, scope, consistency/conflict behavior, retention, encryption, and user controls.
  It must not imply unbounded cross-device access.
* "Each node has unique tools" needs a current capability matrix; browser extension,
  desktop control, and cloud actions especially require platform permissions.
* Label the cloud relay separately from a store of record unless the latter is actually
  implemented. Describe handoff as an intended/demo capability if it is not deployed.

Slide 9 -- Future possibilities
-------------------------------
Communication job: Close with a provocative but understandable future direction: a
consented hardware bridge could let agents interact across a user's device ecosystem.

Current layout / visual inventory: Title plus one long bullet at the upper body; most of
the body is blank; no visual asset. Reserve a short framing sentence at upper left and
use the rest of the body for the concept diagram.

Proposed visual: a conceptual USB bridge diagram, intentionally labeled "exploratory."
Put a small USB-C dongle in the center. On the left, show a user's laptop; on the right,
show a user's phone and tablet; above, a remote agent service. Use separate labeled
paths rather than claiming one USB protocol handles all roles: "HID input" (keyboard /
pointer), "display or screen stream" (only where supported), and "authorized control
session." Gate every path through a visible "user approval + encrypted session" shield.
This retains the provocative idea while making the trust boundary explicit.

Suggested on-slide copy: "A consented hardware bridge could extend an agent's reach
across the devices a user already owns."

Accuracy care:
* A USB device can emulate HID peripherals such as a keyboard, mouse, or trackpad, but
  it does not simply "pretend to be a monitor" across arbitrary computers, phones, and
  iPads. Display transport/capture/control support depends on host OS, port mode,
  drivers, and platform restrictions.
* Do not say it sends "all the data" to remote servers. Define the minimum data types,
  consent event, encryption, retention, and processing location. This is a significant
  privacy/security claim.
* Remote control can create serious authorization and abuse risks. Make clear that any
  implementation requires explicit per-device permission, visible user control, and
  platform-policy compliance; present it as future exploration, not a current feature.
