## Capabilities it proposed

### "Make this change across my Mac and logged-in sites, and keep working until you can prove the final state is correct; if one step fails, tell me exactly what remains and safely repair only the reversible parts."
- **useful because:** Today the system can execute actions and produce receipts, but a receipt is not proof that an external service accepted the change. This gives the owner a single outcome across browser, Mac, relay, and pendant: an explicit target invariant, independent postcondition checks, partial-failure accounting, and a repair/resume path rather than false success.
- **path:** faculty-judgement → faculty-action → faculty-perception → browser-extension → mac-planner → mac-terminal → relay-realtime → unified
- **model tier:** gpt-5.6-luna for planning and reconciliation; gpt-4.1-mini for cheap repeated postcondition extraction; gpt-realtime-2.1 only to communicate urgent confirmation or failure on the pendant.
- **latency:** Reversible steps begin within 2 seconds; verification may take 5–20 seconds per external surface. Long jobs continue on the relay after disconnect, with a concise pendant update when done.
- **cost:** Approximately $0.02–$0.15 per ordinary workflow, dominated by planner/reconciliation calls and browser page extraction; repeated verification should use the cheaper tier and hashes/diffs to avoid resending full context.
- **security:** Private logged-in page contents and local file/app state leave the device only to the authenticated relay/model as required. Never auto-submit irreversible actions: require explicit pendant confirmation showing the exact mutation. Store only redacted evidence snippets and hashes, with short retention. If verification is ambiguous, report unknown rather than claiming success.
- **missing:** A first-class goal/invariant record linked to every action job (what must be true, acceptable evidence, expiry).; Independent verification steps that can read the resulting browser/Mac state after execution and classify proven/failed/ambiguous.; Durable partial-progress and resume/compensation semantics spanning Mac jobs and browser commands.; Pendant-friendly approval and completion/failure events tied to the same job ID.

### "If this exact situation occurs, carry out the approved action automatically—but only while the facts I approved are still true, and tell me if the situation changed instead of using stale permission."
- **useful because:** The owner cannot safely delegate conditional real-world actions today. Existing routines, watches, plans, and approvals are separate: an approval can outlive the page state it was based on, or a delayed Mac/browser job can act after circumstances change. This would let the owner delegate time-sensitive work without granting a broad standing permission or forcing them to stay present.
- **path:** faculty-judgement → faculty-perception → faculty-action → browser-extension → mac-planner → mac-terminal → relay-realtime → unified
- **model tier:** Use the background tier for polling and deterministic condition evaluation; use gpt-5.6-luna only to interpret an ambiguous condition or construct the proposed action; use gpt-realtime-2.1 only for a just-in-time pendant confirmation or exception.
- **latency:** Condition checks should be seconds to minutes depending on the trigger, with no model call for unchanged structured facts. Once triggered, start within 2 seconds; refuse execution if the approval lease or state hash is stale.
- **cost:** Low for structured triggers: approximately $0.001–$0.02 per evaluation cycle when deterministic, with occasional $0.02–$0.10 planner calls for ambiguous page changes. Storage is a small signed condition/approval record.
- **security:** A permission must be narrowly bound to operation type, account/site, maximum amount or scope, expiry, and a hash of the facts shown to the owner. Private browser data stays behind the authenticated bridge/relay; secrets never enter the model. Any irreversible action requires an explicit policy choice and a single-use approval token; if facts drift, pause and notify rather than guessing.
- **missing:** A durable conditional-operation primitive with trigger, predicate, action, expiry, and failure policy.; Signed state snapshots and approval leases bound to the exact precondition hash, with revocation and audit history.; A deterministic event source joining browser changes, Mac state, and relay schedules without repeatedly sending full context to a model.; A safe executor that re-checks predicates immediately before each side effect and reports stale/changed conditions to the pendant.


## Changes it proposed to its own stack

### `integration` — Introduce a signed, append-only operation envelope shared by relay, Mac agent, and browser bridge. Each envelope carries operationId, parent decisionId, target invariant, preconditions, approval state, idempotency key, per-step lease, typed result, evidence reference, and terminal outcome (proven/failed/unknown). Require every surface to echo the operationId; have the relay reconcile late/out-of-order events and expose one causal timeline to the pendant. This is a protocol change, not another action endpoint, and it must cover browser commands and Mac jobs uniformly.
- **owner gets:** The owner gets one trustworthy answer about a real-world request instead of disconnected Mac job IDs, browser command IDs, and spoken claims. If the link drops or a step partially succeeds, they can resume safely without duplicate purchases/messages or wondering which device acted.
- effort: Medium-high: define schema/state machine, add persistence and signing at relay, adapt Mac job and browser bridge adapters, add replay/idempotency tests, and render a compact timeline plus proof state in the pendant/dashboard.  ·  risk: Schema bugs could strand jobs or cause duplicate execution. Roll out read-only correlation first, then enforce idempotency for reversible actions; retain compatibility with existing job receipts and provide a migration/replay tool. Never infer success from missing events.
- cost: Negligible per-request storage/compute; roughly 1–3 KB of metadata per step plus short-lived evidence hashes. No model cost except optional reconciliation.  ·  latency: Adds under 100 ms for envelope persistence and event correlation; no extra model round trip on the happy path.
- security: Operation envelopes and evidence references must be authenticated and scoped to the owner; redact page text and local paths, sign cross-surface events, and expire evidence according to retention policy. Approval tokens must be single-use and bound to operationId plus exact mutation.
- depends on: Durable job runner and browser command queue must preserve operationId/idempotency keys.; A verifier endpoint/tool (currently requested but unavailable) to classify postconditions as proven/failed/ambiguous.; Pendant confirmation and action-lease indicators for irreversible steps.; Relay storage/retention policy for evidence references.

### `browser-harness` — Add a browser-bridge liveness gate and queue reconciler: when heartbeat is absent, stop retrying commands, mark them waiting-for-device (not failed), coalesce duplicate idempotent requests, and notify the relay with the exact pending count. On reconnect, perform a read-only tab/session handshake, replay only commands whose lease and idempotency key are still valid, and expire stale commands with a pendant-readable explanation. Expose a one-click/dashboard drain or cancel operation rather than leaving seven opaque pending commands.
- **owner gets:** The owner will not get repeated timeouts or accidentally replayed browser actions after reopening Safari. They will know what is waiting, what expired, and what can safely resume—even when the browser extension disappears while they are away.
- effort: Medium: heartbeat state machine, durable queue metadata, idempotency/coalescing, reconnect handshake, and dashboard/relay notification.  ·  risk: A reconnect race could duplicate an action or incorrectly discard a valid one. Default to no replay for writes, replay reads only, and require explicit approval to resume any mutation; preserve existing receipts.
- cost: Small D1/local JSON metadata overhead; no additional model calls in the normal path.  ·  latency: Adds one handshake round trip on reconnect; prevents 45-second per-command timeout delays while offline.
- security: Keep session/tab identifiers scoped and do not expose URLs or private page text in notifications; authenticate heartbeats and bind replay leases to the owner/session.
- depends on: Browser extension heartbeat/polling endpoint already present (/browser/heartbeat, /browser/poll).; Durable browser command queue and idempotency keys (existing/partially implemented).; Pendant or relay event channel for waiting/expired status.

### `integration` — Add a cross-surface shadow-execution engine that runs an approved action plan against captured, redacted state snapshots before touching the live Mac or browser. It should compute an expected diff and dependency impact (files, calendar entries, messages, account fields), detect conflicting concurrent changes, and attach the snapshot hash to the eventual live execution. The live executor must abort if the current state no longer matches the simulated basis, then request a fresh plan.
- **owner gets:** Before asking the system to do something consequential, the owner could see not merely the fields that will change but whether the whole multi-device plan is internally consistent. This catches stale tabs, changed prices, overwritten files, and contradictory steps before any real side effect.
- effort: High: normalize Mac and browser state into a common redacted model, implement adapters for read-only shadow actions, diff/impact rendering, snapshot hashing, and abort-on-drift enforcement.  ·  risk: A simulation can miss behavior that only occurs live, so it must be labeled predictive and never treated as proof. Snapshot capture could expose private data; redact aggressively and expire snapshots. If an adapter cannot model a step, mark it unknown and require a live confirmation rather than silently proceeding.
- cost: Extra local storage and read-only adapter work; deterministic simulation is cheap, with planner escalation only when conflicts or unmodeled effects require interpretation.  ·  latency: Adds roughly 1–5 seconds for local plans and potentially longer for multi-tab reads, but avoids expensive failed or duplicated live actions.
- security: Snapshots remain encrypted/local where possible; send only minimal structured diffs to the relay. Bind approval to the exact plan and snapshot hash, and invalidate it on any state drift.
- depends on: A common typed operation envelope and invariant/approval lease.; Read-only browser inspection and AppleScript adapters for Mac state.; A diff viewer and pendant-friendly summary of predicted effects.; A live executor that enforces snapshot-hash preconditions.
