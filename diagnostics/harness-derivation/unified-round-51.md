## Capabilities it proposed

### "“Only interrupt me when it is actually worth it—and if I miss it, make sure it comes back.”"
- **useful because:** Today relay jobs, browser watches, Mac reminders, and spoken conversation can each notify independently, causing duplicate or badly timed interruptions. A single attention contract would merge events, rank urgency, observe whether the owner is currently speaking/typing/in a meeting, deliver one concise pendant utterance when safe, and retain an acknowledged/snoozed receipt so nothing urgent disappears. This is genuinely cross-surface: browser supplies private-page changes, Mac supplies focus/calendar state and can prepare a review card, relay arbitrates while awake, and the pendant is the only always-with-owner output.
- **path:** browser-extension → mac-planner → mac-vision → relay-realtime → unified → faculty-perception → faculty-judgement → faculty-action → dashboard-ux
- **model tier:** Use cheap background model for event normalization, deduplication, and urgency scoring; use gpt-5.6-luna only for ambiguous prioritization; use realtime only for the final low-latency spoken interruption and follow-up. Mac/browser actions remain gated by existing owner policy.
- **latency:** Event ingestion under 2 seconds; notification decision under 5 seconds. Deliver at the next safe attention window (for example, end of a call or 10-minute quiet boundary) rather than interrupting immediately. Owner can force immediate delivery with the button/voice.
- **cost:** Roughly $0.01–$0.05 per day for background event normalization and scoring at ordinary notification volume; realtime cost only when an interruption is actually spoken. Dominant cost is repeated context if full browser/Mac state is resent, so use compact typed event records with TTLs.
- **security:** Private browser titles/snippets and Mac focus/calendar state leave the device and are stored as sensitive event metadata; minimize content, encrypt in transit/at rest, apply per-source retention, and never speak message contents aloud unless the owner has enabled it. No external send/delete/purchase is performed by this capability; any action card still requires confirmation.
- **missing:** A durable attention-event schema with source, urgency, sensitivity, dedupe key, expiry, and delivery policy; A relay-side arbitration queue with snooze/ack/escalate receipts and quiet-hour handling; Mac focus/meeting signal and browser-watch event adapters; Pendant delivery-state protocol (spoken, missed, acknowledged) and a compact local indicator using the existing single LED/button; Dashboard review queue showing why an event was delivered, deferred, merged, or suppressed

### "“When something could send, buy, delete, or publish, let me approve it from the pendant without having to find the right screen—and prove afterward exactly what happened.”"
- **useful because:** The owner can safely delegate work across logged-in browser sessions and the Mac while away from the keyboard. The relay prepares the action, the browser/Mac produce a human-readable before-state and exact diff, and the pendant presents a short summary plus a one-time challenge. A deliberate button press followed by a spoken confirmation authorizes only that exact action; the resulting receipt is returned to the pendant and dashboard. This is not merely a draft or an approval prompt: it binds authorization to the worn device, the specific action hash, a short expiry, and post-action evidence.
- **path:** relay-realtime → browser-extension → mac-planner → mac-vision → mac-terminal → unified → faculty-perception → faculty-judgement → faculty-action → dashboard-ux
- **model tier:** Use a cheap background model for extracting and formatting the proposed diff. Use gpt-5.6-luna for ambiguous risk classification and concise spoken summaries. Use realtime only for the live challenge/confirmation exchange; deterministic protocol code, not a model, validates the action hash, expiry, and single use.
- **latency:** Prepare a review packet in under 10 seconds for ordinary actions. The pendant challenge should arrive within 1 second once the packet is ready; authorization expires after 60 seconds. Post-action receipt should reach the pendant within 5 seconds, with dashboard detail available asynchronously.
- **cost:** About $0.01–$0.05 per delegated transaction for diff summarization and risk reasoning; realtime is used only for the short approval exchange. Storage and signing overhead are negligible compared with browser/Mac execution.
- **security:** The pendant must never authorize an action based on a stale or truncated summary. Sign a canonical action manifest containing target account/session, URL or file path, operation, parameters, and before-state hash; require secure transport, single-use nonce, expiry, and replay protection. Do not speak secrets aloud. Sending mail, purchases, deletion, publication, or credential changes always require explicit confirmation; reversible local reminders remain configurable without a gate. Store receipts with redacted values and user-controlled retention.
- **missing:** A cryptographically bound action-manifest and one-time approval protocol shared by relay, Mac agent, and browser bridge; A compact pendant challenge/response firmware path with local button debouncing, timeout, and delivery receipt; Canonical before/after snapshots for browser DOM mutations and Mac filesystem/app actions; A risk-policy service that classifies operations and chooses what must require physical confirmation; An audit UI that lets the owner inspect the exact manifest, evidence, and resulting receipt


## Changes it proposed to its own stack

### `hardware` — Revise the product pendant (not the current DK) to add a small ERM/LRA haptic actuator with a dedicated low-side driver and a fuel-gauge/charger telemetry path, while retaining the existing button and LED. Define three short patterns (urgent, deferred-ready, acknowledged) and expose battery percentage/estimated runtime to the relay. The attention arbiter can then deliver private cues without speaking sensitive content aloud, and suppress delivery when charge is critically low.
- **owner gets:** The owner can notice an urgent result in a noisy room or while wearing headphones without the pendant saying private information out loud. Battery-aware scheduling prevents a long background job or repeated audio retries from unexpectedly killing the device.
- effort: Product hardware revision, enclosure/acoustic validation, Zephyr drivers and BLE/LTE telemetry schema, relay policy integration, and manufacturing test. Prototype with an I2C fuel-gauge breakout and PWM haptic driver first; then layout a small production board.  ·  risk: Added vibration can be annoying or reveal presence; provide intensity/off settings and quiet hours. Driver or gauge bugs must fail safe (no continuous motor drive). Battery estimates are advisory until calibrated. Recover by retaining LED/audio fallback and watchdog-limited actuator pulses.
- cost: Approximately $3–$8 BOM increase in volume (actuator, driver, gauge, passives, board/enclosure changes); negligible API cost. Haptic pulses consume tens of mW briefly, while the gauge adds a tiny idle draw; LTE remains the dominant power cost.  ·  latency: Local haptic cue is sub-100 ms after a delivery command. Battery telemetry adds no user-visible latency; it can be piggybacked on existing status frames.
- security: Battery and delivery state are low sensitivity. Avoid transmitting raw microphone/audio or message content to the haptic controller; send only an opaque pattern ID and duration. Manufacturing/debug interfaces must not expose secrets.
- depends on: A durable attention-event/arbitration queue and delivery receipts; A pendant protocol extension for haptic pattern IDs and battery telemetry; Production pendant constraints and battery/charger selection; Firmware fault-injection and long-duration motor watchdog tests

### `integration` — Introduce a single-use, signed cross-surface action manifest protocol. Before any irreversible Mac or browser operation, the executing surface must return a canonical manifest (actor/session, target, operation, redacted parameters, before-state hash, expiry, and risk class) to the relay. The relay sends only a compact digest and plain-language summary to the pendant; a physical button press plus spoken nonce authorizes that manifest. Execution is rejected if any field, target tab/session, or before-state hash changes, and the action result must return a signed receipt with after-state evidence.
- **owner gets:** They can approve a consequential action while away from the Mac without trusting a vague “okay?” prompt, and can later prove whether the exact intended email, purchase, deletion, or publication happened. A stale tab, changed page, prompt injection, or replayed approval cannot silently turn into a different action.
- effort: Define manifest schema and canonicalization; implement signing/nonces and relay verification; add browser-bridge and Mac-harness adapters; add pendant challenge/response firmware and dashboard receipt rendering; build replay, stale-state, tab-confusion, and dropped-link tests.  ·  risk: False rejects may interrupt work, and clock or state-hash disagreements can block legitimate actions. Recover with a fresh manifest/review rather than bypassing verification; keep low-risk reversible actions on the existing path. Loss of the pendant means the owner uses an explicit dashboard fallback with stronger confirmation.
- cost: Negligible API cost; a few kilobytes of manifest/receipt storage per action and small cryptographic CPU work. Firmware RAM impact should stay below roughly 8–16 kB if hashes and nonce state are bounded.  ·  latency: Adds roughly 1–3 seconds for manifest generation and pendant round-trip; execution remains asynchronous if the owner walks away after approval.
- security: Substantially reduces replay, confused-deputy, stale-tab, and prompt-injection risk, but makes the manifest and receipt security-critical. Keep private values redacted in spoken/UI summaries, rotate signing keys, and retain only the minimum evidence needed.
- depends on: Pendant-local approval/timeout protocol; Browser and Mac action adapters that can produce stable before-state hashes; Relay durable job and receipt storage; Owner-configurable risk policy and dashboard evidence view
