## Capabilities it proposed

### "When I say “save this for later” while I’m looking at a private webpage, remember exactly what I was looking at and why, then bring it back to me on the pendant or Mac when it becomes relevant—without making me find the page again."
- **useful because:** Today a logged-in page is stranded in a browser tab: the pendant cannot know which tab the owner means, and a later session has no reliable snapshot of the state or intent. This would turn fleeting authenticated context into a durable, searchable handoff across the browser, Mac, relay, and pendant—useful for invoices, support cases, travel pages, and research that must be resumed later.
- **path:** browser-extension → mac-planner → relay-realtime → pendant → dashboard
- **model tier:** Use the realtime tier only to resolve the owner’s short voice instruction and confirm the target tab; use a cheaper background model to title, summarize, extract entities, and rank when to resurface it. The browser extension supplies page evidence; the Mac adds local context only when explicitly relevant.
- **latency:** Acknowledge the save in under 2 seconds; capture and durable storage within 10 seconds. Resurfacing can be scheduled/background and should not consume realtime inference until the owner asks for it.
- **cost:** Roughly $0.01–$0.05 per saved capsule depending on page length and background summarization; dominant costs are model tokens for normalization and encrypted storage/egress, not browser actions.
- **security:** Authenticated page text, URLs, and screenshots leave Safari and are sensitive. Encrypt capsules at rest, retain only the selected extraction plus a short-lived evidence artifact, show source URL/tab/time on every resurfacing, and provide one-tap deletion. Never infer or transmit page content to public relay browsing; the relay should carry encrypted metadata or an owner-requested summary. Saving is reversible, but any follow-up click, form fill, message, purchase, or submission remains a separate action.
- **missing:** A working browser enqueue implementation (all currently granted enqueue wrappers are still stubs); An extension command that captures the active tab plus stable selection/scroll state and returns a signed tab/session identity; An encrypted durable “context capsule” store shared by relay and Mac with retention/deletion controls; A relevance trigger that can compare capsule entities against new calendar, mail, local files, or later browser observations; Pendant/Mac resurfacing UI with source evidence and explicit capsule lifecycle states


## Changes it proposed to its own stack

### `browser-harness` — Add a reconnect-safe browser command lifecycle, beyond the existing request IDs and 45-second wait: every queued command gets createdAt, expiresAt, backend/device binding, replayClass (idempotent-read, idempotent-navigation, non-replayable-mutation), and an append-only state transition log (queued, leased, delivered, result, expired, dead-letter). On extension heartbeat/reconnect, atomically discard expired commands, return pending commands grouped by device/session, and resume only idempotent reads/navigation with the same idempotency key. Expose GET /browser/commands/health and include a compact progress cursor so the planner can poll/resume instead of blocking. Add a startup sweeper so stale commands cannot execute after Safari has been offline; preserve receipts for diagnosis, not execution. This addresses the live state where five commands remain pending while the registered Safari device is offline, and is distinct from the still-missing durable multi-step job runner.
- **owner gets:** If the laptop sleeps or Safari disappears, the pendant will not later click or submit something from an old conversation. When Safari returns, safe page reads can continue automatically and the owner gets one clear status (“resumed”, “expired”, or “needs restarting”) instead of a silent timeout or duplicate action.
- effort: Medium: browserBridge lifecycle/state machine and SQLite/D1-backed command records, heartbeat reconciliation, sweeper, and planner polling adapter; extension needs only to accept a cursor and report its device/session identity. Add failure-injection tests for offline/reconnect, duplicate polls, restart, and clock skew.  ·  risk: A reconnect race could deliver a command twice or expire a valid read; idempotency keys and atomic lease transitions make duplicates harmless, while expiry and dead-letter receipts allow recovery. Non-replayable mutations are never auto-replayed; they remain visible as abandoned work for the planner. No approval gate is added.
- cost: Negligible API cost; a few D1/SQLite writes per browser command and heartbeat. Storage grows with receipts, so compact terminal records and configurable retention are needed.  ·  latency: No change while online; reconnect adds one heartbeat reconciliation round (typically <1s). Planner polling becomes incremental rather than a hard 45s wait.
- security: Reduces stale-session execution risk and binds commands to the intended device/session. Preserve authenticated page contents only in existing result retention; health endpoints expose metadata (counts/state), never page text.
- depends on: A functioning browser enqueue implementation in the agent harness (currently all granted wrappers are stubs); chg-14accc01's existing request IDs/idempotency/tab affinity; Extension heartbeat identity and a durable command store; chg-16bc5dee's durable job runner can consume these terminal states later

### `browser-harness` — Add an owner-visible active-tab handoff protocol: the Safari extension periodically publishes only a short-lived tab handle (deviceId, tabId, title, origin, last interaction time, and a one-time nonce), and the pendant voice turn can bind “this page” to that handle. The browser result must include the nonce and a compact viewport/selection anchor, allowing the planner to prove which tab was read even if several authenticated tabs share the same domain. Handles expire on navigation, tab close, or timeout and are never silently guessed from URL matching. Add a small Mac dashboard tray showing the currently bound tab and an explicit “unbind” control; this is a binding primitive, not a page-watch or durable job runner.
- **owner gets:** The owner could say “what does this mean?”, “save this”, or “fill the easy parts” while looking at a private page and have the system act on the page they actually mean. Today multiple logged-in tabs are indistinguishable to the voice path, so the assistant risks answering from the wrong account, case, or order—or cannot act at all.
- effort: Medium: extension heartbeat payload and navigation invalidation, browserBridge tab-handle registry, nonce verification in browser_* actions, and a small Mac tray/status surface. Add tests with two tabs on one origin, navigation races, extension reconnect, and voice turns arriving after a tab closes.  ·  risk: A stale handle could reject a valid request or, worse, target the wrong tab; expiry, nonce checks, and navigation invalidation make failure explicit rather than guessing. The handle contains no page body or credentials. Recovery is simply asking the owner to rebind the visible tab.
- cost: Negligible model/API cost; a few bytes per heartbeat and a small in-memory/SQLite registry. No additional browser-minute usage.  ·  latency: Adds one local registry lookup and nonce check (milliseconds). Heartbeat metadata can be sent at a low cadence; voice acknowledgement remains within the normal realtime turn.
- security: Improves isolation between authenticated tabs and accounts. Do not expose URLs/titles beyond the owner’s authenticated Mac/relay path; hash or redact query strings, and keep handles short-lived. This does not add an approval gate or reduce owner access.
- depends on: A functioning browser enqueue/extension bridge rather than the current schema-only stubs; Safari extension heartbeat with tab identity and navigation events; POST /execute browser action plumbing; A lightweight Mac dashboard/tray surface for binding visibility
