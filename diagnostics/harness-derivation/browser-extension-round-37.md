## Capabilities it proposed

### "Use my logged-in browser to answer a question, but keep the page itself private: send only the smallest locally extracted evidence needed, and let me verify every answer against the original page."
- **useful because:** Today an authenticated page can be read by the browser tier, but there is no owner-visible boundary between the full page and the model's context. This would let the owner ask about sensitive health, financial, employment, or legal pages while minimizing cloud disclosure, without losing citations or the ability to inspect the source in Safari.
- **path:** browser-extension → mac-planner → relay-realtime → pendant → dashboard-ux
- **model tier:** Use a cheap local Mac model or deterministic extractor first to identify relevant DOM regions, fields, and short quote windows; use the slower background model only to synthesize those bounded evidence capsules. Use realtime only to speak the final answer and handle follow-up questions.
- **latency:** 2–6 seconds for local extraction and capsule generation; 5–12 seconds for synthesis. A citation tap or spoken 'show me' should open the exact Safari region, not transmit the whole page.
- **cost:** Usually well below one normal page-reading request because only selected snippets and metadata reach the synthesis model; dominant cost is the optional synthesis call. Local extraction uses Mac CPU and browser-extension work, with negligible API cost.
- **security:** Raw DOM, screenshots, cookies, and unrelated page regions stay on the browser/Mac. The capsule should contain only query-relevant text, origin, timestamp, selector/anchor, and a cryptographic hash of the source region. The relay must reject oversized or unbounded capsules, redact detected secrets, and make any model/provider transfer visible in the receipt. If extraction is uncertain, say so and offer to open the source rather than broadening capture silently.
- **missing:** A local evidence-capsule protocol and extractor that can select bounded DOM regions from an authenticated tab; A Mac-side verifier that re-reads the cited selector/hash and reports whether the page changed; Relay routing that accepts capsules without requesting the original page; Pendant/dashboard UI for confidence, source anchor, and a 'show source in Safari' action; Per-origin privacy policy and an owner-visible receipt recording exactly what left the device


## Changes it proposed to its own stack

### `browser-harness` — Add an offline-aware, resumable browser lease spanning relay, Mac, and Safari: when a browser job is queued, persist its step graph and session affinity; detect extension heartbeats/tab loss, ask the Mac surface to launch or foreground Safari and navigate to a neutral bootstrap page, then resume only idempotent reads once the extension returns. Emit explicit states (queued, waiting-for-browser, resumed, stale-session, completed) and send the pendant a short status rather than letting the request hang for 45 seconds. Never replay clicks, typing, or submits after a lease break; mark those steps for review.
- **owner gets:** A voice request involving a logged-in page would keep working when Safari is asleep, briefly disconnected, or its tab disappears. The owner would know whether the answer is pending or impossible instead of hearing silence, while private browser work remains private and irreversible actions cannot be accidentally replayed.
- effort: Medium-high: durable step/lease records in the browser runner, heartbeat and tab-recovery logic in browserBridge/browserSessions, a Mac callback to launch/foreground Safari, and relay/pendant progress events. Test Safari restart, duplicate polling, and stale tabs.  ·  risk: A neutral bootstrap navigation could disturb the owner's current Safari window; use a new tab or a dedicated window and restore focus. A session may expire while offline, so reads must return re-authentication-needed rather than guessing. Recovery is idempotent only for navigation/read steps; all mutations are halted on lease loss. Keep an audit trail and allow cancellation.
- cost: Low ongoing API cost: heartbeat/status and durable metadata are local/relay storage; one short status utterance per state transition. Main cost is implementation and a few extra Mac/browser round trips on recovery.  ·  latency: Normal jobs unchanged. Offline recovery adds roughly 2–10 seconds to relaunch/heartbeat; the pendant gets immediate progress feedback instead of a 45-second timeout.
- security: No credentials leave Safari. The Mac only receives bootstrap/navigation instructions and opaque job IDs. Session affinity and origin checks must prevent resuming a job in the wrong tab/account; do not capture page content until the intended origin is verified.
- depends on: A functioning browser command enqueue path (current granted enqueue tools are stubs and POST /execute timed out with Safari offline); Durable browser step runner/session records (chg-16bc5dee remains open); Mac action that can launch or foreground Safari and report completion; Relay-to-pendant progress/status event path

### `browser-harness` — Add a signed browser-evidence boundary that classifies extracted page material as untrusted data, never executable instructions. The extension should produce typed records (text, link, amount, date, form field) with origin, frame, selector, timestamp, and integrity hash; the relay/model receives them in a data-only channel whose contents cannot alter the action plan. Any page instruction aimed at the agent is surfaced as quoted page text, not obeyed. Mac verification re-reads the cited region before an action plan can use it.
- **owner gets:** The owner could ask the system to work inside logged-in sites without a malicious or merely over-helpful webpage tricking it into revealing data, navigating elsewhere, or preparing an unintended action. They would get answers grounded in the page while the page remains an untrusted source, like an email attachment rather than a colleague with authority.
- effort: High: typed extraction schema and signing in the extension, data/instruction separation in relay prompts and planner state, origin/frame validation, Mac re-verification, and adversarial tests against prompt injection in visible text, hidden DOM, iframes, and accessibility labels.  ·  risk: Classification can hide useful text or produce false positives; preserve the original snippet for owner inspection and allow a read-only answer path. Integrity hashes do not prove a page is truthful, only that the cited content was not changed between extraction and verification. Never treat this as a substitute for stopping before irreversible actions.
- cost: Small per-request overhead for typed metadata and hashes; moderate engineering and test cost. No additional model call is required for normal pages, though difficult extraction may use a low-cost local model.  ·  latency: Adds roughly 100–500 ms for local typing, hashing, and selector verification; dynamic pages may require one extra browser read.
- security: Substantially reduces browser prompt-injection and confused-deputy risk. The extension must not sign arbitrary script output, must bind records to the active origin/tab, and must exclude cookies, hidden secrets, and unrelated frames. Store receipts with short retention.
- depends on: The proposed local evidence-capsule protocol; Typed browser result and provenance support; Mac-side source re-verification; A relay prompt contract that marks browser content as data-only
