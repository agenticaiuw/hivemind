## Capabilities it proposed

### "When I say “save this for later” while wearing the pendant, capture what I am looking at in Safari, the short reason I gave, and the relevant local Mac context as one private, searchable research card; keep a compact version available on the pendant when the Mac is offline, and let me later ask “why did I save this?”"
- **useful because:** Today a spoken thought, a browser page, and local context live in separate places, so the owner must manually copy URLs, explain the purpose again, and hope the page remains available. This would preserve the meaning and provenance of an idea at the moment it occurs, then make it retrievable from either the pendant or Mac without replaying the original browsing session.
- **path:** pendant captures the utterance and gives immediate confirmation → browser extension reads the active tab URL/title/selected or main text under the paired private-browser session → Mac planner gathers only explicitly relevant local context and stores the searchable card → relay assigns the card identity, synchronizes it when the Mac is unavailable, and serves the compact offline pendant copy → dashboard provides provenance, expiration, redaction, and deletion controls
- **model tier:** Use deterministic extraction and hashing for URL/title/timestamps and a background-tier model to write a short reason and keywords. Escalate to the planner tier only when the page is ambiguous or the owner asks a semantic question; realtime is only for the spoken confirmation and retrieval conversation.
- **latency:** Acknowledge the save on the pendant in under 1 second with a local placeholder. Capture browser metadata within 3 seconds; text summarization can finish in the background. Offline mode should preserve the utterance and URL locally, then synchronize on reconnection.
- **cost:** Approximately $0.001–$0.01 per saved card depending on page-text length and whether semantic summarization is needed. Storage and browser extraction dominate operational cost; most saves should avoid the expensive planner tier.
- **security:** The active tab may contain credentials, health, financial, or work information. Require explicit pairing and a clear spoken/visual indication when page content is being captured; default to URL/title/selection rather than the whole DOM, redact secrets and form values, encrypt relay and Mac storage, apply per-card TTLs, and provide pendant commands to delete the last card or all cards. Never send captured page text to the relay unless the owner’s capture policy permits it.
- **missing:** A cross-surface private-card schema with provenance (tab/session, URL, timestamp, selection hash), sensitivity labels, TTL, and deletion propagation; A browser-extension command to return the active tab’s bounded selection or readable region without form values; A small encrypted offline card cache and sync protocol shared by pendant and relay; A Mac-local search/index and a retrieval response that can cite the original browser source; User-configurable capture policy distinguishing URL-only, selection, and page-summary modes


## Changes it proposed to its own stack

### `integration` — Add a durable cross-surface execution trace and continuation ledger. The pendant/relay assigns a traceId and intentId at utterance time; every relay dispatch, Mac job, shell command, browser command, retry, and result receipt carries that ID. Persist a compact append-only event record on the Mac and relay (with payload redaction and a 30-day TTL), reconcile duplicate/out-of-order events by idempotency key, and expose one GET /continuations/:traceId plus a relay push topic. When the pendant reconnects, it receives a concise status (running, waiting for Mac/browser, completed, failed with next retry time) rather than losing the task. Add a background reconciler that marks stale leases, retries only retry-safe operations, and emits a human-readable completion/failure receipt. This is deliberately observability and recovery only: it does not gate or refuse any FULL_CONTROL action.
- **owner gets:** If the owner says “do this” and walks away or the pendant link drops, they can later ask “what happened?” and get one trustworthy answer spanning shell, Safari, Mac, and relay—not a partial job list. Failures become actionable (“browser was offline; resumed at 9:14”) instead of silent or duplicated work, and repeated retries stop rerunning completed steps.
- effort: Medium-high: shared trace schema and propagation in relay, executor, browserBridge, and jobTracker; small durable event store and reconciler; dashboard/pendant status view; integration tests for disconnect, restart, duplicate, and out-of-order delivery.  ·  risk: Trace records could leak URLs, shell commands, or private snippets; redact arguments and store hashes/metadata by default, encrypt relay records, and make detailed evidence opt-in. Reconciliation bugs could duplicate mutations, so only actions already declared idempotent/retry-safe are auto-retried; all others are reported as needing continuation, never replayed automatically. Recover by disabling the reconciler while retaining raw receipts.
- cost: Low ongoing API cost: deterministic ID/event handling and a cheaper background reconciler; roughly 1–3 KB of metadata per action before retention, with relay storage and dashboard reads dominating rather than model tokens.  ·  latency: No added latency on the first action beyond generating an ID and one local append (<10 ms target). Reconnect status is immediate from persisted state; background reconciliation may add seconds only after failures.
- security: Improves auditability without adding authority. Use scoped trace tokens, redact command text/DOM content and credentials, encrypt relay-at-rest data, and enforce owner-device pairing for continuation queries. Never expose raw shell/environment values in pendant speech.
- depends on: chg-5fc73ce3 (implemented per-action receipts); relay durable state and paired-device identity; chg-14accc01's resumable browser queue or equivalent lease API; a stable Mac job lifecycle event hook
