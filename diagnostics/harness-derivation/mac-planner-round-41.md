## Capabilities it proposed

### "“When the pendant audio sounds bad, diagnose the whole path and fix the best thing automatically.”"
- **useful because:** Today the owner has no way to distinguish a bad microphone, overloaded Opus codec, LTE loss, relay transcoding, pendant underrun, or the ESP32/headphone resampler. This capability would turn an intermittent and frustrating failure into a short spoken diagnosis and a concrete repair, rather than asking the owner to understand several devices.
- **path:** pendant: a double-press or long-press marks the last 10 seconds as a diagnostic window and plays a short synthetic calibration chirp; it records only local metrics unless the owner explicitly starts a live test → relay-realtime: coordinates a timestamped synthetic probe through capture, Opus, relay, TTS/transcode, and return playback; compares packet loss, jitter, clock drift, clipping, and latency against the negotiated profile → mac-planner: checks Mac audio route, TTS sample rate, bridge availability, and recent pipeline receipts; applies safe configuration repairs such as selecting the correct output route or restarting the bridge process → browser-extension: reads the browser's authenticated bridge/session state only when the active call uses it, identifying stale leases or a disconnected tab without scraping unrelated pages → dashboard: presents one evidence-backed result with the failing segment, what was changed, and a before/after score; stores metrics and hashes, not raw diagnostic speech → iOS: offers the same diagnostic history and a remote “start test” control when the pendant is not within reach
- **model tier:** Use a deterministic background diagnostic worker and small local rules for signal analysis; reserve realtime only for the owner's spoken request and the final one-sentence explanation. No expensive model is needed for packet, clock, clipping, or route diagnosis.
- **latency:** Initial spoken acknowledgement under 500 ms; a normal diagnosis in 10–20 seconds. Repairs that require reconnecting the bridge may take up to 30 seconds, with progress surfaced on the pendant LED and dashboard.
- **cost:** Usually under $0.01 per invocation and often zero model cost: synthetic probes and local metrics dominate. A model call is only needed to summarize unusual multi-fault evidence.
- **security:** The default test uses synthetic tones and metadata, not retained speech. The optional recent-audio window must be clearly bounded and deleted after analysis. Changing the Mac output route or restarting a bridge is reversible but should be recorded; never inspect unrelated browser tabs or upload private page contents as part of an audio test.
- **missing:** A versioned end-to-end audio profile with timestamps and sequence numbers; Pendant firmware diagnostic trigger and local metrics buffer; Relay probe orchestration and metric correlation across uplink/downlink; Mac read-only audio-route/bridge health inspection plus a narrowly scoped repair action; ESP32 bridge telemetry for resampler, SBC queue, underruns, and headphone connection; A shared diagnostic receipt schema and dashboard presentation


## Changes it proposed to its own stack

### `integration` — Ship a negotiated 24 kHz superwideband audio contract end to end instead of treating 24 kHz as a TTS-only convention. The relay should advertise a versioned profile (capture/playback rate, Opus mode, frame duration, bitrate, channel count, sequence/timestamp rules); the pendant should ACK the profile and stamp every uplink/downlink frame; the Mac TTS/transcode path should emit that profile; and the ESP32 bridge should either preserve the negotiated mono 24 kHz stream or explicitly report its SBC/44.1 kHz fallback. Add an automated loopback fixture that injects a speech/test tone, records at the pendant, checks sequence loss, resampling, clipping, underruns, and end-to-end latency, then writes a signed receipt visible in the dashboard. This is designed around the current single full-duplex I2S peripheral and tight bridge RAM: no second audio bus and no large buffering; use small bounded jitter buffers and make fallback observable rather than silent.
- **owner gets:** The owner gets genuinely intelligible, consistent speech in both directions and can tell whether a bad call is the network, codec, pendant, or headphone bridge. Today the system reports 24 kHz PCM on the Mac and 24 kHz decode on the pendant, but the microphone is 15.625 kHz/16 kHz Opus and the bridge forcibly resamples to 44.1 kHz SBC; this contract closes that gap instead of merely labeling individual stages “wideband.”
- effort: Medium-high: protocol/version negotiation and telemetry in relay + nRF9160 firmware + Mac audio path, bridge resampler/buffer changes, and a hardware-in-loop test fixture. Start with a software loopback and one known headset, then validate on the dev kit.  ·  risk: A profile mismatch could produce silence or distorted playback, and changing I2S clocking can affect the existing full-duplex path. Recover by retaining the current profile as an explicit v1 fallback, rejecting unknown profiles before audio starts, and gating rollout on loopback receipts. No owner data needs to leave the device beyond the already-uploaded audio; test recordings should be synthetic or deleted after the receipt.
- cost: Low incremental API cost: telemetry and negotiation are tiny; synthetic test audio avoids model calls. Engineering/hardware test cost is the dominant expense (roughly $50–$150 for a repeatable audio fixture/headset if not already available).  ·  latency: Target under 120 ms added buffering; 20–60 ms frames remain feasible. The current measured Opus CPU load (~87% of one core with encode+decode) may require encoder/decoder scheduling or a higher-memory production MCU, but no extra model latency is needed.
- security: Audio remains end-to-end within the existing relay path; receipts must contain metrics and hashes, not raw speech. Profile negotiation and receipts should be authenticated to prevent a malicious bridge from downgrading or injecting frames.
- depends on: A relay audio-profile negotiation endpoint and typed frame metadata; nRF9160 firmware support for 24 kHz capture or an explicitly documented capture fallback; Mac TTS/transcode output tagged with the negotiated profile; ESP32 bridge firmware that reports SBC/44.1 kHz fallback and bounded jitter-buffer health; A dashboard view for audio receipts and a hardware-in-loop test command
