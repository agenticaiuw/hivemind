## Capabilities it proposed

### "“Prepare this booking or purchase, show me the exact final change, and only carry it through once I approve—if the browser or Mac disconnects, recover safely and tell me whether it actually completed.”"
- **useful because:** Today the mind can prepare browser/Mac actions and record receipts, but it cannot treat a consequential multi-surface action as one transaction. This capability prevents duplicate submissions and false success: it freezes the exact final delta, binds approval to that version, executes each step once, verifies the external service’s acknowledgment, and reconciles after a dropped link before offering retry. The pendant gets a concise pending/completed/needs-review state while the Mac/browser do the work.
- **path:** faculty-judgement → faculty-action → relay-realtime → browser-extension → mac-planner → mac-vision → mac-terminal → unified
- **model tier:** Use the realtime model only to explain the proposed delta and capture the owner’s approval. Use a cheaper background model for plan validation, idempotency/reconciliation, receipt comparison, and post-disconnect polling; deterministic executors perform the actual clicks/API/AppleScript steps.
- **latency:** Show a frozen preview in under 2 seconds when tabs/Mac are reachable; execute in the background with progress updates within 1–3 seconds per step. On disconnect, stop issuing new writes immediately, poll/reconcile for up to 2 minutes, then surface a clear needs-review state rather than retrying blindly.
- **cost:** About $0.01–$0.08 per transaction depending on reconciliation and page extraction; most cost is browser snapshots and background model checks, not realtime speech. Storage is small structured plans, approval nonce, hashes, and receipts.
- **security:** Only authenticated tabs already open in the owner’s browser and explicitly authorized Mac actions are used. The approval must be bound to a hash of the exact before/after values, destination, amount, and expiry; any DOM/value drift invalidates it. Never send credentials or page contents beyond the existing browser bridge/relay. Require explicit approval for purchases, submissions, messages, cancellations, or anything irreversible; redact sensitive receipt fields in pendant speech.
- **missing:** A durable two-phase transaction record spanning browser and Mac (prepare/freeze/approve/execute/reconcile), with idempotency keys and an approval-expiry nonce.; A verifier that distinguishes external acknowledgment from local click success and can poll/reconcile after link loss.; A single owner-facing pendant state machine for prepared, approved, executing, acknowledged, uncertain, reconciled, and failed.; Browser bridge availability/heartbeat and durable runner completion when the current browser device is offline.

### "“When I’m physically with my Mac, let me authorize a sensitive action by pressing the pendant, and make the browser or Mac accept it only while that short-lived presence proof is valid.”"
- **useful because:** The owner gets a practical, phishing-resistant way to authorize sensitive local actions without speaking secrets aloud or leaving a standing approval behind. The pendant supplies an independent physical presence signal; the Mac and browser verify that signal before acting, and the relay records the authorization for later audit. This is not merely a confirmation prompt: it binds authorization to the owner’s nearby wearable, the specific action digest, the intended computer/session, and a short expiry.
- **path:** pendant → relay-realtime → mac-planner → mac-vision → browser-extension → faculty-judgement → faculty-action → unified
- **model tier:** Use deterministic cryptographic verification and local state for the authorization path. Use the realtime model only to explain the action digest and ask for a press; use a cheaper background model for audit summarization and anomaly review.
- **latency:** The pendant press should unlock a prepared action in under 500 ms locally, with Mac/browser verification under 2 seconds. Presence proofs expire within 30–60 seconds and are single-use.
- **cost:** Negligible inference cost for each authorization; approximately $0.001 or less in relay/storage overhead. Main engineering cost is secure key provisioning, replay protection, and adapters in the Mac and browser executors.
- **security:** Private keys must remain on the pendant or a secure element; relay stores only signed action digests and timestamps. Bind each proof to a nonce, exact action hash, target device/session, and expiry. Reject replay, altered payloads, stale proofs, and unexpected target changes. Provide a lost-pendant revocation path and never treat Bluetooth proximity alone as authorization.
- **missing:** A pendant-resident signing/proof primitive with protected key storage and a physical-button trigger.; Mac and browser executor middleware that verifies target-bound, single-use proofs before side effects.; Relay endpoints and durable audit records for nonce issuance, proof consumption, revocation, and recovery.; A clear owner flow for revoking a lost pendant and falling back to an explicitly slower alternate approval method.


## Changes it proposed to its own stack

### `integration` — Add a cross-surface transaction coordinator between faculty-judgement and the existing browser/Mac executors. It persists a versioned action plan with before/after evidence, idempotency key, approval nonce/expiry, and correlation ID; exposes prepare→approve→execute→verify→reconcile states; refuses writes when evidence hash or tab/session changes; serializes browser and Mac side effects; after disconnect polls receipts and the external page before classifying acknowledged/uncertain/failed. Emit compact state transitions to the relay/pipeline so the pendant can say exactly what is waiting without claiming success.
- **owner gets:** A booking, purchase, or submission either completes once with proof or is clearly waiting for review. The owner will not be charged twice or be left guessing whether a disconnected browser click worked.
- effort: Medium-high: durable state schema and state machine, executor adapters, crash/restart recovery, external-ack verifiers for common page patterns, and contract tests for duplicate delivery and disconnect at every step.  ·  risk: A verifier may misclassify a site’s confirmation or a stale page may block a valid action. Default to uncertain/needs-review, never automatic retry for irreversible writes; retain raw receipts and provide undo only where the target supports it. Roll out first to reversible reminders/drafts, then gated transactions.
- cost: Negligible API cost for the coordinator; background reconciliation adds roughly $0.01–$0.05 per uncertain job and small durable metadata/receipt storage.  ·  latency: Preparation adds one evidence snapshot/hash (usually <1 s); normal execution is unchanged. Disconnect cases may wait up to a configured reconciliation window rather than immediately returning.
- security: Approval nonce is scoped to exact payload, account/session, target, and short expiry. Store hashes and redacted evidence by default; encrypt receipts and avoid copying credentials or full private pages into relay logs.
- depends on: A durable job runner and browser command queue with idempotency/session affinity (chg-16bc5dee, chg-14accc01); The existing receipt/undo plumbing (chg-5fc73ce3); A shared typed context/correlation service (chg-a82e0b13 or equivalent); Browser bridge heartbeat currently reports home-chrome offline; owner must bring the extension online for authenticated execution

### `hardware` — Add a secure authorization path to the pendant: a device-unique private key in protected storage (or a small secure element), monotonic anti-replay counter, and firmware support for signing a displayed/action-digest-bound nonce only after a deliberate physical button gesture. Add revocation and recovery metadata without storing the owner’s action contents.
- **owner gets:** The owner can authorize a sensitive action with a deliberate physical gesture on the device they are wearing, without dictating a secret or trusting an ambient voice command. A stolen browser session or copied transcript cannot reuse the approval.
- effort: High: secure key provisioning and lifecycle, signed-message protocol, firmware UI/LED feedback, Mac/browser verification middleware, relay persistence and revocation, plus red-team tests for replay, relay compromise, clock skew, lost pendant, and target substitution.  ·  risk: A lost pendant could block approvals or, if key lifecycle is wrong, authorize unwanted actions. Default-deny on malformed/stale proofs, require a physical long-press for high-risk actions, maintain a server-side revocation list, and provide a recovery ceremony using the owner’s existing trusted Mac.
- cost: Roughly $1–$4 incremental secure-element/BOM cost if the current board lacks protected key storage, plus negligible per-action API/storage cost; firmware and verification engineering dominate.  ·  latency: Local signing is sub-100 ms; network verification adds roughly 100–500 ms. Expiry and single-use checks may briefly delay actions when the relay is unreachable, so only pre-approved low-risk fallback behavior should exist.
- security: Improves authorization security by requiring possession plus physical intent, but creates a new root of trust. Keys must never be exportable; relay logs should contain only hashes, counters, target IDs, and timestamps; revocation must work even if the pendant is offline.
- depends on: A pendant firmware signing/proof primitive and protected key storage; A relay nonce/verification/revocation protocol; Mac and browser executor middleware that checks proofs before side effects; An owner-approved lost-device recovery flow
