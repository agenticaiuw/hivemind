## Capabilities it proposed

### "“I’m leaving—pack up what I’m doing so I can continue from the pendant, and pick it back up when I return.”"
- **useful because:** Today leaving the desk severs context: open Mac work, authenticated browser tabs, and half-finished plans are not converted into something usable while walking. This creates an intentional, privacy-bounded handoff: a short spoken queue for the commute, a resumable workspace on the Mac, and a clear return point rather than a vague promise that an agent kept working.
- **path:** pendant → relay-realtime → mac-planner → mac-vision → browser-extension → unified → faculty-perception → faculty-judgement → faculty-action
- **model tier:** Use the realtime tier only to hear the short departure/return command and deliver the first acknowledgment. Use a cheaper background model to summarize the captured workspace and rank next steps; use the local Mac planner for app/browser state and no cloud model for raw private page contents unless the owner permits it.
- **latency:** Acknowledge in under 1 second. Capture Mac/browser state in 5–15 seconds, produce a 30–90 second audio queue in under 60 seconds, and make the return workspace available as soon as the Mac reconnects. Offline pendant playback must not wait for the Mac.
- **cost:** One small background summarization per handoff (roughly a few cents or less depending on transcript/page volume); realtime cost is limited to two short utterances. Dominant costs are private-page extraction and audio generation, not orchestration.
- **security:** Snapshot only the active window, selected browser tabs, task text, and provenance—not arbitrary screenshots or full page bodies. Redact secrets and mark authenticated excerpts as private. Never send mail, submit forms, or alter files as part of packing. Returning may reopen sensitive tabs, so require a local button press or spoken confirmation if the snapshot contains private browser sessions. Expire the handoff after 24 hours and provide one-tap deletion.
- **missing:** A first-class handoff snapshot schema tying Mac window/app state, browser tab/session IDs, plan/job IDs, and pendant audio-item IDs together; A local pendant queue/marker that survives a dropped link and reports played/paused/expired state; A return-time revalidation step that checks tabs/files have not changed before reopening or continuing; Reliable browser bridge connectivity and explicit offline behavior (current home-chrome is offline with pending commands); A compact audio renderer/acknowledgment path with the negotiated 24-kHz profile

### "“Stay with me quietly in this conversation. When I ask you something, check my private notes and logged-in work pages, then whisper only a short, sourced answer through the pendant.”"
- **useful because:** The owner can participate in a meeting or conversation without stopping to search their Mac. The pendant provides the ears and discreet audio; the Mac and authenticated browser provide reach into private material; the relay keeps the interaction low-latency. This is different from a meeting brief or a background digest: it answers a question arising now, with citations and a deliberate silence when evidence is insufficient.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → mac-vision → unified → faculty-perception → faculty-judgement → faculty-action
- **model tier:** Realtime handles the short spoken request and final one-sentence response. A cheaper background/local model retrieves and ranks notes and authenticated pages; the Mac/browser agents perform only read-only searches. Escalate to the expensive model only when sources conflict or the owner asks for synthesis.
- **latency:** Acknowledge within 300 ms and return a sourced answer within 3 seconds for cached/local notes, or 8 seconds for authenticated browser retrieval. The pendant must say 'I don't have enough evidence' rather than fill silence with a guess.
- **cost:** Usually one short realtime turn plus a low-cost retrieval/reranking call, well under a few cents per question; browser extraction and repeated audio delivery dominate, not the model reasoning.
- **security:** Requires an explicit session start and a visible/audio recording indicator; default to no raw meeting-audio retention. Only search allowlisted notes and currently selected browser sessions, never arbitrary mail or accounts. Cite source title and freshness without reading sensitive excerpts aloud unless requested. Pause on a button press or the phrase 'quiet now'; never send, edit, or submit anything.
- **missing:** A consent-scoped live-session envelope carrying the selected source set, expiry, recording policy, and pause state across pendant, relay, Mac, and browser; Low-latency read-only fan-out from Mac notes and authenticated browser tabs with typed citations and freshness; A speech-turn arbiter that suppresses duplicate/low-confidence answers and guarantees a concise one-sentence output; A pendant-local privacy indicator and stop latch that works if the relay link drops; The end-to-end negotiated 24-kHz audio delivery path, with explicit fallback metadata


## Changes it proposed to its own stack

### `firmware` — Ship a negotiated 24-kHz superwideband Opus profile end to end: capture at the actual 15,625-Hz I2S rate, resample once with a fixed-point polyphase stage to 24 kHz, encode mono Opus at an explicit 24-kHz/24–32-kbps profile, and advertise that profile in the session handshake. Keep the existing 16-kHz/16-kbps mode as a fallback selected by measured CPU/packet-loss budget. On the relay, remove any implicit 16-kHz downsample, preserve the profile in queued audio jobs and receipts, and validate decoded sample rate/frame duration before delivery. On playback, retain the existing 24-kHz decode but replace the 31,250-Hz wire-clock assumption with a negotiated rate conversion contract so the ESP32's mandatory 44.1-kHz SBC path remains the only final resample. Add loopback fixtures for tones, speech, packet loss, and clock drift; reject a session rather than silently claiming 24 kHz when a stage falls back.
- **owner gets:** The pendant would sound intelligibly fuller and less muffled for both live replies and queued briefings, with no false promise that '24 kHz' survived the trip. Calls remain usable when bandwidth or battery is poor because fallback is explicit, not a broken half-upgrade.
- effort: Medium-high: firmware resampler/profile and handshake, relay transcode/schema updates, ESP32 clock-contract update, and hardware-in-the-loop audio fixtures. The current implementation is a prototype and the owner explicitly asked to ship this path.  ·  risk: A second resampler and higher Opus bitrate can increase CPU, latency, airtime, and dropouts; current hardware reports ~87% of one core when encode and decode both run. Mitigate by benchmarking encode-only/decode-only separately, selecting profile before streaming, bounded jitter buffers, and automatic fallback. Never silently mix 16-kHz and 24-kHz timestamps. Recovery is reconnect into the legacy profile.
- cost: No API-model cost change. Rough firmware/storage work fits existing flash but needs profiling; 24–32 kbps uses about 1.5–2x radio airtime versus 16 kbps, with corresponding modem energy increase. A production device may need a better audio codec/DSP if the nRF9160 cannot sustain duplex headroom.  ·  latency: Target unchanged 60-ms frames plus <=20 ms resampling; expect roughly 5–15 ms extra buffering during negotiation and possibly higher airtime latency. Keep live voice on the realtime tier; queued audio can use the cheaper background path.
- security: Audio remains encrypted in the existing authenticated session; profile metadata and loopback diagnostics should exclude raw speech by default. Store only hashes/metrics in receipts, apply short retention to generated audio, and require explicit opt-in before uploading diagnostic clips.
- depends on: Relay must expose and persist negotiated audio profile rather than assuming 16 kHz; Firmware needs a fixed-point 15,625→24,000 resampler and CPU/RAM benchmark; ESP32 bridge must accept the negotiated wire-clock contract while retaining its 44.1-kHz SBC constraint; End-to-end loopback and packet-loss test fixture

### `integration` — Add a durable Handoff Envelope that links one departure snapshot across /capture, /plan, /execute, Mac job receipts, browser session/tab IDs, pipeline audio items, and pendant delivery state. The envelope stores a redacted task summary, source references and hashes, precondition/evidence timestamps, expiration, owner approval scope, and a resume policy. Packing is append-only; returning first revalidates each source and marks changed/missing tabs or files for review instead of replaying stale actions. Expose one status/undo/delete operation so the owner can say 'what did I pack?', discard it, or resume the safe subset.
- **owner gets:** It turns the proposed leave/return experience from a collection of jobs into one trustworthy bookmark. The owner can walk away without losing the thread and can see exactly why a return action was or was not resumed, even when the browser was offline or the Mac rebooted.
- effort: Medium: shared schema plus adapters around existing capture/planning/job/session/audio receipts, durable storage, and a small resume UI/voice vocabulary. No new model is required.  ·  risk: Adapters may disagree about identifiers or accidentally replay stale actions. Use immutable envelope IDs, source hashes, TTL, explicit 'changed' state, and default to read-only resume; destructive actions remain confirmation-gated. If one surface fails, preserve the envelope and deliver a partial handoff.
- cost: Negligible API cost; one compact background summary and optional audio render per envelope. Storage is small metadata plus references, not copied private pages or screenshots.  ·  latency: Packing adds roughly 1–3 seconds for metadata and 5–60 seconds for optional summary/audio. Return begins with a fast receipt lookup, then revalidation in background; no need to block spoken acknowledgment.
- security: Improves security by centralizing redaction, TTL, deletion, and provenance. Do not duplicate authenticated content into relay prompts; retain tab/file references and hashes, encrypt any audio, and log access without raw contents.
- depends on: A durable pendant audio queue/marker and delivery acknowledgment; The negotiated 24-kHz audio contract (or explicit fallback metadata); Browser bridge reconnect/offline queue with stable session and tab affinity; Faculty-action checkpoint/receipt protocol for any resumed mutation
