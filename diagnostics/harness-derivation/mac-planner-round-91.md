## Capabilities it proposed

### "“Pick up where I left off on the Mac.” Later: “Resume that.”"
- **useful because:** The owner gets a genuine cross-device continuation instead of a generic summary: the pendant identifies the current thread, the Mac and authenticated browser recover the exact work state, and the system reopens the same materials without making them reconstruct context by hand. It also survives leaving the desk or a dropped connection.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → mac-vision → dashboard
- **model tier:** Use the cheaper background model to build and refresh the capsule; use realtime only to resolve the owner's short voice reference and speak the final 20–30 second handoff. Use the local Mac planner for deterministic reopen/continue actions.
- **latency:** Initial capture under 5 seconds after the voice request; capsule refresh can run in the background. Resume should return a spoken confirmation within 3 seconds, then reopen apps/tabs asynchronously with progress receipts.
- **cost:** Typically $0.01–$0.05 per capture/resume, dominated by summarizing browser/file evidence; most refreshes can be hash-and-metadata only and avoid model calls. LTE transfer stays small because the pendant receives only the short spoken result, not page contents.
- **security:** Authenticated tab text, filenames, and window titles leave the Mac only for this capsule and must be redacted by default. Store references and hashes rather than copied contents, encrypt the capsule, expire it (for example 7 days), and let the owner say “forget that thread.” Never submit forms, send messages, or delete files as part of resume; report blocked or stale references instead. Browser sessions must remain bound to the existing authenticated tab/session.
- **missing:** A durable task-capsule schema and API linking pendant utterance, relay job, Mac job, browser session/tab IDs, file paths, evidence hashes, and pending actions; A real implementation of the newly granted mac_readonly_inspect and mac_read_sources tools (both currently return “schema but no implementation”); Browser-extension extraction of selected authenticated tabs with stable tab IDs and redacted evidence, plus stale-page detection; A resume endpoint that converts a capsule into an ordered mac_run_actions plan and returns per-action receipts/progress to the relay; A pendant-to-thread reference mechanism so “that” resolves to a capsule without sending full history each turn

### "“Stop everything and protect my data.” (A physical pendant gesture, even if the Mac screen is locked.)"
- **useful because:** Today there is no single owner-controlled emergency stop spanning the wearable, relay, Mac executor, and authenticated browser. This would let the owner immediately halt queued or running automation, prevent a stale command from replaying, revoke browser control, stop audio retention, and leave a clear incident receipt—without finding the laptop or speaking a long explanation.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → mac-vision → dashboard
- **model tier:** No expensive model is needed for the stop path: firmware and relay perform deterministic cancellation and revocation. Use a cheaper background model only afterward to summarize what was stopped and what could not be stopped; realtime may speak the short confirmation.
- **latency:** Pendant-to-relay stop acknowledgement under 1 second when connected; queued commands must be rejected immediately on reconnect. Mac/browser revocation and cancellation receipts should arrive within 5 seconds, with honest per-job status if an external mutation already completed.
- **cost:** Negligible model cost for the emergency path; a short post-incident summary is typically under $0.01. Main engineering cost is reliable distributed cancellation, not inference.
- **security:** The gesture must be hard to trigger accidentally but work without an open microphone. Use a deliberate long-press plus button/LED confirmation, TLS-authenticated device nonce, replay protection, and a local audible/vibration confirmation. The stop operation should cancel pending work, revoke browser command leases, terminate active Mac jobs where possible, pause new execution, and mark already-completed external actions as completed rather than falsely claiming rollback. It must not pretend that sent email, submitted forms, or other irreversible effects were undone.
- **missing:** A signed, replay-protected pendant emergency-stop envelope and firmware state that survives reconnects; A relay-wide execution lease/revocation service consulted by Mac and browser workers before every step and at bounded intervals; Mac and browser adapters that can cancel active jobs, invalidate queued commands, and return typed stopped/completed/unknown receipts; A single owner-visible incident timeline showing which actions were prevented, interrupted, or already completed; A post-stop recovery flow to explicitly re-enable each surface, rather than silently resuming old work


## Changes it proposed to its own stack

### `integration` — Ship a cross-surface Task Capsule service between relay, Mac planner, and browser bridge. On every long-running or interrupted job, persist a compact capsule keyed by a user-visible thread ID: current goal, last successful step, pending steps, Mac app/window references, browser session/tab IDs, file paths, evidence hashes, timestamps, and expiry. Add POST /capsules, GET /capsules/:id, POST /capsules/:id/resume, and DELETE /capsules/:id. Resume must validate that apps/tabs/files still exist, produce a dry-run plan, then invoke the existing /execute path and append receipts to the existing job journal. Implement the already-granted mac_readonly_inspect/mac_read_sources bridges so capsule capture can observe state without using the mutating executor.
- **owner gets:** After walking away, losing LTE, or saying “not now,” the owner can return to the exact unfinished work instead of explaining it again or risking duplicate actions. They see what is stale and what will reopen before anything is sent or submitted.
- effort: Medium-high: relay schema and retention, Mac read-only adapters, browser evidence normalization, resume planner, and tests for stale tabs/files and duplicate execution.  ·  risk: A capsule could expose private browser or file metadata, or resume against a changed page. Mitigate with metadata-first storage, redaction, encryption, short TTL, stale-reference checks, idempotency keys, and never auto-submit external mutations. Recovery is DELETE capsule plus existing job cancel/undo where supported; failed steps remain in the journal.
- cost: Small persistent storage and hashing cost; roughly $0.01–$0.05 per model-assisted capture/resume, with metadata-only refreshes usually below that. No pendant hardware cost.  ·  latency: Capture is near-instant for hashes/metadata; model summarization runs asynchronously. Resume confirmation target is under 3 seconds, with reopening and verification continuing via receipts.
- security: Adds a sensitive artifact class. Encrypt at rest, bind to owner/session, redact bodies by default, log every read/resume, enforce TTL, and support explicit “forget this thread.” Browser cookies/tokens never enter the capsule.
- depends on: Actual implementations for mac_readonly_inspect and mac_read_sources (currently schema-only despite being granted); Stable browser tab/session identity and extraction receipts; A relay-to-pendant thread-reference protocol; Idempotent job execution and durable journal linkage

### `firmware` — Add a tiny priority control plane on the pendant WebSocket: task/capsule references, acknowledgements, cancellation, and resume tokens use a separate sequenced queue from audio frames. Under LTE-M contention, downlink control packets pre-empt optional speech playback, are retried idempotently from RAM, and are persisted to the existing microSD failure buffer only when the link is down. Include a monotonic device sequence and expiry so a delayed “resume” cannot execute twice.
- **owner gets:** A dropped or overlapped voice connection will not lose the one short instruction that ties the owner to unfinished Mac/browser work. They can walk away and later say “resume” without creating duplicate jobs or repeating sensitive actions.
- effort: Medium firmware and relay protocol change: frame type, bounded queue, reconnect replay, sequence tests, and relay deduplication. It must fit the current prototype rather than assume a new SoC.  ·  risk: Queue corruption or replay could produce a stale command. Bound the queue, authenticate every envelope, expire tokens, require the relay to acknowledge a job ID, and treat unknown/expired references as no-ops with a spoken failure. SD wear is controlled by only writing undelivered control envelopes.
- cost: No per-call model cost and negligible additional LTE bytes. Uses a few KB of the existing 211,608 B application RAM; no hardware BOM change.  ·  latency: Control acknowledgements should arrive in under a second when LTE is available; speech may be interrupted or delayed slightly because control is prioritized.
- security: Control envelopes must be TLS-protected and nonces/sequence numbers checked. Do not put page text, credentials, or file contents on the pendant—only opaque capsule IDs and short status codes.
- depends on: A relay capsule/job reference API; Existing WebSocket reconnect and SD fallback path; Relay-side idempotency and receipt linkage; A durable pendant-to-thread reference mechanism

### `relay` — Introduce a signed, short-lived global execution lease with an epoch counter. Every Mac and browser action must carry the current epoch and check it before each step; a pendant emergency gesture increments the epoch, cancels queued jobs, invalidates browser command leases, and causes workers to stop at the next safe boundary. Persist a per-action terminal receipt (prevented, interrupted, completed, or unknown) and require an explicit re-enable operation to issue a new epoch.
- **owner gets:** The owner gets a real emergency brake across all automation surfaces, including work already handed off to a background worker. They can stop the system from the pendant and later know exactly what did and did not happen, instead of guessing whether a command is still running.
- effort: High distributed-systems work: relay lease authority, worker checks, pendant envelope/reconnect handling, cancellation adapters, race-condition tests, and dashboard incident history.  ·  risk: A network partition may prevent immediate cancellation on an offline Mac, and stopping mid-step may leave a partial local mutation. Use bounded check intervals, local deny-new-work state, idempotency keys, explicit unknown outcomes, and never claim rollback of an external action. Recovery is a new epoch plus deliberate re-enable.
- cost: No meaningful model cost; small durable relay state and one tiny control message per job step. No hardware cost if the existing button/LED is used, though a production pendant should add haptic confirmation.  ·  latency: Adds a sub-100 ms local lease check per action and typically under 1 second over the live link; offline surfaces can only enforce stop when reachable.
- security: This becomes a high-value control channel: authenticate the pendant, bind it to the owner, rotate keys, reject replays, audit every epoch change, and keep the emergency gesture local/offline-capable.
- depends on: A firmware emergency-stop gesture and signed envelope; Mac and browser workers checking the lease before every side effect; Durable action receipts with explicit unknown state; A reconnect protocol that delivers the latest revoked epoch before accepting work

## Its own summary

Round 91 produced two new, connected deliverables: (1) a durable cross-surface Task Capsule so “pick up where I left off” can recover exact unfinished Mac/browser work with evidence, stale checks, and receipts; (2) a pendant priority control plane so capsule IDs, acknowledgements, and resume tokens survive LTE-M audio contention and reconnects. I also verified that the newly granted mac_readonly_inspect and mac_read_sources interfaces exist only as schemas: live calls return “schema but has no implementation yet.” I still need those adapters implemented, plus the relay capsule API, stable browser evidence IDs, and pendant thread-reference/idempotency protocol. No further owner permission is needed for the proposed reversible/read-only workflow.

**Biggest unknown:** Whether the backend can durably bind a short pendant utterance such as “resume that” to one unambiguous Mac/browser thread without resending private context; this needs a stable thread/capsule identifier and relay-side expiry/selection policy.
