# Harness derivation — mac-planner — round 76

Model: `gpt-5.6-luna`  ·  probes against `http://localhost:8000`

## What it established

- **cross-surface recovery gap** — Live Mac state confirms browser extension offline with 5 pending commands; browser actions fail after ~45 seconds rather than becoming resumable. /ops/status also reports Accessibility trusted=false and Screen Recording false, so computer-use cannot be assumed ready.
  - evidence: GET /browser/status returned online:false, pendingCommands:5; GET /jobs returned browser_read_page and browser_navigate failures with durationMs 45050; GET /ops/status returned accessibility.trusted:false and screenRecording.granted:false.

## Capabilities it proposed

### "“Start this here, finish it wherever you can, and if anything disconnects, pick up exactly where you left off.” For example: gather the details from my logged-in browser tabs, make a draft in a Mac workspace folder, and leave a short spoken completion or recovery note on the pendant."
- **useful because:** Today a long task can span the pendant, relay, authenticated browser, and Mac but each handoff is effectively a new request. A durable cross-surface workflow would checkpoint every read and mutation, survive a sleeping Mac/browser tab or dropped radio link, retry only safe idempotent steps, and return a human-readable receipt naming the exact unfinished step. This is meaningfully more than generic background jobs: it makes heterogeneous device work recoverable instead of silently partial or duplicated.
- **path:** pendant → relay → browser-harness → mac-planner → dashboard
- **model tier:** Use the realtime tier only for the owner's live command and concise interruption/recovery narration; use a cheaper background model for step planning, checkpoint reconciliation, and summarizing receipts. Deterministic workers should execute browser/Mac steps.
- **latency:** Acknowledge the command in under 2 seconds. Checkpoint after each step (typically under 1 second). Resume polling on reconnect within 5 seconds; background completion can take as long as the underlying browser or Mac operation.
- **cost:** Roughly one realtime turn for intent plus 2–6 background model calls for planning/reconciliation and final summary; dominant cost is context rehydration unless checkpoints store compact typed inputs/outputs. Browser and Mac calls are otherwise local/relay operations.
- **security:** Private page text, file paths, and generated drafts cross the relay and are retained in job state; encrypt sensitive checkpoint payloads, minimize snippets, apply TTLs, and bind browser checkpoints to the authenticated tab/session. Never replay send/delete/buy steps after reconnect; mark them pending for the owner's existing confirmation policy. Every step needs a receipt with source tab/URL or Mac path, before/after hashes, and retry count.
- **missing:** A durable saga/workflow record with typed step states (pending, running, succeeded, retryable, blocked, abandoned), leases, and compact checkpoint payloads; Heartbeat and resumable polling across relay, browser extension, and Mac local agent instead of a single blocking browser wait; Idempotency and compensation metadata for Mac mutations and browser actions, plus a recovery worker that can safely resume after process/device restart; Pendant reconnect delivery for completion/failure summaries and a dashboard view of the exact stalled step

### "“Use my private browser tabs and Mac files to answer this, but keep the raw contents on my devices.” Return only the minimum facts, redacted excerpts, and verifiable citations needed for the answer or draft."
- **useful because:** The owner cannot safely use the hive for sensitive work today without sending page text, email, or file contents through the relay/model. A device-resident privacy firewall would let the browser and Mac perform extraction, comparison, and redaction locally, while the server receives typed claims, hashes, and small owner-approved excerpts. This enables useful work on private accounts without turning every request into raw-data export.
- **path:** browser-extension → mac-planner → relay-realtime → faculty-perception → faculty-judgement → faculty-action → dashboard
- **model tier:** Use local deterministic extractors and a small local model for classification/redaction whenever possible. Use the background model only on the redacted evidence bundle; reserve realtime for the owner's live request and concise answer.
- **latency:** Local policy evaluation and redaction under 2 seconds for ordinary pages/files; up to 10 seconds for multi-document comparison. Spoken response begins as soon as the redacted evidence bundle is ready.
- **cost:** Usually one inexpensive background inference over a compact evidence bundle; raw-content transfer and repeated context retransmission are avoided, reducing token cost. Local extraction consumes Mac CPU but no meaningful API budget.
- **security:** The firewall must treat URLs, filenames, account identifiers, mail addresses, and inferred secrets as sensitive; use deny-by-default field release, per-session purpose binding, local audit logs, cryptographic content hashes, and short-lived redaction tokens. Never allow a model-generated summary to silently re-identify masked data. Mutating actions still use the owner's existing confirmation rules.
- **missing:** A local privacy-policy engine shared by the browser extension and Mac agent, with field-level allow/deny/redact decisions; A typed evidence-envelope protocol containing claims, provenance, hashes, confidence, sensitivity, and expiry without raw source payloads; Local extraction/redaction implementations for authenticated DOM regions, Mail/Calendar snippets, and Mac files; Relay and model-router support that rejects raw private payloads when a redacted envelope was requested; A dashboard showing exactly which fields left the device and allowing the owner to change policy per task


## Changes it proposed to its own stack

### `integration` — Implement a cross-surface saga coordinator between the existing job, browser, and Mac bridges. A workflow record should map one owner request to ordered typed steps and external IDs (browser commandId, Mac jobId, pipelineId), persist compact input/output hashes and source provenance, lease each step with heartbeat/expiry, and expose resume/reconcile endpoints. On reconnect or worker restart, retry only explicitly idempotent steps; otherwise mark the step blocked and deliver a recovery receipt rather than duplicating a mutation. Add a single workflow status stream that merges browser heartbeat/results, Mac job receipts, and pendant pipeline events.
- **owner gets:** A request that spans a logged-in tab and the Mac will stop disappearing halfway through or running the same action twice after Wi‑Fi, browser, or laptop sleep. The owner gets one truthful status—completed, waiting on a named step, or safely abandoned—with a one-tap/voice resume path.
- effort: Medium-high: a durable state machine and storage schema, adapters for browser and Mac IDs, lease/retry worker, reconnect delivery, and failure-injection tests for sleeps, duplicate results, and late callbacks.  ·  risk: Incorrect reconciliation could replay a form submission or file deletion. Default unknown steps to blocked, require explicit idempotency keys for mutations, retain before/after hashes, and use existing job cancel/undo where available. If the coordinator is unavailable, current direct /execute and browser paths continue unchanged.
- cost: Small persistent metadata and event-log cost per workflow; background reconciliation uses a cheap model only when semantic recovery is needed. No meaningful pendant hardware cost.  ·  latency: Initial acknowledgment unchanged; each step adds a sub-second durable checkpoint. Reconnect recovery becomes seconds rather than a lost 45-second blocking wait.
- security: Workflow state can contain private URLs, snippets, and paths. Encrypt payloads, store hashes instead of raw content where possible, enforce per-session access, and expire sensitive checkpoints. Never expose secrets in spoken receipts.
- depends on: Existing browser request IDs/idempotency and tab affinity need a non-blocking progress/resume API (chg-14accc01 is still open specifically because browserBridge waits 45 seconds).; A stable typed Mac job receipt schema from /jobs/:jobId/receipts and /journal/:jobId.; A relay-to-pendant reconnect queue for completion and blocked-step notifications.

### `browser-harness` — Make browser execution offline-aware: before dispatch, consult the bridge heartbeat and return a typed unavailable state immediately when offline; move queued commands into a durable pending state with TTL and owner-visible count instead of holding an HTTP request for 45 seconds. When the extension heartbeats again, reconcile commands by idempotency key, emit progress, and expire stale reads safely. Keep mutations blocked from automatic replay and surface them as needing review.
- **owner gets:** The owner would hear “Safari is offline; I saved this task and will resume when it reconnects” in seconds instead of waiting 45 seconds for a failed request, and would never face five invisible pending commands or accidental duplicate browser actions.
- effort: Medium: bridge heartbeat gate, durable queue state transitions, non-blocking polling/SSE, idempotent result reconciliation, TTL cleanup, and tests for late/duplicate extension results.  ·  risk: A false offline report could delay a read; fail-open is unnecessary for reads because they can be resumed. A stale heartbeat could cause a mutation to be incorrectly replayed, so mutations must remain non-replayable unless explicitly proven idempotent. Preserve the existing direct path as fallback.
- cost: Negligible storage/event overhead; no model calls required for the fast path.  ·  latency: Offline failure goes from ~45 seconds to under 1 second; online commands retain current latency, with progress available during long operations.
- security: Pending commands may contain private URLs or form data; encrypt or redact queue payloads, bind them to the browser session, and expire them. Do not speak sensitive page contents in the offline notice.
- depends on: Existing POST /browser/heartbeat, GET /browser/poll, POST /browser/result/:commandId, and GET /browser/status.; The resumable progress portion of chg-14accc01; its current 45-second blocking wait is directly observed live.; A durable command queue with per-command idempotency and session affinity.

### `model-routing` — Add a device-local evidence gateway and enforce a redacted-envelope mode end to end. Browser and Mac adapters must extract source facts locally, classify sensitivity, redact or hash disallowed fields, and send the relay only a signed envelope of claims plus provenance. The relay/model router rejects raw page/file payloads when this mode is requested, and the dashboard exposes an export ledger of every field released.
- **owner gets:** They could ask questions about private work accounts and local documents without having to choose between usefulness and exporting their raw personal data. They would see exactly what crossed the device boundary and have a durable way to detect accidental over-sharing.
- effort: High: shared policy schema, local DOM/file extractors, signed envelope verification, router enforcement, redaction tests against secrets and re-identification, and dashboard UX.  ·  risk: Over-redaction can make answers incomplete; return an explicit missing-evidence explanation rather than silently guessing. A compromised local adapter could mislabel data, so the relay must verify envelope signatures and reject untyped payloads. Keep an owner-controlled unrestricted mode separate and visibly labeled.
- cost: Lower model/API cost for large private sources because only compact evidence leaves the device; moderate engineering and local CPU cost for extraction/redaction; no hardware cost.  ·  latency: Adds roughly 1–10 seconds of local extraction/redaction, but avoids repeated large-context uploads and can stream an initial evidence summary sooner.
- security: Substantially reduces raw private-data exposure, but provenance and hashes can still leak correlation information; salt hashes per task, minimize metadata, encrypt local audit logs, and expire envelopes.
- depends on: A typed evidence-envelope format with provenance, sensitivity, confidence, expiry, and task purpose.; Local browser/Mac extraction and redaction libraries.; Relay-side schema enforcement and a visible export ledger; these do not exist in the current stack.
