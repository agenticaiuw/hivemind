## Capabilities it proposed

### "If something I asked the Mac or browser to do failed—or may have silently done nothing—figure out why, recover with the safest working route, and tell me exactly what happened."
- **useful because:** Today a UI receipt can say success while Accessibility rejects every synthesized event, and browser commands can pile up while the extension is offline. This turns opaque failures into automatic cross-surface recovery: the pendant hears a concise explanation, while the relay and Mac retain evidence and a retry outcome.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → unified
- **model tier:** Use a cheap background planner for diagnosis and retries; reserve realtime for the one-sentence spoken update and only escalate to the expensive tier when the recovery plan is ambiguous.
- **latency:** Run a 1–2 second readiness preflight before UI work, verify the postcondition within 3 seconds, and retry/fallback for up to 30 seconds in the background. Speak immediately with 'I’m checking the connection' rather than blocking the conversation.
- **cost:** Usually one cheap planner call plus structured status polling; roughly $0.005–$0.03 per incident depending on whether a screenshot or long journal context is needed. The expensive part is avoidable context and vision uploads, so send only typed readiness and receipt deltas by default.
- **security:** Private URLs, page text, shell output, and screenshots stay on the Mac unless the owner explicitly asks for relay diagnosis. Recovery must preserve the owner's existing maximum-access/no-gate policy, but every attempt, fallback, postcondition, and silent-input warning is recorded. Never claim success from an unverified UI receipt.
- **missing:** A shared readiness/postcondition contract for Mac UI, browser bridge, and shell actions; A local remediation worker that can reconnect/poll the browser bridge and select CLI/AppleScript/API fallbacks without replaying completed action IDs; Attribution propagation from relay/planner into every job and receipt (the live journal currently has 112 unattributed actions); A durable retry/result stream so recovery survives a Mac-agent restart (the browser runner backlog is still open)

### "Pause this wherever it is, keep the exact place and evidence, and resume it when I’m back at my Mac—tell me only what changed while I was away."
- **useful because:** Today a task is tied to one live conversation or a fragile Mac/browser attempt. The owner cannot safely walk away, lose the browser connection, return later, and continue from the exact verified step without risking duplicate clicks or losing private-page context. This would make the pendant a physical pause/resume control for work spanning the wearable, relay, Mac, and authenticated browser.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → unified → faculty-perception → faculty-judgement → faculty-action
- **model tier:** Use a cheap background model to serialize checkpoints, compare the resumed environment, and summarize deltas; use realtime only for the short spoken pause/resume confirmation and escalate to the expensive tier when the checkpoint no longer matches.
- **latency:** A button press or spoken pause should be acknowledged in under 1 second and checkpoint within 5 seconds. Resume readiness should be checked in under 3 seconds; reconciliation may continue in the background while the owner receives a concise status.
- **cost:** About $0.003–$0.02 per pause/resume, dominated by a compact reconciliation call; no screenshot or page text should be resent unless structural fingerprints disagree.
- **security:** Private browser session handles and checkpoint evidence remain on the Mac/relay, encrypted and scoped to the owner. A resumed action must never silently substitute a different tab, account, or page; if identity/fingerprint changes, stop at a reviewable diff. Pause, discard, and resume are explicit owner intents, but this does not add a general approval gate to ordinary actions.
- **missing:** A cross-surface checkpoint protocol containing action cursor, idempotency keys, pre/postcondition evidence, tab/session identity, and expiry; Pendant-local pause/resume affordance and durable pending-task indicator that survives a dropped link; Relay storage and notification for suspended tasks with lease ownership and conflict resolution; Mac/browser reattachment plus environment-diff verification before continuing; A spoken delta serializer that reports only changes since the checkpoint


## Changes it proposed to its own stack

### `mac-harness` — Add a non-blocking execution-readiness and postcondition verifier around every Mac/browser action. Before dispatch, snapshot typed reachability (Accessibility identity and event probe, screen recording, foreground app, browser bridge lease/queue depth, shell availability). After dispatch, require an action-specific observable postcondition: changed volume/value, opened app/window, file hash, browser URL/title or extracted text, or explicit shell exit/output. Attach readiness, verification, fallbackUsed, and failureClass to the existing receipt; mark UI actions as unverified when Accessibility is false even if the low-level API returned success. Emit a compact remediation event for the relay rather than making the executor gate or refuse anything.
- **owner gets:** The owner stops hearing false 'done' reports. When the agent cannot control the screen, or Safari has gone offline, it can say exactly that and use a working CLI/AppleScript/browser route where available; every action still retains maximum access and no approval gate.
- effort: Medium: one typed verifier and action adapters in executor/actionReceipts, plus browser lease/status integration and a small remediation mapper. Add integration tests for the current Accessibility mismatch and offline queue.  ·  risk: Some actions have no observable postcondition and will become 'unverified' rather than failed; adapters could misclassify a legitimate no-op. Recover by preserving raw results and allowing the planner to select an explicit verification mode. Never replay an action solely because verification timed out.
- cost: Negligible API cost; fewer expensive planner retries. Local storage increases receipts by roughly 1–3 KB per action and keeps sensitive evidence as hashes/typed facts unless explicitly requested.  ·  latency: About 50–300 ms for local readiness checks; up to 3 seconds only when an action requests postcondition polling. Shell-only reads can skip the UI/browser checks.
- security: Improves honesty without narrowing permissions. Raw shell output and private page content remain local; relay receives class/status/hashes by default. Existing owner policy of unrestricted execution and no confirmation remains unchanged.
- depends on: A stable typed action-to-postcondition registry for shell, AppleScript, UI, and browser actions; Fix planner-tier/request-id propagation so receipts stop accumulating unattributed actions; Durable browser command polling/retry so remediation can survive a bridge restart

### `model-routing` — Make request identity and planner-tier attribution mandatory end to end: mint one traceId at the pendant/relay boundary, carry it through planning, delegated Mac/browser jobs, retries, and receipts, and persist planner tier, model, token estimate, latency, fallback chain, and terminal outcome. Add a compact per-request timeline to the existing journal/ops snapshot and use it to route routine status/recovery work to the cheap model automatically.
- **owner gets:** The owner can ask 'what happened and why did it take so long?' and get one trustworthy answer instead of disconnected Mac jobs. It also prevents expensive realtime reasoning from being spent on routine battery checks, retries, or completion receipts.
- effort: Medium: request-context middleware plus fields in relay job records, local jobTracker, routingStats, and journal projection; add dashboard and spoken receipt serializers.  ·  risk: Older jobs remain unattributed and mixed-version clients may omit fields. Treat missing fields as explicitly unknown, never infer them, and preserve backward-compatible reads.
- cost: Small local/D1 storage increase; likely lowers API spend by routing recovery, status, and scheduled work to the background tier. No extra model call is required for attribution.  ·  latency: Negligible per request; a few milliseconds for context propagation and journal aggregation.
- security: Trace IDs must be opaque and contain no URL, account, or prompt text. Keep model/token metadata separate from private action payloads; redact shell output and page text from relay-facing summaries.
- depends on: A shared trace-context schema between relay-realtime, mac-planner, browser-extension, and unified; A durable browser job runner/result stream so delegated work has one trace across restarts; Dashboard and spoken receipt support for the new timeline fields

### `firmware` — Add a pendant-side task-control state machine with durable intent records: short press acknowledges the current remote task, long press pauses it, double press requests cancel, and LED/haptic patterns show queued, paused, waiting-for-Mac, resumed, failed, or completed. The firmware should persist only a compact task handle, cursor version, and requested transition in its existing flash/NVS, retry delivery after reconnect, and never execute remote work itself.
- **owner gets:** The owner can safely walk away from the Mac and still control a long-running browser or desktop task without reopening the app or relying on a live voice session. A glance or vibration tells them whether work is paused, waiting, or actually finished instead of leaving them guessing.
- effort: Medium firmware and relay integration: define signed task-transition messages, debounce button gestures, add reconnect replay and server acknowledgements, then expose the state in spoken receipts and the Mac dashboard.  ·  risk: Accidental long/double presses could pause or cancel work, and stale transition messages could target an old task. Require a matching task-handle/version, make cancel idempotent, use a distinct long-press duration, and provide a short haptic confirmation before sending the transition.
- cost: Negligible API cost. A few hundred bytes of persistent state and under 8 KB firmware/RAM budget; no new hardware if the existing button and LED/haptic path support the patterns.  ·  latency: Local feedback under 100 ms; transition delivery depends on the relay link and is retried in the background.
- security: The pendant sends intent only, never private page content. Authenticate transitions to the paired relay and reject stale or unpaired task handles; preserve the existing no-gate execution policy for actions themselves.
- depends on: A durable cross-surface task/checkpoint identity and lifecycle API; Relay support for idempotent pause/cancel/resume transitions; Mac/browser jobs that can honor a pause at action boundaries and report acknowledgements
