## Capabilities it proposed

### "“Do this, and if my Mac or browser isn’t ready, don’t pretend—pause it, tell me what’s blocked, and resume automatically when it’s safe.”"
- **useful because:** Today a UI action can return a success receipt while Accessibility/Screen Recording or the browser bridge is unavailable. The owner needs a reliable promise: intent survives leaving the conversation, blocked work is explainable, and no irreversible step happens without a fresh confirmation. This uses the pendant as the always-with-owner confirmation surface, the relay as durable coordinator, and the Mac/browser as the only actors with private reach.
- **path:** pendant → relay-realtime → mac-planner → mac-vision → browser-extension → unified → faculty-perception → faculty-judgement → faculty-action → dashboard
- **model tier:** Use the realtime tier only to interpret the spoken goal and explain a block in one sentence. Use a cheaper background model to resume a queued plan, reconcile evidence, and draft repair instructions; deterministic preflight and action execution should be code, not an LLM.
- **latency:** A preflight response in under 2 seconds when online; a blocked result can be immediate. Resume on reconnect/permission-change within 30 seconds, with no repeated owner prompt. Final irreversible action waits for pendant button confirmation (up to the owner's configured window).
- **cost:** About $0.01–$0.05 per resumed job if model reconciliation is needed; most attempts should cost no model tokens after the initial plan because preflight, leases, idempotency, and evidence checks are deterministic. Storage and event traffic dominate at scale.
- **security:** Private page contents remain on the browser bridge/Mac unless explicitly projected. The relay stores only the goal, typed step state, hashes, and evidence references with short TTL. Never infer permission readiness from a receipt: require observed Accessibility/Screen Recording/browser-online signals and before/after evidence. Expire leases, redact secrets, bind commands to tab/session and owner pendant session, and require confirmation immediately before sending, deleting, purchasing, or other irreversible effects.
- **missing:** A durable cross-surface action-lease/state machine with states planned, preflight-blocked, ready, executing, evidence-pending, confirmed, completed, and failed.; A shared readiness/evidence envelope emitted by perception and consumed by action; receipts must distinguish observed effect from attempted/no-op.; Reconnect and permission-change events from the Mac agent and browser bridge, plus a relay wake-up/retry scheduler.; A pendant-local confirmation token/LED/audio affordance that is bound to one exact irreversible step and expires.; Dashboard and spoken repair UX showing the one blocker, required owner action, retry history, and an honest final receipt.

### "“Before you make a plan from my accounts, tell me when my information conflicts, ask me the one question that would resolve it, and keep the plan safely provisional until I answer.”"
- **useful because:** Real life data disagrees: a calendar invite changes while an email still names the old time, a travel page shows one reservation while a receipt shows another, or a task is marked done in one system but open in another. Today an assistant tends to silently choose a source or make the owner repeat the whole context. The owner should get a short, spoken uncertainty alert, one decisive question, and a plan that updates itself when the answer or a source change arrives.
- **path:** browser-extension → mac-planner → mac-vision → mac-terminal → relay-realtime → pendant → faculty-perception → faculty-judgement → faculty-action → dashboard
- **model tier:** Use deterministic identity/entity matching, timestamps, and source precedence first. Use a cheaper background model to cluster contradictions and draft candidate interpretations. Use realtime only to ask the single targeted question and explain the consequence in plain speech.
- **latency:** For an explicit request, return the contradiction and question within 5 seconds; background monitoring can reconcile on source events or scheduled checks. Keep provisional plans immediately usable, but do not execute an affected irreversible step until resolved.
- **cost:** Roughly $0.01–$0.04 per contradiction cluster when model interpretation is required; ordinary timestamp/source comparisons should be near-zero model cost. Browser reads and durable provenance storage dominate.
- **security:** Only inspect already-authorized private tabs/files and project the minimum conflicting fields. Never expose secret values in spoken prompts or relay logs. Identify sources by capability and timestamp, not by blindly trusting a website. Treat the owner's answer as scoped to the named entities and expiry window. Require confirmation before any irreversible action whose inputs were conflicted.
- **missing:** A typed contradiction record containing entities, claims, source URLs/files, observed times, sensitivity, confidence, and expiry.; Cross-surface entity resolution that can recognize the same meeting, reservation, person, or task across browser and Mac data without exporting full private content.; A provisional-plan state whose dependent steps automatically re-evaluate after the owner answers or a source changes.; A pendant interaction that supports one short answer plus defer/never-ask-again, with the answer bound to the exact contradiction.; Dashboard and receipts that show which claim won, why, and what would trigger re-evaluation.


## Changes it proposed to its own stack

### `firmware` — Make the 24 kHz playback path deadline-aware end to end: add a bounded 3-frame jitter buffer, sequence/timestamp checks, Opus packet-loss concealment, and a decode watchdog on the pendant. If a 24 kHz frame misses its 60 ms deadline or CPU headroom drops below a measured threshold, switch that utterance to a pre-negotiated lower-complexity/16 kHz fallback rather than emitting silence; report a typed audio-quality event to relay with packet loss, underruns, decode time, and fallback reason. Relay and Mac queueing must honor the event and avoid sending more concurrent audio jobs.
- **owner gets:** The owner should hear a complete, intelligible answer while walking through radio loss or a busy device—not a silent gap caused by a prototype path spending roughly 87% of one core on encode and decode. A graceful fallback is more useful than claiming '24 kHz' while dropping speech, and the telemetry lets the system improve routing without asking the owner to debug UART logs.
- effort: Medium: firmware audio scheduler/buffer and Opus PLC work, relay event schema and transcoder negotiation, Mac/bridge queue backpressure, plus long-run RF-loss and CPU-load tests. Requires measuring actual available RAM/stack margins on the current DK before choosing buffer size.  ·  risk: A fallback transition can sound different or duplicate a frame; sequence-aware crossfade and utterance-level mode changes limit artifacts. A bad watchdog could reset playback, so keep a kill switch and retain the current path behind a feature flag. Recovery is automatic re-negotiation on the next utterance and a diagnostic receipt if quality remains degraded.
- cost: No meaningful API increase; telemetry is small. Adds roughly 3×60 ms compressed-frame buffering plus metadata (likely under 10 KB RAM, to be validated against 211,608 B application RAM). Power rises slightly from buffering and telemetry; no new hardware required for the prototype.  ·  latency: Adds at most 120–180 ms startup buffering; no added latency after playback begins. Fallback prevents unbounded stalls and should reduce perceived latency during loss.
- security: Audio telemetry contains no speech, only counters and reason codes. Keep it session/job scoped and avoid uploading raw packets beyond the existing relay path.
- depends on: A typed end-to-end audio event/receipt schema shared by pendant, bridge, relay, and Mac.; A 24 kHz acceptance harness that injects packet loss, jitter, and CPU contention and verifies intelligibility/no-silence behavior.; Relay-side codec capability negotiation and queue backpressure.

### `integration` — Introduce a single signed ActionEvidenceEnvelope exchanged by perception, judgement, action, relay, Mac, and browser: {jobId, stepId, actor, readiness signals with timestamps, intended effect hash, pre-state evidence hash, post-state evidence hash, observedAt, confidence, reversible, blocker}. Action must refuse to advance on stale/missing readiness or absent post-state evidence; relay receipts render attempted, blocked, no-op, and verified-complete as different outcomes. Bind each envelope to the pendant session and an idempotency key so reconnects cannot replay a send/delete/purchase.
- **owner gets:** The owner gets an honest answer about whether something happened. A successful-looking receipt that changed nothing is worse than a clear “blocked: Accessibility is off.” When it does work, they receive evidence tied to the exact tab/file and can safely leave the Mac while the job continues.
- effort: Medium integration change across schemas, relay persistence, Mac preflight/action adapters, browser bridge results, and dashboard/voice formatting; add failure-injection tests for stale permissions, disconnected bridge, tab changes, and effect-without-evidence.  ·  risk: Strict gates will block some actions that would have worked, so allow an explicit owner-approved diagnostic/retry path but never silently bypass evidence for irreversible steps. Evidence hashes can become stale after page mutation; reject and re-plan rather than trusting them. Keep a compatibility adapter for old receipts during migration.
- cost: Negligible model cost; small durable event rows and hashes per step. Dashboard work is the main engineering cost.  ·  latency: Adds one deterministic preflight and postcondition observation, typically 100–500 ms locally; no extra model round trip for ordinary actions.
- security: Improves security by preventing stale-session or wrong-tab execution. Do not store raw private page content in relay; store redacted excerpts or hashes and keep full evidence local to Mac/browser.
- depends on: Mac/browser readiness signals (Accessibility, Screen Recording, bridge online, tab/session identity).; Durable job/step persistence and idempotency keys.; Owner confirmation affordance on pendant for irreversible steps.
