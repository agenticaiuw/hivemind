## Capabilities it proposed

### "I’m stuck—look at what I have open, figure out the next three useful steps, and help me do the safest one."
- **useful because:** Today the wearable, Mac, and browser each know only part of the problem. This creates a grounded rescue loop: the Mac contributes active apps and local files, the browser contributes authenticated page evidence without exposing credentials, the relay compares options and remembers the case, and the pendant reduces the result to one spoken choice. It is useful when the owner is interrupted or cognitively overloaded, not just when they can formulate a precise command.
- **path:** pendant → mac-vision → mac-planner → browser-extension → relay-realtime → dashboard
- **model tier:** Use the low-latency model only for the pendant conversation and final choice. Use a cheaper background planner to inspect the bounded Mac/browser snapshot, deduplicate evidence, and produce three ranked next steps. Use the action facet only after the owner chooses one.
- **latency:** Initial spoken acknowledgement under 1 second; collect the Mac/browser snapshot in 3–8 seconds; present choices within 10 seconds. If a page or file is slow, say which source is pending rather than blocking the conversation.
- **cost:** About $0.01–$0.05 per rescue episode depending on screenshot/OCR and private-page extraction; the dominant cost is multimodal Mac/browser evidence, not the short spoken response. Cache unchanged tab and window fingerprints to avoid resending context.
- **security:** Only already-visible Mac windows and explicitly selected authenticated tabs may be inspected. Send page excerpts and file metadata, not cookies, full local files, or hidden tabs. Before any action, show the exact target and expected side effect on the dashboard and speak a concise confirmation; drafts and reversible edits can be prepared but not sent. A kill button on the pendant should cancel queued work.
- **missing:** A cross-surface snapshot protocol with stable window/tab IDs, timestamps, and sensitivity labels; Mac-vision support for a bounded active-window/app/file summary rather than an unrestricted screenshot stream; Browser extraction that returns cited snippets from selected authenticated tabs while preserving session privacy; A background triage planner that ranks next steps and records why each was chosen; Pendant choice/cancel protocol and a dashboard card showing the three options plus evidence; A shared job that can hand the selected step to Mac or browser and return a receipt

### "Keep me informed without interrupting me: let only genuinely urgent things reach me as distinct silent patterns on the pendant, and give me a spoken digest when I ask."
- **useful because:** The owner can currently receive spoken/audio interaction or inspect a screen, but cannot reliably distinguish an urgent event from ordinary completion noise while their phone and Mac are out of sight. A tactile urgency channel would work in a meeting, while walking, or with audio muted, and would turn the pendant into an attention filter rather than another notification stream.
- **path:** relay-realtime → faculty-perception → faculty-judgement → pendant → mac-planner → browser-extension → dashboard
- **model tier:** Use a cheap background classifier for incoming calendar, browser-watch, Mac-job, and relay events; use the expensive realtime model only when the owner asks for the digest or clarification. Deterministic policy should map urgency classes to patterns, with the model unable to silently escalate arbitrary events.
- **latency:** Urgency classification under 2 seconds after an event arrives; tactile alert delivery within 1 second of classification. Spoken digest should begin under 1 second after the owner presses the button, with background assembly continuing if sources are slow.
- **cost:** Usually under $0.01 per event batch; model cost is dominated by extracting meaning from private browser pages or long Mac outputs. Tactile delivery and digest retrieval are otherwise negligible.
- **security:** The relay must not expose private event text to the pendant for a low-level alert—send only urgency class, pattern ID, and opaque event ID. The digest retrieves details only after the owner requests it. Require explicit per-source subscriptions, quiet hours, rate limits, and a physical cancel/disable gesture; never infer medical, safety, or financial urgency without a deterministic source rule and clear labeling.
- **missing:** A pendant hardware revision with a low-power haptic actuator and driver (the current nRF9160 development kit exposes only one button and one LED in the known design); Firmware support for at least four distinct haptic patterns, acknowledgment, quiet mode, and missed-alert persistence within the available RAM/flash; A relay event-normalization and urgency-policy service spanning Mac jobs, selected authenticated browser watches, calendar/notifications, and relay jobs; A privacy-preserving opaque alert envelope and on-demand digest endpoint; Dashboard controls for source subscriptions, urgency thresholds, quiet hours, and an audit trail of why each alert fired; End-to-end tests for dropped cellular links, duplicate events, and alert acknowledgment/replay


## Changes it proposed to its own stack

### `mac-harness` — Add a durable shell execution journal and resumable command runner without changing FULL_CONTROL_MODE: before each run, record a command fingerprint, cwd, selected environment facts, timeout, and declared outputs; stream bounded stdout/stderr chunks and exit state into the job record; on timeout, disconnect, or agent restart, classify the last checkpoint as not-started/running/finished/unknown, avoid blind reruns of unknown commands, and expose a resume/retry action that can continue from an explicit step boundary. Attach an artifact manifest (paths, sizes, hashes) and a reversible/irreversible hint to the receipt, with secret-pattern redaction applied only to logs, never to execution.
- **owner gets:** Long Mac tasks would stop disappearing when the laptop sleeps or the bridge drops. The owner could ask from the pendant, leave, and later receive an honest result plus the files produced, rather than a vague failure or a dangerous duplicate run. It also makes the existing maximum-access policy more trustworthy by showing exactly what happened.
- effort: Medium: local-agent journal schema and streaming (~2–3 days), shell wrapper/checkpoint protocol (~2 days), relay job resume endpoint and dashboard/pendant receipt integration (~2 days), failure-injection tests (~1 day).  ·  risk: A command with external side effects can still be duplicated if it dies after performing the side effect but before recording completion; unknown states must therefore remain unknown and require an explicit retry choice. Hashing large outputs costs I/O, and log redaction can hide useful text if overbroad. Recovery is to preserve raw local job state, cap hashes by size, and mark every inferred field with confidence.
- cost: Negligible API cost for shell work; roughly 1–3 KB of D1 metadata plus bounded log chunks per run, with larger stdout/artifacts retained locally and only summarized to the relay. Engineering/storage cost is the main expense.  ·  latency: No meaningful added latency before launch (one journal write); streaming adds small local I/O. Receipt generation may take under a second, while hashing large artifacts is asynchronous.
- security: Improves auditability without adding gates. Environment snapshots and command output can contain secrets, so default relay projection must exclude env values and redact credential-shaped output; artifact paths should be owner-visible but not broadcast to other surfaces unless requested.
- depends on: A durable job/receipt contract shared by local-agent and relay; A relay resume/status endpoint; Pendant spoken progress and completion receipt support; No change to the owner's FULL_CONTROL_MODE policy

### `integration` — Implement the already-granted bounded Mac diagnostics as a real typed RPC, with one fixed query per call and a versioned response envelope: host identity, OS, hardware, battery, network, audio, displays, permissions, disk, processes, and local-agent health. Include collectedAt, source, freshness, and unavailable reasons; route it through the same relay job/receipt path so a remote planner can distinguish 'false' from 'not measured'. Do not expose arbitrary command execution through this interface; keep FULL_CONTROL shell unchanged for execution.
- **owner gets:** The hive could stop guessing whether the Mac is awake, reachable, permissioned, connected to Wi‑Fi, or playing audio. The pendant could say “your Mac is online but Screen Recording is off” instead of silently queuing work, and planners could choose the browser, relay, or Mac based on current facts.
- effort: Small to medium: implement the fixed query mapper in local-agent, add authenticated RPC/response validation, then wire the relay and dashboard status card; add tests for unavailable permissions and stale responses.  ·  risk: A process summary or network detail may reveal more than intended, and stale health can misroute work. Minimize by returning coarse process categories by default, sensitivity-tagging fields, applying a short TTL, and making freshness mandatory in every response. Recovery is to fall back to the existing bridge heartbeat and report unknown.
- cost: Near-zero model cost; one small status payload per diagnostic request and modest local CPU. Dashboard storage should retain only the latest snapshot, not a history of process or network details.  ·  latency: Typically sub-second locally, up to a few seconds if the Mac bridge is asleep. It should never block the pendant conversation; use cached data with an age label.
- security: Read-only and bounded, but still sensitive. Require the existing local-agent authentication, omit usernames/paths/SSID unless explicitly requested, and make relay projections field-scoped.
- depends on: Implement one of the granted mac_readonly_diagnostics interfaces (currently schema-only); An authenticated local-agent diagnostics route; A typed freshness/sensitivity schema shared with relay and faculty-perception
