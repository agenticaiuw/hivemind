## Capabilities it proposed

### "“Do that, and tell me whether it really happened.”"
- **useful because:** Today the Mac executor can return success for synthesized clicks, typing, or key presses even when Accessibility is granted to the wrong binary and the event never reaches the screen. This gives the owner a truthful result rather than a confident lie: the Mac checks reachability and a post-action change, the browser bridge supplies tab evidence when the task is web-based, and the pendant speaks a concise success/no-op/retry report.
- **path:** pendant → mac-planner → mac-vision → browser-extension → relay-realtime → dashboard
- **model tier:** Use the cheap planner and deterministic checks for pre/post observation; invoke realtime only to phrase the spoken result or ask a follow-up. Use vision only when accessibility and semantic checks cannot verify the UI.
- **latency:** Under 500 ms for reachability/status checks; 1–3 s for app/document postconditions; up to 8 s for a vision fallback. Never wait silently: stream 'sent', 'verifying', and 'confirmed/no change' events.
- **cost:** Usually near-zero model cost (local observations and hashes); occasional vision fallback dominates, roughly one image inference per ambiguous action. Relay speech is the normal small TTS/STT cost only when the owner asks by voice.
- **security:** Postcondition evidence may contain window titles, URLs, or snippets from private tabs; keep raw screenshots local, send only redacted status and hashes to relay, and require the existing owner confirmation only where the current policy already requires it. This is observability, not a new gate.
- **missing:** A reliable Accessibility grant for the actual AI Pendant Agent binary (or a signed helper with matching bundle identity); A typed postcondition schema for shell, UI, and browser actions; A browser reconnect/janitor to clear or classify the current nine stale pending commands; A planner/relay event contract that carries evidence and distinguishes sent from confirmed

### "“Set this up and keep making sure it stays that way.”"
- **useful because:** The owner cannot currently ask the hive to establish a desktop or web outcome and then protect it over time. An action can finish, a laptop can sleep, an app can undo it, or a browser session can change, with no continuing assurance. This capability turns a one-shot request into a cross-surface invariant: establish the desired state, independently re-check it, and tell the owner only when it drifts or cannot be restored.
- **path:** pendant → relay-realtime → mac-planner → mac-vision → browser-extension → dashboard
- **model tier:** Use a cheaper background model for compiling the owner's natural-language request into a typed invariant and for scheduled checks. Use realtime only for the initial spoken interaction and drift notification. Use deterministic Mac/browser probes first; reserve vision or the expensive model for ambiguous state interpretation.
- **latency:** Initial establishment should respond within 5 seconds when the relevant surface is online. Routine checks should be silent and cheap, with a spoken alert within 30 seconds of detected drift. Recovery may run asynchronously while the owner is away.
- **cost:** Near-zero model cost for typed probes and hashes; background model cost is limited to invariant compilation and exceptional drift interpretation. API cost is dominated by rare vision checks and relay TTS alerts.
- **security:** Invariants could reveal private app names, URLs, files, or account state. Keep evidence local by default, send only a redacted status to the relay, encrypt persisted definitions, and require the existing confirmation policy before any recovery that could have external side effects. Never silently submit browser forms or send messages.
- **missing:** A durable invariant/monitor store with owner-defined cadence, quiet hours, expiry, and pause controls; A common postcondition vocabulary spanning shell, files, macOS apps, and authenticated browser tabs; A scheduler that survives Mac sleep/offline periods and asks the relay to resume checks when the Mac returns; A drift event and recovery protocol shared by the Mac agent, browser bridge, relay, pendant, and dashboard; Independent verification after recovery rather than trusting the action receipt alone


## Changes it proposed to its own stack

### `mac-harness` — Add a non-blocking action truth layer. Before dispatch, snapshot the relevant reachability state (Accessibility identity, secure-input, foreground app, browser session heartbeat). After dispatch, run an action-specific verifier: shell exit code and declared output predicate; file hash/size; app setting readback; UI accessibility-tree/text/window-state delta; browser URL/title/DOM fingerprint or command result. Store sentAt, verifiedAt, verification method, observed delta, and confidence in the existing receipt, with explicit states sent, confirmed, no-op, indeterminate, or failed. If no-op/indeterminate, automatically try one safe alternate implementation (for example AppleScript/API instead of synthetic typing) and report both attempts; never claim success solely from dispatch completion. Emit compact progress to /pipeline/events and expose aggregate no-op rates in /ops/snapshot for dashboard and relay.
- **owner gets:** The owner stops being told that a UI action succeeded when the Mac's current Accessibility identity means it did nothing. They get a fast, honest answer and useful recovery instead of silently losing work.
- effort: Medium: verifier registry for existing action types, one receipt schema extension, local observation adapters, and dashboard/relay rendering. Start with UI typing/clicks, shell, file writes, and browser navigation.  ·  risk: A legitimate action may have no visible delta (e.g. clicking an already-selected control), or the verifier may inspect stale UI. Mark those indeterminate rather than false, retain raw evidence locally, and allow the existing undo/job retry paths. Alternate execution must be bounded to avoid duplicate side effects.
- cost: Negligible for local checks and hashes; occasional accessibility-tree or browser extraction work is local. Vision fallback is the only material API cost and should be rare.  ·  latency: Adds roughly 50–300 ms for local pre/post checks; verification can stream asynchronously so the owner hears progress immediately. Vision fallback may add several seconds.
- security: Receipts gain potentially sensitive window titles, URLs, and snippets. Keep raw evidence local, redact relay payloads, and apply TTL deletion; no new permission gate is introduced.
- depends on: Fix Accessibility entitlement/grant so the running AI Pendant Agent identity can actually post events, or expose a truthful 'cannot verify UI' state; Extend actionReceipts.js and GET /jobs/:jobId/receipts with verification fields; Wire /observe and /browser/status heartbeat snapshots into executor pre/post hooks; Define compact /pipeline/events and relay status payloads for sent-vs-confirmed; Browser reconnect/janitor should classify the existing stale pending command queue

### `integration` — Build a permission-drift and dependency repair loop. On agent startup and before UI/browser work, compare the running bundle identity, Accessibility/Input Monitoring/Screen Recording state, browser-extension heartbeat, relay reachability, and configured paths. Persist a versioned diagnostic incident (for example ACCESSIBILITY_IDENTITY_MISMATCH or BROWSER_QUEUE_STALE) rather than burying it in a generic failure. Generate one Mac-native repair action/instruction with the exact System Settings pane and affected binary, let the pendant announce the short reason, and automatically re-probe after the owner fixes it. Keep the incident attached to subsequent jobs so the planner stops retrying impossible actions.
- **owner gets:** The owner gets one understandable explanation—'the agent is not allowed to control the screen' or 'the browser bridge has nine stale commands'—and a guided path to restore capability, instead of repeated no-op actions and 45-second timeouts.
- effort: Medium: normalize existing /ops/status and /observe facts into incident codes, add repair recipes and post-fix probes, and surface active incidents in dashboard, relay status, and job receipts.  ·  risk: A permission may legitimately be absent or a stale queue may contain useful work. Diagnose and label only; do not revoke, delete, or gate anything automatically. Queue cleanup remains an explicit repair action and all incidents retain evidence.
- cost: No model cost for deterministic checks; tiny relay/database storage for incident records. No additional hardware.  ·  latency: A few hundred milliseconds at startup or before a relevant action; avoids the current 45-second browser timeout and repeated retries.
- security: System Settings instructions and bundle IDs are not sensitive; do not transmit private page contents. Incident payloads should exclude command strings and URLs unless already present in the job's local receipt.
- depends on: GET /ops/status; GET /observe; GET /browser/status; GET /jobs/:jobId; POST /pipeline/events; A small local incident store and repair-recipe registry; Browser reconnect/janitor for stale pending commands

### `routines` — Add an event-sourced invariant engine separate from one-shot jobs and page watches. Each invariant stores a typed desired state, evidence predicate, check cadence, expiry, quiet hours, last independently verified value, and a recovery recipe. The engine consumes Mac/browser/relay presence events, schedules checks on the cheapest available surface, records drift and recovery attempts, and requires two consecutive positive observations before declaring a repaired state. When the Mac is asleep or permissions are invalid, it records 'unverified' rather than treating absence as drift, then resumes from the relay when presence returns.
- **owner gets:** They can say 'keep this true' for things such as a file backup being current, a meeting app being configured, a focus mode remaining enabled, or a private web setting retaining a value—and receive a useful drift alert instead of discovering later that a one-time action silently stopped holding.
- effort: Medium-to-large: new durable state machine and scheduler, typed probes/recovery recipes for Mac and browser, relay wake/resume events, and dashboard controls for pause, expiry, evidence, and history.  ·  risk: A recovery recipe could repeatedly undo the owner's intentional change or create an action loop. Bound retries, require an explicit owner-selected recovery policy, detect conflicting manual changes, and expire invariants by default. Offline and permission failures must remain unverified, never falsely healthy or broken.
- cost: Small persistent storage and background polling cost; deterministic checks are inexpensive. Background model use is limited to compiling new invariants or resolving ambiguous drift.  ·  latency: No impact on ordinary actions. Checks run asynchronously; alerts are near-real-time after a presence event, while recovery can take seconds to minutes.
- security: Invariant definitions and evidence may expose private files, app state, or logged-in pages. Store raw evidence locally, redact relay notifications, encrypt definitions, and never include page contents in routine heartbeat payloads.
- depends on: A durable invariant store and scheduler independent of existing /routines; Typed cross-surface postcondition/probe adapters; Relay presence and wake/resume event delivery; A recovery policy model with bounded retries and explicit expiry; Dashboard and pendant controls for pause, inspect evidence, and abandon
