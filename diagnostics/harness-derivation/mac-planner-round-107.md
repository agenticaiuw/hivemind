## Capabilities it proposed

### "If something I asked you to do in a logged-in browser fails because the bridge is offline, tell me what failed, keep the safe read-only part, and resume it automatically when the browser reconnects—without replaying a stale form submission or click."
- **useful because:** The live Mac agent has seven pending browser commands while the bridge is offline, and prior navigations have timed out. Today the owner gets opaque failures and cannot know whether retrying could duplicate a mutation. This makes the wearable, relay, Mac, and authenticated browser behave as one recoverable system: the pendant can report the interruption, the relay can retain the work, the Mac can reattach, and the browser can revalidate before continuing.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use the cheap background model for queue classification, URL/title revalidation, and compact failure summaries; reserve realtime only for the spoken interruption/recovery sentence. No model is needed for idempotency, tab affinity, or mutation quarantine.
- **latency:** Detect disconnect within one heartbeat (about 5–10 seconds), speak a short status on the next available relay turn, and resume read-only extraction within 10 seconds of a healthy browser heartbeat. Never auto-resume a write step; stage it for the owner.
- **cost:** Usually <$0.01 per interrupted job; most work is deterministic state and browser polling. Realtime/TTS cost occurs only for the brief spoken alert, and background summarization dominates when a long page must be re-explained.
- **security:** Authenticated page text must remain local to the Mac/relay policy and be redacted before any spoken alert. Persist tab/session IDs, URL, title, step hashes, and before/after evidence—not passwords or full page bodies. A reconnect must prove the same tab/session and a fresh URL/title/DOM fingerprint; otherwise quarantine and ask. Never replay submit/send/delete/purchase or arbitrary click steps automatically, even though the owner permits broad Mac access.
- **missing:** A durable per-step browser work capsule with read/write classification, idempotency key, precondition fingerprint, retry count, and quarantine state; A browser heartbeat/reconnect handshake that returns tab identity and a fresh page fingerprint before releasing queued commands; Relay-to-pendant delivery of a compact interruption and resume receipt, with a deduplicated alert ID; A deterministic rule that permits automatic retries only for reads/navigation and converts mutations into a reviewable plan with evidence; A dashboard view for quarantined steps and an explicit resume/discard action

### "Keep a draft I asked you to prepare synchronized across my Mac editor and logged-in browser: if I edit it while you work, detect the conflict, preserve both versions, and tell me the smallest decision needed so I can continue without losing either one."
- **useful because:** Today a server plan, a Mac file, and a browser form are separate copies. If the owner edits one while the agent is preparing another, the system can overwrite work, submit stale text, or force them to reconstruct the difference. This would give them a genuinely collaborative handoff: the pendant identifies the conflict, the relay retains the draft state, the Mac computes a local diff, and the browser supplies the current authenticated target.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use deterministic hashes, file/editor version tracking, and structured field diffs first. Use a cheaper background model only to summarize non-sensitive conflicts; use realtime only to speak the one decision required. Never ask the expensive realtime model to regenerate an entire draft merely because versions diverged.
- **latency:** Capture a version before each agent write, detect divergence within 2 seconds of a local edit or browser result, and present a compact conflict card within 5 seconds. Applying the owner's selected resolution should complete in under 3 seconds.
- **cost:** Usually below $0.01 per conflict; local diffing and browser metadata dominate. Model spend is limited to ambiguous prose conflict summaries, and spoken output is one short TTS response.
- **security:** Drafts may contain private email, work, or account data. Keep full versions on the Mac or the authenticated browser session, send only redacted field names and hashes to the relay by default, and require explicit selection before any version is copied into a form or sent. Preserve the owner's original and never silently overwrite or submit.
- **missing:** A cross-surface draft identity and version manifest binding a local file/editor buffer to a browser form or message; Mac file/editor change notifications and a bounded three-way diff service that can work without Accessibility for supported editors; Browser extraction of current field values plus stable field identifiers, not just page text; Relay storage for encrypted, expiring draft versions and conflict events; A pendant/dashboard conflict card with choices such as keep mine, keep agent, merge this field, or discard draft


## Changes it proposed to its own stack

### `browser-harness` — Implement a reconnect-safe browser work capsule and release protocol between the existing command queue and job receipts. At enqueue, persist a capsule per step containing request/idempotency key, session+tab affinity, read/write class, URL/title/DOM fingerprint, and a redacted evidence pointer. On browser heartbeat, require a fresh tab identity and fingerprint; automatically release only idempotent reads/navigation, mark all mutations quarantined, and emit one deduplicated pipeline event plus a pendant-sized receipt. Expired or mismatched capsules are discarded with an explicit reason instead of replayed.
- **owner gets:** When the browser bridge goes offline, the owner gets a truthful one-sentence status and later receives the safe result without duplicated clicks or submissions. A stale logged-in tab can never silently consume an old command after reconnect.
- effort: Medium: queue schema and state machine, heartbeat response fields, browser extension handshake, receipt/event integration, and a small dashboard queue. Add crash/restart tests for offline, timeout, reconnect-to-different-tab, and mutation quarantine.  ·  risk: A false fingerprint mismatch may leave safe work waiting; recover with a visible Retry after revalidation. A bug in classification could release a mutation, so default unknown actions to quarantine and log every release decision. Do not delete current pending commands until their capsules are migrated.
- cost: Negligible storage and polling overhead; one short background classification per multi-step job at most. No additional realtime calls except optional spoken alert/TTS.  ·  latency: Adds one heartbeat/fingerprint round trip before resuming, typically under 1–2 seconds; prevents 45-second browser timeout loops by failing fast when offline.
- security: Improves security by binding commands to a tab/session and retaining redacted evidence only. Authenticated content remains on the Mac/approved relay path; no credentials are persisted. Mutations remain owner-reviewed.
- depends on: chg-14accc01 request IDs/tab affinity/typed results must be completed as the queue substrate; browser-extension reconnect and Safari handshake; a durable job runner (chg-16bc5dee); pipeline event/audio delivery for the pendant receipt

### `mac-harness` — Add a read-only Safari fallback adapter for browser status and page capture when the extension is offline: use the already-granted Safari automation channel to enumerate windows/tabs, read URL/title and selected visible text, and return a typed source capsule. Mark the result as safari-automation (not extension) with lower confidence, never expose cookies, and refuse all form filling, clicks, navigation, or submissions through this fallback. When the extension reconnects, reconcile by tab URL/title before merging evidence.
- **owner gets:** A disconnected browser extension would no longer turn every logged-in question into a dead end. The Mac could still answer a read-only question or preserve a page snapshot, while the stronger browser session resumes later for actions.
- effort: Medium: implement a narrow AppleScript adapter, typed redaction/size limits, source labeling, and reconciliation tests against extension tab IDs. Keep it separate from FULL_CONTROL computer actions.  ·  risk: Safari may return incomplete or stale text, or a dialog may block automation. Surface source and timestamp, fail closed on ambiguous tab identity, and never use this path for mutations. If Safari automation is revoked, report unavailable rather than falling back to UI scraping.
- cost: Near-zero API cost; local AppleScript only. Small CPU/token cost for text extraction and redaction.  ·  latency: Fast local read (roughly 1–3 seconds), avoiding a 45-second extension timeout; extension reconnect still adds its own handshake.
- security: Read-only authenticated content stays on the Mac; no credentials or cookies leave Safari. Because this bypasses the extension, audit every read with tab URL, timestamp, and redacted excerpt hash.
- depends on: Safari automation grant already present in /ops/status; reconnect-safe browser work capsule proposed above; a typed page-capture route or extension-compatible source-capsule schema

### `integration` — Create a three-way draft synchronization protocol spanning Mac and browser rather than treating each action result as a replacement string. Assign every draft a stable draftId and immutable base revision; record agent revision and owner revision separately, with per-field hashes for browser forms and byte/line ranges for local files. Before any write, compare both descendants to the base, emit a conflict event when they diverge, and expose a resolution token that applies only the selected fields. Expire drafts and securely erase versions after a short retention window.
- **owner gets:** The owner can edit while the agent works without losing their changes or having stale text silently enter a private form. They get a precise choice instead of a vague failure or a full restart.
- effort: Medium-high: local file/editor watchers for supported apps, browser field identity extraction, encrypted short-lived version storage, three-way merge tests, and a small conflict UI/pendant protocol.  ·  risk: Some editors or dynamic forms will not expose stable identifiers; fall back to whole-document conflict and preserve both copies. A merge bug could alter wording, so unresolved prose conflicts must remain untouched and require explicit field-level choice.
- cost: Low storage and compute; conflict summaries may incur a small background-model call. No realtime call unless the owner asks for a spoken explanation.  ·  latency: Normal writes add a local hash check under 100 ms; conflict detection should be seconds, with no browser submission until resolution.
- security: Improves safety by preventing stale writes. Full drafts stay on the Mac/browser path with encryption and TTL; relay receives hashes, metadata, and redacted summaries unless the owner explicitly requests content sharing.
- depends on: browser bridge returning stable tab/session and form-field identifiers; Mac editor/file change observation without requiring Accessibility for supported applications; durable encrypted draft/version store; pendant and dashboard resolution UI
