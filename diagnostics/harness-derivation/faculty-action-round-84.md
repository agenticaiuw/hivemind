## Capabilities it proposed

### "“Handle this end to end, and keep me in control.” The system should carry out a reversible multi-step task across my logged-in browser and Mac, pause only at irreversible steps, and let me approve, cancel, or resume it from the pendant."
- **useful because:** Today the mind can decide a goal but execution is fragmented: browser commands can time out, Mac jobs can continue without the pendant knowing whether they are safe to resume, and a spoken approval is not a durable transaction boundary. This gives the owner one honest action state: what was planned, what precondition was checked, what changed, what is waiting for approval, and how to undo it. It is genuinely cross-node: the relay persists the job, the browser supplies private web state, the Mac performs local actions, and the pendant provides a physical cancel/approve affordance.
- **path:** relay-realtime → faculty-judgement → faculty-action → browser-extension → mac-planner → mac-vision → mac-terminal
- **model tier:** Use the realtime model only to interpret the owner's short command and announce state; use a cheaper background model for plan decomposition, precondition/proof reconciliation, and retries. Deterministic code should enforce effect classes, idempotency, expiry, and approval gates.
- **latency:** Acknowledge in under 1 second; produce a plan in 2–5 seconds; execute reversible steps asynchronously with progress updates. Never wait indefinitely on an offline browser: mark blocked after a bounded timeout and offer resume rather than retrying blindly.
- **cost:** Roughly one realtime turn plus 1–3 cheap background turns per task; dominant cost is private-page extraction and any vision loop, not the state machine. Persist compact step records and hashes rather than resending full context.
- **security:** Private URLs, page text, and local file paths leave their originating surface only as narrowly scoped evidence. Encrypt persisted evidence and expire it. Sending mail, deleting files, purchases, form submission, and other irreversible effects require explicit approval tied to the exact before/after summary. A physical pendant cancel must revoke the lease immediately; stale approvals and duplicate retries must be rejected.
- **missing:** A durable cross-surface transaction/step schema with idempotency keys, preconditions, evidence hashes, leases, expiry, and resumable checkpoints; A relay-to-pendant push channel for progress plus a local button/LED state machine for cancel, approve, and blocked/offline states; A single executor that can route each step to browser or Mac, verify typed results, and reconcile receipts before advancing; Owner-granted browser bridge polling and a connected pendant are required for the full experience; current probes show home-chrome offline and no pendant in the device table


## Changes it proposed to its own stack

### `integration` — Implement a relay-owned Action Transaction Coordinator between the existing /execute, Mac jobs, and browser command queue. It should compile a goal into typed steps (surface, effect class, idempotency key, preconditions, approval requirement, lease expiry), dispatch one step at a time, correlate browser result or Mac receipt by the same step ID, and advance only after proof matches the precondition/postcondition. Persist a compact event log and expose GET /action-transactions/:id, POST /action-transactions/:id/approve, POST /action-transactions/:id/cancel, POST /action-transactions/:id/resume. On timeout or disconnect, freeze the lease and resume from the last proven checkpoint instead of replaying writes.
- **owner gets:** The owner gets reliable “it was done once” behavior instead of duplicated browser submissions, ambiguous Mac jobs, or a false completion after a timeout. They can leave home, reconnect later, and hear exactly which step is waiting, what evidence proves prior steps, and what can still be undone.
- effort: Medium-high: relay schema/state machine, adapters for existing Mac receipts and browser typed results, and tests for duplicate delivery, timeout, reconnect, approval expiry, and partial undo. No new model is required for enforcement.  ·  risk: A bad proof adapter could advance without real completion, or an overly strict one could strand work. Default closed on missing/contradictory evidence; retain receipts and offer manual resume. Never auto-retry effect=write unless the step declares an idempotency key and the target confirms it.
- cost: Small D1 write/read overhead per step and one cheap background planning call; no material realtime cost. Evidence should be hashes/snippets with short retention, not full pages by default.  ·  latency: Adds tens to hundreds of milliseconds per step for persistence and verification; avoids the much larger cost of blind 45-second browser retries.
- security: Improves security by making approval scoped to an exact step and expiring it with the lease. Private evidence remains surface-local where possible; transaction IDs and hashes cross the relay, not secrets.
- depends on: Typed browser results and Mac action receipts must include stable step/action IDs and idempotency keys; An authenticated relay-to-pendant event path and a physical cancel/approval affordance; Owner enabling the browser bridge when private browser work is needed

### `hardware` — Add a tiny bistable 3-color status indicator and a vibration motor to the wearable, driven by a safety-isolated local action-state controller. The relay can publish only a compact signed state token (idle, working, waiting-for-owner, blocked, completed, failed); the pendant renders that state with color/pattern and a short vibration code, retaining the last state through LTE loss. The controller must fail closed: loss of link or an invalid/expired token can never authorize an action, and the existing user button remains a cancel/acknowledge input rather than an execution trigger.
- **owner gets:** The owner can tell at a glance or by touch whether the system is still working, waiting for them, or stopped—even in a noisy room, while driving, or when speech cannot be heard. They stop wondering whether a request was lost, and can safely cancel a live operation without opening the Mac dashboard.
- effort: Moderate hardware revision and firmware protocol: add a low-power RGB LED, coin vibration motor, driver transistor, signed state-token parser, and persistence of one compact state record. Validate visibility, haptic distinguishability, and behavior across LTE reconnects before production enclosure work.  ·  risk: Extra power draw and accidental button interpretation could confuse the owner. Use distinct, documented patterns; require a deliberate long press for cancel/acknowledge; rate-limit vibration; and preserve the current LED-only fallback if the motor or token parser fails. This is an addition to the prototype, not a claim that the current DK can support it.
- cost: Approximately $2–6 in components and under 20 mA peak while indicating; negligible API cost because only a signed state token crosses the relay. Battery impact is dominated by vibration and should be duty-cycled.  ·  latency: State changes reach the pendant on the next relay poll/push, typically sub-second online and eventually after reconnect; local rendering is immediate.
- security: The indicator is intentionally non-authorizing. Signed, expiring state tokens prevent stale server state from being mistaken for approval, and no private page content is displayed or stored on the wearable.
- depends on: A relay action-state protocol that emits signed, expiring compact tokens; A pendant firmware event path that persists the last safe state and handles long-press cancel locally; A connected production pendant rather than the current unconnected development-kit situation
