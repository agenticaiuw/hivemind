## Capabilities it proposed

### "“When I approve a prepared change on the pendant, carry it out even if the connection briefly drops—but never twice—and tell me exactly what happened.”"
- **useful because:** Today judgement can prepare an action and the Mac/browser can execute one, but a real-world approval is split across unreliable links and there is no end-to-end guarantee that the approval, execution, and receipt refer to the same one-time change. This gives the owner a safe commit protocol: the pendant shows the final before/after summary, the owner's button press or spoken approval creates a short-lived one-time authorization, the relay holds it through a reconnect, the Mac/browser performs the idempotent step, and the pendant gets a concise success/failure/expired result. It is useful specifically because no single surface can both authenticate the human's physical approval, reach private browser state, survive disconnects, and report a durable receipt.
- **path:** faculty-judgement creates a normalized action plan and irreversible-step boundary → relay-realtime assigns a one-time nonce, expiry, and durable delivery state → pendant displays a compact diff and records a local approval event (or cancellation) → mac-planner dispatches the approved plan through mac_run_actions or the job queue → browser-extension executes authenticated tab steps and returns typed before/after evidence → relay records the receipt and pushes the outcome back to the pendant; faculty-action can report or undo
- **model tier:** Use a cheap background/deterministic executor for queue delivery, idempotency and receipt validation; use the realtime tier only for the short approval conversation and spoken result. No expensive model call is needed to replay or verify a known plan.
- **latency:** Preview should reach the pendant in under 1 s; approval acknowledgement under 300 ms when online. Reconnect delivery may take seconds. The authorization should expire after 60 s (configurable), and every retry must be safe because the same operation key is reused.
- **cost:** About $0.001–$0.01 per invocation, dominated by the initial judgement/preview model call; retries, relay storage, Mac execution, and browser bridge traffic are negligible. A receipt/undo path avoids paying for a second model call in the common case.
- **security:** Never send credentials or page contents to the pendant; show only a redacted diff and origin/tab identity. Bind the nonce to plan hash, account/session, exact irreversible step, device identity, and expiry; reject replay, altered plans, stale tabs, and duplicate operation keys. Require a fresh physical button hold for irreversible actions, with spoken approval as non-authorizing. Persist an audit receipt and provide undo where the operation supports it. Data leaves the Mac only as the minimum redacted preview and result.
- **missing:** A durable one-time approval envelope shared by pendant, relay, Mac, and browser bridge; Offline pendant approval spool with replay protection and a visible pending/expired state; An executor-side idempotency/compare-before-commit check for browser and Mac actions; A unified receipt schema linking plan hash, approval nonce, tab/session, before/after evidence, and undo token; The owner must still grant Accessibility/Screen Recording if a step requires GUI-only control; AppleScript and existing browser routes remain usable without it

### "“Carry this request through all the dependent systems: if the private site accepts the change, update my Mac calendar and remind me; if it fails, leave everything untouched and tell me exactly where it stopped.”"
- **useful because:** The owner cannot currently ask for a single dependable real-world outcome spanning a logged-in website and local Mac state. A browser action may succeed while the calendar step is skipped, or a retry may create duplicate reminders. This capability is a compensating transaction (a saga), not merely a queued click: it commits each step only after verifying the prior step, uses idempotency keys, and performs safe compensation for already-completed reversible steps. The pendant gives one concise outcome instead of forcing the owner to reconcile several surfaces.
- **path:** faculty-judgement turns the request into a dependency graph with commit points, allowed compensations, and a final success invariant → relay-realtime persists the graph and resumes it after disconnects or Mac sleep → browser-extension reads the authenticated page, performs the approved reversible/irreversible step, and returns authoritative evidence → mac-planner uses Calendar/reminder APIs or AppleScript to create the local follow-up only after the browser commit is verified → faculty-perception independently checks each resulting state and detects partial completion → pendant receives step-by-step progress and a final success, partial-success, or safely-rolled-back result
- **model tier:** Use a cheaper background model for graph compilation and recovery classification; deterministic adapters perform known browser and Calendar operations. Reserve realtime for approval and concise progress, not orchestration.
- **latency:** Show the first plan on the pendant in under 2 seconds. Each dependent step may take seconds to minutes because sites can be eventually consistent; reconnect resumption must not restart a committed step. A stalled graph should become paused, not silently fail, after a bounded timeout.
- **cost:** Approximately $0.002–$0.03 per request, mostly one planning/recovery call; deterministic execution and verification dominate latency rather than API cost. Compensation avoids costly duplicate actions and support effort.
- **security:** Require approval for the exact graph and every irreversible node; bind all nodes to the original plan hash and operation id. Keep private page contents on the Mac/bridge; send only redacted values and evidence hashes to relay/pendant. Never compensate by sending a message or canceling a purchase automatically. If compensation is unsafe, stop in partial-success state and ask the owner.
- **missing:** A durable dependency-graph job format with node state, commit markers, idempotency keys, and compensation policy; Adapters that can verify authenticated browser outcomes and local Calendar/reminder outcomes without GUI permissions; A recovery worker that resumes paused graphs after reconnect and never replays committed nodes; A partial-success UI and explicit owner choices for unsafe compensation; A shared redacted evidence/receipt format across browser and Mac


## Changes it proposed to its own stack

### `integration` — Add a postcondition-verification stage to every irreversible Mac/browser job. The planner must emit a typed expected invariant (for example, appointment status=confirmed, draft remains unsent, reminder exists with exact time). After execution, a separate perception pass re-reads the authoritative surface—browser tab/session for web state, AppleScript/read-only route for Mac state—and stores a signed verification record alongside the existing receipt. If the invariant is false, ambiguous, or the tab/session changed, mark the job “unverified” rather than successful, stop retries, push a pendant alert with the observed value, and offer an explicit recovery/undo job. Use the same operation key for retries and require compare-before-commit when possible.
- **owner gets:** The owner stops hearing “done” when a click timed out, a site rejected a field, or the wrong tab was active. They get a truthful result grounded in the resulting state, plus the exact observed discrepancy and a recovery choice. This works without Accessibility for AppleScript/browser-readable surfaces and degrades honestly for GUI-only actions.
- effort: Medium: define invariant and verification schemas, add read-only adapters for existing Mac and browser surfaces, extend receipt storage/UI, and add pendant result states. One or two weeks for a narrow set of actions; broader semantic verification is incremental.  ·  risk: A site may update asynchronously or expose stale cached text, causing a false unverified result; use bounded polling with timestamps and show evidence. Verification must never itself mutate state. If the verifier crashes, preserve the receipt as executed-but-unverified and allow manual inspection; do not automatically retry irreversible work.
- cost: Roughly one cheap read/verification model call only for semantic invariants ($0.001–$0.02), otherwise deterministic selectors/AppleScript. Additional browser/Mac round trips add modest bandwidth and relay storage.  ·  latency: Adds approximately 0.5–5 s after execution depending on eventual consistency; pendant can say “checking” immediately. No added latency before approval or before the action starts.
- security: Store hashes and minimal redacted evidence rather than full page contents; bind verification to URL/tab/session and plan hash. Read-only verification can inspect private data on the Mac but must not export secrets. Access failures become unverified, never success.
- depends on: A typed action plan with expected postconditions; Existing job receipts and undo routes; Browser session/tab affinity and typed browser results; Mac read-only AppleScript or equivalent route coverage; A pending pendant result state; GUI-only verification remains blocked until the owner grants Accessibility/Screen Recording

### `integration` — Introduce a durable cross-surface saga coordinator rather than treating each Mac/browser action as an independent job. Persist a DAG of typed nodes with dependency barriers, commit markers, idempotency keys, expected postconditions, and explicit compensation policies. On reconnect, resume only the first uncommitted node; after each node, run a read-only verifier before releasing dependents. Expose partial-success and paused-for-owner states through the existing job and receipt APIs, and make unsafe compensation impossible to auto-run.
- **owner gets:** They can ask for an outcome that crosses a private website and their Mac without manually checking whether half the work happened. A site rejection will not leave a misleading calendar reminder, and a dropped connection will not duplicate a booking or reminder. When full rollback is impossible, the owner gets an honest partial result and a precise next choice.
- effort: High integration effort: schema and durable worker first, then browser and Calendar adapters, verifier contracts, recovery tests, and pendant progress states. Start with browser-booking-to-Calendar/reminder as a narrow vertical slice.  ·  risk: Some external actions cannot be undone; the coordinator must stop before those nodes unless separately approved and must surface partial completion. Eventual consistency can make a successful node look absent, so use bounded verification and never retry an ambiguous irreversible node. Recover by leaving the graph paused with its evidence and operation key.
- cost: Small durable storage and queue cost; one cheap planning or recovery call per graph ($0.002–$0.03), with deterministic steps otherwise. Verification adds browser/Mac requests but prevents duplicate side effects.  ·  latency: Adds verification latency between dependent steps (typically 1–5 seconds, longer for eventually consistent sites); disconnect recovery becomes reliable rather than immediate. The pendant can stream node status so the owner is not left guessing.
- security: Keep credentials and full private content on the Mac/browser surfaces. Relay stores only encrypted/redacted plan values, hashes, state transitions, and receipts. Bind every node to the owner's approval, session/tab identity, and idempotency key; require fresh approval for any compensation or newly discovered irreversible node.
- depends on: A versioned plan/receipt schema that supports dependency graphs and postconditions; Durable relay job execution across Mac sleep and reconnect; Browser command queue with stable tab/session affinity; Read-only Calendar/reminder verification adapters; Pendant progress and partial-success states; Owner Accessibility/Screen Recording only where no AppleScript or browser-readable adapter exists
