# Harness derivation — mac-planner — round 130

Model: `gpt-5.6-luna`  ·  probes against `http://localhost:8000`

## What it established

- **audio transport readiness** — Relay pipeline currently reports TTS as 24 kHz mono PCM and uploads pcmBytes to the relay, while pendant hardware specification requires Opus decode at 24 kHz/60 ms frames. The end-to-end 24 kHz path is therefore not yet proven as the device's native packet format.
  - evidence: GET /ops/status reports textToSpeech='macOS say (24 kHz PCM)'; GET /pipeline run job_309f5663... has TTS done format=s16le sampleRate=24000 and relay_result meta pcmBytes=75734; pendant spec reports playback='Opus decode on-device at 24 kHz / 60 ms frames'.

## Capabilities it proposed

### "“Play my queued briefings on the pendant, and keep going from where I left off if the connection drops.”"
- **useful because:** The current pipeline can render 24 kHz mono PCM and mark it waiting, but the wearable's actual decoder is Opus at 24 kHz in 60 ms frames. An interrupted download or format mismatch can strand an otherwise completed briefing. This would make long briefings and scheduled audio dependable: the owner hears each item once, can pause/resume, and does not need to repeat the request after LTE or bridge loss.
- **path:** relay-realtime → mac-planner → unified → faculty-perception → faculty-action
- **model tier:** Background/scheduled work uses a cheaper model only to rank and label queued audio; no expensive realtime reasoning is needed during playback. Realtime is used only when the owner interrupts or asks a follow-up. The pendant firmware handles packet timing locally.
- **latency:** Start playback within 2 seconds when a complete object is available; resume within 1 second after link recovery. Upload/render can remain asynchronous. A 60 ms jitter buffer and at least 3 acknowledged frames should mask normal LTE variability.
- **cost:** Small per-briefing relay/storage cost; roughly one TTS render plus Opus transcode, dominated by audio duration and R2 egress. No extra LLM call for ordinary playback. Receipts and resume metadata are tiny D1 records.
- **security:** Audio may contain private calendar/mail content. Bind each manifest and frame request to the owner's authenticated device/session, use short-lived signed URLs, encrypt in transit, and delete audio plus manifests according to the existing retention policy. Never synthesize or enqueue a new spoken response from a stale or unverified job. Playback is safe without confirmation; generating a briefing that reads private sources still follows their source permissions.
- **missing:** A canonical Opus 24 kHz/60 ms object format and manifest (codec, sequence count, duration, hash, loudness metadata) instead of accepting ambiguous PCM at relay_result; Resumable range/frame fetch with per-frame acknowledgements, idempotency keys, and a durable pendant playback cursor that survives reboot; A relay-side transcode/validation step that rejects mismatched sample rate/codec before advertising 'waiting for the pendant'; A Mac/relay fallback policy: if the pendant is offline, retain the item and expose queued/started/paused/completed state rather than replaying it; Firmware implementation within the nRF9160 CPU/RAM budget, including jitter buffer, cursor persistence, and an explicit cancel/skip gesture

### "“When I say ‘put this in front of me,’ use the pendant to hand the conversation to my Mac: open the relevant document or logged-in page, place the exact cited passage and next action in a review note, and tell me when the handoff is ready.”"
- **useful because:** Today the pendant can converse and the Mac can act, but the owner must manually explain the handoff, find the source again, and reconstruct what was decided. This creates a physical-to-desktop continuation: a short spoken request becomes a bounded, source-linked workspace waiting on the Mac without losing the conversational context or silently submitting anything.
- **path:** relay-realtime → faculty-perception → faculty-judgement → mac-planner → browser-extension → unified → faculty-action
- **model tier:** Use the realtime tier only to recognize the handoff intent and capture the owner's short clarification. Use a cheaper background model to resolve citations, select the target app/page, and format the review note. The Mac executor performs deterministic opening and note-writing actions.
- **latency:** Acknowledge on the pendant within 500 ms, create a handoff capsule within 3 seconds, and stage the Mac workspace within 8 seconds when the required app/session is available. If a private browser session is unavailable, leave a clearly marked pending capsule rather than guessing.
- **cost:** One small background-model call per handoff, plus negligible relay/D1 storage and normal Mac/browser operations. No vision call is needed when an existing URL, file path, or cited source locator is available; vision is an optional fallback only.
- **security:** The capsule may contain private mail, calendar, or logged-in webpage content. Encrypt it in transit, bind it to the paired pendant and Mac session, redact secrets by default, and retain it briefly. Opening a page and creating a note are reversible; sending, deleting, purchasing, or submitting anything must remain outside the handoff and require the owner's existing confirmation policy. Show source URL/path, timestamp, and quoted hash in the note so stale content is visible.
- **missing:** A cross-surface handoff capsule schema carrying conversation ID, source citations, quoted text hash, target surface, requested next action, freshness deadline, and sensitivity; A relay-to-Mac delivery/acknowledgement channel with idempotency and expiry, distinct from ordinary action jobs; A provenance-aware Mac staging operation that can open a file/page and create a review note without treating the note as an instruction to submit; Browser-session reattachment and freshness verification before placing authenticated content in the capsule; Pendant feedback states for accepted, waiting-for-Mac, ready, stale, and failed handoffs

### "“When I walk away from my Mac, pause anything private and put my browser work into a safe state; when I come back wearing the pendant, restore only what I was actively using.”"
- **useful because:** The pendant is continuously with the owner and can provide a stronger presence signal than a Mac timer. This would prevent private mail, account pages, or spoken audio from remaining exposed during an unexpected interruption, while preserving the exact working state instead of forcing a full restart. It is a coordinated physical-presence feature that neither the pendant nor Mac can safely provide alone.
- **path:** relay-realtime → mac-planner → browser-extension → faculty-perception → faculty-action → unified
- **model tier:** No LLM is needed for presence transitions. Use deterministic firmware/relay state machines; a cheap background model may classify which open work is resumable after return. Realtime is reserved for an explicit spoken override.
- **latency:** Pause or mute within 2 seconds of confirmed departure and secure browser state within 5 seconds. Resume only after a stable return signal for 3–5 seconds, avoiding flapping at the edge of radio range.
- **cost:** Negligible model cost; small relay state and event traffic. Hardware cost depends on presence signal: approximately $2–5 for a BLE-capable companion/proximity design if the current radio cannot provide sufficiently reliable proximity, with modest battery impact.
- **security:** A proximity token must not become an unlock credential by itself. Use encrypted rotating challenge-response, require the already-paired pendant and Mac identity, and let the owner choose whether return restores tabs, unmutes audio, or only displays a summary. Never auto-submit or send anything. Departure should redact or lock sensitive content, not delete it.
- **missing:** A signed, debounced pendant-presence signal with explicit departed/returned confidence and replay protection; Mac privacy actions that can mute pendant playback, lock or blur selected windows, and snapshot browser session state without destructive mutation; Browser extension support for freezing authenticated tabs and restoring only the owner-approved active set; A durable cross-surface state machine with crash recovery and an owner-visible audit trail; A first-run policy UI defining which apps/pages/audio may pause, hide, or restore


## Changes it proposed to its own stack

### `firmware` — Add a resumable, manifest-driven playback protocol for generated speech. The relay publishes an authenticated manifest containing Opus 24 kHz/60 ms frame count, SHA-256, duration, and expiry; the nRF9160 fetches frames in small windows, decodes into a bounded jitter buffer, persists only the next frame cursor and manifest ID, and ACKs the highest contiguous frame. On reconnect it resumes from that cursor, validates the final hash, and emits explicit started/paused/completed/corrupt/expired events. Keep microSD as the existing failure buffer only, not routine audio storage.
- **owner gets:** A dropped bridge or LTE connection no longer forces the owner to restart a briefing or wonder whether it played. Scheduled audio becomes trustworthy while preserving the owner's rule that the pendant should not routinely fill its SD card with recordings.
- effort: Medium-high: relay manifest/range endpoints and transcode validation, firmware Opus frame windowing/cursor persistence/events, and Mac dashboard receipt display. Test modem loss, reboot, duplicate frames, expired URLs, and PCM/Opus mismatch.  ·  risk: A corrupt cursor or interrupted SD write could skip or repeat a frame; recover by replaying the last acknowledged frame and treating the manifest as idempotent. Decoder timing or RAM pressure could cause underruns; use a 3–5-frame buffer, measure heap, and fall back to whole-object download when the manifest is unsupported.
- cost: No additional LLM cost. Minor D1/R2 metadata and egress overhead; bandwidth is approximately the encoded audio size. Firmware uses a few KB of RAM for frame metadata/buffer; playback decode is about 25.4 ms per 60 ms frame on the measured 64 MHz core, materially below the simultaneous encode+decode prototype load.  ·  latency: First audio can remain under 2 seconds; reconnect resumes in about one frame window rather than re-rendering. Hash validation adds only end-of-item time.
- security: Signed, short-lived frame URLs and device/session binding prevent cross-account audio access. Manifest hashes detect tampering or stale PCM. Expiry and deletion must follow the existing 30-day audio-retention policy.
- depends on: A single canonical relay contract for Opus rather than the currently observed PCM payload at relay_result; Durable relay playback state and typed pipeline events; A small firmware update that can persist a cursor without violating the microSD failure-buffer policy
