# Harness derivation — mac-terminal — round 64

Model: `gpt-5.6-luna`  ·  probes against `http://localhost:8000`

## What it established

- **browser bridge liveness** — The Mac agent currently reports browser extension online and 5 pending commands, but recent execute jobs waited ~45 seconds and failed 'browser extension is offline'. This indicates online status is not equivalent to active polling and stale commands can accumulate.
  - evidence: GET /ops/status at 2026-08-07T11:49:35Z: browser online=true, pendingCommands=5. GET /jobs and GET /logs: browser_read_page and browser_navigate failed after ~45050 ms with offline message; GET /logs shows repeated failures.

## Capabilities it proposed

### "“Before you start, verify that the Mac and the browser session are actually reachable right now—and if one is stale, use the part that is available and tell me exactly what you could not verify.”"
- **useful because:** Today the owner can be told that the browser is online even while commands are timing out and five requests are pending. They cannot obtain a trustworthy, active end-to-end readiness answer before delegating work. This capability prevents wasted 45-second waits, makes failures intelligible, and lets the pendant distinguish a live Mac, a live browser poller, and merely cached status.
- **path:** pendant → relay-realtime → mac-planner → mac-terminal → browser-extension → dashboard
- **model tier:** Deterministic health probes and signed challenge correlation do the normal work; use the background model only to turn the typed result into a concise explanation or choose an alternate route. Realtime is needed only when the owner asks verbally.
- **latency:** Active Mac challenge plus browser poll acknowledgment should complete in 2–5 seconds; if the browser does not answer within the lease window, return a definitive stale/unreachable result rather than waiting 45 seconds.
- **cost:** Near-zero model/API cost for the probe. Dominant cost is engineering and a small amount of durable heartbeat/lease metadata; no browser-minute budget should be spent merely checking readiness.
- **security:** Challenge tokens must be single-use, short-lived, and bound to the paired Mac/browser session; never include page contents, cookies, URLs, or command output. A stale result must be marked unknown, not healthy. The probe must be read-only and must not open tabs or alter the owner's session.
- **missing:** A single end-to-end readiness protocol spanning relay, Mac agent, and browser extension; Active challenge/ack messages with monotonic timestamps and lease generations; Separate freshness fields for Mac process health, browser heartbeat, browser poll, and pending command age; A typed readiness result consumed by the planner before dispatch; Pendant/relay rendering for verified, degraded, and unknown states


## Changes it proposed to its own stack

### `mac-harness` — Add a shell flight recorder and failure-aware continuation layer without reducing FULL_CONTROL_MODE. For every run_shell action, persist a bounded stdout/stderr artifact (spill larger output to a content-addressed local file), exit code/signal/timeout, start/end timestamps, cwd, selected non-secret environment facts, host fingerprint, and a normalized command label. Redact probable secrets before relay/dashboard storage while retaining the local raw artifact. Classify failures (timeout, missing binary, permission, network, nonzero application error), then let the same job resume with a model-generated corrected command or retry only when the failure class is transient; never replay completed action IDs. Expose transcript pointers and retry lineage through GET /jobs/:jobId/receipts, GET /journal/:jobId, and GET /ops/snapshot, with a cleanup endpoint/retention policy for artifacts.
- **owner gets:** When a Mac task fails after they walk away, the pendant can say exactly which command failed, what it was doing, and whether it recovered—rather than silently stopping or asking them to reproduce a terminal session. Long build/test output remains inspectable without flooding the expensive voice context, and retries continue from the failed step instead of repeating earlier side effects.
- effort: Medium: executor/runShell wrapper, bounded artifact store and redaction, failure classifier, resumable job state, three read routes, dashboard/relay formatting, and tests for timeout, secrets, truncation, and retry lineage.  ·  risk: Command output can contain credentials or private data; raw artifacts must remain local by default and only redacted excerpts/pointers leave the Mac. A bad transient classification could retry a non-idempotent shell command, so automatic retry must be restricted to explicit retry-safe labels or commands proven read-only; otherwise record a suggested retry and let the planner choose. Crash during recording must not change command execution semantics.
- cost: Near-zero API cost; local disk bounded by retention (for example 100 MB), with CPU overhead only for teeing output, hashing, and redaction. A small model call is used only for failure diagnosis/correction, not normal commands.  ·  latency: Negligible on normal commands; failed jobs add roughly one planner turn and any retry runtime. Large output is streamed to disk rather than held in memory.
- security: Improves auditability while preserving owner-approved unrestricted execution. Store raw stdout/stderr and environment only on-device, redact before relay, hash artifacts, and expire them automatically. No new approval gate.
- depends on: chg-5fc73ce3 receipt/undo infrastructure; GET /jobs/:jobId/receipts; GET /journal/:jobId; GET /ops/snapshot; durable job lifecycle with resumable step state

### `browser-harness` — Add a bridge liveness reconciler and stale-command janitor. Correlate extension heartbeat age, poll activity, pending-command count, command lease age, and the Mac agent's observed browser status instead of treating online=true as sufficient. Before dispatch, fail fast with a typed bridge_unavailable result when the last poll is stale; periodically expire/requeue orphaned commands whose 45-second lease elapsed, preserving idempotency keys so a late extension result cannot double-apply. Emit one deduplicated incident per outage and clear it on the first successful poll, with status exposed in /browser/status, /ops/status, /jobs, and the relay stream.
- **owner gets:** A browser request currently waits 45 seconds and then says the extension is offline, while status can still say online and pending commands accumulate. The owner gets a truthful, quick answer, no ghost work, and automatic continuation when Safari comes back instead of repeatedly asking the same thing.
- effort: Medium: heartbeat/poll timestamps, lease janitor, idempotent requeue state, typed failure, deduplicated incident event, and tests for stale/late results and restart recovery.  ·  risk: A late browser result could arrive after requeue; content-addressed action IDs and lease generations must discard duplicates. Clock skew is possible, so use monotonic local age where available. Never fail over authenticated Safari work to the relay, which lacks the owner's session.
- cost: Negligible compute and storage; avoids wasting browser-minute budget and planner calls on known-unavailable commands.  ·  latency: Unavailable browser calls fail in about one heartbeat interval (target 2–5 seconds) instead of 45 seconds; healthy calls are unchanged.
- security: No new data access. Preserve tab/session affinity and keep private-page evidence on the Mac; outage telemetry should contain only session ID hash, not page contents or URLs.
- depends on: chg-14accc01 request IDs/tab affinity/idempotency; POST /browser/heartbeat; GET /browser/poll; GET /browser/status; GET /jobs; GET /ops/status; GET /pipeline/stream

### `integration` — Create a cross-surface causality ledger that links one owner request across relay, planner routing, Mac execution, browser command, and pendant delivery using a single correlation ID and append-only event sequence. Each event should record the selected surface, decision reason, freshness proof used, action/receipt ID, result, and whether the event was observed, inferred, or merely attempted. Add a compact owner-facing 'why/where/what happened' projection that can be spoken without replaying the full prompt context, plus an exportable JSON evidence bundle for disputes or debugging.
- **owner gets:** The owner should be able to ask, “What exactly did you do, where did it happen, and why did you believe it worked?” Today local receipts and job records exist, but they do not establish one trustworthy story across the pendant, relay, Mac, and browser—especially when a stale browser status conflicts with a failed command. This would make the system accountable rather than merely plausible.
- effort: Medium-to-large: shared correlation schema, append-only storage and retention, event propagation through relay and Mac/browser bridges, provenance projection, and recovery for partially delivered events.  ·  risk: The ledger could expose private URLs, commands, or page evidence; default spoken output must be summarized and redacted, with detailed export kept local or explicitly requested. Clock ordering must use sequence numbers and monotonic timestamps rather than wall-clock time alone. Event loss must be represented as unknown, never silently filled by inference.
- cost: Small durable-storage and hashing cost; negligible model cost because the owner projection is deterministic for normal events. A background model is optional only for explaining unusual partial failures.  ·  latency: No blocking cost on successful execution if events are buffered locally; the owner-facing summary becomes available within a few seconds. Durable flush may add minimal local I/O.
- security: Improves accountability without adding execution restrictions. Bind event ingestion to the existing paired relay/Mac identity, sign event batches, encrypt detailed evidence at rest, and redact secrets before relay transmission.
- depends on: chg-5fc73ce3 receipt/undo infrastructure; GET /jobs/:jobId/receipts; GET /journal/:jobId; GET /pipeline/stream; GET /ops/status; GET /browser/status; GET /routing
