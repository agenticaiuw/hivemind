## Capabilities it proposed

### "“I’m leaving my Mac. Package up exactly where I am across my open tabs and apps, and when I’m back, bring me back to the right place and remind me what I was doing.”"
- **useful because:** Today work is fragmented across Safari/Chrome tabs, Mac applications, and the pendant conversation. The owner should be able to leave without manually reconstructing their state: the system would preserve the active work thread, distinguish intentional context from unrelated tabs, and restore it later with a short spoken orientation. This depends on the pendant’s physical presence, the Mac’s application state, the browser’s private sessions, and the relay’s durable memory together.
- **path:** pendant → mac-planner → browser-extension → relay-realtime → unified
- **model tier:** Use deterministic local capture and matching for app/tab titles, URLs, window geometry, selected project, and job checkpoints. Use the background tier to produce a compact orientation and only escalate to the realtime tier when the owner asks for spoken clarification during return. No planner call is needed for ordinary capture/restore.
- **latency:** Capture in under 2 seconds when the owner presses the pendant button; restore the Mac workspace in under 5 seconds after return. Spoken orientation should begin within 1 second of the pendant reconnecting.
- **cost:** Low per handoff: mostly local metadata and relay storage. One background summarization call only when the workspace contains enough changed material to require a narrative; raw page contents remain local unless explicitly requested.
- **security:** Browser URLs, window titles, and app state can reveal sensitive work. Encrypt the handoff capsule, bind it to the paired pendant and Mac, allow per-app exclusions, and default to storing metadata rather than page contents. Never transmit cookies, form values, or screenshots to the relay without explicit request. Restoration must not submit forms or send messages.
- **missing:** A durable cross-surface handoff capsule schema with app/tab/job provenance and owner-selected sensitivity rules; Mac APIs to capture and restore window/application state without losing existing sessions; Browser extension support for tab-group capture and reattachment to the same authenticated session; Pendant reconnect/button event delivered to the relay with a stable handoff identifier; A return-flow UI and spoken summary that can resolve stale or missing tabs instead of silently opening substitutes

### "“Give me a focused 25-minute block. Keep my Mac and browser quiet, but let through anything genuinely urgent, and tell me when the block is over.”"
- **useful because:** The owner currently has separate distraction tools and browser sessions, but no single intent spanning Mac notifications, authenticated browser tabs, relay routines, and the physical pendant. A pendant-triggered focus block would turn a spoken or button request into a coordinated, reversible state: suppress noise everywhere, continue monitoring only narrowly defined urgent signals, and provide a physical end-of-block cue without requiring the owner to keep checking the screen.
- **path:** pendant → mac-planner → browser-extension → relay-realtime → unified → faculty-perception → faculty-judgement → faculty-action
- **model tier:** Deterministic state machine for start, timer, suppression, restore, and end notification. Background model classifies candidate events against the owner's configured urgency rules. Realtime is used only if the owner asks a follow-up while the block is active.
- **latency:** Start suppression within 2 seconds of the button or spoken command. Restore within 2 seconds of expiry or cancellation. Urgent-event classification should be asynchronous and should not delay the focus state.
- **cost:** Near-zero for the timer and local notification controls. Background classification is occasional and can be batched; no planner call for ordinary start/stop. Relay storage is one small focus-session record.
- **security:** Notification contents and private browser activity are sensitive. Keep raw content on the Mac/browser; send the relay only urgency category, timestamp, and session ID. Require explicit per-source configuration, never auto-read arbitrary pages, and make restoration idempotent so a dropped connection cannot leave notifications suppressed indefinitely. The owner must always be able to cancel with a pendant press.
- **missing:** A cross-surface focus-session protocol with expiry, cancellation, lease renewal, and crash-safe restoration; Mac notification and Do Not Disturb integration exposed as reversible typed actions; Browser extension hooks to pause non-urgent page watches and queue low-priority commands; A local urgency classifier with owner-editable source and keyword rules; Pendant firmware support for distinct start/cancel/expired haptic or LED patterns; Relay watchdog that restores or expires sessions when the Mac or pendant disconnects


## Changes it proposed to its own stack

### `mac-harness` — Add a failure-aware continuation layer above the unrestricted executor. For every action, persist a typed outcome (transport/offline, permission, timeout, command error, semantic mismatch) plus stderr/exit status, observed bridge state, and the last successful receipt. Before retrying, consult an idempotency-key circuit breaker: suppress identical retries after a configurable failure threshold, refresh the relevant prerequisite (for example browser heartbeat/session reattachment or Mac permission status), then resume only from the last successful action. Surface a compact recovery plan and a `resume job` operation through /jobs and the relay, while preserving FULL_CONTROL_MODE and never blocking an owner-requested action; retries must be explicit in the job trace. Attribute every action to its routing tier/model and retain the failed command's redacted argv/env metadata.
- **owner gets:** When a browser bridge disappears or a permission is missing, the owner gets an intelligible diagnosis and a job that can continue instead of six silent duplicate failures or starting over. A spoken “finish that” can resume the unfinished work safely, while the owner can see whether the issue was offline, permission, timeout, or the command itself. This directly addresses the live state: 16 failed actions, 112 actions without tier attribution, and one browser navigation repeated six times with a 100% failure rate.
- effort: Medium: extend jobTracker/action receipts with normalized failure fields and continuation checkpoints; add a small retry/circuit-breaker module, prerequisite probes, resume endpoint, and relay status serialization; add tests for browser-offline, permission-denied, timeout, and successful resume.  ·  risk: A bad classifier could label a recoverable failure permanent or resume from an unsafe checkpoint. Recovery: default to no automatic retry after the threshold, preserve the complete trace, allow explicit force-retry from the owner, and make each continuation idempotent. Do not transmit command contents or secrets to the relay; send only category, counts, and redacted diagnostics.
- cost: Negligible API cost; mostly local JSON/D1 metadata. A cheaper deterministic classifier avoids spending planner tokens on routine failure diagnosis; escalate only ambiguous semantic failures.  ·  latency: Adds milliseconds for local classification. Prerequisite refresh may add 1–3 seconds, but avoids repeated 120-second shell/browser attempts and avoids rerunning completed steps.
- security: No reduction in the owner's deliberate maximum-access policy. Improve auditability by hashing/redacting argv, environment, and stderr before relay export; keep raw diagnostics local and apply retention limits.
- depends on: Existing action receipts and jobTracker persistence; Existing /jobs, /jobs/:jobId/receipts, /jobs/:jobId/cancel, and relay_job_status surfaces; Browser heartbeat/session state and Mac observability endpoints (/ops/status, /browser/status); Routing attribution hooks in routingStats.js

### `model-routing` — Make routing metadata an end-to-end trace context rather than an in-memory planner receipt. Generate a requestId at the pendant/relay boundary and propagate it through relay jobs, Mac /plan and /execute, browser commands, action receipts, and journal entries; record tier, model, prompt/completion token estimates, escalation reason, latency, and final outcome on every action. Add a deterministic preflight router that consults /ops/status (browser online, required permissions, relay reachability) and routes simple status/recovery queries to deterministic/background tiers, while marking impossible browser work as `waiting_for_surface` instead of repeatedly invoking the planner.
- **owner gets:** The owner can ask what happened and receive one coherent answer: which device acted, what failed, how long it took, and whether model spend was justified. The system will stop wasting expensive planner calls when the browser is offline and will give a useful “reconnect Chrome” explanation instead. Today routing reports 7 requests but 112 journal actions have no tier attribution, so cost and failure explanations are incomplete.
- effort: Medium: introduce a trace-context object shared by relay and local-agent requests; persist compact routing receipts with jobs; update browser command envelopes and journal serializers; add preflight rules and dashboard aggregation.  ·  risk: Metadata can become noisy or accidentally include sensitive prompts. Keep command text out of cross-device receipts, store only hashes/intent labels and token counts, enforce bounded retention, and tolerate missing context without failing execution. Preflight must be advisory/status classification only, consistent with FULL_CONTROL_MODE and the owner's no-gates policy.
- cost: Slightly more local storage and D1 writes; reduces planner spend by avoiding doomed retries and selecting deterministic/background handling for status work.  ·  latency: A local preflight is sub-100 ms; propagation is negligible. It removes multi-second model calls for known-offline surfaces.
- security: Improves auditability without restricting capability. Relay receives redacted IDs and outcome categories, never raw shell commands, environment, cookies, or page contents.
- depends on: Existing routingStats.js and /routing endpoint; Existing jobTracker/actionReceipts/journal persistence; Relay job identifiers and browser request IDs; Read-only /ops/status and /browser/status telemetry

## Its own summary

Recorded two owner-facing capabilities that are not available today: a privacy-preserving leave-and-return workspace handoff spanning the pendant, Mac, authenticated browser, and relay; and a pendant-triggered cross-surface focus block with urgent-only monitoring, crash-safe expiry, and restoration. Both require new cross-surface protocols and hardware/integration work rather than merely wiring existing actions together.

**Biggest unknown:** Whether the Mac and browser platforms expose reliable APIs for restoring exact window/tab state and controlling notification suppression; implementation should treat unsupported state as an explicit partial restore, never claim success silently.
