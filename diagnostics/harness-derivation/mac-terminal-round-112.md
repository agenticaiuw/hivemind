## Capabilities it proposed

- **useful because:** Today the Mac agent can claim UI success while Accessibility is actually unavailable, and browser commands can accumulate while the extension is offline. A coordinated preflight-and-recovery path would let the pendant ask once, have the Mac choose a reachable route (typed action, shell, AppleScript, or browser queue), retry safely after reconnect, and return a truthful verified/unverified/blocked result instead of a misleading success.
- **path:** pendant → relay → mac-planner → mac-vision → browser-extension → dashboard
- **model tier:** deterministic preflight and recovery first; background model only to map the user's goal to an alternate route; realtime only for the spoken request and concise status
- **latency:** 150–400 ms for /observe and reachability preflight; under 2 s for deterministic fallback; browser reconnect recovery can run in the background. Spoken acknowledgement should be immediate and revised when proof arrives.
- **cost:** Usually zero model calls for typed actions and health checks; roughly 2k–4k input tokens only when goal-to-fallback mapping is ambiguous. Dominant cost is existing Mac/browser execution, not inference.

Commands and UI evidence stay on the Mac unless a user-visible receipt is requested; redact shell output and page content in relay receipts. Never treat an action as verified solely because an executor returned success.
- **missing:** A shared preflight contract that exposes accessibility/input reachability, browser online state, and fallback eligibility to the planner; An idempotent browser pending-command replay worker with expiry and deduplication; A typed result merger that can revise queued/running outcomes when delayed browser or Mac evidence arrives; A dashboard/pendant status event for blocked_unreachable and completed_unverified

### "Before my next meeting, check whether I can realistically make it, open the route on my Mac, and if I'm going to be late prepare a message for me—but don't send anything unless I say so."
- **useful because:** The owner currently has separate calendar, browser, Mac-control, and pendant surfaces, but no single spoken workflow that joins the next event's location and time with live travel conditions, presents a decision, and prepares a timely recovery action. This saves the owner from manually switching apps while preserving control over external communication.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** background model for extracting the next meeting and summarizing travel uncertainty; deterministic calendar/session reads and route calculations where possible; realtime only for the spoken answer and urgent status changes
- **latency:** Initial answer within 5 seconds when Calendar and browser are online; route refreshes in the background every 10 minutes until departure or meeting start. Preparing a draft should take under 2 seconds after the owner confirms the intended recipient.
- **cost:** One background request of roughly 3k–6k input tokens per meeting check, dominated by authenticated calendar/event context and live travel data; refreshes should use cached facts and deterministic comparison, not the realtime tier.
- **security:** Calendar locations, travel origin, and authenticated browser data are sensitive and should remain on-device or in the paired relay with short retention. Never send a late message automatically; require an explicit owner confirmation. Do not expose private event titles or recipient details in a generic dashboard. Travel estimates are uncertain and must be stated as ranges with timestamp and source.
- **missing:** A cross-surface event resolver that can read the next calendar event and normalize its location, timezone, and start time; A travel-estimate adapter that can use the browser's authenticated map/session context or an approved public route source without losing session affinity; A small decision engine for leave-by time, uncertainty bounds, and late-risk classification; A draft-only message handoff from Mac to the owner's chosen mail or messaging app with a confirmation token; A pendant notification schedule that survives relay or Mac reconnects and cancels itself when the event changes
