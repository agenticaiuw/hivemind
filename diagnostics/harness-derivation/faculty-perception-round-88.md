## Changes it proposed to its own stack

### `integration` — Add a fail-closed perception precondition to the action executor and durable job runner. Before any ui_click, ui_menu, type_text, press_keys, or other focus-dependent step, fetch /observe (or a short-lived signed snapshot), require inputReachability.status=ready, accessibility trusted=true, and screenRecording=true where screenshots are needed. If false, skip the GUI step, try only an explicitly declared AppleScript/browser alternative, and write a typed blocked receipt containing the exact observed reason, timestamp, target app, and fallback attempted. Recheck after focus-changing steps so stale readiness cannot authorize a later action.
- **owner gets:** The owner stops receiving false success for actions that visibly did nothing. They get either a real change through a reachable API or a clear explanation and recovery path, without needing to know macOS TCC details.
- effort: Medium: shared action middleware, receipt schema/status propagation, route-policy table, and tests simulating stale/failed /observe responses. No owner-side code change; Accessibility remains optional for GUI work.  ·  risk: A strict gate may reject operations that would have worked through an unusual non-UI path, or interrupt a long job when permissions change. Recover by allowing only typed non-GUI routes, re-planning from the blocked receipt, and retaining existing cancel/undo behavior. Never downgrade a blocked GUI step to success.
- cost: Negligible API cost: one local readiness GET per GUI job or per focus boundary. Small local storage increase for snapshots and receipts; no cloud upload.  ·  latency: ~100–300 ms preflight locally, plus a recheck at focus boundaries. Avoids minutes of silent no-op work.
- security: Improves safety and provenance. Permission/process metadata remains local; screenshots remain prohibited unless Screen Recording and vision consent are both true. A signed short TTL snapshot prevents another process from spoofing readiness.

### `browser-harness` — Add lease expiry and quarantine semantics to browser command polling. A claimed command gets a short lease with heartbeat; if the extension is offline or no result arrives before the lease, atomically return it to queued once, then move it to stale/needs-review after a bounded retry count. Expose command age, lease expiry, attempts, and last-seen extension time in /browser/status and /browser/poll. Never hand a command marked processing to a second consumer without an idempotency key, and never let a four-hour-old command keep appearing as live work.
- **owner gets:** The owner will not have browser work silently trapped in a zombie “processing” state or accidentally replayed when Safari reconnects. They receive a precise stale warning and can retry intentionally, rather than waiting or risking duplicate navigation/form actions.
- effort: Medium: durable command schema migration, atomic claim/lease update, extension heartbeat comparison, retry/quarantine endpoint/state, and dashboard/status rendering. Existing request IDs and idempotency work can be reused.  ·  risk: A slow but valid page could be quarantined prematurely, or a temporary network gap could cause a retry. Use generous per-step leases, extension heartbeat renewal, idempotency keys, and explicit owner retry. Recovery is safe because stale commands are not auto-executed after quarantine.
- cost: Negligible model/API cost; a few D1 fields and periodic heartbeat requests. Reduced wasted Mac/browser retries.  ·  latency: Adds no delay to normal polling; reconnect recovery becomes bounded instead of waiting indefinitely.
- security: Reduces duplicate authenticated actions. Stale commands containing private URLs/forms remain stored under existing retention controls and should be redacted in dashboard summaries.
- depends on: Browser extension heartbeat must include a monotonic client timestamp or lease token; Durable browser command queue must persist status transitions atomically
