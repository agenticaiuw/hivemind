## Capabilities it proposed

### "“When I’m traveling, reconcile my logged-in airline and hotel reservations with live public disruption information, tell me what changed, and prepare—not send—any rebooking or calendar updates.”"
- **useful because:** Only the browser can read the owner’s reservation details behind existing logins, while the relay can cheaply check public delay/cancellation feeds when the Mac is asleep. Combining both prevents false alarms from generic flight data, and the Mac can turn a confirmed change into a ready-to-review calendar/reminder update delivered to the pendant.
- **path:** browser-extension → relay-realtime → mac-planner → pendant → dashboard
- **model tier:** Use a cheap background model for scheduled public-status polling and initial diffing; use the realtime tier only when the owner asks by voice or when a genuinely urgent disruption needs concise spoken explanation. Use the Mac planner for calendar/update drafting, not for browser extraction.
- **latency:** Background checks complete within 1–3 minutes of a scheduled cadence; urgent spoken answer under 5 seconds when cached evidence exists, otherwise under 20 seconds for one authenticated read plus public lookup.
- **cost:** Low: public polling uses cached relay/web-search work and a cheap model; one disruption event costs roughly $0.01–$0.05 depending on authenticated page extraction and synthesis. Realtime cost is reserved for the spoken interaction.
- **security:** Reservation pages, confirmation codes, names, and itinerary details remain on the Mac/browser path; relay receives only public flight/hotel identifiers and coarse event data. Never speak or persist full confirmation codes. Draft rebooking or calendar changes stop before submission; show exact proposed changes and require the owner’s existing explicit approval before any irreversible booking or message.
- **missing:** Durable authenticated page-watch definitions with recovery when Safari loses its tab; A public/private origin fan-out job runner with durable retries and evidence joining; A cross-surface itinerary schema linking reservation, public status, calendar event, and provenance; A review artifact/voice notification path that can deliver urgent diffs to the pendant

### "“From the private page I’m viewing, find every date, deadline, renewal, cancellation window, and fee that affects me; read me the important ones, cite the exact page text, and prepare local reminders for my review.”"
- **useful because:** This turns an authenticated page into practical memory without asking the owner to copy text or expose the whole page. The browser alone can see the logged-in terms or account page, the Mac can create reminders, and the pendant can deliver a concise spoken result while the owner is away from the screen.
- **path:** browser-extension → mac-planner → relay-realtime → pendant → dashboard
- **model tier:** Use a background/cheap extraction model for the page projection and date normalization. Use the realtime model only for the owner’s spoken request and concise readout; use deterministic local parsing for ISO dates, recurrence, currencies, and reminder payloads.
- **latency:** A single open-page request should return a spoken summary within 5–15 seconds; reminder drafts appear on the Mac immediately after extraction. No background polling is required unless the owner explicitly asks for a future recheck.
- **cost:** Approximately $0.01–$0.04 per page, dominated by authenticated-page extraction and synthesis; reminder creation and pendant delivery are local/relay overhead.
- **security:** Only the active tab’s relevant rendered regions leave Safari; unrelated content, hidden fields, passwords, and payment details are excluded. Exact quotations may contain sensitive terms, so retain them locally and speak only the minimum needed. Creating reminders is reversible, but the system must show the title/date/source before saving if the owner has not explicitly asked to save them.
- **missing:** Semantic page projection with field-level sensitivity and exact-text provenance; A date/deadline extraction schema that preserves timezone, locale, recurrence, and uncertainty; A bridge from browser evidence capsules to local reminder drafts; Pendant speech cards that include a short result plus a tap/voice path to the cited source


## Changes it proposed to its own stack

### `browser-harness` — Add a bridge identity-and-queue recovery controller. Persist a stable browser device identity (not the transient extensionId), last heartbeat, tab inventory, and per-command lease/attempt state. When a device re-registers under a changed extension id (as live state did: Safari disappeared and only tabless home-chrome remained), reconcile queued commands by session/tab affinity: rebind only when the target session's tab is positively reidentified; otherwise mark commands as stale-rebind-needed instead of letting them sit in the 9-command queue. Add a lightweight GET /browser/diagnostics (device transitions, queue age, lease expiry, last poll/result, failure class) and automatic exponential retry for navigation timeout/offline errors, with a hard TTL and an explicit recoverable result. Keep browser-private jobs on Safari; never silently route them to public relay Browser Run.
- **owner gets:** The owner stops seeing 45-second hangs and phantom 'online' status after Safari or the extension restarts. A page task either resumes on the same logged-in tab, clearly reports that the session must be reopened, or expires promptly; queued work cannot accidentally target a different browser session.
- effort: Medium: browserBridge/browserSessions persistence, heartbeat identity handshake in the extension, queue reconciliation worker, diagnostics route, and integration tests for extension restart/tab replacement.  ·  risk: A false tab rebind could expose or mutate the wrong logged-in page; require exact session URL/origin plus a stable tab marker and otherwise refuse to rebind (observability refusal, not an owner approval gate). Retry must deduplicate via existing idempotency keys. Recovery: stale commands remain inspectable and can be explicitly retried after a fresh heartbeat.
- cost: Negligible API cost; a few KB of local JSON state and small heartbeat/diagnostic traffic. Retry reduces wasted 45-second model/tool invocations.  ·  latency: Healthy commands unchanged; failures become a fast lease/diagnostic result (seconds) rather than repeated 45-second waits. Reconnect adds one heartbeat round trip.
- security: Improves isolation by preventing stale commands from crossing browser identities or tabs; diagnostics must redact URLs/query strings and page text, exposing only origin, ids, timestamps, and failure class.
- depends on: A functioning extension enqueue/poll path and stable extension-side device UUID; Existing browserSessions tab/session affinity and idempotency receipts; Progress/resumable polling work from chg-14accc01; A durable browser job runner from chg-16bc5dee

### `browser-harness` — Add an extension-local semantic page projection layer. Before page content leaves Safari, the extension builds a compact accessibility/DOM projection containing headings, labels, controls, selected visible text, and stable element handles, while tagging fields by sensitivity (password, OTP, payment, identity, private message) and excluding hidden/scripted content by default. The planner requests a projection schema per task (read-only summary, form drafting, navigation), and browser actions target expiring element handles rather than brittle CSS selectors. The extension returns field-level provenance and a local redaction map so the Mac can explain what was seen without persisting secrets. This is a new data boundary and interaction primitive, not a page-watch or durable job runner.
- **owner gets:** Private websites become understandable and operable without shipping an entire page—including hidden tokens, unrelated messages, or autofill secrets—to the model. The owner gets more reliable help with complex logged-in pages and exact explanations of which visible fields were used, even when sites constantly change their markup.
- effort: High: Safari extension content-script/accessibility extraction, sensitivity heuristics, projection schemas, expiring handle validation, local redaction/provenance storage, and Mac-agent protocol support. Requires tests across SPAs, shadow DOM, iframes, and login/payment forms.  ·  risk: Heuristics can mislabel a field or omit important context; fall back to visibly rendered text and report uncertainty rather than silently inventing data. Handles must be origin/tab/document-bound and expire on navigation. The owner policy permits maximum access, so sensitivity tags are for minimization and audit—not an approval gate—and an explicit full-page mode can exist when requested.
- cost: Small local CPU/memory overhead in Safari; lower model/API cost because projections are compact. No additional external API cost beyond the model call.  ·  latency: Adds roughly 100–500 ms for local projection on ordinary pages; substantially reduces retries caused by stale selectors and oversized page payloads.
- security: Improves privacy by keeping secrets and unrelated DOM local, preventing hidden-page data leakage, and binding actions to the exact authenticated origin/tab/document. The extension still needs a clear owner-visible indicator when full-page mode is used.
- depends on: A working browser command enqueue/poll implementation; Safari extension content-script and accessibility-tree access; The existing browser session/tab affinity protocol; A Mac-agent action schema that can carry projection requests, handles, and provenance
