## Capabilities it proposed

### "Just do it, but first figure out which parts of my Mac, browser, pendant, and relay are actually available; use safe fallbacks when one is unavailable, and tell me what you could not do without making me ask again."
- **useful because:** Today the planner can know a route exists while the real surface is unusable: this Mac reports computer-use disabled, missing Accessibility and Screen Recording, and an offline browser extension with seven queued commands. A cross-surface preflight would prevent 45-second browser timeouts and impossible GUI plans, hand public reads to relay/browser-run, hand Mac reads to shell, queue private browser work until the extension returns, and give the pendant one concise capability/fallback explanation. It is materially different from generic goal routing because it uses live permission, heartbeat, queue, and model-consent facts before each step and rechecks them after failures.
- **path:** relay-realtime → mac-planner → browser-extension → mac-vision → unified → faculty-perception → faculty-judgement → faculty-action
- **model tier:** Use a cheap deterministic preflight and routing policy first; use a background/standard model only to map a failed capability to a fallback. Reserve realtime for the owner's spoken explanation or a genuinely ambiguous decision.
- **latency:** Under 300 ms for local /ops/status plus cached relay health; under 1 s for a cross-surface matrix. Do not spend 45 s waiting on a browser command when its heartbeat/queue already says unavailable. Recheck only the affected surface after a failure.
- **cost:** Negligible API cost for local health and typed policy; roughly one small standard-model call only when fallback mapping is ambiguous. Dominant cost is the optional spoken summary, not preflight.
- **security:** Health facts must not include page contents, cookies, or tokens. Private-page work stays on the authenticated browser bridge; public fallback must be explicitly classified as non-private. Persist only capability state, timestamps, reason codes, and job IDs. No mutation is blocked by policy—the owner chose maximum access—but an unavailable or stale surface must not be represented as successful.
- **missing:** A versioned capability matrix contract combining Mac permissions/readiness, computer-use consent, browser heartbeat/queued-command state, relay reachability, and pendant link state; Preflight hooks in POST /plan and POST /execute, with per-step required capabilities and fallback candidates; A bounded health-aware retry/recovery state machine that consumes existing receipts and records why a fallback was selected; Pendant/relay notification payload for unavailable, deferred, and completed-with-fallback outcomes; A durable queue policy for private browser work that distinguishes stale queued commands from safe replayable commands

### "After you do something across my Mac and logged-in browser, tell me whether it actually took effect—not merely whether the commands succeeded—and show me the short before/after proof if I ask."
- **useful because:** Today a successful receipt means an executor reported success, not that the external world changed. A browser submit can be accepted but fail validation, a Mac app can ignore input, or a page can update another tab. The owner needs one trustworthy answer that correlates the Mac observation, authenticated browser evidence, and relay-delivered pendant response, with uncertainty made explicit.
- **path:** relay-realtime → mac-planner → browser-extension → unified → faculty-perception → faculty-judgement → faculty-action
- **model tier:** Use deterministic receipt/evidence correlation and host/browser re-reads first. Use a cheaper standard model to compare before/after semantic state; reserve realtime only for the owner's spoken explanation when the verdict is ready.
- **latency:** For reversible Mac-only work, verify within 2 seconds. For browser workflows, allow up to 10 seconds for a fresh authenticated read. If verification cannot complete, return 'executed but unverified' rather than claiming success.
- **cost:** Usually no additional model call when typed fields or hashes match; one small standard-model comparison for semantic page changes. Main cost is one additional browser or Mac read, not realtime inference.
- **security:** Proof may contain private page text, so keep raw snapshots on the Mac/browser bridge and send the relay only a redacted verdict, field names, hashes, and minimal snippets on explicit request. Bind evidence to job ID, tab/session ID, URL, and timestamps to prevent stale-tab confusion. Never treat a public fallback as proof of a private mutation.
- **missing:** A cross-surface verification record linking action receipts to postcondition checks; Typed postconditions for Mac actions and browser mutations (field value, URL/state, app status, or semantic predicate); A browser read-after-write primitive that guarantees the same tab/session and returns provenance-bound evidence; A Mac observe-after-action primitive for foreground app state, document values, and synthesized-input reachability; A redaction layer and pendant-friendly proof summary format; A verdict state machine distinguishing succeeded-and-verified, succeeded-but-unverified, failed-before-change, and changed-but-postcondition-failed


## Changes it proposed to its own stack

### `integration` — Add a preflight-and-fallback middleware between planner and executor. For every planned action, declare required surface facts (e.g. browser_online, tab_attached, accessibility, screen_recording, vision_consent, relay_reachable). Read a short-lived capability snapshot from /ops/status and /browser/status, annotate each step as ready/deferred/fallbackable, and persist that decision in the job and receipt. Execute only ready steps; for fallbackable steps select a declared alternative (relay/public web, shell/status, or durable browser queue), then recheck the affected surface once after a failure. Emit one structured completion event containing completed, deferred, fallback, and reason codes for relay/pendant narration. This is observability and recovery, not an approval gate.
- **owner gets:** The owner gets a fast truthful answer instead of waiting through impossible actions: e.g. 'I can read the Mac, but browser work is queued because the extension is offline; I did the public portion now.' It also stops identical browser timeouts and makes partial completion understandable.
- effort: Medium: capability schema, planner annotations, executor middleware, fallback registry, and relay event formatting; add integration tests for offline extension, missing permissions, stale heartbeat, and successful recovery.  ·  risk: A stale health snapshot could incorrectly defer a newly available surface or choose an inferior fallback. Use TTLs, include snapshot timestamps in receipts, and allow one bounded recheck. Never silently substitute a public source for a private authenticated page.
- cost: No meaningful model cost; local HTTP checks and JSON receipts. Small storage increase per action for capability snapshot and reason codes.  ·  latency: Adds about 100–300 ms to local jobs; avoids current 45-second browser timeout loops. Fallback execution can proceed in parallel where dependencies allow.
- security: Improves privacy by making private/public boundary explicit and preventing accidental public fallback. Does not narrow FULL_CONTROL_MODE or add confirmations.
- depends on: A typed required-capabilities field in the existing action registry; A fallback registry that marks which alternatives are privacy-equivalent versus public-only; A relay event schema for deferred/fallback completion; The existing /ops/status and browser status endpoints being reachable from the executor

### `integration` — Create a cross-surface postcondition verifier that runs after an action batch. The planner must attach a typed expected outcome to each write. After execution, the verifier retrieves the same browser tab/session or Mac foreground context, compares the observed state to the expectation, stores a provenance-bound verification record, and emits a four-state verdict: verified, unverified, unchanged, or contradicted. Aggregate verdicts across the batch and expose a redacted proof card to the relay/pendant; retain raw evidence locally. A receipt may remain successful while the user-facing result is 'completed but unverified' until this check passes.
- **owner gets:** The owner can trust 'done' to mean the intended world state was observed, not just that an API or keystroke returned without an error. When something is ambiguous, they get a precise next step and compact proof instead of having to inspect the Mac themselves.
- effort: Medium-high: typed postconditions in the planner/action registry, same-context read-after-write adapters for Mac and browser, evidence correlation, verdict persistence, and redacted voice/dashboard rendering.  ·  risk: Some applications update asynchronously or expose nondeterministic text, causing false 'contradicted' results. Support settling windows, semantic predicates, and an explicit unverified state; never retry a mutation merely because verification is inconclusive.
- cost: One extra read per write and occasional small standard-model semantic comparison; no realtime call required for normal operation. Raw evidence increases local storage modestly.  ·  latency: Adds 0.5–10 seconds depending on the surface, but replaces false immediate success with an honest bounded result. Independent postconditions can be checked in parallel.
- security: Raw private evidence stays on the Mac/browser bridge. Relay receives only redacted fields, hashes, timestamps, and verdict unless the owner explicitly requests proof. Same-tab/session binding reduces cross-account leakage.
- depends on: Action schemas that carry typed expected outcomes; Browser same-tab read-after-write with provenance; Mac observe support for application/document postconditions; A local evidence redaction and retention policy; Relay/pendant event support for proof cards and four-state verdicts
