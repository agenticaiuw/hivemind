## Capabilities it proposed

### "“That failed—figure out what went wrong, pick up from the last successful step, and finish it.”"
- **useful because:** Today a failed Mac/browser job leaves the owner to reconstruct the error and repeat earlier work. This would turn a failure into a recoverable conversation: the pendant gives a concise diagnosis, the relay assembles evidence, and the system resumes only the unfinished portion while preserving the owner’s authenticated browser state.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** Use deterministic receipt/exit-code analysis first and a cheaper background model for diagnosis and continuation planning; use realtime only to explain the result or answer the owner’s follow-up. Escalate to the expensive model only when the failure is ambiguous or the next step has meaningful semantic alternatives.
- **latency:** Immediate spoken failure summary in under 2 seconds from stored receipts; continuation planning in 5–15 seconds; execution proceeds asynchronously with a pendant notification when complete. Do not block on an expensive model for obvious timeout, missing-path, or stale-tab failures.
- **cost:** Usually near-zero incremental API cost because exit metadata, receipts, browser command results, and workspace facts are already structured. Ambiguous recovery costs one background planning call, roughly a few cents or less; storage is bounded failure artifacts and checkpoints.
- **security:** Recovery evidence may contain private shell output, local paths, or authenticated page text. Keep raw artifacts local/encrypted with short retention, redact tokens and cookies, and send the relay only structured error summaries by default. Never silently substitute a different recipient, destination, payment, or submitted browser form; semantic changes must be surfaced as a new plan for owner review. Exact retries of the original trusted action remain available under the owner’s maximum-access policy.
- **missing:** A durable cross-surface checkpoint graph that relates Mac action IDs, browser command IDs, and their dependency edges rather than only a flat job list; A bounded local artifact store with redaction and TTL, plus a relay endpoint that can fetch selected evidence on demand; A recovery planner contract that distinguishes exact retry, deterministic repair, and semantically different alternatives; A continuation executor that resumes from the last successful node and reports any changed preconditions without replaying completed work

### "“Pack up what you’re doing so I can close the lid, then continue it later exactly where you left off.”"
- **useful because:** Today a task’s state is scattered across Mac processes, browser tabs, shell cwd, temporary files, and relay job records. The owner cannot intentionally pause a real workflow and later resume it as a coherent unit. A portable task capsule would preserve the useful state and make interruption—sleep, reboot, lost network, or switching machines—ordinary rather than destructive.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** Use a cheap deterministic serializer and integrity checker for the capsule. Use a slower background model only to summarize human intent and identify which external state must be revalidated; realtime is only for the spoken pause/resume interaction.
- **latency:** A pause acknowledgement and capsule manifest in under 2 seconds; capture local/browser state asynchronously in under 30 seconds for ordinary jobs. Resume should validate dependencies first and then start within 5 seconds, with the owner notified if anything drifted.
- **cost:** Minimal API cost for manifests and hashes; occasional background summarization is a few cents or less. Storage depends on selected artifacts, with a default small manifest and explicit opt-in for large files or screenshots.
- **security:** Capsules can contain private paths, shell output, authenticated-tab identifiers, and pending form data. Encrypt them, bind browser references to the owner’s device/session, expire abandoned capsules, and never export cookies or credentials. On resume, revalidate external state; do not assume a saved form or page is unchanged. Any irreversible action remains a newly presented step, not a replayed side effect.
- **missing:** A versioned capsule format spanning Mac action receipts, shell cwd/environment fingerprints, browser tab/session affinity, pending checkpoints, and relay job IDs; A local encrypted capsule store with resumable upload and conflict handling after reboot or device change; A pause protocol that drains in-flight actions and records a consistent cut between completed and pending steps; A resume validator that checks repository hashes, app availability, browser tab identity, network assumptions, and expiry before continuation; Pendant and dashboard controls for naming, listing, expiring, and resuming capsules


## Changes it proposed to its own stack

### `mac-harness` — Add a command-outcome and recovery ledger around run_shell without changing FULL_CONTROL_MODE: capture bounded stdout/stderr plus exit code, signal, timeout, cwd, duration, environment fingerprint (never secrets), and a normalized failure class (not-found, permission, dependency, transient-network, parse, timeout, unknown). Persist content-addressed output artifacts and link them to the existing action receipt/job. On failure, record a resumable checkpoint and generate a machine-readable retry plan (same command, adjusted timeout/cwd, or an explicitly different alternative) so the relay can say what failed and resume only the unfinished step rather than replaying a whole multi-action job.
- **owner gets:** When the Mac task fails after you leave, the pendant can tell you exactly whether it was a missing file, timeout, or network problem and continue from the failed step. Large output need not be stuffed into conversation, while you retain a trace you can inspect; retries stop wasting time repeating already-completed shell work.
- effort: Medium: executor wrapper and D1/job schema changes, artifact store with size/redaction limits, failure classifier, retry-plan serializer, and relay/dashboard rendering. Add integration tests for timeout, nonzero exit, truncation, and resumed multi-step jobs.  ·  risk: Capturing command output can expose private file contents or tokens; redact common credential patterns, cap inline output, encrypt or access-control artifacts, and expire them independently of receipts. A bad classifier could suggest an unsafe alternative, so alternatives are advisory data for the trusted planner, never auto-executed as a different command. Preserve raw receipt and allow manual retry of the exact original.
- cost: Negligible model/API cost for ordinary runs; modest storage for bounded artifacts (for example 256 KB inline plus compressed object spill). A cheaper background classifier or deterministic rules handle most failures; use the expensive model only when recovery reasoning is requested.  ·  latency: Near-zero execution overhead for metadata capture; artifact hashing adds milliseconds. Failure explanation can be immediate from deterministic classes, with slower model analysis only on demand.
- security: Improves auditability but creates a sensitive output archive. Keep artifacts local or encrypted, apply TTL and per-job access controls, omit environment values and redact secrets before persistence. No new authorization gate is introduced, honoring maximum-access policy.
- depends on: Existing actionReceipts.js receipt IDs and GET /jobs/:jobId/receipts; A durable job/checkpoint store so completed action IDs survive process restarts; A bounded local artifact store and relay endpoint for fetching selected failure evidence

### `mac-harness` — Add a local workspace inventory service that periodically indexes developer-relevant roots (home, Documents, Desktop, configured project roots) into a compact manifest: repo path, branch/status summary, package/build markers, recently modified files, and filesystem watch timestamps. Expose a read-only resolver used before shell planning (e.g. resolve 'owner project' or 'the repo with package.json and agentic-gadget') and return ranked candidates with exact paths and freshness; never guess a cwd silently when confidence is low.
- **owner gets:** The agent stops wasting several turns hunting for a project or running commands in the wrong directory. Saying “run the tests in my agent project” can become a fast, accurate action even after the Mac reboots or the project moves within the home folder.
- effort: Medium: initial scanner with macOS filesystem APIs, FSEvents/incremental refresh, manifest schema and TTL, local-agent read route, and planner integration. Keep indexing bounded to configured roots and ignore build/cache/node_modules contents.  ·  risk: Paths and repository names are sensitive metadata; keep the index local, redact secrets and file contents, enforce per-job access, and provide an exclude list. Stale manifests can misroute work, so every resolved candidate should include freshness and be verified with a cheap existence/git check immediately before execution.
- cost: No model cost for indexing or deterministic resolution; small local disk footprint (typically KB–MB) and low background CPU during changes. Reduces expensive planner turns and shell retries.  ·  latency: Sub-millisecond to tens of milliseconds for lookup; an occasional initial scan may take seconds but runs outside an owner interaction.
- security: Adds a searchable map of private paths, so encrypt or permission the manifest and avoid indexing secrets/content. It does not change unrestricted execution or introduce approval gates.
- depends on: A local-agent read-only route for workspace resolution; Mac filesystem watch/incremental scan implementation; Planner support for using a resolved cwd while displaying the selected path in the action receipt
