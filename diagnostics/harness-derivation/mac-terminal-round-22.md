## Capabilities it proposed

### "“Make the computer ready for this, then do it.”"
- **useful because:** Today a voice request can fail because the browser extension is offline, Safari has no attached tab, accessibility is unavailable, or the Mac agent is stale. This lets the owner state the goal once; the pendant reports the blocker, the Mac repairs only the local connection state it can repair, the browser reattaches the right private session, and the relay resumes the original job with a sourced completion receipt instead of asking the owner to repeat everything.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** Use the realtime tier only for the short spoken blocker/status exchange. Use the cheaper background planner for readiness diagnosis and the actual browser/Mac job; use deterministic health checks and typed reconnect actions before any model call.
- **latency:** Immediate spoken acknowledgement under 1 second; readiness checks 1–3 seconds; reconnect/reopen usually under 15 seconds. If a human login or permission is genuinely required, stop and tell the owner exactly which screen to visit, then resume when the heartbeat returns.
- **cost:** About $0.01–$0.05 per invocation when deterministic checks suffice; model cost dominates only ambiguous diagnosis and task planning. Heartbeats and receipts are negligible.
- **security:** The repair path may open apps or URLs but must not bypass authentication, change permissions, or move private page content to the relay. Keep session/tab identifiers and evidence local; relay only receives health state, blocker reason, and final redacted receipt. Require confirmation only for the owner's already-defined destructive actions (sending, deleting, buying), not for reversible readiness actions.
- **missing:** A readiness contract exposing local-agent, browser-extension, Safari-session, accessibility, and network health as typed dependencies; Safe idempotent reconnect/open/focus actions and a browser tab/session reattachment operation; The cross-surface execution lease and handoff journal proposed above; A pendant status-event protocol for blocker/recovered/completed states

### "“Use the pendant as the key for this task, and revoke it when I say stop.”"
- **useful because:** The owner could delegate one concrete goal to the Mac and authenticated browser without granting an invisible, indefinite trust relationship. A physical press or spoken confirmation on the worn pendant would bind the request to the owner, let the relay authorize only the named task and selected private session, and let the owner revoke it from anywhere—even if the Mac is unattended. This is not available today: the pendant starts conversations, but it is not an authenticated, task-scoped authority for the other nodes.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** Use deterministic cryptographic checks and typed capability evaluation for authorization; use the realtime model only to explain the request and status. No expensive model call is needed to mint, validate, expire, or revoke a token.
- **latency:** A local pendant confirmation and relay-issued grant should complete in under 2 seconds. Revocation should reach the Mac and browser within one heartbeat interval (target under 5 seconds), with the Mac refusing new work immediately when its lease expires.
- **cost:** Negligible API cost after implementation: small D1/token-state writes and heartbeat traffic dominate; model cost is limited to the spoken explanation. Hardware can use the existing button/LED initially; a production pendant should add a secure element or protected key storage, roughly $1–$3 BOM and negligible active power.
- **security:** Use asymmetric device identity, nonce-bound grants, audience (relay/Mac/browser), task hash, permitted operations, private-session identifier, expiry, and revocation epoch. Never transmit the owner's long-lived secret to the Mac or browser. Keep authenticated page data local; the relay carries opaque grants and receipts. A lost pendant requires server-side revocation; a compromised Mac must not mint grants. The grant authorizes execution of the specified task, not unrestricted shell access, while preserving the owner's deliberate maximum-capability policy inside that grant.
- **missing:** A hardware-backed pendant identity and signed button-confirmation protocol; Relay token minting, revocation, expiry, and replay protection stored durably in D1; Mac-agent and browser-bridge verification middleware that fences jobs on grant validity; A dashboard view showing active grants, scope, expiry, and immediate revoke, plus a pendant LED/error signal for revoked or expired authority


## Changes it proposed to its own stack

### `integration` — Add a cross-surface execution lease and handoff journal. Every voice goal becomes a durable intent envelope with owner-visible goalId, required capabilities (for example authenticated Safari versus public web), preferred executor, lease expiry, and a resumable step cursor. The relay publishes heartbeats for pendant reachability; the Mac agent publishes local-agent and browser-extension reachability; the browser bridge publishes tab/session leases. If the chosen executor disappears, the relay does not blindly retry: it records the exact unavailable dependency, keeps the envelope pending, and on reconnect resumes from the last completed receipt. For public work it may hand off to Browser Run; for private work it waits for Safari and says so on the pendant. Emit a one-line spoken status when a lease is lost or recovered, plus a dashboard timeline linking each handoff to existing action receipts.
- **owner gets:** A request such as “check this logged-in page and prepare a draft” will survive leaving the Mac, a sleeping laptop, or a temporarily offline extension without duplicate clicks or a mysterious failure. The owner hears whether it is waiting for their private browser, has moved to the server, or completed, and can resume from the pendant rather than starting over.
- effort: Medium-high: shared envelope schema and D1/local durable stores, heartbeat endpoints, lease expiry/reconciliation, Browser Run eligibility routing, browser tab reattachment, and pendant status events. Reuse existing action IDs, receipts, journal, and routing stats; add fault-injection tests for Mac sleep, extension disconnect, relay restart, and duplicate reconnect.  ·  risk: A stale lease could cause duplicate work or two executors to act concurrently; require idempotency-key ownership and fencing tokens, with reconciliation preferring the receipt already persisted. A handoff must never move authenticated page data to Browser Run; capability requirements must mark private-session-only. Recovery is to inspect the journal and cancel or resume the envelope.
- cost: Negligible when idle (heartbeat traffic and D1 writes); roughly 1–3 extra small model calls only when routing ambiguity or reconciliation needs semantic judgment. LTE status messages are tiny; no page contents leave the Mac unless the existing browser policy permits it.  ·  latency: No added latency for direct online execution beyond one local envelope write. Failure recovery adds seconds for heartbeat detection and extension reconnection; spoken status can be immediate from the relay.
- security: Improves auditability and prevents cross-executor replay, but introduces durable metadata about goals and session availability. Store only capability labels and opaque session/tab IDs in the relay; keep URLs and authenticated evidence on the Mac unless explicitly returned.
- depends on: The existing actionReceipts/idempotency implementation (chg-5fc73ce3); A resumable browser queue with progress polling (the unimplemented portion of chg-14accc01); A relay-to-Mac heartbeat/lease endpoint and a pendant status-event path; Explicit private-session-only versus public-web capability metadata

### `hardware` — Give the production pendant a deliberate privacy-presence control: a capacitive skin/contact or proximity sensor plus a long-press gesture, backed by a small secure-state flag. When the owner removes the pendant or long-presses, it emits a signed privacy event; the relay immediately suppresses spoken/private content, the Mac agent locks or obscures designated sensitive windows and pauses browser extraction, and the dashboard shows the fleet in privacy mode. Re-presence plus an explicit short press restores the prior task without discarding its cursor or receipts.
- **owner gets:** The owner could walk into a meeting, hand the Mac to someone, or simply take off the pendant and know that private browser findings and spoken answers stop everywhere—not just on the device. Returning does not force them to restart a long-running task.
- effort: New pendant enclosure/sensor and firmware event, secure event signing, relay fleet privacy state with replay protection, Mac window/privacy adapter, browser extraction pause/resume, and dashboard status. Design the event as fail-safe for content delivery but never as a destructive computer lock; test removal, LTE loss, relay restart, and accidental sensor contact.  ·  risk: A false removal could interrupt audio or pause work; debounce and require a configurable hold time, while preserving the task state. A lost or dead pendant must not leave the Mac permanently locked—privacy state expires conservatively and can be cleared in the dashboard or by a local explicit action. Window hiding is platform-specific and must not claim success without a receipt.
- cost: Roughly $2–$6 added BOM for a contact/proximity sensor, glue/enclosure changes, and a few milliwatts only while sensing; negligible API cost beyond one small fleet event and receipts per transition.  ·  latency: Local sensor-to-relay event target under 1 second when connected; on LTE loss, the pendant can immediately stop its own playback and mark the Mac state unknown. Restoration waits for authenticated presence and a heartbeat, typically a few seconds.
- security: Improves privacy by making absence a signed, fleet-wide signal. Do not send microphone audio or page contents with the event. Use a hardware-backed device key and monotonic event counter so an intercepted old 'present' event cannot undo privacy mode.
- depends on: A hardware-backed pendant identity and signed event channel; A relay-wide privacy-state protocol understood by Mac and browser nodes; Typed Mac/browser privacy actions with truthful receipts; A production enclosure with a reliable skin/contact or proximity sensor
