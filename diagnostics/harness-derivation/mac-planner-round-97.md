## Capabilities it proposed

### "“Do this when I’m free”: stage the browser/Mac work now, wait for a real interruption-safe gap, then carry it out and tell me on the pendant exactly what happened; let me cancel it with one button press."
- **useful because:** Long tasks would stop competing with meetings and active work. The pendant supplies the owner’s intent and cancellation; relay keeps the request alive; Calendar/Mail and Mac foreground state identify a safe gap; the browser bridge performs logged-in steps; receipts return to the pendant. This is more useful than either an immediate automation or a generic overnight job.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use the cheap background planner to decompose and poll the queued task; use realtime only for the initial voice exchange, spoken status, and cancellation. Use a stronger planner only when the browser task is ambiguous.
- **latency:** Acknowledge and stage within 2 seconds. Gap evaluation every 2–5 minutes (or on Calendar/foreground events); start within 30 seconds of a qualifying gap. Pendant cancellation should take under 1 second. No microphone needs to remain open.
- **cost:** About $0.002–$0.02 per request depending on decomposition; polling and gap checks should be deterministic or use a cheap model. Browser extraction and receipts dominate compute, not voice.
- **security:** Private calendar/mail snippets and authenticated page data leave the Mac only as compact task context and cited results. Store the queued plan encrypted with a TTL and bind browser work to a named tab/session. Do not submit irreversible browser actions unless the owner explicitly included submission; always retain before/after receipts. A physical pendant cancel must win over queued execution.
- **missing:** A durable deferred-job state machine with a next-eligible-time and cancellation token, distinct from the existing immediate jobs queue; A Mac context event/periodic sampler that reports Calendar busy/free, foreground app, idle/active state, and a freshness timestamp without Accessibility (AppleScript can cover Calendar/foreground where possible); Browser bridge online/reconnect and a queue consumer that can resume a named authenticated tab after a dropped link; Pendant firmware/server protocol for one-button cancel and concise queued/running/completed/error tones; A dashboard view for staged jobs, eligibility reason, TTL, and receipts

### "“I’m leaving the Mac—package this exactly so I can resume it from the pendant later.” Preserve the current Mac app/document state, authenticated browser tabs, unsent drafts, evidence, and next safe step; let me ask the pendant what is waiting and resume or abandon it when I return."
- **useful because:** Today a task is split across a browser session, Mac files/apps, and conversation history; walking away loses the working set or forces the owner to reconstruct it. A resumable handoff would make the pendant a true continuation of the Mac rather than a separate voice endpoint. It is specifically a state-preservation and restoration capability, not a generic background job or page watch.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use a cheap background model to summarize and validate the handoff capsule. Use realtime only when the owner asks the pendant for status or gives resume/abandon commands. Use a stronger model only to resolve conflicting state during restoration.
- **latency:** Create a capsule in under 5 seconds after the owner says to leave. Pendant status should answer in under 2 seconds. Restore should begin within 10 seconds of returning the Mac, with a clear partial-restore report.
- **cost:** Roughly $0.003–$0.02 per handoff, dominated by optional document/browser summarization. Deterministic file manifests, app identifiers, tab metadata, and action receipts should avoid model calls.
- **security:** Capsules may contain private file paths, authenticated tab identifiers, drafts, and snippets. Encrypt them, keep the default retention short, bind browser data to the original session, exclude passwords/tokens and full page bodies unless explicitly requested, and provide a physical pendant abandon/delete command. Restoration must never silently send, submit, or delete anything.
- **missing:** A cross-surface handoff-capsule schema with typed state, provenance, sensitivity labels, expiry, and a resumable step pointer; Mac snapshot/restore adapters for open documents, app context, unsaved draft locations, and the active project without requiring Accessibility for the basic tier; Browser extension export/import of tab/session identity and staged form state without exporting credentials; Relay storage and synchronization for encrypted capsules plus pendant-sized status summaries; A restoration reconciler that detects changed files/tabs and presents conflicts instead of replaying stale actions; A user-facing dashboard and pendant commands for list, resume, fork, abandon, and securely erase

### "“Before you use my Mac or logged-in browser, show me exactly what private data will leave each device, what will stay local, and let me say ‘redact that’ or ‘local only.’ Then proceed with the least-data version and give me a receipt afterward.”"
- **useful because:** The owner currently has maximum-control automation but no intelligible, per-task data boundary. This would let them use powerful cross-device actions without needing to understand prompts, tokens, browser sessions, or relay internals. It is a live privacy contract spanning the pendant, Mac, browser, and relay—not merely an execution confirmation.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use deterministic typed accounting for paths, snippets, tab origins, and payload sizes. Use a cheap model to phrase the summary for speech; realtime is only needed for the owner’s short redact/local-only replies.
- **latency:** Generate the data-flow preview in under 2 seconds for ordinary tasks. Apply redaction before any network submission. Final receipt should be available within 3 seconds of task completion.
- **cost:** Usually below $0.005 per task because accounting is deterministic; model cost is only the short spoken explanation. Storage cost is small for hashed receipts and policy decisions.
- **security:** The preview itself must not reveal the sensitive data it is describing. Use category labels, hashes, lengths, and destination names by default, with optional local-only reveal. Enforce the selected policy at every handoff, not just at planning time; fail closed if a new field appears. Keep the policy decision and receipt tamper-evident but avoid retaining raw content.
- **missing:** A typed end-to-end data-flow ledger attached to every plan, browser command, Mac action, and relay message; A preflight transformation layer that can remove fields, replace values with local summaries, or force a computation to remain on the Mac; A small pendant interaction protocol for redact, local-only, allow-once, and revoke-current-task; Browser and Mac adapters that report actual outbound fields rather than only intended actions; Tamper-evident receipts showing destinations, categories, byte counts, and policy decisions; A dashboard view that lets the owner inspect and revoke standing data policies

### "“If that multi-step task partly failed, figure out exactly what changed, what did not, and repair only the missing pieces—without repeating anything that already happened.”"
- **useful because:** Cross-surface work can succeed in one place and fail in another: a file may be created while a browser update times out, or a draft may be staged while its evidence fetch fails. Today the owner must manually inspect every surface and risks duplicate actions. A bounded reconciliation mode would make failures recoverable rather than opaque.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use deterministic receipt/state comparison first; use a cheap background model to classify discrepancies and generate a repair plan. Realtime is only for announcing the failure and accepting “repair,” “leave it,” or “discard.”
- **latency:** Report partial failure within 3 seconds of detection. Produce a repair plan within 10 seconds for ordinary jobs; execute only the missing idempotent steps after the owner’s command.
- **cost:** Low: receipts and hashes dominate, with roughly $0.002–$0.01 for discrepancy classification. Avoid re-running expensive browser extraction when prior evidence remains valid.
- **security:** Never infer success from a timeout. Preserve before/after evidence, use idempotency keys, and treat unknown outcomes as requiring reconciliation. Repair plans must exclude irreversible steps unless explicitly reissued. Keep sensitive evidence local or hashed in relay receipts.
- **missing:** A cross-surface transaction journal with per-step preconditions, postconditions, idempotency keys, and unknown-outcome status; State probes for Mac files/apps and browser pages that can verify postconditions without replaying actions; A reconciliation planner that computes the minimal missing-step set and detects conflicting external changes; A durable repair lease and retry budget shared by Mac and browser workers; Pendant and dashboard controls for inspect, repair, abandon, and export the failure receipt


## Changes it proposed to its own stack

### `integration` — Add an interruption-aware deferred-job coordinator between /plan, /execute, /jobs, /routines, Calendar/Mail context, and the browser queue. It should persist eligibility rules (free calendar window, foreground/idle constraints, quiet hours), wake on context events or bounded polling, lease one job at a time, honor pendant cancellation, and attach the existing per-action receipts and undo links. This is scheduling/orchestration, not a new unrestricted executor and not an approval gate.
- **owner gets:** The owner can say “when I’m free” once and trust that work will happen without interrupting a meeting or getting lost when the Mac/browser link briefly drops. They receive a clear staged/running/completed result rather than having to ask where the job went.
- effort: Medium-high: durable state schema and lease/retry worker, Mac context adapter, relay reconnect handling, and pendant cancel/status events; reuse existing jobs, routines, browser commands, and receipts.  ·  risk: A stale context could start during a newly begun meeting, or retries could duplicate browser steps. Mitigate with short-lived context freshness, idempotency keys, a single active lease, step-level receipts, and cancellation checked before every step. Recovery is cancel/undo where supported and an explicit failed receipt where it is not.
- cost: Low background model/API cost; mostly deterministic polling and D1/local state. One cheap planner call per staged job plus occasional extraction calls.  ·  latency: Immediate acknowledgement remains under 2 seconds; execution intentionally waits for the next eligible window. Context freshness adds at most one short poll interval.
- security: No new access beyond existing Calendar/Mail AppleScript and browser sessions. Keep private context local/relay-minimized, TTL queued plans, and redact snippets in dashboard/pendant speech.
- depends on: Browser extension must reconnect and expose reliable command acknowledgements (currently live status reports browser online=false with 5 pending commands).; Implement the newly granted bounded mac_read_sources/mac_readonly_inspect surfaces; today they are schemas with no implementation.; Owner must manually enable Accessibility/Screen Recording if foreground/UI evidence is required; current /ops/status reports both false.
