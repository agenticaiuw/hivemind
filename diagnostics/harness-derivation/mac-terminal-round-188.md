## Capabilities it proposed

### "“What actually needs my attention right now?” Give me a ranked, spoken answer that combines my live Mac work, authenticated Safari tabs, pending Mac actions, reminders/calendar, and anything the pendant has queued or failed; if I say “handle the first one,” carry it through the right surface and report the evidence, not just ‘done.’"
- **useful because:** This is the single most useful everyday behavior: it turns four disconnected surfaces into one trustworthy attention queue. It is intentionally an interrupt-time triage, not another scheduled briefing: it uses the current foreground app and browser sessions, distinguishes actionable blockers from bulk notifications, and can immediately hand the selected item to the browser or Mac while the pendant remains the conversational control.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → mac-vision → dashboard
- **model tier:** Use a cheap background ranker to normalize signals and cache a compact attention queue; use realtime only for the owner's spoken question and the final decision. Use the Mac planner/browser harness for execution and faculty-judgement/action for risk and evidence.
- **latency:** Initial spoken triage under 2 seconds from cached snapshots; refresh only stale sources in parallel within 5 seconds. Execution may take longer but must stream stage and evidence back to the pendant.
- **cost:** Typically one small background ranking call plus one realtime turn; roughly $0.01–$0.05 depending on how much browser/page text is refreshed. Browser extraction and Mac work dominate latency, not token generation.
- **security:** Authenticated page text and local window metadata leave the browser/Mac only to the relay/model when needed; redact secrets and page bodies from durable logs. Never claim completion without a URL/file/job receipt. A destructive or externally communicative action should be announced before execution, while ordinary navigation, reading, and local organization can follow the owner's maximum-access policy.
- **missing:** A cross-surface attention-item schema with source, urgency, freshness, evidence URL/path, and executable continuation token; A parallel snapshot collector for foreground Mac state, browser sessions/page watches, reminders/calendar, and pendant outbox/error state; A spoken continuation protocol that binds “the first one” to a stable item ID and returns receipts/evidence

### "“Continue the thing that failed.” Identify the last incomplete browser/Mac workflow from my pendant history, explain the exact step and side effect state in one sentence, resume only the unfinished steps, and read back the final evidence or the precise blocker."
- **useful because:** Failures today strand the owner between a spoken request and a half-completed browser or shell job. This gives the wearable a durable ‘pick up where we stopped’ affordance across a relay restart, Mac restart, or browser reconnect, without redoing a sent email, submitted form, or moved file.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → mac-vision → dashboard
- **model tier:** Use deterministic ledger/journal reconciliation and a cheap classifier to locate the unfinished step; use realtime only to explain the checkpoint and converse if ambiguity remains. Use mac-planner/browser harness to resume and faculty-action to emit receipts.
- **latency:** Checkpoint answer under 1.5 seconds from local journals; reconciliation and browser/Mac resume begin immediately and stream progress. A restart scan should complete within 10 seconds.
- **cost:** Usually a small classification call, under $0.01, with realtime only if the checkpoint is ambiguous. The expensive part is re-opening and inspecting browser/Mac state.
- **security:** Persist only action IDs, step hashes, redacted paths/URLs, and evidence digests—not shell environment or page secrets. Resume must be idempotent by action/step identity and explicitly avoid replaying completed external side effects. If state cannot be proven, stop and say what is unknown rather than retry blindly.
- **missing:** Boot-time reconciliation that marks orphaned processing jobs and closes or classifies open ledgers; A stable job-to-ledger-to-browser-command correlation ID and idempotency key on every step; A resume executor that verifies preState/postState and skips completed side effects; Pendant protocol for asking for and announcing a resume, including stale/offline handling

### "“Run this on my Mac even if the relay is down.” While the pendant and ESP32 bridge are USB-attached, accept the spoken/button request locally, execute the Mac action, and return audio plus truthful LED status; when disconnected, queue the exact request and replay it once on reconnect instead of pretending it ran."
- **useful because:** The hardware is physically on the owner's desk today but has not registered LTE. This makes the wearable useful immediately in the real offline/USB state: a dropped cloud link no longer turns the pendant into a dead microphone, and the owner gets an honest local-vs-queued distinction.
- **path:** pendant → mac-planner → relay-realtime → mac-vision → dashboard
- **model tier:** Use a small local/relay classifier for short commands and deterministic Mac actions; reserve realtime for spoken interpretation and responses. The pendant firmware only handles transport state, request IDs, durable outbox, and LED/audio truth—not language reasoning.
- **latency:** Button-to-local dispatch under 300 ms after USB framing; spoken result under 2 seconds for status/open/volume-type actions. Reconnect replay starts once and reports each state transition.
- **cost:** Near-zero incremental API cost while USB-local; one normal realtime turn only when cloud interpretation is needed. Main cost is firmware/bridge protocol and Mac local-agent integration.
- **security:** USB-local requests inherit the owner's deliberate full-control Mac policy, but every request needs a nonce/request ID and a visible local/queued state. Store only encrypted or redacted request metadata in the pendant outbox; never cache credentials or arbitrary command output. Reject stale replay IDs and require idempotency for retries.
- **missing:** A direct USB serial protocol between nRF9160, ESP32 audio bridge, and local-agent with framed request/response messages; Local speech/request routing when LTE/relay is unavailable, or a clearly defined subset of deterministic commands; Exactly-once replay integration between pendant_store OUTBOX and Mac job/action IDs; Audio reply path from local-agent through the ESP32 bridge to the pendant

### "“While you’re doing that, change the plan: skip the last email, save the draft, and tell me what remains.” Let me interrupt any running Mac/browser task from the pendant, have the agent checkpoint the current step, revise only the unfinished plan, and continue without restarting or duplicating completed side effects."
- **useful because:** Today a spoken request is effectively fire-and-forget once execution begins. The owner must wait, cancel ineffectively, or issue a second request that can conflict with the first. Mid-task steering makes the system feel like an assistant rather than a batch queue, especially for long browser workflows and shell jobs.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → mac-vision → dashboard
- **model tier:** Use a low-latency realtime turn only to capture the interruption and resolve its target; use a cheaper planner to recompute the remaining DAG from the checkpoint. Deterministic action execution and faculty-action enforce step identity and receipts.
- **latency:** Acknowledge the interruption on the pendant within 500 ms, checkpoint at the next safe boundary within 2 seconds, and present the revised remaining steps within 5 seconds. For a currently blocking process, use a real process signal rather than waiting for its original timeout.
- **cost:** One small realtime interruption turn and one planner call, usually $0.01–$0.05; most cost is browser/Mac execution, not the dialogue.
- **security:** The interrupt must bind to an unambiguous job ID and preserve an immutable record of what already happened. Never undo or resend a side effect merely because the plan changed. The owner’s stated maximum-access policy remains intact; the safety requirement is truthful checkpointing, not a new approval gate.
- **missing:** A pendant interrupt frame carrying active job ID, revision number, and replacement instruction; Preemptible Mac shell and computer-use execution with process-group signaling and safe step boundaries; A plan-revision protocol that preserves completed action IDs and invalidates only the unfinished suffix; Browser command cancellation/replacement and a streamed state model shared with Mac jobs

### "“What changed in the tabs I left open?” Compare authenticated Safari tabs with their last known snapshots, summarize only meaningful changes, identify which changes require action, and if I say “take care of it,” update the right page or create a local follow-up with a citation to the exact changed content."
- **useful because:** The owner loses time reopening the same tabs and reconstructing what changed. This turns the browser’s persistent sessions into longitudinal memory: it distinguishes a changed price/status/deadline from cosmetic page churn and connects a detected change to a concrete Mac action or spoken follow-up.
- **path:** pendant → relay-realtime → browser-extension → mac-planner → mac-vision → dashboard
- **model tier:** Use deterministic snapshot hashing and a cheap diff extractor first; invoke a stronger model only for semantic change ranking and spoken compression. Use browser automation for authenticated inspection and Mac actions for local follow-ups.
- **latency:** Return a cached change list in under 2 seconds; refresh stale tabs concurrently within 8 seconds. A selected follow-up should begin immediately and stream its citation and result.
- **cost:** Low: hashing/diffing is local; one small summarization call per changed tab batch, roughly $0.005–$0.03. Browser refreshes dominate latency.
- **security:** Keep page snapshots local to the browser/Mac where possible, persist only hashes, extracted changed spans, URL, timestamp, and redacted citations. Respect authenticated-session boundaries and never expose unrelated tab content in spoken output. Do not act on a changed page if the DOM no longer matches the cited evidence.
- **missing:** Versioned per-tab snapshots with semantic extraction and retention policy; A browser-side change detector that can compare authenticated content without exporting whole pages; A spoken diff/result format with stable tab IDs and exact citations; A bridge from a selected change to a Mac reminder, job, or browser action

### "“Get the latest invoice from the portal and put it in my Taxes folder.” Use my already-authenticated browser session to locate and download the correct document, verify its date/amount against the page, move it into the right local project folder, and read me the saved path and evidence."
- **useful because:** This crosses the boundary no single node can cross: the browser has the authenticated portal, while the Mac has the private filesystem and the pendant is the quickest way to ask. It removes a tedious, error-prone transfer without asking the owner to copy links, download files, or explain where they belong.
- **path:** pendant → relay-realtime → browser-extension → mac-planner → mac-vision → dashboard
- **model tier:** Use a cheap planner for folder and filename resolution; browser automation handles the authenticated download; Mac execution verifies file metadata/hash and performs the local move. Realtime only interprets the short request and reports the result.
- **latency:** Find and inspect the portal document within 10 seconds; download, verify, and file it within 30 seconds. Stream ‘found / downloading / verified / saved’ so silence is never mistaken for failure.
- **cost:** Usually one small planning call, about $0.01–$0.04, plus browser/Mac execution. File transfer itself has no model cost.
- **security:** The document crosses from an authenticated browser session to local storage and must not be sent to an unrelated cloud service. Keep content on the Mac/browser bridge, log only URL, metadata, checksum, and destination, and reject ambiguous invoices rather than choosing silently. Do not delete or overwrite an existing file without the owner’s explicit instruction.
- **missing:** A browser download handoff that returns a local artifact handle rather than page text or a cloud URL; A Mac-side artifact verifier/mover with checksum, collision, and quarantine handling; Cross-surface provenance linking the portal URL, extracted invoice metadata, downloaded file, and final path; A policy for authenticated document handling and redacted receipts


## Changes it proposed to its own stack

### `mac-harness` — Make run_shell execution produce a truthful, resumable command receipt without reducing FULL_CONTROL_MODE: invoke commands through a tracked child-process wrapper that records the original action and any rewrite, resolved cwd, sanitized environment fingerprint (never values), pid, start/finish/duration, numeric exit code/signal, bounded stdout/stderr digests, timeout/kill reason, and reversible/permanent classification. Pass the job abort signal to the child so cancellation can actually terminate it. On startup reconcile processing jobs and open ledgers: mark orphaned steps interrupted, close successful ledgers, and expose a verified resume plan keyed by jobId + actionId + step hash. - effort: Medium-to-large Mac-agent change across computerControl, executor, jobTracker, actionLedger, orchestrator startup, and the resume endpoint; add crash and timeout integration tests.  ·  risk: A wrapper can change shell signal and process-group semantics; roll out behind a receipt version, keep the current exec path as fallback, and compare results in dry-run tests. Never auto-resume a step whose post-state cannot be verified. Child process groups must be killed on timeout/cancel to avoid orphans.
- cost: No meaningful API cost; a few hundred bytes to a few KB of receipt storage per action, bounded by existing retention caps. Small CPU overhead for hashing and process tracking.  ·  latency: Negligible (<10 ms per command), with materially faster cancellation and recovery. Startup reconciliation adds at most a short scan of the existing capped stores.
- security: Improves auditability while preserving the owner's deliberate unrestricted capability. Environment values remain excluded; command and paths need redaction rules. Pid/exit metadata and hashes are safe to persist, but logs must not duplicate stdout containing secrets.
- depends on: A stable jobId-to-ledger correlation passed in planMeta; A real closeLedger call for every orchestrator execution path; Signal-aware shell spawn with process-group cleanup; A versioned resume/idempotency contract shared by Mac and browser actions
