## Changes it proposed to its own stack

### `integration` — Implement a cross-surface Action Lease + Attestation protocol. Relay creates a nonce-bound lease containing plan hash, target surface/session, allowed effect class, expiry, and approval transcript hash. Before every write, Mac/browser return signed (or HMAC-authenticated) preflight evidence: online heartbeat, entitlement state, target identity, and expected-state digest. Executor refuses on stale/mismatched evidence. After execution, faculty-perception submits independent postcondition evidence; receipts become succeeded, refused, or unknown rather than treating dispatch as success. Pendant announces the exact reason and offers retry only after readiness changes.
- **owner gets:** The owner can safely say “do it” while walking away and trust that the system either changed the intended thing or clearly said it could not. It prevents today's known failure mode where GUI actions are dispatched while Accessibility/Screen Recording are off and the browser is offline.
- effort: Medium-high: protocol schema and durable lease store, relay propagation, browser heartbeat/result changes, Mac preflight adapters, verifier library, dashboard states, and integration tests for stale leases, wrong tabs, offline devices, and ambiguous outcomes.  ·  risk: A false negative may refuse a legitimate action, which is recoverable by refreshing readiness and asking again. A false positive is more serious; mitigate with nonce binding, short TTLs, target hashes, independent read-back, and default unknown on missing proof. Roll out read-only/preflight telemetry first, then reversible writes, then irreversible actions behind explicit confirmation.
- cost: Small storage/compute overhead; deterministic checks dominate. Background reconciliation is cheap; no extra realtime model call beyond the owner's approval.  ·  latency: Adds ~100–500 ms for preflight and ~1–3 s for postcondition read-back, preferable to silent incorrect execution.
- security: Improves least privilege and replay resistance. Do not store raw approval audio or secrets; store transcript hash, lease metadata, and redacted evidence. HMAC keys must remain device-specific and rotate.
- depends on: Fresh readiness/entitlement state from faculty-perception; A relay-visible durable lease/approval record; Browser bridge heartbeat and typed result support; Mac action receipts (already implemented, but currently lack gates/preconditions)

### `hardware` — Add a low-power coin vibration motor (or piezo haptic actuator) with a dedicated GPIO driver and a simple three-pattern status vocabulary: short pulse = lease accepted, double pulse = blocked/refused, long pulse = verified completion. Keep the existing LED/audio semantics, expose patterns as a tiny device command so relay can push them even when audio is unavailable. Add a physical silent-mode toggle or firmware setting, rate limits, and watchdog-safe driver behavior.
- **owner gets:** The owner can know whether a remote action was accepted, blocked, or truly completed without looking at a screen or opening the microphone. That is especially valuable while the Mac/browser is offline or GUI entitlements are missing: the pendant gives an unmistakable refusal instead of leaving them guessing.
- effort: Low-medium hardware revision and firmware work: actuator, transistor/driver if needed, GPIO allocation, sealed enclosure test, and three short patterns. Validate comfort and accidental activation in daily wear; simulator can test event sequencing before hardware.  ·  risk: Vibration may disturb or drain the battery, or be mistaken for a notification. Make silent mode explicit, cap duty cycle, never use haptics for safety-critical claims without the server receipt, and fall back to LED/audio. Prototype board has provisional I/O, so confirm pin budget and power rail before layout.
- cost: Roughly $0.20–$2 actuator plus <$1 driver/passives per unit; tens of milliwatts only during brief pulses, near-zero idle. No model/API cost.  ·  latency: Local acknowledgement can be under 100 ms after relay command; completion pulse waits for verified postcondition.
- security: Haptic patterns must never imply success before cryptographically or otherwise authenticated receipt; commands need the same device/session binding as action leases. Silent mode state should not leak sensitive task content.
- depends on: Cross-surface Action Lease/Attestation protocol; Pendant firmware command channel and local event queue; Power-rail and enclosure validation for the eventual wearable design
