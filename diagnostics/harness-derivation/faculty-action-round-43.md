## Capabilities it proposed

### "“Do this, even if I walk away—finish it only while my approval is still valid, and tell me exactly what happened.”"
- **useful because:** Today an approved action can sit behind an offline browser bridge or an unready Mac and later fail ambiguously (or be retried without a fresh decision). This gives every action a short-lived, scope-limited lease: the pendant records the owner's approval, the relay durably queues and expires it, the Mac/browser executes only after a live preflight, and the pendant receives a completion/failure receipt. It is useful precisely because no one node can both capture physical approval, survive disconnection, reach private browser sessions, and perform the Mac action.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** deterministic for lease validation, preflight, queueing, expiry, and receipts; background model only to summarize a completed receipt; realtime only to phrase the spoken acknowledgement
- **latency:** Immediate pendant acknowledgement under 300 ms; preflight/dispatch under 2 s when Mac and browser are online; completion notification when the action finishes. No model call on the critical path.
- **cost:** Near-zero model cost for normal actions; roughly 1 background summarization call only when a multi-step receipt needs prose (about 1–3k tokens). Storage is a small D1/job record plus a compact pendant receipt.
- **security:** Lease must bind to exact action hash, target account/tab/session, allowed effects, expiry, and one-use nonce; relay stores no page secrets beyond existing job references. Never auto-renew. Destructive effects still require a second confirmation at commit. If the Mac loses readiness, browser goes offline, or proof is stale, expire and report—do not retry blindly. Dashboard must show pending leases and allow revocation.
- **missing:** A lease API shared by relay, Mac agent, and browser bridge (issue, claim, renew-for-progress only within original expiry, revoke, expire); Mac/browser preflight that returns structured readiness and blocks dispatch when Accessibility, Screen Recording, or browser polling is unavailable; Pendant firmware event/LED/audio UX for approve, executing, succeeded, failed, and expired states (offline queue for the approval); Receipt correlation from relay job ID through Mac/browser action receipts back to the pendant and dashboard; Explicit owner policy schema distinguishing reversible actions from commit points

### "“Handle this end to end, and if you get stuck, ask me one simple question on the pendant instead of making me start over.”"
- **useful because:** Today a long Mac/browser task either fails when it reaches an ambiguity or requires the owner to remain at the computer. This capability turns uncertainty into a resumable, physical conversation: the Mac or authenticated browser pauses at a typed checkpoint, the always-awake relay sends a concise choice or missing-value prompt to the pendant, the owner answers with a button/voice response from anywhere, and execution resumes from the exact checkpoint. It is not merely an approval prompt—the system can ask for a correction, choose among alternatives, or defer, while preserving the task's evidence and progress.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** Deterministic checkpoint protocol and response routing; background model to compress the question and choices; realtime only if the owner answers by voice and clarification is needed
- **latency:** Pendant prompt delivery within 2 seconds when connected; a response is acknowledged immediately and resumes the worker within 3 seconds. Paused tasks persist for days without consuming model calls.
- **cost:** One small background summarization call per ambiguity, roughly 500–1,500 tokens; no model cost while paused. D1 checkpoint and response records are tiny.
- **security:** Each prompt must show the requesting task, target account/site, and consequence in plain language. Responses bind to a nonce and checkpoint hash, expire after a configurable period, and cannot authorize a new action outside the presented choices. Sensitive values should be entered only through a secure pendant path and never spoken back. Dashboard must expose the full pause/resume audit trail.
- **missing:** A durable checkpoint protocol in the Mac job runner and browser bridge with serializable state, evidence capsule, and resumability contract; Relay push/poll delivery for pending questions plus nonce-bound responses from the pendant; A compact pendant interaction vocabulary for choice, correction, defer, and cancel, including offline response spooling; Planner support for declaring safe checkpoints and formulating bounded questions instead of failing on ambiguity; Dashboard UI for paused tasks, unanswered questions, expiry, and manual recovery


## Changes it proposed to its own stack

### `relay` — Add an Action Lease Coordinator between judgement and all execution surfaces. Persist a lease record keyed by jobId/actionHash with owner approval timestamp, exact action scope, target surface/session, expiry (default 10 minutes), one-use nonce, risk class, and state (issued/claimed/running/committed/succeeded/failed/expired/revoked). Require Mac and browser workers to claim with a readiness attestation; reject claims when the bridge is offline or Mac permissions are not ready. Stream state transitions to the pendant and dashboard, and make every transition idempotent.
- **owner gets:** An action they approved will either finish predictably or stop safely with a clear reason instead of timing out after 45 seconds, sitting in a stale browser queue, or being retried after circumstances changed.
- effort: Medium: D1 schema/API and relay tests; adapters in local-agent job runner and browser bridge; pendant notification messages; dashboard timeline. Add fault-injection tests for disconnects, duplicate claims, expired leases, and commit/retry races.  ·  risk: A too-short lease could interrupt a legitimate long task; use progress heartbeats without extending the absolute deadline. A lost completion packet could make the pendant say 'unknown'; receipts remain queryable and the relay replays terminal state. Never treat a worker heartbeat as owner reapproval.
- cost: No recurring model cost; a few D1 writes per action and tiny telemetry payloads. Optional background summarization remains bounded.  ·  latency: Adds one deterministic claim/preflight round (typically <200 ms locally, <1 s relay round trip) but avoids long doomed execution attempts.
- security: Improves safety by binding execution to the approved action hash, target session, nonce, and deadline; lease records must avoid storing secrets and support owner revocation.
- depends on: Structured readiness endpoint from Mac agent (Accessibility, Screen Recording, browser bridge polling, and target session); Shared action/receipt schema across Mac, browser, relay, and pendant; Pendant firmware notification and offline approval event support

### `integration` — Introduce a resumable Human-in-the-loop Checkpoint protocol spanning local-agent jobs, browser sessions, relay, and pendant. A worker can emit a checkpoint containing a stable job/action hash, bounded question, typed choices or a redacted input schema, evidence capsule, continuation token, deadline, and safe rollback point. Relay persists and delivers it; pendant returns a nonce-bound response; the worker resumes only if the checkpoint hash and target session still match. Add crash recovery, duplicate-response handling, expiry, cancellation, and a dashboard timeline.
- **owner gets:** They can leave the Mac during a difficult task and answer only the one decision that genuinely requires them, rather than babysitting the screen or restarting the entire workflow after a harmless ambiguity.
- effort: High: define a serializable continuation contract for shell, GUI, and browser steps; implement relay storage and pendant transport; add resume adapters and fault-injection tests for worker/relay/device disconnects.  ·  risk: Some actions cannot safely resume after a crash; those checkpoints must be marked non-resumable and restart from a verified boundary. A malformed or stale response must fail closed. Never expose raw passwords or page contents in a prompt unless explicitly classified and encrypted.
- cost: No recurring cost while waiting; one compact background-model call per checkpoint to phrase choices, plus small durable storage. Reusing evidence capsules avoids resending full context.  ·  latency: Adds sub-second deterministic checkpoint persistence and response validation; resumption depends on the worker's next preflight, typically a few seconds.
- security: Responses are scoped to a checkpoint nonce, action hash, target browser session, and expiry. The relay stores redacted prompt metadata and encrypted sensitive input only when required; every pause, response, and resume is auditable.
- depends on: A common typed job/evidence schema shared by Mac and browser workers; Pendant transport supporting push notifications and compact response events; Relay durable state and replay of pending checkpoints; Worker-specific safe-boundary and continuation adapters
