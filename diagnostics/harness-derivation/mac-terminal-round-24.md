## Capabilities it proposed

### "If a task spans my Mac and logged-in browser, keep it alive through disconnects: retry when the right device returns, never duplicate a completed step, and tell me exactly what finished and what still needs me."
- **useful because:** Today the live agent can leave browser commands pending while the bridge is offline, and Mac readiness can be false when Accessibility or Screen Recording is missing. The owner should not have to remember which steps ran or restart a workflow—especially for a long task started from the pendant.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** background for workflow bookkeeping, retries, reconciliation, and spoken summaries; realtime only for the initial request and urgent status questions
- **latency:** Acknowledge on the pendant in under 2 seconds; resume within 30 seconds of a heartbeat returning; status summary within 5 seconds of each retry outcome.
- **cost:** Usually <$0.01 per workflow: deterministic state transitions and receipt reconciliation dominate; background model only for ambiguous recovery or the final concise summary.
- **security:** Private URLs, page extracts, and local command receipts remain on the Mac/relay according to existing retention. Never resend a browser form submission or shell mutation solely because a network response was lost; require an explicit owner confirmation for an actually irreversible step, while preserving the owner's no-gate policy for ordinary Mac execution.
- **missing:** A durable cross-node workflow/DAG state store shared by relay and Mac, with step idempotency keys and dependency leases; A reconciliation probe that distinguishes 'not started', 'completed but reply lost', and 'unknown side effect' for browser and shell actions; Heartbeat-triggered retry policy with exponential backoff, quiet hours, and a pendant/dashboard explanation of degraded state; A single completion receipt that links Mac job receipts, browser command receipts, and relay delivery attempts

### "Before I rely on you, tell me whether you actually checked everything relevant across my Mac, logged-in browser, and relay-held tasks—and if you say nothing needs me, show me what was checked, what was unreachable, and how fresh each result is."
- **useful because:** An ordinary briefing can sound complete even when the browser bridge is offline or a permission is missing. The owner needs an honest, coverage-aware absence claim rather than false reassurance, especially when delegating work while away from the Mac.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** deterministic coverage computation and freshness checks first; background model only to compress the evidence into a short spoken explanation; realtime only for follow-up questions
- **latency:** Return a coverage verdict in under 3 seconds from cached observations; refresh reachable surfaces within 20 seconds; explicitly label any surface that could not be checked.
- **cost:** Typically <$0.005 per check set: endpoint reads and cached fingerprints dominate, with minimal background summarization only when many sources are present.
- **security:** The coverage report itself reveals which private accounts, tabs, files, or jobs exist. Keep it owner-scoped, speak only names and statuses by default, and require an explicit request to reveal snippets or URLs. Never claim a negative result for an unobserved surface.
- **missing:** A typed inventory of checkable sources and their authority/coverage scope across Mac, browser sessions, relay jobs, and pendant queues; Freshness leases and explicit unreachable/stale/error states rather than treating empty results as success; A deterministic completeness verdict with per-source evidence IDs and a dashboard drill-down; A spoken response format that distinguishes 'checked and clear' from 'not checked' and 'checked with low confidence'


## Changes it proposed to its own stack

### `integration` — Add a cross-node execution ledger and recovery coordinator above the existing Mac job store and browser command queue. Each workflow is a versioned DAG whose steps carry an idempotency key, device/session affinity, precondition fingerprint, receipt links, retry budget, and an explicit outcome enum (succeeded, failed-before-effect, failed-after-effect, or unknown). The relay owns the durable ledger and leases; Mac and browser agents atomically claim steps, report heartbeats, and expose a read-only reconciliation operation. On reconnect, reconcile unknown steps from local receipts/page state before retrying. Render one compact pendant/dashboard timeline rather than separate Mac and browser histories.
- **owner gets:** A lost connection will no longer force the owner to guess whether an order lookup, file operation, or draft was already done. Long tasks can resume safely across sleep, browser restarts, and relay reconnects without duplicate side effects.
- effort: Medium-high: new relay D1 schema and coordinator, adapters in jobTracker/browser bridge, reconciliation handlers, and dashboard timeline; staged rollout can start with read-only workflows and simulated disconnect tests.  ·  risk: A faulty reconciliation rule could classify an effect incorrectly or retry a non-idempotent action. Default unknown to paused, preserve all raw receipts, and provide operator replay/repair tooling; do not delete existing job history.
- cost: Negligible steady-state storage and request overhead; roughly one small D1 write per transition/heartbeat. Background model cost only for ambiguous human-readable recovery summaries.  ·  latency: Adds tens of milliseconds to normal step dispatch; reconnect recovery is bounded by heartbeat plus one reconciliation round, typically under 30 seconds.
- security: Ledger contains sensitive URLs, snippets, and local paths, so encrypt sensitive fields, scope records to the paired owner, and apply existing audio/job retention. It must not become a new channel for raw page contents.
- depends on: Existing Mac action receipts and browser command IDs must be exposed as stable references; Relay↔Mac authentication and pairing already present; A typed, read-only reconciliation endpoint on both Mac and browser surfaces; Dashboard and pendant status rendering for paused/unknown steps

### `mac-harness` — Add a local execution preflight and result normalizer that runs before arbitrary shell actions without blocking them: resolve the project/workspace from known roots and recent successful cwd values, snapshot PATH/tool availability and relevant app permissions, classify the command's expected output shape, and attach exit code, signal, duration, cwd, redacted environment/tool versions, stdout/stderr byte counts plus bounded tail, and an undoability hint to the existing receipt. For failures, automatically suggest one deterministic retry (for example corrected cwd, missing executable path, or expired GUI session) and record whether the retry was attempted.
- **owner gets:** The agent will stop wasting turns hunting for the project or asking the same status question, and spoken results will say whether a command failed before doing anything, ran successfully with noisy output, or needs a Mac permission/session repair.
- effort: Medium: a preflight module, receipt schema extension, workspace index, and tests against the already-proven pmset/scutil/df/git/osascript commands.  ·  risk: Capturing environment or output tails could leak secrets; redact known token/password patterns, never persist full environment, cap output, and let the owner disable command-output retention. A bad automatic retry could repeat a mutation, so only retry commands classified as read-only or explicitly idempotent.
- cost: No model cost; one local process and small receipt metadata per action. Saves planner tokens and repeated failed commands.  ·  latency: Usually 10–100 ms for cached facts; skip expensive scans when a matching cwd/tool fingerprint is fresh.
- security: Improves auditability without adding gates or narrowing FULL_CONTROL_MODE. Store receipts locally, send only summaries to relay, and preserve existing unrestricted execution policy.
- depends on: Stable action receipts and journal endpoints (now present); A local workspace/cwd index with bounded retention; Output redaction and receipt-size limits

### `integration` — Create an owner-visible causal provenance graph for every multi-surface request. At planning time, record the request version, selected surfaces, facts actually used (with freshness and confidence), routing decisions, model tier, generated action arguments, device/session identity, data sent off-device, and each resulting receipt. At completion, materialize a signed, compact explanation with links between cause and effect, including discarded alternatives and the exact uncertainty that caused a pause or fallback. Expose it as a pendant-sized spoken answer and an expandable Mac dashboard view; allow the owner to correct a fact or revoke a provenance edge without deleting the underlying execution receipt.
- **owner gets:** When the pendant says something was done—or failed—the owner can ask “why did you use Safari instead of the Mac, what did you rely on, and what left my computer?” and receive a trustworthy answer grounded in the actual run, not a reconstructed model story. This makes a multi-device personal agent understandable enough to delegate consequential work to it.
- effort: High: define a versioned provenance schema, instrument planner/routing/relay/Mac/browser boundaries, sign and retain append-only edges, build redaction and sensitivity handling, and add spoken plus dashboard renderers.  ·  risk: Provenance can expose private page text, file paths, or credentials and can become misleading if agents write free-form explanations. Store references and hashes by default, redact sensitive values, separate observed facts from inferences, and generate explanations only from recorded edges. Preserve raw receipts if the owner edits or revokes a displayed edge.
- cost: Small local/relay storage and serialization overhead per step; no extra model call for the graph. A cheap background model may summarize a large graph, while realtime only reads a precomputed short explanation.  ·  latency: Negligible dispatch overhead (structured edge writes); explanation retrieval should be sub-second for normal jobs and under a few seconds for long workflows.
- security: Adds an auditable record of data movement, but increases the sensitivity of retained metadata. Encrypt the graph, scope it to the paired owner, apply field-level TTLs, and never include raw secrets in relay payloads or speech.
- depends on: Stable cross-surface request and step IDs across relay, Mac, and browser; Existing Mac job/action receipts and browser command receipts; A durable owner-scoped store with append-only integrity checks; A dashboard/pendant renderer that distinguishes observed evidence from inferred explanation
