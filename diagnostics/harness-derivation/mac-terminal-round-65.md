## Capabilities it proposed

### "“Keep working on this across my Mac and logged-in browser even if I walk away or one device disconnects; resume from the last safe checkpoint and tell me exactly what finished, what failed, and what I should do next.”"
- **useful because:** Today a pendant request can span relay, Mac shell, and private browser tabs, but a disconnect or partial failure leaves the owner reconstructing state. A durable cross-surface run would checkpoint each completed step with evidence, retry only idempotent work, reattach to the right browser session, and deliver a concise spoken completion/failure report when the pendant reconnects. This is more than a Mac job runner: it coordinates the wearable's conversational intent, the always-awake relay, the Mac's unrestricted execution, and browser-only authenticated reach.
- **path:** pendant → relay → mac-planner → mac-terminal → browser-extension → unified
- **model tier:** Use the realtime tier only to capture the goal and speak the final status. Run planning, checkpoint reconciliation, extraction, and retry classification on a cheaper background model; use the expensive tier only when evidence conflicts or the recovery plan is ambiguous.
- **latency:** Acknowledge in under 2 seconds, then execute asynchronously. Reconnect status should be available within 1–2 seconds; ordinary step retries should add under 5 seconds, with no need to keep the voice session open.
- **cost:** Typically <$0.01 per short run on a background model; dominant costs are authenticated browser calls and any generated audio, not Mac command execution. Realtime usage is limited to the initial and final utterances.
- **security:** Private page text and Mac command output may leave the device through the relay; retain only bounded evidence snippets and hashes, redact secrets, and bind checkpoints to the owner/session. Never silently repeat non-idempotent browser submissions or destructive shell commands; mark them manual-stop even though the owner's current policy intentionally permits unrestricted execution.
- **missing:** A single durable run/checkpoint schema spanning Mac jobs, browser command IDs, relay pipeline IDs, and pendant delivery receipts; Idempotency and retry classification for shell and browser steps, with explicit non-repeatable/manual-stop states; Reconnect delivery that summarizes evidence rather than replaying the whole transcript; A coordinator that can reattach an authenticated browser session after extension heartbeat recovery

### "“Pause what I’m doing here and give me this exact work state back later, wherever I am.” The pendant should snapshot my active Mac window, browser tabs and selections, unsaved text, relevant terminal state, and the spoken reason; later I can say “resume the paused thread” and have the Mac and authenticated browser restore the right state before the pendant reminds me where I left off."
- **useful because:** This is not a scheduled briefing or a background job: it preserves the owner's partially completed, human-in-the-loop work when they have to leave suddenly. Today the system can observe apps and run individual actions, but it cannot create a coherent, resumable cognitive checkpoint across a GUI, terminal, private browser session, and the pendant's conversation. The owner would stop losing half-finished investigations and drafts.
- **path:** pendant → relay-realtime → mac-planner → mac-vision → browser-extension → unified
- **model tier:** Use the realtime model only to capture the pause/resume utterance and speak the short orientation. Use a cheaper background model to normalize window/tab metadata, summarize visible text and unsaved drafts, and rank which checkpoint is the requested thread. Use the vision model only for GUI state that accessibility metadata cannot represent.
- **latency:** Pause acknowledgement under 2 seconds; checkpoint creation in under 10 seconds for a typical 5–10 window session. Resume should restore the selected Mac/browser state within 5 seconds and speak a 15-second orientation, with deeper summarization deferred.
- **cost:** Usually under $0.02 per checkpoint, dominated by one or two screenshots/vision calls and summarization; metadata capture and local state hashing are effectively free. No audio generation is needed beyond the short spoken orientation.
- **security:** The checkpoint may contain private browser URLs, authenticated page snippets, draft text, and terminal paths. Store encrypted, redact tokens/password fields, keep screenshots opt-in and short-lived, bind records to the owner's device identity, and provide deletion. Never submit a draft or alter a page while restoring; restore focus and scroll/selection only, and clearly say when exact restoration was impossible.
- **missing:** A durable cross-surface checkpoint object with title, owner-provided reason, app/window identities, browser session/tab IDs, selection/scroll anchors, terminal cwd and recent command metadata, evidence snippets, sensitivity labels, and expiry; Mac APIs to capture and restore window geometry, focus, selection, and unsaved text without relying solely on screenshots; Browser-extension commands for tab-group snapshot and restoration with authenticated session affinity; Pendant/relay commands to list, expire, and resume named checkpoints with a compact spoken orientation; A local-first encrypted store and conflict handling when the Mac or browser is offline

### "“While I’m concentrating, decide which things are worth interrupting me for across my Mac and logged-in browser, and hold everything else until I’m free.” The pendant should let me change the mode with one button press or a short phrase, announce only genuinely urgent items, and give me a compact deferred queue when I switch modes."
- **useful because:** The current system can generate briefings and execute tasks, but it does not arbitrate attention in real time across local Mac notifications, browser events, relay jobs, and the owner's pendant state. The owner would get fewer disruptive alerts without missing a time-sensitive private-site change, failed long-running job, or direct human message. This requires the wearable's immediate presence, the Mac's foreground/app signals, the browser's authenticated reach, and the relay's always-on queue—not any one node alone.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → faculty-perception → faculty-judgement
- **model tier:** Use deterministic local rules for mode, quiet hours, deadlines, and known contacts; use a cheap background model to classify ambiguous events and deduplicate the deferred queue. Reserve realtime for the actual interruption and the owner's mode-change conversation.
- **latency:** Event classification under 500 ms for local/browser events; urgent pendant notification under 2 seconds. Deferred digest can be generated asynchronously in under a minute when requested.
- **cost:** Near-zero for rule-matched events; roughly <$0.005 for an ambiguous batch classification. The main cost is not tokens but durable event retention and browser polling.
- **security:** Notification titles and private-page snippets are sensitive. Classify locally where possible, send only minimal redacted event capsules to the relay, encrypt the queue, and let the owner define VIPs, deadline thresholds, and sites that may never be spoken aloud. Never infer urgency from message content without recording the source and confidence.
- **missing:** A shared event envelope for Mac notifications, browser page-watch changes, relay job failures, and pendant state, with source, urgency, deadline, confidence, and sensitivity; A durable attention policy and deferred queue with deduplication, quiet modes, escalation, expiry, and spoken/non-spoken channel preferences; Mac notification observation and controlled notification-mode integration; Browser event forwarding from authenticated sessions without exposing full page contents; Pendant firmware support for a local mode toggle and queued-alert indicator that works during a dropped relay link


## Changes it proposed to its own stack

### `mac-harness` — Add a structured shell execution ledger without changing FULL_CONTROL_MODE or adding gates: before execution record a normalized command fingerprint, cwd, timeout, initiating run/step id, and declared intent; during execution capture start/end timestamps, exit signal/code, bounded stdout/stderr previews with secret redaction, child-process summary, and resource usage; after execution attach undoability from undo.js, evidence-capsule ids, retry classification, and a machine-readable failure diagnosis. Expose it through /journal and /journal/:jobId with filters for command fingerprint, exit class, and run id, and let the planner request a retry using the receipt rather than re-planning from scratch.
- **owner gets:** When an unattended command fails or partially succeeds, the owner should hear “the build timed out after spawning X; no files changed” rather than a vague failure or an unsafe blind retry. It also makes the Mac tier faster: repeated status checks can reuse recent receipts, and the planner can distinguish a transient network failure from a permanent command error. This improves trust and recovery while preserving the owner's deliberate maximum-access policy.
- effort: Medium: instrument computerControl.runShell/executor and jobTracker, add bounded redaction and child/resource sampling, extend journal serialization and planner input, then test timeout, signal, huge output, and nonzero-exit cases.  ·  risk: Output could contain credentials or sensitive file contents; redact common token patterns, cap bytes, and store hashes instead of full output. Process sampling adds small overhead. If ledger persistence fails, execution must still proceed and return a minimal in-memory receipt. Never let observability become a blocking authorization gate.
- cost: No model API cost; modest local disk growth from bounded receipts (target <16 KB per shell action) and negligible CPU for timestamps/process sampling.  ·  latency: About 10–50 ms per action plus any optional child-process sampling; zero extra network round trips for the normal path.
- security: Improves auditability but creates a sensitive local record. Encrypt or permission-protect the ledger, redact secrets before persistence, and keep raw stdout ephemeral. No change to unrestricted command/network authority.
- depends on: Existing action receipts and /journal routes; A shared run/step identifier from the cross-surface coordinator; A small planner contract for retry classification and evidence-capsule references
