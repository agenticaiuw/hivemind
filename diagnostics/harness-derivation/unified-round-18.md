## Capabilities it proposed

### "When something goes wrong, let me press and hold the pendant to capture an incident packet; when my Mac is reachable, turn it into a sourced bug report draft with the audio, UART/pipeline evidence, timestamps, and a one-sentence spoken receipt—never submit it without approval."
- **useful because:** The owner already wants the pendant to file its own bug reports, but a wearable can capture the moment while the Mac is unavailable. This joins offline SD buffering, LTE-M relay delivery, Mac workspace evidence, and a reviewable draft instead of losing the failure or forcing the owner to reconstruct it later.
- **path:** pendant → relay → mac-planner → mac-terminal → dashboard
- **model tier:** Use firmware for button timing, ring-buffer capture, checksums, and offline queue; relay/background worker for authenticated upload and deduplication; mac-terminal for bounded read-only UART/log and pipeline collection; mac-planner for low-cost incident summarization and draft generation; realtime only for the immediate spoken acknowledgment.
- **latency:** Immediate local haptic/voice acknowledgment under 300 ms; upload opportunistically after link recovery; Mac draft within 60 s of the Mac becoming reachable. The owner reviews and explicitly approves any issue submission.
- **cost:** About $0.01–$0.05 per incident depending on audio duration and summarization; storage and bandwidth dominate, not the short acknowledgment. Keep a configurable 30–90 s compressed audio window and delete after the draft is accepted or expires.
- **security:** Incident audio and local logs may contain private speech, tokens, or personal data. Encrypt the SD packet and relay object, redact secrets from logs, bind packets to the paired device, show exactly which files/snippets leave the pendant, and require confirmation before creating an external ticket or sending anything. Recovery is an idempotent packet ID and a local retained copy until the owner chooses deletion.
- **missing:** A firmware long-press/incident capture event and bounded pre-roll audio ring buffer; A relay endpoint for resumable encrypted incident packets with idempotency and retention controls; A narrowly scoped read-only Mac workspace/UART/log collector (not arbitrary shell); A draft review surface that displays evidence provenance and an approve/send checkpoint; A readiness gate and delivery receipt so the pendant does not claim the report exists while the Mac agent is not ready

### "When I say “save my place,” capture what I’m doing across the pendant, Mac, and logged-in browser; later, when I say “resume,” restore the relevant tabs and workspace, summarize what changed while I was away, and put me at the next safe step without submitting or sending anything."
- **useful because:** Today the owner can lose the thread between a wearable interruption, a Mac workspace, and private browser tabs. This would create a durable, privacy-aware handoff that survives a dropped connection and returns them to work rather than merely reporting device status or replaying a generic briefing.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use a cheap background model to normalize the checkpoint and compute changes; use the realtime model only for the spoken command and concise receipt. Mac and browser agents perform deterministic capture/restoration, while the relay stores the encrypted checkpoint and queues it offline.
- **latency:** A checkpoint receipt under 2 seconds when connected, with an offline pendant acknowledgment under 300 ms. Resume should restore and present a reviewable plan within 10 seconds; never wait on a long model call before acknowledging capture.
- **cost:** Roughly $0.01–$0.04 per resume, dominated by summarizing changed page/workspace state. Checkpoints themselves are small structured metadata and should not duplicate full page contents or audio.
- **security:** Private URLs, tab titles, drafts, and focused-app state are sensitive. Encrypt checkpoints, bind them to the paired device, store only hashes and minimal snippets by default, expire them automatically, and require confirmation before any restoration that could overwrite unsaved work. Browser actions must be provenance-labeled and reversible; no email, form, purchase, or deletion may be performed as part of resume.
- **missing:** A cross-surface checkpoint schema with stable tab/session identifiers, Mac workspace references, pendant event IDs, timestamps, and sensitivity labels; A relay-backed encrypted checkpoint store with offline queueing, TTL, conflict versions, and deduplicated diffs; Browser session reattachment and a restore transaction that previews tabs/actions before applying them; A Mac workspace snapshot/restore adapter that can detect unsaved changes and refuse destructive replacement; A change summarizer that compares checkpoint state with current state using hashes and small evidence snippets; A pendant command/status protocol for save, queued, synced, conflict, and resumed states


## Changes it proposed to its own stack

### `integration` — Introduce an end-to-end audio capability contract and calibration handshake. At session start, the pendant advertises capture/playback rates, frame sizes, codec mode, and I2S clock; the relay records those parameters in each pipeline job; the Mac TTS bridge selects an explicit target; and the ESP32 bridge is changed from its hard-coded 44.1 kHz SBC path to consume a negotiated 24 kHz mono stream (or perform one measured, declared resample). Add a loopback acceptance test that injects a swept tone and speech fixture, measures sample-rate drift, underruns, clipped samples, latency, and packet loss across nRF9160 → LTE-M → relay → Mac → relay → nRF9160 → ESP32, then refuses to mark a run complete if any stage silently changes rate.
- **owner gets:** Speech will sound consistent and intelligible rather than being labeled 24 kHz in the cloud while the physical bridge silently converts through 31.25/44.1 kHz and can starve its Bluetooth buffer. The owner gets a trustworthy spoken receipt that the audio actually reached the pendant, not merely that a server generated PCM.
- effort: Medium-high: protocol metadata, relay schema, Mac renderer/validator, ESP32 clock/resampler path, and a hardware-in-loop fixture. Implement in phases: metadata and telemetry first, then bridge clocking, then automated acceptance tests.  ·  risk: A clock or codec change could cause silence, pitch shifts, or increased CPU use. Preserve the current 31.25 kHz fallback behind a negotiated legacy mode, gate rollout by device capability, and retain raw test artifacts for rollback. The nRF9160 has only 211,608 B app RAM and Opus already consumes roughly 87% of one core encode+decode, so avoid a second large buffer or simultaneous high-quality resampler.
- cost: Negligible per-call API cost; modest engineering/test hardware cost (USB audio fixture or tone source, roughly $30–$100). ESP32 CPU/RAM impact should be bounded by a streaming fixed-point resampler and <44 kB buffering, with no new cloud audio retention beyond existing policy.  ·  latency: Adds only a small session-start negotiation (<100 ms). A single declared resample may add <10 ms; eliminating buffer starvation should reduce worst-case stalls.
- security: Capability metadata is non-sensitive. Test packets and incident fixtures must be labeled synthetic; production audio remains encrypted and subject to the owner's short-retention policy.
- depends on: A bounded audio-pipeline validation endpoint or CI/hardware-in-loop runner; ESP32 firmware change to remove the hard-coded 44.1 kHz SBC assumption; A documented 24 kHz acceptance target and fallback negotiation semantics; Mac agent readiness (Accessibility/Screen Recording are currently missing, though audio rendering itself is evidenced)

### `interaction` — Add a cross-surface physical approval channel: when Mac/browser prepares an irreversible action, the dashboard displays the exact before/after diff and provenance, while the relay sends a short spoken summary and unique challenge to the pendant. A deliberate button sequence (long press, then confirm press) bound to that challenge approves only that transaction; timeout, mismatch, link loss, or a different pending action cancels it. The pendant must report approved/cancelled/expired locally and the relay must enforce single-use idempotency.
- **owner gets:** The owner can safely approve a prepared browser or Mac action without finding the right window or giving a vague spoken “yes” in a noisy environment. They get a tangible, context-bound confirmation method while retaining a visible review on the Mac.
- effort: Medium: relay challenge state machine, pendant button UX/firmware, Mac/browser diff display, and audit receipts. Add simulator tests for replay, timeout, reconnect, and two simultaneous pending actions.  ·  risk: Accidental presses or an attacker with relay access could trigger an action. Require a spoken challenge fragment plus the physical sequence for high-risk operations, bind approval to device/session/action hash, expire quickly, and default to cancellation. Existing actions remain available as rollback paths.
- cost: Negligible API cost; small persistent challenge records and audit metadata. No new audio retention is required beyond the short spoken challenge.  ·  latency: Challenge delivery should be under 1 second when connected; confirmation can be queued during a brief link loss but must not execute until the relay verifies freshness and action identity.
- security: Improves authorization by adding possession of the paired pendant, but increases consequence of pendant theft. Add pairing revocation, PIN escalation for sensitive actions, replay protection, and an owner-visible approval history.
- depends on: A typed action identity and provenance record shared by Mac, browser, relay, and dashboard; Relay support for expiring single-use challenges and idempotent execution; A firmware button event protocol with distinct long-press/confirm semantics; A Mac/browser review surface that can render exact before/after diffs


## What it asked for

### `s1-6qry` (skill) — incident_capture_and_delivery_receipt
- does: On a configurable long press, freeze a short pre-roll plus post-roll microphone window, attach monotonic time, firmware version, link state, battery, and recent fault counters, encrypt and checksum the packet, and queue it on microSD only if LTE-M upload is unavailable. On eventual delivery, accept a signed receipt from the relay and expose a local status event so the owner hears whether it was captured, uploaded, or awaiting Mac-side drafting.
- must be on-device because: The pre-roll microphone data, button edge, link transition, and SD failure buffer exist only on the pendant; this must work offline and survive a dropped LTE-M session. Server code cannot recover audio that was never locally buffered.
- trigger: Long press (e.g. 1.5 s) starts capture; release ends capture after a bounded post-roll, with a short press reserved for conversation. Server push or reconnect delivers signed receipt; no scheduled trigger.
- storage: Encrypted CBOR or compact binary packet on microSD, one file per incident, 30–90 s Opus audio plus metadata; keep until signed relay receipt and owner retention policy permit deletion. Target under 256 KiB for metadata plus audio index, with audio chunked separately.
- RAM budget: Use a 2–4 s circular PCM buffer (~16–32 KiB at 15,625 Hz mono 16-bit), then stream Opus/post-roll directly to SD or LTE-M. Reserve under 48 KiB peak additional RAM, avoid a second full audio buffer, and do not run incident encoding concurrently with normal conversation Opus if the existing ~87% one-core load would overrun.
