## Capabilities it proposed

### "“If I walk away or one of my devices disconnects, keep my task safe, then resume exactly where it stopped when the right hand comes back—without repeating anything—and tell me what still needs my attention.”"
- **useful because:** Today a multi-step request can be left half-done when the Mac loses reachability or the browser bridge disappears, and a retry can duplicate an external action. The owner should be able to leave a task in progress, regain it later, and see a trustworthy distinction between committed, unverified, and not-yet-executed steps. This is more than background execution: it preserves semantic transaction state across different hands and reconciles uncertain outcomes before continuing.
- **path:** faculty-judgement emits a versioned semantic task graph and classifies each step as pure, reversible, or externally committing → faculty-action executes the graph and writes an append-only checkpoint after every step, including idempotency key, pre-state fingerprint, post-state evidence, and uncertainty status → Mac planner/terminal performs local files, apps, and scripts; mac-vision is used only when accessibility and screen proof are available → browser extension performs authenticated tab actions with tab/session affinity and DOM evidence; it can report an external commit that happened before disconnect → relay remains awake, stores encrypted task checkpoints and retry leases, and sends compact state changes to the pendant → pendant shows resumable-task state locally, vibrates/LED-signals blocked or reconciled states, and offers a physical resume/cancel action when connectivity returns → unified presents one owner-facing timeline that reconciles duplicate reports from Mac, browser, and relay
- **model tier:** Use deterministic state-machine logic for checkpointing, deduplication, lease expiry, and reconciliation; use a background model for semantic step interpretation and recovery suggestions. Reserve realtime only for the owner's live spoken status request or urgent interruption.
- **latency:** Healthy local continuation should add under 300 ms per checkpoint. Reconnect reconciliation may take 1–5 seconds for local work and longer for authenticated browser work; the owner should immediately receive a concise 'paused / committed-but-unverified / resumed' status rather than wait for a full explanation.
- **cost:** Low per step: mostly local/relay storage and deterministic checks. A background model call is needed only when an interrupted step's evidence is ambiguous, roughly one short call per ambiguous interruption; realtime cost is limited to live conversation. Dominant cost is encrypted checkpoint retention and browser/Mac evidence capture, not inference.
- **security:** Checkpoints must never store passwords, cookies, raw page contents, or arbitrary command output by default—store hashes, redacted snippets, and local references. Resume leases must be single-use, scoped to the exact task version and step, and expire. External commits require reconciliation before retry; if outcome cannot be proven, stop and ask the owner rather than duplicate. A physical pendant cancel must override queued continuation.
- **missing:** A durable cross-surface task-graph and checkpoint protocol, distinct from per-surface job receipts; A reconciliation adapter for each committing action type (browser submit, email send, file move, calendar mutation); Relay storage and event APIs for encrypted checkpoints, leases, and reconnect notifications; Pendant firmware/UI support for resumable task state and physical cancel/resume; A local evidence redaction and hashing layer on Mac and browser; A policy and test suite for uncertain external outcomes and exactly-once versus at-least-once actions


## Changes it proposed to its own stack

### `integration` — Add a proof-carrying action contract between faculty-judgement and faculty-action. Each decision is compiled into a typed ActionPlan containing target surface, ordered steps, reversibility class, preconditions, expected postconditions, freshness TTL, idempotency key, and required evidence (API response, filesystem hash, app state, or browser DOM citation). Before execution, faculty-action performs a cheap live preflight across the relevant hands: Mac reachability/Accessibility, browser heartbeat and tab affinity, relay/pendant connectivity, and permission state. It routes around unavailable hands only when the plan explicitly permits a fallback; otherwise it returns a structured blocked receipt without attempting no-op GUI actions. After each step it verifies postconditions and emits a signed receipt chain linking plan hash, observed evidence, and timestamps; stale leases or lost reachability automatically stop subsequent steps. Reversible plans remain proactive; irreversible plans execute only with a judgement-issued approval token, not an action-agent guess.
- **owner gets:** The owner stops hearing 'done' when Mac UI actions actually did nothing (the current machine reports Accessibility=false and input reachability failed), and gets an exact explanation of what was executed, what was proven, and where the plan stopped. Multi-step work can safely span pendant, relay, Mac, and logged-in browser without silently continuing after a disconnected or stale hand.
- effort: Medium-high: shared ActionPlan/receipt schema, preflight adapters for Mac/browser/relay, lease and idempotency storage, verification implementations for common action types, and dashboard/pendant-readable blocked receipts. Requires coordination with judgement and each surface.  ·  risk: Over-strict postconditions could falsely stop useful work; recover by classifying evidence as required vs best-effort and allowing explicit plan-level fallback. Network loss may leave an external action committed but receipt delayed; idempotency keys and reconciliation scans handle retries. Never treat a tool's success boolean as proof. Approval tokens must be scoped, single-use, and expiry-bound.
- cost: Small background-model/worker overhead for compiling and verifying contracts; avoids expensive realtime retries and duplicate external actions. Storage is a few KB per action chain plus optional evidence hashes (raw private page content should remain local).  ·  latency: Adds roughly 100–500 ms for preflight and per-step verification on healthy local surfaces; blocked actions return faster than futile GUI loops. Long browser work remains asynchronous.
- security: Improves least privilege and auditability: plans declare surfaces and evidence, receipts omit secrets, approval tokens are scoped, and private browser evidence stays on the Mac unless explicitly requested. Prevents acting through an untrusted/offline extension or false GUI receipt.
- depends on: A shared schema/versioning owner across faculty-judgement and faculty-action; A relay event/receipt channel that can deliver blocked/completed status to the pendant; Browser bridge heartbeat plus durable command idempotency and tab/session affinity; Mac permission/reachability probe exposed as a machine-readable preflight result; A policy defining which action classes are reversible and which require owner approval
