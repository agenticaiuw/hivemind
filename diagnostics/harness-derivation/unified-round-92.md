## Capabilities it proposed

### "“What happened with that thing I asked you to do?” Give me a spoken, evidence-linked recap across the pendant, relay, Mac, and logged-in browser: what I asked, what was attempted, what changed, what failed, and where the resulting files or drafts are. If it failed, resume from the last completed step rather than starting over."
- **useful because:** Today status, Mac receipts, browser results, and the pendant conversation are separate. This would let the owner leave mid-task and later get one trustworthy answer grounded in the actual action trace, not a model guess. It is inherently cross-surface: the pendant supplies the vague spoken reference, relay resolves the durable job, Mac/browser supply receipts and artifacts, and the relay speaks the result.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → dashboard
- **model tier:** Use the cheap background model to correlate job/event records and compose the evidence brief; use realtime only to resolve a genuinely ambiguous spoken reference or answer a follow-up. No model call is needed for straightforward receipt lookup.
- **latency:** Under 2 seconds for an unambiguous status lookup; under 10 seconds to aggregate a multi-step trace; resume work asynchronously and notify the pendant/dashboard when complete.
- **cost:** Usually <$0.001 per lookup (database queries plus a small background-model summary); $0.01–$0.05 only when reconciling many heterogeneous receipts. Storage is the dominant cost, not inference.
- **security:** Expose only records belonging to the owner's authenticated job/session; redact secrets and page contents from spoken output; dashboard links should require the existing login. Resuming a failed job must preserve idempotency and never duplicate an external submission. Follow current owner policy: no new approval gate is introduced.
- **missing:** A durable cross-surface correlation ID from the original utterance through relay job, Mac actions, browser commands, and produced artifacts; A normalized event/receipt schema with step dependencies, partial completion, failure reason, and resume token; A resolver for vague spoken references such as “that thing” using recent interaction and job context; An artifact index mapping outputs to local paths, browser drafts, and dashboard links; A background summarizer and pendant notification hook

### "“Tell me the private result only when I’m actually wearing the pendant; otherwise leave a redacted notice on my Mac.” The system should use a local wear/proximity signal to decide whether sensitive browser or Mac results may be spoken, queue a minimal opaque alert when the pendant is off, and speak the full result when it is put back on and the owner asks."
- **useful because:** A browser session can expose financial, medical, work, or account data, while the Mac may be visible to other people. Today the system has no reliable way to distinguish the owner wearing the pendant from it sitting on a desk, so it must either over-share or remain silent. This gives the owner useful asynchronous work without turning the pendant into an accidental loudspeaker.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → dashboard
- **model tier:** Deterministic policy and local state machine for wear detection, redaction, queueing, and routing; background model only summarizes the already-authorized result. Realtime is used only when the wearer explicitly asks for the queued detail.
- **latency:** Local wear-state transition under 250 ms; redacted Mac notice under 2 seconds; full spoken result on explicit request under 5 seconds.
- **cost:** Near-zero for routing and redaction; <$0.01 for an occasional background summary. Small persistent metadata per notification; no audio or page content needs to be stored solely for this feature.
- **security:** Wear detection is a privacy signal, not authentication: require the existing authenticated session and an explicit spoken request before releasing sensitive content. Store only opaque notification IDs on the pendant; never cache page text or secrets locally. Fail closed when the signal is stale, contradictory, or the pendant is unpaired.
- **missing:** A production wear/proximity sensor and tamper/staleness detection; A signed, monotonic wear-state event from firmware to relay; A sensitivity classifier and field-level redaction policy shared by Mac/browser/dashboard; A notification router that can hold opaque pending results until a later wearer request; An explicit owner policy for how long a result may remain releasable after the pendant is removed


## Changes it proposed to its own stack

### `integration` — Introduce a single immutable traceId and typed event envelope shared by realtime utterances, relay jobs, Mac planner steps, browser bridge commands/results, action receipts, and artifacts. Persist a DAG (not just a flat log) with parent step, idempotency key, status, timestamps, evidence pointers, and resumable checkpoint. Add one read API that materializes a redacted human timeline and machine resume plan across all surfaces.
- **owner gets:** When work crosses the Mac and private browser, the owner can finally ask a natural-language follow-up and receive a factual answer or continue from where it stopped, without repeating instructions or wondering whether an action actually happened.
- effort: Medium-high: event schema and migrations, adapters in relay/local-agent/browser bridge, artifact indexing, redaction, and tests for retries and partial failure.  ·  risk: Schema drift or missing adapters could create incomplete timelines; mitigate with versioned envelopes, explicit unknown events, and retaining existing per-surface logs as source of truth. Resume must require idempotency checks and refuse ambiguous checkpoints rather than replaying blindly.
- cost: Small D1/R2 metadata increase; background summarization is usually <$0.01 per completed trace. No extra realtime inference for simple lookups.  ·  latency: Negligible for action execution; status reads add one indexed query and aggregation, typically <2 seconds.
- security: Trace data is sensitive because it links private pages, files, and voice intent. Enforce owner/session scoping, field-level redaction, short-lived artifact URLs, and never put raw secrets into the pendant transcript.
- depends on: The existing durable job/receipt and browser command records must expose stable IDs; A resumable browser queue (the 45-second blocking wait remains an open defect in chg-14accc01); An artifact metadata table and redaction policy

### `hardware` — Add a low-power vibration motor (or linear resonant actuator) with a dedicated driver and a second capacitive/gesture input in the production pendant, while retaining the existing button/LED. Expose short local patterns for job-complete, urgent-failure, privacy/mute, and incoming-owner interruption; the relay/Mac can enqueue a signed notification, but the pendant can render it offline after link loss.
- **owner gets:** The owner can know a long-running Mac/browser task finished without staring at a dashboard or hearing an interruption in public. A discreet tactile cue is more reliable than the single LED, and a second gesture gives a private way to acknowledge or mute an alert while the phone is inaccessible.
- effort: Medium hardware revision: actuator, driver transistor, enclosure/acoustic isolation, firmware event queue, haptic-pattern tuning, and end-to-end tests for LTE loss and low-power states. The second input is optional but strongly preferred; if rejected, retain the current one-button interaction and use distinct press durations.  ·  risk: Vibration can annoy or reveal presence, drain power, or be mistaken for an urgent alert. Mitigate with user-configurable patterns, quiet hours, rate limits, a long-press mute, and a local privacy latch. Mechanical noise could leak into the mic; test actuator placement while recording. Recovery is graceful fallback to the existing LED/audio notification.
- cost: Roughly $1–$4 BOM increase for actuator/driver and under 10 mA while vibrating (duty-cycled); a second capacitive input adds about $0.50–$2. No inference cost.  ·  latency: Local cue can render in tens of milliseconds after a queued event; no network round trip if the notification was buffered before disconnect.
- security: Notification payloads must be opaque event IDs, not page titles or secrets; resolve details only after an authenticated spoken request. Physical access should not reveal sensitive task contents through patterns.
- depends on: A durable cross-surface trace/job event ID and notification queue; A local privacy/mute latch policy; Production pendant constraints beyond the current nRF9160 DK; Firmware power-state and actuator driver support

### `hardware` — Add a dedicated wear-presence sensor to the production pendant (skin-contact capacitive electrode or optical/IR proximity sensor), with a tamper/stale-data watchdog and a secure monotonic event counter. Keep the sensor decision local; emit only signed worn/not-worn transitions and confidence, never raw biometric measurements. Give firmware a fail-closed state and a configurable debounce window before sensitive notification routing changes.
- **owner gets:** The pendant can safely act as a private channel only when it is on the owner's body. When it is left on a table, the Mac can show that work is ready without reading private results aloud; when picked up, the owner can retrieve them deliberately.
- effort: Medium product hardware and firmware revision: sensor placement and enclosure testing, low-power driver, secure event signing, debounce/state persistence, and integration tests for clothing, charging, movement, and false positives.  ·  risk: False 'worn' readings could disclose private content; false 'not worn' readings are inconvenient. Mitigate by fail-closed routing, requiring a fresh explicit spoken request for sensitive content, confidence thresholds, and never using wear state as sole account authentication. Sensor adds standby power and may be affected by sweat or gloves.
- cost: Approximately $0.50–$3 BOM and well under 1 mA average with duty cycling; negligible inference cost. Production validation and enclosure tooling dominate engineering cost.  ·  latency: Sensor transitions can be available locally in <250 ms; notification routing remains network-limited only after a state change.
- security: Raw sensor data remains local and is discarded. Signed state transitions prevent a forged browser/Mac event from claiming the pendant is worn, but the system must still enforce normal session authentication and redaction.
- depends on: A shared sensitivity/redaction policy across browser, Mac, relay, and dashboard; A signed event envelope and notification queue; Owner policy for stale wear state and release timeout; Production pendant design review
