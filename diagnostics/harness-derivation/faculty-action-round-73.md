## Capabilities it proposed

### "Do this across my Mac and logged-in browser, but only carry out steps that are still valid; stop at any irreversible step and show me exactly what would happen, then tell me what completed and what remains."
- **useful because:** Today judgement can choose surfaces and the Mac can return receipts, but there is no shared execution contract that turns a multi-surface decision into a dependency-aware, stale-safe run. This would prevent a later step from acting on an earlier failed or changed state, and gives the owner one truthful completion report rather than scattered job/browser statuses.
- **path:** faculty-judgement emits a typed action contract → faculty-action validates preconditions, leases, dependencies, and idempotency before dispatch → mac-planner/mac_run_actions executes reversible Mac steps → browser-extension/browser_run_actions executes authenticated-tab steps with tab/session affinity → relay records progress and rehydrates the run after disconnect → pendant announces waiting-for-approval, completion, or blocked states
- **model tier:** Use the cheap planner/router for contract validation and step compilation; reserve realtime only for the owner's live approval conversation. Use background execution for long-running jobs and a small deterministic reducer for receipts.
- **latency:** A contract should validate in under 300 ms; each surface dispatch remains bounded by its existing round-trip. Approval prompts should reach the pendant within 1 s, while disconnected work can continue asynchronously.
- **cost:** Low API cost: deterministic validation/reduction dominates, with one cheap model call only when translating an ambiguous goal into steps. Browser/Mac execution and receipt storage dominate latency, not tokens.
- **security:** Never transmit page secrets into the contract or receipt; store references and redacted hashes. Bind each step to an app/path/tab/session and an expiry. Require explicit pendant approval for send/submit/delete/purchase/auth changes. If a precondition changes, fail closed rather than guessing. Keep an append-only receipt plus compensating undo where available.
- **missing:** A typed action-contract schema and validator shared by judgement, action, Mac, browser, and relay; Precondition evaluation and dependency-aware scheduler that can skip stale steps; A durable run state machine with lease expiry, resumable checkpoints, and per-step idempotency keys; Pendant-visible approval/blocked events and a final cross-surface receipt reducer

### "Hold this consequential task until I am physically present, then ask for one button press on the pendant and finish it across my logged-in browser and Mac; if the deadline passes or anything changes, stop and tell me exactly what remains."
- **useful because:** The owner can currently approve in conversation, but cannot create a durable, presence-bound handoff that survives a dropped link and guarantees the approval came from a deliberate physical interaction at execution time. This is useful for purchases, submissions, account changes, and other actions where a spoken 'yes' hours earlier should not be enough.
- **path:** judgement creates a sealed, deadline-bound commitment containing the intended outcome and a redacted preview → relay stores the commitment and wakes it when its deadline or prerequisite arrives → pendant displays a short hash/summary, indicates waiting state locally, and captures a deliberate button gesture with a nonce → faculty-action verifies the nonce and fresh owner presence, then dispatches dependent Mac and authenticated-browser steps → Mac and browser return before/after evidence and signed receipts; relay delivers a final spoken/status summary
- **model tier:** Use a deterministic state machine and cheap model for preview compression and result explanation; use realtime only when the owner is actively approving through the pendant.
- **latency:** Local button acknowledgement under 150 ms; approval-to-dispatch under 1 s when both bridges are online. Waiting and deadline handling are asynchronous.
- **cost:** Low: mostly durable state and cryptographic nonce checks; one small model call for the owner-facing preview/result. Browser and Mac round trips dominate latency.
- **security:** Bind approval to a one-time nonce, commitment hash, device identity, expiry, and narrow action scope. Never put secrets or full page contents in the pendant display or relay events. Require a fresh observation after approval; invalidate on changed URL, recipient, amount, or account. Irreversible actions need this physical confirmation and cannot be approved by a stale voice transcript.
- **missing:** A pendant-local one-shot approval primitive with nonce display, haptic/LED feedback, replay protection, and offline persistence; A relay commitment store with deadline wakeups and atomic consume semantics; Cross-surface proof format tying the physical approval to the exact browser/Mac action set; Owner-facing recovery flow for expired, changed, or partially completed commitments


## Changes it proposed to its own stack

### `integration` — Implement a shared ActionContract v1 and reducer between judgement and existing executors. Each run contains contractVersion, runId, owner-visible goal, ordered/parallel steps, target surface, idempotencyKey, preconditions (resource fingerprint + observedAt + expiry), effect class, approval requirement, timeout, and compensation. The relay persists a state machine (planned→ready→running→blocked/awaiting_approval→succeeded/failed/compensated), grants a short lease per step, and accepts exactly-once step receipts from Mac/browser. On reconnect it reconciles receipts by idempotencyKey before dispatching anything; a changed fingerprint becomes blocked, never retried blindly. Reduce all receipts, browser results, journal entries, and pipeline events into one final run report and pendant event.
- **owner gets:** A dropped connection, changed webpage, or half-completed Mac job would no longer cause duplicate sends, stale edits, or an untruthful 'done'. The owner gets one actionable answer: completed steps, blocked step and reason, safe undo options, and the exact approval needed to continue.
- effort: Medium-high: schema, durable reducer, adapters for existing Mac/browser jobs, lease/reconciliation tests, and pendant event rendering.  ·  risk: A strict validator may block a task that could have succeeded; recover with an owner-visible 'update and retry' action, never silent fallback. Reducer bugs could misreport completion, so derive status only from signed/typed receipts and retain raw events.
- cost: Negligible storage/compute; one small D1/R2 record per step and no extra model call on retries. Existing receipts and browser results are reused.  ·  latency: Adds <100 ms local validation plus one persistence write per transition; reconnects become safer but may wait for fresh observation when fingerprints expire.
- security: Improves safety by keeping secrets out of contracts, binding actions to resource fingerprints, expiring leases, and enforcing approval classes. Contract and receipts must be access-controlled and redact page contents.
- depends on: Action receipt implementation chg-5fc73ce3 is present but currently has no enforced gates or preconditions; A durable browser job runner and authenticated session affinity; Pendant-visible approval/blocked event handling; Shared event IDs across /browser/result, /journal, /pipeline/events, and Mac job receipts

### `browser-harness` — Add an offline-command quarantine and reconnect watchdog around the existing browser queue. When heartbeat expires, stop accepting new mutating commands, mark the five currently pending commands as paused (not failed), notify the relay/pendant with count and oldest age, and require a fresh session/tab fingerprint before replay. On reconnect, reconcile each command by idempotency key and discard commands whose URL/session or precondition hash changed; retain safe read-only commands for bounded replay. Add a visible drain/clear action and TTL-based expiry so stale private-page work cannot execute days later.
- **owner gets:** The browser is offline right now with five queued commands. This prevents a later browser reconnect from unexpectedly submitting stale forms or repeating actions, while preserving harmless research so the owner does not lose work.
- effort: Medium: heartbeat state transitions, queue metadata, reconnect reconciliation, relay event, and dashboard/pendant status.  ·  risk: A legitimate command may expire or be quarantined; expose each paused command and allow explicit resume after re-observation. Never auto-replay writes after an offline interval.
- cost: Minimal D1/local queue metadata; no model calls. One heartbeat request at the existing cadence.  ·  latency: No effect while online; reconnect adds one observation round before replay.
- security: Reduces stale-session and delayed-submit risk. Store only redacted URL/session identifiers and hashes, not page secrets.
- depends on: Existing /browser/heartbeat, /browser/poll, /browser/result/:commandId, /browser/sessions; Durable browser job runner proposal chg-16bc5dee; Pendant-visible blocked/approval events; Owner-controlled browser extension heartbeat

### `interaction` — Add a cryptographic presence-bound approval protocol spanning the pendant and relay: the relay creates a one-time commitment nonce over a canonical, redacted action manifest (targets, recipient/amount, expiry, and effect class); the pendant stores it locally, shows a compact confirmation phrase/hash, and accepts a long-press plus button sequence offline. It signs/derives an approval token with monotonic counter and nonce, queues it until link returns, and the relay atomically consumes it only for that exact manifest. Any changed precondition, deadline, or action set invalidates the token. Emit explicit waiting/approved/expired/blocked states and attach the token ID to every Mac/browser receipt.
- **owner gets:** The owner gets a trustworthy 'I approved this exact thing while holding my pendant' guarantee, even if the voice link drops. A stale conversation, replayed request, or changed webpage cannot silently become a purchase, submission, or account change.
- effort: Medium-high firmware + relay protocol work, plus receipt plumbing and a small pendant UI/state machine.  ·  risk: Button misfires or lost queued tokens could inconvenience the owner; use a cancellable local state, clear timeout, and a spoken/LED recovery path. If signing material is unavailable, fail closed rather than treating a voice acknowledgement as equivalent.
- cost: Negligible API cost; small persistent token record and a few bytes of pendant flash/RAM. Hardware can use the existing button/LED if firmware access is granted.  ·  latency: Immediate local acknowledgement; online dispatch adds one relay round trip. Offline approvals wait safely instead of expiring into execution.
- security: Strongly improves anti-replay and confused-deputy resistance. The action manifest must redact secrets, tokens must be single-use and expiry-bound, and device keys must never leave the pendant.
- depends on: Pendant firmware access and a local approval state machine; Relay durable atomic consume/deadline storage; Canonical action-manifest and receipt schema; Existing Mac/browser action dispatch and undo/receipt routes

## Its own summary

Fresh live checks found a concrete action gap: the Mac bridge and relay are reachable, but the browser extension is offline with 5 pending commands, and the local agent is not ready because Accessibility/Screen Recording remain absent. I recorded two distinct proposals: (1) a shared typed ActionContract with enforced preconditions, leases, dependency scheduling, idempotency, approval classes, and one cross-surface receipt reducer; (2) an offline browser-command quarantine that pauses and revalidates queued work rather than replaying stale mutations. I also informed faculty-judgement how this differs from an event ledger: the ledger deduplicates observations, while the contract makes decisions executable safely.

**Biggest unknown:** Whether the owner will enable the browser bridge and TCC permissions. Until then, browser-mutating work must remain paused; AppleScript-backed Mac actions can still proceed. The pending 5 commands need inspection and quarantine semantics before any reconnect.
