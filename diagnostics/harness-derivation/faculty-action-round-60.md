## Capabilities it proposed

### "When you’ve prepared something consequential on my Mac or in a logged-in website, ask me on the pendant for a one-button approval, carry it out only once, and tell me exactly what happened—even if I walk away during the process."
- **useful because:** Today the mind can decide and several hands can prepare work, but an approval can be lost between surfaces or an action can be left half-done. This gives the owner a dependable, reversible transaction boundary: private browser data stays in the browser, Mac work stays on the Mac, the relay survives disconnection, and the pendant is the physical final say.
- **path:** faculty-judgement creates a typed action plan and risk summary → relay-realtime sends a short approval prompt and receives the pendant's button event → relay durable job runner holds a lease and two-phase transaction record → browser-extension reads/fills the authenticated tab and returns before/after evidence → mac-planner/mac-terminal performs the Mac-side reversible step → faculty-action commits only after all preconditions and the pendant approval match, then reports a receipt back through relay and pendant
- **model tier:** Use the cheap background model for plan normalization, evidence comparison, and receipt summarization; reserve realtime only for the brief approval prompt and interruption handling.
- **latency:** Approval prompt under 1 second; after approval, visible commit within 5 seconds for a normal Mac/browser action. If either surface misses its lease heartbeat, abort before commit and tell the owner, rather than guessing.
- **cost:** About $0.01–$0.05 per transaction, dominated by evidence extraction and any browser/Mac model calls; approval and lease bookkeeping are negligible. No audio needs to be resent beyond the short prompt and result.
- **security:** The relay stores only an opaque plan hash and expiry, not page contents or credentials. Browser and Mac return redacted evidence plus hashes. Require a fresh physical button press for irreversible actions, bind approval to plan hash, target tab/session, and expiry, make retries idempotent, and expose undo where the underlying operation supports it. Never auto-approve on timeout or reconnect.
- **missing:** A durable two-phase transaction/lease protocol joining browser and Mac job records; A pendant approval event and explicit cancel/timeout event in the relay; Precondition and plan-hash verification at commit; A single cross-surface receipt that links browser and Mac evidence; Owner approval policy defining which risk classes require the physical button

### "Give the hive permission to do exactly this one thing in my account, for the next ten minutes, and nothing else; show me what it was allowed to touch and revoke it when it’s done."
- **useful because:** The owner gets useful delegation without granting the Mac, browser, or relay a standing master key. This makes cross-device action safe enough for private accounts: one request can span the logged-in browser and Mac, but its authority is narrow, visible, expiring, and independently auditable.
- **path:** faculty-judgement turns the request into a typed scope (account, tab/app, allowed reads, exact mutations, expiry) → relay issues and tracks a single-use capability token and revocation state → browser-extension enforces the token on the authenticated tab and returns redacted evidence → mac-planner/mac-terminal enforces the same token for local actions → faculty-action assembles the signed receipt and the pendant speaks the scope, completion, or revocation result
- **model tier:** Use a cheap background model to normalize the requested scope and summarize receipts; use realtime only if the owner asks follow-up questions while the temporary delegation is active.
- **latency:** Scope preview under 2 seconds; token issuance and revocation under 300 ms online. If the relay is unreachable or the scope is ambiguous, do not issue authority.
- **cost:** Roughly $0.005–$0.03 per delegation, dominated by scope explanation or evidence summarization; cryptographic checks and revocation are negligible.
- **security:** Never expose credentials to the model or relay. Bind the token to the exact browser tab/app, operation names, data classes, plan hash, and expiry; require fresh pendant confirmation for any external send, purchase, deletion, or permission change; revoke on completion, timeout, disconnect, or owner cancellation; retain hashes and signed receipts rather than content.
- **missing:** Cross-surface capability-token enforcement (not just approval); Authenticated relay issuance/revocation and a durable revocation list; Browser and Mac middleware that rejects unscoped mutations; A scope-preview response and owner policy for high-impact operation classes; A signed, merged receipt proving what the temporary authority actually touched


## Changes it proposed to its own stack

### `integration` — Build a cross-surface transaction coordinator between the existing /plan, /execute, browser command queue, Mac jobs, and relay. It should issue a planHash-bound transaction with explicit prepare/commit/abort states, per-step idempotency keys, leases, precondition snapshots, and one merged receipt. A pendant approval event commits only the exact still-valid hash; disconnect, stale tab, changed page, or lease expiry aborts safely. Keep browser and Mac evidence local/redacted and persist only hashes, statuses, and receipt pointers.
- **owner gets:** The owner gets one trustworthy answer to “did it happen?” and cannot accidentally approve a stale or duplicated action. Walking out of range or losing the browser no longer leaves an ambiguous half-completed task.
- effort: Medium-high: shared transaction schema and durable state machine, adapters for Mac jobs and browser commands, relay lease/watchdog, and a small pendant event protocol; integration tests for reconnect, duplicate delivery, stale evidence, and undo.  ·  risk: A coordinator bug could block legitimate work or falsely report completion. Default all unknown states to abort/needs-review, retain the existing per-surface receipts, and provide an operator recovery endpoint that never retries irreversible steps blindly.
- cost: Low ongoing storage and compute; one small durable record plus hashes per transaction. Model cost should fall because receipts and evidence are structured rather than re-summarized from full context.  ·  latency: Adds roughly 100–300 ms bookkeeping before prepare/commit; lease heartbeats run asynchronously. Commit remains bounded by the slowest Mac/browser step.
- security: Improves security by binding approval to target, plan hash, evidence version, and expiry; reduces sensitive data copied into relay. Requires careful nonce/idempotency-key handling and authenticated pendant events.
- depends on: Owner-defined risk classes and which require physical approval; A relay-to-pendant approval/cancel event path; Browser and Mac adapters exposing prepare/commit boundaries; Durable job runner (the existing browser durable-runner backlog item must be completed)

### `interaction` — Route the existing Mac job approval gate into the relay/pipeline as a typed approval challenge instead of emitting only 'Waiting for your approval on the dashboard'. The challenge carries jobId, action type, concise spoken summary, expiry, and nonce; the pendant can approve/cancel with its single button, while the dashboard remains a secondary view. On reconnect, replay the challenge once, suppress duplicates, and update the same job receipt.
- **owner gets:** The owner can approve a safe action while wearing the pendant, without being at the Mac or opening the dashboard. A command that currently stalls silently becomes a clear, bounded interaction that either completes or expires safely.
- effort: Medium: add approval challenge/result events to the relay schema, bridge local approval-gated jobs to those events, add pendant button handling and replay/nonce tests.  ·  risk: A spoken prompt could be misunderstood, and duplicate button delivery could double-run an action. Show the action class and target in the prompt, require a deliberate second press for irreversible classes, bind the nonce to the job, and default timeout/reconnect to cancel.
- cost: Negligible relay storage and bandwidth; avoids expensive realtime turns by using a compact event. One short TTS prompt costs only a few cents or less depending on the existing speech path.  ·  latency: Approval delivery should be sub-second when LTE is live; commit follows existing job latency. Reconnect adds bounded delay and never auto-commits.
- security: Improves security only if approval events are authenticated and nonce-bound; do not put page contents or secrets in the spoken prompt. Keep dashboard approval and pendant approval mutually exclusive.
- depends on: Relay approval event route and authenticated pendant event; The pending physical_action_confirmation/action_lease_indicator device skills (already requested); Existing local approval gate and job receipt plumbing; Owner's manual Accessibility/Screen Recording grants remain needed for GUI-only actions

### `integration` — Add a cross-node capability-token firewall for actions. Before faculty-action hands work to the Mac or authenticated browser, the relay mints a short-lived, single-use token scoped to an exact operation, target (app/tab/account), fields or files allowed, maximum side effects, and expiry. Mac and browser adapters must present that token for every mutation; they return a signed receipt containing the token hash, target identity, and before/after evidence. A token cannot be replayed on another tab, job, or surface, and relay logs contain only the scope and hashes—not credentials or page contents.
- **owner gets:** The owner can let the hive act on private accounts without giving every node broad, permanent control. A prompt injection, stale browser tab, duplicate retry, or compromised relay worker is contained to one narrowly authorized action instead of becoming permission to send mail, move money, or alter unrelated files.
- effort: High: define a shared token/receipt format, add enforcement middleware to Mac jobs and browser commands, bind tokens to session/tab identity and idempotency keys, implement revocation and expiry, and test confused-deputy, replay, reconnect, and partial-failure cases.  ·  risk: Strict scopes may reject a legitimate multi-step task or strand an in-flight job. Start in audit-only mode, provide explicit scope expansion as a new approval, preserve existing receipts for recovery, and fail closed for mutations while allowing read-only work to continue.
- cost: Small D1 and local-agent overhead per action; no additional model call is required. Token and hash storage is tiny compared with browser evidence or audio.  ·  latency: Adds one local verification and usually one relay lookup per mutation (target under 50 ms when connected); cache only the single-use token at the executing surface, never broad credentials.
- security: Substantially reduces blast radius and secret propagation. Requires secure randomness, authenticated transport, replay protection, clock-skew tolerance, careful redaction, and a recovery path for token revocation. This is intentionally distinct from an approval UI: approval says yes, while the token says exactly what yes permits.
- depends on: A shared identity for relay, Mac agent, browser bridge, and pendant events; Browser bridge online heartbeat and durable command IDs; Mac job receipts with target metadata; Owner-defined operation classes and maximum side-effect scopes
