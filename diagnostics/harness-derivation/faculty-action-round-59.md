# Harness derivation — faculty-action — round 59

Model: `gpt-5.6-luna`  ·  probes against `http://localhost:8000`

## What it established

- **audio path** — Current prototype is asymmetric: I2S microphone capture is 15,625 Hz, uplink Opus is 16 kHz/16 kbps, while playback decodes 24 kHz/60 ms frames and resamples to 31,250 Hz I2S; encode+decode consumes roughly 87% of one core.
  - evidence: get_hardware_spec(audio)

## Capabilities it proposed

### "“Finish this across my Mac and my logged-in browser, and if anything fails, put everything reversible back and tell me exactly what changed.”"
- **useful because:** Today the mind can delegate work, queue browser commands, and issue receipts/undo, but the implemented receipt layer explicitly has no precondition gates and cannot coordinate a partial multi-surface rollback. This gives the owner a trustworthy action transaction: the Mac can prepare a document, the browser can fill a private form, and a dropped pendant/link or failed later step cannot leave silent half-completion. The owner gets one concise spoken result plus a durable evidence bundle, rather than guessing which hand stopped where.
- **path:** pendant: capture the goal, speak progress/final receipt, and offer a physical cancel/confirm signal for the final irreversible step → relay-realtime: create a durable saga/job and resume status delivery when the live link returns → mac-planner/mac-vision/mac-terminal: perform typed Mac steps and verify postconditions → browser-extension: operate the owner-authenticated tab, capture before/after page evidence, and stop at irreversible checkpoints → relay: persist step state, idempotency keys, compensation records, and a compact proof bundle for later review
- **model tier:** Use the normal planner/judgement tier for decomposition and verification; reserve realtime only for the short spoken interaction. Run long retries, polling, and evidence summarization on a cheaper background model.
- **latency:** Acknowledge in under 1 second; begin reversible steps immediately. Each step may take seconds, but the owner should hear a progress event within 5 seconds and receive a final receipt when the Mac/browser finishes, even if they leave.
- **cost:** Roughly one planner call plus inexpensive background verification/summarization per saga; dominant cost is browser/Mac screenshots and re-sent evidence context, so store hashes and short snippets rather than whole pages.
- **security:** Private authenticated page data and local file metadata leave the browser/Mac only to the relay's job store; redact secrets from receipts. Never auto-compensate an irreversible send/purchase/delete: require the owner's explicit pendant or voice confirmation, show the exact final mutation, and lease the approval so an old confirmation cannot be replayed.
- **missing:** A real saga coordinator spanning Mac jobs and browser command IDs, with durable dependencies and idempotent retries; Precondition/postcondition gates that can refuse to continue when the app, tab, URL, DOM/value, file hash, or account identity differs; Compensation hooks that restore earlier reversible Mac/browser mutations on later failure, plus a single cross-surface proof/undo receipt; A final-action approval lease and pendant-visible progress/cancel state

### "“Do it, then check the real result and tell me whether it actually took effect.”"
- **useful because:** Action receipts currently describe what the Mac or browser executor returned, not whether an external system accepted the change. A browser click can be acknowledged while a form validation error, stale tab, network retry, or calendar conflict leaves no change. This capability performs an independent post-action read through the other available hand (fresh page/API state or a local file/status query), compares it to the intended effect, and speaks a truthful verified/uncertain/failed result. It is especially valuable for the owner's failed Gmail/GitHub/Calendar requests and prevents reporting intent as completion.
- **path:** pendant: receive the short verified/uncertain/failed spoken receipt and optionally ask for retry → relay-realtime: correlate the mutation with a fresh verification job and retain evidence while the owner is away → mac-planner/mac-vision/mac-terminal: execute local mutations and independently re-read files, app state, or network responses → browser-extension: reattach to the same authenticated session, refresh or reopen the relevant page, and extract the resulting record rather than trusting the click result → faculty-perception: classify fresh evidence and detect stale/ambiguous state before faculty-judgement reports success
- **model tier:** Use a cheap background verifier with deterministic typed comparators for most checks; use the expensive realtime tier only to resolve genuinely ambiguous evidence or explain a concise exception.
- **latency:** Return an immediate 'working' acknowledgement, then verify within 5–15 seconds for local/browser changes; long-running external systems can remain queued and notify through the pendant when the read-back is available.
- **cost:** One extra browser read or Mac status call per mutation, plus a small comparator; API cost is low and dominated by screenshots/page extraction only when structured evidence is unavailable.
- **security:** Verification reads can expose private account data, so retain only the minimum matching field and a source URL/tab ID, redacting tokens and message bodies. Never treat cached DOM or an old receipt as proof; require a fresh timestamp and matching account/record identity. Do not send or retry an irreversible action automatically merely because verification is uncertain.
- **missing:** A typed intent-to-observation contract (expected record, fields, and comparator) for each action type; Freshness/session/account checks and a verifier separate from the mutating executor; Cross-surface evidence storage linking mutation receipt to read-back citation; Spoken receipt states that distinguish attempted, verified, contradicted, and unable-to-verify

### "“Send this private page to the person I’m with, but only let them see exactly this one thing for the next ten minutes.”"
- **useful because:** The owner can read authenticated pages in Safari, but cannot safely turn a selected fact into a controlled, recipient-bound handoff. Today they must expose the whole tab, copy sensitive text manually, or use an ordinary share link that may persist indefinitely. This would let the pendant identify the intended excerpt, the browser extract it from the logged-in page, the relay issue a one-time capability, and the nearby recipient prove possession before seeing it. It is a new action surface: sharing a narrowly scoped result, not merely reading or changing the owner’s account.
- **path:** pendant: capture the spoken scope and recipient cue, show a short code/QR via the LED or paired display, and require a deliberate button press before release → browser-extension: extract only the named fields from the authenticated tab, retain source URL/locator evidence, and never transmit session cookies or the whole page → Mac: render or print the one-time handoff code and show the exact excerpt and expiry for owner review → relay: mint a single-use, recipient-bound encrypted capability, enforce expiry/revocation and prevent replay, then deliver a compact spoken/audible completion receipt → faculty-perception/judgement: resolve which page and fields the owner meant, detect ambiguity, and refuse broad or secret-bearing scopes
- **model tier:** Use the ordinary judgement tier for scope resolution and a cheap deterministic service for token minting, field filtering, expiry, and audit. Realtime is needed only for the short spoken confirmation.
- **latency:** Show a preview in under 3 seconds and make the recipient handoff available within 5 seconds after confirmation. Revocation should take effect immediately; expired links must fail without model work.
- **cost:** Low per handoff: one short planning call plus relay storage and cryptographic token operations. Cost is dominated by authenticated-page extraction only when the requested field is not structurally identifiable.
- **security:** Default-deny extraction and redact credentials, cookies, hidden DOM, and unrelated fields. Bind the capability to a one-time recipient challenge and exact content hash; require owner confirmation for every release, never allow forwarding or indexing, log access time/device, and support immediate revocation. The relay must store ciphertext or only a pointer to an encrypted payload with short retention.
- **missing:** A field-scoped authenticated-page extraction contract with DOM provenance and secret redaction; One-time recipient challenge/QR or short-code exchange between pendant, Mac, and relay; Encrypted ephemeral payload storage with replay prevention, revocation, and access receipts; A pendant-visible confirmation/revocation interaction and a Mac preview surface; A policy engine that distinguishes harmless excerpts from secrets and blocks the latter by default

### "“If that failed, show me why and give me a safe way to retry it—without making me explain everything again.”"
- **useful because:** The owner’s history contains repeated opaque failures for Gmail, GitHub, Calendar, and browser access. Existing job receipts can say an action failed, but they do not produce a cross-surface diagnostic that distinguishes a dead bridge, stale tab, permission problem, changed DOM, rejected server request, or a genuinely unsafe request. This capability automatically preserves a redacted, replayable failure bundle and proposes the smallest safe recovery, so the owner gets a useful explanation and can retry from the exact checkpoint rather than starting over.
- **path:** pendant: speak one sentence naming the failure class and offer retry/cancel; provide a physical cancel path while a retry is pending → relay: correlate request, bridge heartbeat, Mac job, browser command, and pipeline events into one incident timeline; encrypt and expire the bundle → Mac: collect local executor diagnostics, app/frontmost state, exit codes, and pre/post observations without recording microphone input → browser-extension: capture tab/session identity, URL, command result, relevant DOM locator/error region, and bridge heartbeat while redacting page secrets → faculty-action: synthesize a recovery plan that is idempotent and reversible, then resume only from the first failed checkpoint
- **model tier:** Use deterministic classifiers for transport/permission/stale-state failures and a cheaper background model for summarizing evidence. Invoke the realtime tier only for the short owner-facing explanation or an ambiguous recovery choice.
- **latency:** Failure diagnosis should be available within 2 seconds of the failed result; collecting a full redacted bundle may take up to 10 seconds. Never block the initial safe cancellation on model latency.
- **cost:** Low-to-moderate: mostly local structured logs and hashes; screenshots or DOM excerpts are collected only when needed. Background summarization costs more than classification but can run after the spoken response.
- **security:** Diagnostics can contain authenticated URLs, file paths, clipboard contents, and page text. Apply field-level redaction before relay upload, retain bundles briefly, require owner confirmation before retrying any write/send, and exclude audio and raw keystrokes by default. A replay must use fresh credentials/session state, never stored cookies or captured secrets.
- **missing:** A cross-surface incident schema with causal event ordering and stable request/step IDs; Redaction at capture time for browser DOM, clipboard, shell output, URLs, and local paths; Failure classifiers and typed recovery suggestions with confidence; A checkpoint-aware replay executor that can revalidate preconditions before retry; A pendant/Mac incident viewer with retry-from-checkpoint and delete-bundle controls


## Changes it proposed to its own stack

### `integration` — Add an end-to-end 24 kHz audio conformance runner that uses a deterministic PCM/I2S test fixture on the pendant (not the Mac microphone), sends the exact production Opus uplink through the relay, decodes the 24 kHz/60 ms downlink, and measures sample-rate tags, packet loss concealment, round-trip latency, drift, clipping, and weighted SNR against the golden vector. Have the Mac harness start/stop the run, collect /pipeline events and audio artifacts, and publish a signed pass/fail receipt with firmware, relay, codec, and wire-clock versions. Fail closed when capture is still 15,625 Hz or when any stage silently resamples to 16 kHz.
- **owner gets:** The owner can hear a genuinely superwideband pendant conversation instead of trusting a green build or a claimed 24 kHz decoder. A single repeatable test catches the current split (15,625 Hz capture versus 24 kHz playback) before it reaches their daily wearable, without opening the Mac microphone.
- effort: Medium: add a firmware test mode and PCM fixture, relay-side vector/metrics code, and a Mac command that runs the test and stores a compact receipt. No production audio behavior changes until the receipt passes.  ·  risk: A test fixture can mask real microphone/I2S clock problems; include a second run using the physical mic with a local speaker/loopback jig, and label synthetic versus physical results. Keep the test mode gated and never enabled in release firmware. Recover by retaining the current 16 kHz uplink fallback when conformance fails.
- cost: Negligible API cost; one background verification job and bounded audio artifacts. Hardware fixture is roughly $20–$60 (I2S DAC/ADC or loopback board), powered only during tests.  ·  latency: No production latency impact. The test takes roughly 1–3 minutes per firmware/relay build and measures, rather than adds to, the 60 ms frame path.
- security: Synthetic vectors and aggregate metrics stay local or in short-retention job storage; do not upload owner speech. The physical-mic run must explicitly use a test tone or discard raw samples immediately.
- depends on: A firmware-accessible I2S/PCM injection or loopback test mode; A Mac-side build/device runner (the requested mac_read_build_and_devices capability); /pipeline/audio and /pipeline/:pipelineId/audio/:direction artifact access; A defined 24 kHz acceptance threshold and clock-drift budget
