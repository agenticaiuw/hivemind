## Capabilities it proposed

### "“Make this safe to share.” Use what I’m currently viewing in Safari and the relevant local Mac files to create a redacted share packet, save it locally, and stage it in the right browser upload or message composer without sending anything."
- **useful because:** Today the owner must manually inspect private browser pages and local files for secrets, copy the useful parts, redact account numbers/tokens/personal details, create an attachment, and navigate back to the correct logged-in destination. A pendant request could coordinate all of that across the browser’s private session, the Mac filesystem, and a reviewable staged draft while preserving the owner’s final send decision.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → mac-vision → dashboard
- **model tier:** background for extraction, classification, and redaction proposals; planner only when the destination or source set is ambiguous; realtime only for the short spoken confirmation and owner edits.
- **latency:** 5–15 seconds for a small page/file set; up to 60 seconds for multiple PDFs or long documents. The pendant should immediately acknowledge the scope and announce when the review packet is ready.
- **cost:** Roughly $0.01–$0.08 per invocation depending on document count and OCR; most cost is source extraction and redaction review, not the brief spoken response. Deterministic secret-pattern scanning should handle common credentials cheaply.
- **security:** Source content can include logged-in pages, documents, credentials, and personal data. Keep originals on the Mac/browser session; send only the minimum extracted text to the analysis model; never upload originals to the relay; preserve an encrypted local original and redacted derivative; show every redaction and destination before staging; require explicit owner confirmation before any browser submit, send, or upload.
- **missing:** A cross-surface source scope contract that identifies the active Safari tab plus explicitly selected local files; A provenance-preserving redaction engine combining deterministic patterns with model suggestions and a review diff; A local artifact builder that emits PDF/text/ZIP derivatives with a manifest of omitted fields; A browser staging operation that targets an existing composer/upload control and verifies the staged attachment without submitting; A durable review packet and pendant-friendly approval/edit loop


## Changes it proposed to its own stack

### `browser-harness` — Add an offline-aware command lease and recovery controller for the Mac browser bridge. Every queued browser command gets createdAt, expiresAt, attempt count, idempotency key, and operation class. When /browser/status or /browser/heartbeat reports the extension offline, stop issuing duplicate retries; on reconnect, automatically replay only unexpired idempotent reads, coalesce identical pending reads, and move expired/failed navigations to a dead-letter record with the exact error and source job. Emit a single recovery receipt linking the original job, command, attempts, and final outcome, and expose pending/expired/dead-letter counts in /ops/status and /journal. This is observability and recovery, not an approval gate.
- **owner gets:** The Mac currently has 11 browser commands stranded while the extension is offline, and browser_navigate has failed 10/10 times. The owner would stop hearing repeated 'I did it' attempts for work that never reached Safari, and queued read tasks would resume automatically after the bridge returns instead of silently aging out.
- effort: Medium: browser command store/heartbeat worker, replay/coalescing logic, receipt schema, and dashboard/status wiring; add fault-injection tests for disconnect/reconnect and duplicate delivery.  ·  risk: A reconnect could replay a stale read or a navigation into the wrong tab if affinity is not validated. Mitigate with TTL, session/tab identity checks, idempotency, and dead-lettering; never replay mutating commands automatically. Recovery is visible and the original job remains inspectable.
- cost: Negligible API cost; fewer planner retries and repeated browser calls should reduce tokens. Small local JSON/D1 growth for dead-letter records, bounded by retention.  ·  latency: No added latency while online; reconnect recovery adds one heartbeat interval and avoids repeated failed 20-second waits.
- security: Preserves existing browser session boundary; receipts should hash URLs/form data rather than persist secrets. No new permissions.
- depends on: chg-14accc01 request IDs/idempotency/tab affinity/typed results; POST /browser/heartbeat and GET /browser/status; GET /jobs/:jobId/receipts and GET /journal/:jobId; GET /ops/status and GET /ops/snapshot

### `model-routing` — Feed a compact, TTL-bound execution-health header into planning and tool selection: browser online/offline and heartbeat age, pending-command count, recent failure rate by action type, Mac agent readiness, and last receipt status. The router should deterministically downgrade or redirect browser-dependent plans when the bridge is offline (for example, answer from existing captures or ask the owner to reconnect), and after a failed execution attach a machine-readable failure fact to the next planning turn. Keep the header under ~200 tokens and expire it within 60 seconds so it does not become stale prompt baggage.
- **owner gets:** The agent would know before acting that Safari is unreachable instead of spending repeated waits on doomed browser_navigate calls, then claiming progress. It could give an immediate truthful answer, use a cached cited result, or choose a Mac-local alternative, while reducing the expensive planner context and retries.
- effort: Medium: define a health projection schema, compute it from /ops/status, /browser/status, /routing and job receipts, inject it into /plan and tool dispatch, and add deterministic routing tests for stale/offline/recovered states.  ·  risk: A stale or overly broad health signal could suppress a browser task that would have succeeded. Use short TTL, distinguish offline from unknown, and permit explicit owner requests to attempt once; record the decision and source timestamps in the job receipt.
- cost: Small local computation; likely saves planner calls and ~8–10k-token prompts on failed workflows. No new model spend.  ·  latency: Adds a local status read (target <100 ms) before dispatch; avoids current multi-second or 20-second failed browser attempts.
- security: Only operational metadata enters prompts; do not include URLs, page text, cookies, or form values. Existing bearer-protected routes remain the source.
- depends on: GET /ops/status; GET /browser/status; GET /routing; GET /journal/:jobId; POST /plan; POST /execute; GET /jobs/:jobId/receipts

### `integration` — Build a local share-safe artifact pipeline between the active browser session and Mac workspace. It must accept a source manifest (active tab plus selected files), extract content with provenance, run deterministic secret/PII detectors plus a cheaper model redaction pass, produce a redacted derivative and machine-readable manifest, and expose a browser-staging action that attaches only the derivative to the selected composer/upload target. The staging step must return a screenshot/DOM receipt and remain unsent. Originals never leave the Mac or browser session; the pendant receives only the redaction summary and review link.
- **owner gets:** The owner could turn a private page or local document into something safe to share in one spoken request, instead of manually hunting credentials and personal data across tabs and files. They would get a concrete artifact and see exactly what was removed before anything is staged.
- effort: High: implement source-manifest and provenance schemas, local extraction and artifact generation, detector/redaction review UI, secure derivative storage, browser upload targeting, and end-to-end tests with PDFs, screenshots, and logged-in pages.  ·  risk: A detector can miss a secret or redact useful context, and browser targeting can attach the wrong file. Mitigate with layered deterministic and model checks, visible before/after diff, conservative uncertainty labels, destination verification, short-lived derivatives, and an explicit final send boundary.
- cost: Low-to-moderate per task; deterministic scans are cheap, while OCR/model review costs roughly $0.01–$0.08 depending on source size. Local storage cost is small and originals remain local.  ·  latency: About 5–15 seconds for a page and a few files, longer for OCR-heavy PDFs. Browser staging adds one verification round trip.
- security: Improves privacy by keeping originals local and minimizing relay/model payloads, but introduces sensitive derivative files and redaction manifests; encrypt them, bind them to the job, expire them automatically, and exclude raw secrets from receipts and logs.
