## Capabilities it proposed

### "“If one of my devices is unavailable, keep the request alive and finish it through the best available path—and tell me plainly what is waiting, what already happened, and what could not be done.”"
- **useful because:** Today the relay is reachable but the Mac reports ready=false (Accessibility and Screen Recording missing), the computer-use loop is disabled, and the browser extension is offline with five queued commands. A pendant request can therefore look accepted while silently having no executor. This capability turns outages and permission loss into an explicit, recoverable handoff: the relay records a goal and an execution lease, the Mac/browser advertise health, and the system either reroutes a safe read to another surface or resumes exactly once when the missing surface returns. The owner gets a short spoken/LED status rather than a false success, and a final receipt that separates completed, skipped, and pending steps.
- **path:** pendant: button starts/ends the request and plays a terse state update; LED distinguishes queued, executing, waiting-for-Mac, and failed → relay-realtime: persists the intent, leases steps, applies expiry and idempotency, and emits a spoken update without keeping the expensive realtime model busy → mac-planner: publishes /ops/status readiness and executes Mac-native fallback steps when permissions and app access are available → browser-extension: heartbeats and claims only commands for its bound tab/session; reconnect replays pending work without duplicating a completed step → relay/background worker: wakes on heartbeat/job timeout and performs retry/reroute bookkeeping; dashboard/iOS shows the same state and receipts
- **model tier:** Use realtime only for the initial conversational acknowledgment and urgent spoken status. Use a cheaper background model for step decomposition, capability-health matching, fallback selection, and final reconciliation; deterministic code handles leases, idempotency, retries, and receipts.
- **latency:** Acknowledge from the pendant in under 1 second. Health/routing decision in under 2 seconds when a node is online. A disconnected node may wait until its next heartbeat; surface a 30-second stale warning and an owner-configurable expiry rather than polling expensively.
- **cost:** About $0.002–$0.01 per request beyond the normal voice turn, dominated by one small background planning/reconciliation call; heartbeat, lease, retry, and receipt work is database/Worker compute. Avoid sending full page or Mac context on every status update.
- **security:** Health metadata must not include page contents, credentials, or shell output. Bind browser work to an extension/session/tab identity and Mac work to the paired host. Persist only the goal, step hashes, surface, timestamps, and typed result summaries. Never retry a non-idempotent browser submission or shell mutation automatically; preserve the existing before/after receipt and checkpoint semantics. Tell the owner when a fallback changes what was actually done.
- **missing:** A shared capability-health schema with freshness and surface-specific failure reasons; A durable step lease/idempotency record spanning relay, Mac bridge, and browser bridge; Heartbeat-triggered resume and timeout worker; current browser has pending commands but no demonstrated end-to-end claim/resume contract; Pendant status vocabulary for queued/waiting/rerouted/completed states; A compact cross-surface receipt that can be rendered as speech, LED patterns, and dashboard history

### "“Remember this exactly where I found it, and let me ask about it later from the pendant even if that tab or my Mac is closed.”"
- **useful because:** A useful fact often exists only in a private Safari tab or a local Mac file, then disappears when the tab closes. This would create a small, provenance-preserving capsule rather than dumping an entire page into long-term memory: the browser supplies the authenticated URL/tab and selected text or DOM citation, the Mac supplies local-file provenance when relevant, the relay stores an encrypted, expiring snapshot plus a compact semantic index, and the pendant can retrieve it by voice. Later answers can quote the captured evidence and say when it was captured, instead of pretending that a stale memory is current.
- **path:** pendant: voice command “remember this” and later spoken retrieval; button controls capture timing so no microphone is left open → browser-extension: captures only the user-selected text/region, URL, title, tab/session identity, and a DOM locator/source hash; does not scrape unrelated tabs → mac-planner/mac-terminal: captures a selected local artifact or command result with path, modification time, content hash, and a redacted excerpt when the source is on the Mac → relay: encrypts and stores the capsule with owner-defined TTL, sensitivity label, and source provenance; retrieves only matching capsules for a later question → dashboard/iOS: shows capsule list, source link, expiry, evidence excerpt, and delete/export controls
- **model tier:** Realtime handles only the short capture acknowledgment or spoken lookup. A cheaper background model generates a compact title, entities, and retrieval keywords; deterministic code preserves the exact excerpt/hash and enforces TTL. Use no model for a direct exact-quote lookup.
- **latency:** Capture acknowledgment under 1 second; persist the capsule in under 3 seconds. Exact retrieval under 1 second; semantic retrieval under 3 seconds. Never block the owner on summarizing a large source—store first and summarize asynchronously.
- **cost:** Roughly $0.001–$0.01 per capture for optional compacting, plus small D1/R2 storage; exact lookup costs no model call. The dominant cost is embedding/semantic indexing if enabled, so cap excerpt size and index only owner-selected content.
- **security:** Authenticated page content and local files are highly sensitive. Require an explicit user gesture/phrase for capture, never capture whole tabs by default, encrypt at rest, keep raw content local when the owner chooses, redact credentials/financial identifiers before indexing, and give every capsule a visible source, TTL, and delete action. A later answer must distinguish captured evidence from current web state and offer a fresh browser check rather than silently using stale text.
- **missing:** A first-class capsule schema (source surface, citation, exact excerpt/hash, sensitivity, TTL, and capture consent); A browser command for selected-region capture and a Mac command for selected-file/command-result capture; Relay encryption/key handling and retrieval endpoint separate from general context graph memory; Pendant capture/retrieval intent and a compact spoken provenance format; Dashboard/iOS capsule management and retention controls

### "“Only show private Mac and logged-in-browser results when I’m actually wearing the pendant; if I take it off, pause the sensitive work and continue when I put it back on.”"
- **useful because:** Today the Mac, browser, and relay can continue acting while the owner is away, but none of them has reliable proof that the intended person is physically present. This would let the owner walk away from a shared room without leaving private notifications, authenticated-page excerpts, or draft contents exposed, while preserving useful continuity: non-sensitive background work may finish, sensitive results remain sealed, and the pendant announces the exact point at which work resumes.
- **path:** pendant: periodic authenticated presence beacon, local wear/presence sensor, and a short button gesture to re-authorize; LED indicates present, paused-sensitive, or expired authorization → mac-planner: receives the signed presence state, suppresses private onscreen/audio presentation when absent, and checkpoints work without discarding results → browser-extension: keeps authenticated tabs bound to the paired presence epoch and withholds page text, screenshots, and form previews after the epoch expires → relay: stores encrypted pending results, rotates short-lived presence leases, and sends only coarse state transitions to the pendant; it may continue explicitly non-sensitive background jobs → dashboard/iOS: shows the last presence epoch, paused jobs, and a deliberate resume control without exposing the sealed payload on an untrusted surface
- **model tier:** No realtime model is needed for presence enforcement. Deterministic firmware/relay cryptography handles leases and state; a cheap background model classifies a job's output sensitivity at planning time, with owner-configurable overrides. Realtime is used only if the owner asks for a spoken explanation while present.
- **latency:** Presence loss recognized within 2–5 seconds, with no model round trip. Re-authorization and release of sealed results under 1 second after a valid button gesture. Background jobs continue without waiting for model responses.
- **cost:** Negligible per-event API cost; cryptographic lease checks and D1 writes dominate. Optional sensitivity classification costs roughly $0.001–$0.01 per job, cached for the job lifetime.
- **security:** Presence must be cryptographically bound to the paired pendant, not inferred from an easily spoofed MAC-visible Bluetooth name. Do not transmit raw audio, page content, or credentials in the beacon. Use short-lived rotating tokens, replay protection, and a fail-closed policy for sensitive presentation. The owner must be able to revoke a lost pendant from the dashboard. Clearly distinguish ‘paused because absent’ from ‘failed’; never delete sealed results automatically without the configured retention policy.
- **missing:** A real pendant presence/wear signal or secure proximity channel; the current single-button/LED prototype has no presence sensor; Firmware support for rotating signed presence leases and replay counters within the device's constrained RAM/flash budget; A relay-side encrypted sealed-result store and presence-epoch API; A Mac/browser presentation broker that classifies and withholds sensitive output without terminating resumable work; An owner-facing sensitivity policy and lost-pendant revocation flow


## Changes it proposed to its own stack

### `hardware` — Add a low-power capacitive skin-contact/proximity sensor and a hardware-backed identity element to the pendant, while retaining the existing single button and LED. Firmware should derive a signed, rotating presence epoch from contact plus an authenticated nearby-host handshake; it should never expose a raw sensor stream. Put the sensor on an always-on low-power GPIO/I2C path and reserve the secure element for lease signing/revocation keys.
- **owner gets:** The owner could leave a shared room without private Mac/browser results remaining audible or visible, then resume them immediately on return. It also gives the system a trustworthy way to tell the owner ‘you are present’ rather than guessing from an online Mac or an easily spoofed Bluetooth name.
- effort: Medium hardware revision and firmware integration: choose a skin-contact electrode/sensor, add secure-element support, define signed epoch packets, validate false-positive/false-negative behavior across clothing and charging, and add a lost-device revocation path in the relay.  ·  risk: A contact sensor can misclassify pockets, loose wear, or another person holding the pendant. Use conservative expiry and require the existing button for sensitive reauthorization when confidence is low. Secure-element provisioning and board changes add manufacturing complexity; retain a development bypass only in lab firmware, never production.
- cost: Roughly $2–$8 per unit for a basic capacitive/proximity component plus $1–$3 for a secure element, with milliwatt-or-less idle draw if duty-cycled. No per-request API cost beyond lease state writes.  ·  latency: Presence transitions can be detected locally in roughly 1–3 seconds; no model latency. Signed lease verification is sub-millisecond on the Mac/relay.
- security: Meaningfully improves physical-presence assurance, but it is not biometric authentication. Never treat it as sufficient for irreversible financial or account actions; combine it with the existing action-specific controls. Protect private results by failing closed when the lease is stale or revoked.
- depends on: The presence-lease capability proposed this round; Pendant firmware support for rotating signed epochs within the existing constrained RAM/flash budget; Relay and Mac/browser presentation layers that consume presence epochs
