## Capabilities it proposed

### "“Did that actually happen? Give me one short proof, and tell me if the pendant, relay, Mac, or browser is still waiting.”"
- **useful because:** Today receipts can say a UI action succeeded even when /observe proves events never reached the screen, while pipeline and browser work can remain processing/offline. This capability gives the owner a truthful end-to-end answer: correlate the pendant request, relay job, Mac receipt, browser result, and a fresh perception check, explicitly distinguishing completed, delivered-but-not-confirmed, blocked, and still waiting. It is valuable precisely because no single node sees the whole causal chain.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → faculty-perception → faculty-judgement
- **model tier:** Use deterministic correlation and perception first; use a cheap background model only to compress the evidence into one spoken sentence. Reserve realtime for the owner's follow-up question.
- **latency:** 2–5 seconds for cached job/pipeline/browser state; up to 15 seconds when a fresh AppleScript or authenticated browser read is needed. Never claim success while verification is pending.
- **cost:** Usually near-zero model cost for typed state joins; roughly $0.001–$0.01 only when a background summarizer is needed. Dominant cost is a Mac/browser verification round trip, not tokens.
- **security:** Proof may include private page titles, snippets, or application state; redact secrets and minimize to the requested action. Do not perform a new action while verifying. UI receipts must be marked untrusted whenever /observe inputReachability is failed; require owner confirmation before treating an irreversible action as complete.
- **missing:** A durable cross-surface correlation ID carried from pendant audio/event through relay job, Mac job, browser command, and receipt; A read-only verifier that maps each action type to an observable postcondition and records evidence timestamp/source; A state reconciler that closes stale processing runs or labels them explicitly as abandoned/unknown, rather than leaving them indefinitely processing; A spoken proof formatter with redaction and confidence labels

### "“I have to leave now—hand this unfinished task to whichever device can continue it, and when I come back tell me exactly where it stopped, what is already done, and what still needs my approval.”"
- **useful because:** Today work is split across a live pendant conversation, relay jobs, Mac execution, and private browser sessions, but an interruption can strand the task or cause the next surface to repeat steps. The owner needs a single resumable handoff that preserves the exact checkpoint, evidence, pending approvals, and prohibited repeats across devices. This is not a briefing, watch, or generic background job: it is transactional continuity for an in-progress multi-surface task.
- **path:** pendant → relay-realtime → mac-planner → browser-extension → faculty-perception → faculty-judgement → faculty-action
- **model tier:** Use deterministic checkpointing and typed state transitions first. A cheap background model may summarize the checkpoint; realtime is only needed when the owner asks for the spoken handoff or resumes interactively.
- **latency:** Checkpoint on disconnect or explicit 'leave it' within 1 second; resume preparation within 5 seconds after another surface appears. Never execute a pending irreversible step automatically during handoff.
- **cost:** Near-zero model cost for checkpoint persistence and reconciliation; approximately $0.001–$0.01 for a concise background summary. Storage and state reconciliation dominate, not inference.
- **security:** The checkpoint may contain private browser URLs, form contents, email drafts, or calendar data. Encrypt sensitive fields, bind checkpoints to the paired owner and task, expire abandoned checkpoints, and require explicit approval before any irreversible continuation. Never copy credentials or raw secrets into the pendant.
- **missing:** A durable task-checkpoint schema spanning relay, Mac jobs, browser sessions, pipeline events, and action receipts; Per-step idempotency and a do-not-repeat ledger that records whether a step was attempted, verified, or only staged; A resumability state machine with explicit interruption, waiting-for-owner, expired, resumed, and abandoned states; A cross-surface handoff protocol so the pendant can park work and the Mac/browser can resume it without relying on transcript text; A compact checkpoint renderer that can speak the stopping point and pending approval without exposing private page contents

- **owner gets:** The owner stops receiving false 'done' answers: they can see exactly which leg failed or is still pending, including the current known condition that Mac UI events report success while doing nothing and that the browser is offline with queued commands.
- effort: Medium: schema migration plus deterministic joiner, verifier adapters for AppleScript/browser/audio, dashboard rendering, and relay/pendant spoken formatter; add replay tests for dropped links and duplicate events.  ·  risk: Incorrect joins could attribute one request's proof to another; prevent with immutable IDs and never infer identity from text alone. Verification itself must be read-only. On verifier failure, report unknown rather than success. Keep raw history untouched for audit.
- cost: Negligible API cost; storage grows by a small leg/evidence record per job. Background reconciliation can run on the cheap tier or deterministically.  ·  latency: No impact on command execution. Cached truth in under 1 second; fresh postcondition checks add roughly 1–15 seconds depending on Mac/browser availability.
- security: Evidence capsules need TTL, redaction, and per-surface access controls because browser/application state can be private. Never include raw page content or secrets in pendant speech.
- depends on: A durable correlation ID propagated by relay, Mac job tracker, pipeline events, and browser command queue; Action-specific postcondition adapters that use AppleScript/DOM/audio telemetry rather than Accessibility-dependent UI claims; A stale-run policy for existing processing records; The owner-facing dashboard and pendant formatter

- depends on: A typed cross-surface task graph and immutable correlation IDs; Action-specific postcondition verification, especially a safe alternative when GUI Accessibility is unavailable; Durable owner-approval tokens that cannot be replayed; Relay-side lease/expiry and recovery semantics; Browser and Mac adapters that expose staged versus committed state
