## Capabilities it proposed

### "“Do this, but only go as far as you can prove; if it needs my approval, buzz me and let me confirm on the pendant.”"
- **useful because:** The mind can decide a multi-step action today but cannot reliably distinguish a queued receipt from a real-world effect: the Mac currently reports UI success while Accessibility is denied, and the browser can be offline with commands pending. This makes execution honest and recoverable across the wearable, always-awake relay, Mac, and authenticated browser.
- **path:** faculty-judgement emits a typed plan with risk, preconditions, and the exact final side effect → relay persists a short-lived action lease, correlates request/action IDs, and survives the Mac or browser reconnecting → Mac agent runs a capability preflight (Accessibility, Screen Recording, focused app, filesystem/app state), executes only steps whose preconditions pass, then observes postconditions → browser extension reports online/session/tab affinity and returns evidence for private-page steps; public steps may use relay browser only when appropriate → pendant receives blocked/approval states, speaks a concise explanation, and uses the existing physical button for explicit confirmation of the final irreversible step → faculty-action compiles a truthful completion receipt: observed effect, evidence source/timestamp, or blocked reason; never infer success from queue acceptance
- **model tier:** Use the realtime tier only for the live spoken approval and brief status. Use a cheaper background model for plan validation, receipt summarization, retries, and reconnect reconciliation.
- **latency:** Preflight 1–2 seconds; approval prompt under 1 second after the plan reaches a checkpoint; reconnect reconciliation in background. A blocked result should be immediate rather than waiting for permissions.
- **cost:** Usually <$0.01 in model/API work: most steps are typed checks and local observations; realtime cost is only the short approval exchange. Relay D1/storage and a few telemetry requests dominate operational cost, not inference.
- **security:** Leases must be single-use, short TTL, bound to the intended Mac/browser session and action hash, and reject stale/replayed button presses. Never send private page contents to the relay unless required; keep evidence local where possible. Require explicit pendant confirmation for send/submit/delete/payment/account changes. Report missing permissions and private-session unavailability without pretending the action happened.
- **missing:** Typed action-plan/lease protocol shared by judgement, relay, Mac, and browser; Mac preflight and postcondition observers whose verdicts gate execution (not merely annotate receipts); Pendant protocol/UI for blocked, awaiting-confirmation, and completed-with-evidence states; Browser online/pending-command reconciliation with durable job IDs; Tests covering denied Accessibility, offline browser, reconnect, duplicate button press, and partial multi-step completion

### "“Do the same thing as last time, but show me what is different before you apply it.”"
- **useful because:** The owner can repeat real workflows without remembering every click or restating context: the system would recover the prior successful action as a reusable, evidence-backed recipe, adapt it to today’s data, and expose only the differences for approval. This is more useful than merely keeping an action log because it turns past work into a safe, personal operating procedure across private browser sessions and the Mac.
- **path:** pendant captures the spoken reference (“last time”) and presents a short spoken summary of the proposed differences → relay resolves the reference to a prior completed action graph, retains its provenance and sensitivity boundaries, and coordinates the run if the Mac disconnects → Mac agent re-observes the current filesystem, apps, and permissions, then maps the old recipe to current targets without replaying stale coordinates → browser extension reattaches the authenticated tab/session used by the prior recipe and extracts current values, while refusing to reuse a recipe against a different account or origin → faculty-perception compares prior evidence with current evidence and identifies changed fields, missing preconditions, and uncertainty → faculty-judgement decides whether the delta is safe, asks for approval only when the owner-visible effect differs, and faculty-action executes the approved typed steps with a new receipt linked to the original
- **model tier:** Use a cheaper background model to canonicalize old receipts into recipes and compute diffs. Use the realtime tier only to resolve the owner’s spoken reference and explain the final delta during the live interaction.
- **latency:** Recipe lookup under 500 ms; current-state collection 2–5 seconds; spoken diff under 10 seconds for a normal workflow. If a surface is unavailable, return the saved recipe and an explicit pause point rather than pretending it ran.
- **cost:** Typically <$0.02 per invocation. Local observation and receipt comparison dominate; background model tokens are needed only for ambiguous semantic mapping, while realtime usage is limited to the short voice exchange.
- **security:** Recipes must be scoped to account, origin, device, and action class; never store passwords, tokens, or unrestricted page text. Any change to recipient, amount, destination, permissions, deletion, or submission requires fresh physical confirmation. A recipe must expire or require revalidation when the source page or app changes materially. Keep sensitive evidence local and send only hashes/field-level diffs to the relay.
- **missing:** A versioned action-recipe format derived from receipts, with provenance and sensitivity labels; Semantic target mapping that can replace stale coordinates/selectors with current evidence; Cross-surface identity and origin binding for private browser sessions; A diff renderer shared by relay voice, Mac dashboard, and pendant speech; Policy for recipe expiry, changed high-risk fields, and mandatory physical re-approval


## Changes it proposed to its own stack

### `integration` — Introduce an evidence-gated Action Lease protocol across judgement, relay, Mac, browser, and pendant. A lease contains an action-plan hash, intended surface/session, preconditions, risk class, expiry, and checkpoint index. The executor must return preflight evidence before each checkpoint and postcondition evidence after it; the relay rejects stale or duplicate leases and records reconnect-safe state. For UI actions, accessibility/screen-recording reachability is a hard gate; queue acceptance is never an effect. The pendant button acknowledges only the explicitly named irreversible checkpoint, with the spoken target and hash rendered in the receipt.
- **owner gets:** When the owner asks the system to act, they either get proof that it happened or a clear explanation of what blocked it. They stop losing trust to fake “done” messages when the Mac lacks permission or Safari is disconnected, while still being able to approve a real send/submit from the device in their hand.
- effort: Medium-high: shared schema and state machine, relay persistence/idempotency, Mac/browser observers, pendant event handling, and end-to-end fault-injection tests.  ·  risk: A false-negative preflight could pause a harmless action; recover with a retry/recheck path and allow read-only actions to proceed under a lower risk class. A lease bug could duplicate a side effect; enforce unique action IDs, atomic relay transitions, and require postcondition evidence. Never auto-fail over private browser work to a public backend.
- cost: Negligible inference cost for typed checks; modest D1 writes and telemetry. Engineering cost is in protocol and test coverage, not hardware.  ·  latency: Adds roughly 1–2 seconds for preflight and postcondition checks; avoids long waits and unsafe retries when a surface is unavailable. Pendant confirmation adds only human decision time at irreversible checkpoints.
- security: Improves security: short-lived, session-bound, single-use leases and explicit physical confirmation reduce replay and accidental side effects. Evidence must be redacted and private-page payloads remain on the owning surface.
- depends on: Mac Accessibility and Screen Recording must be granted to the actual AI Pendant Agent binary for UI control; Durable browser job IDs and reconnect reconciliation; A shared typed context/provenance service so lease evidence carries source, timestamp, and sensitivity; Pendant firmware event/state support for awaiting-confirmation and blocked states
