## Capabilities it proposed

### "“Approve that exact change, but don’t do it if the page or data changed since I saw the preview.”"
- **useful because:** Prevents a dangerous class of browser/Mac actions: the owner approves one exact form, message, purchase, or setting, then a page refresh, account change, or reordered list causes the same approval to apply to different data. The pendant can present a short confirmation code; the Mac/browser re-checks the authenticated tab and refuses or re-previews when any bound field, URL, identity, or permission changed.
- **path:** relay-realtime → faculty-judgement → faculty-action → browser-extension → mac-planner → mac-vision → relay-realtime
- **model tier:** Use the realtime tier only to collect the owner's approval and read back a compact code. Use a cheaper background model (or deterministic code) to normalize fields and compare hashes; no model should decide equality of critical values.
- **latency:** Preview in 1–2 s; approval acknowledgement under 300 ms when the Mac and browser are online; final revalidation 1–3 s. If the bridge is offline, keep the approval pending rather than executing later without a fresh revalidation.
- **cost:** Usually <$0.01 per invocation when deterministic hashing handles comparison; a small background-model call (if semantic normalization is needed) dominates. Realtime tokens are limited to the spoken summary/code and confirmation.
- **security:** Sensitive authenticated page data remains on the Mac/browser bridge unless the owner explicitly asks for a remote summary. Bind approval to session/tab ID, canonical URL, account identity, normalized field values, screenshot/source hashes, action type, and a short expiry/nonce. Never treat a matching natural-language description as approval. Require a new button/voice confirmation after any mismatch; log a receipt containing what was approved and what was actually committed.
- **missing:** A first-class approval token containing expiry, nonce, tab/session identity, field-level hashes, and owner confirmation code; A deterministic pre-commit revalidation step shared by browser extension and Mac actions; A refusal/re-preview event delivered to the pendant, plus tests for tab navigation, login/account switch, stale DOM, and duplicate retries

### "“Before I approve this, show me what it will cause everywhere else.”"
- **useful because:** Today a preview usually shows only the immediate form or message. The owner should be able to ask about a consequential change—booking, cancellation, purchase, account setting, or schedule change—and receive a compact impact map: affected calendar events, overlapping commitments, dependent tasks, notifications, files, subscriptions, and likely follow-up work. It must remain read-only until separately approved.
- **path:** browser-extension → mac-vision → mac-planner → faculty-perception → faculty-judgement → faculty-action → relay-realtime
- **model tier:** Use deterministic extraction and graph queries for dates, amounts, identities, and dependencies. Use a cheaper background model to explain the impact map and identify likely-but-uncertain consequences. Reserve realtime for the owner's spoken question and concise readback.
- **latency:** Initial impact map in 3–8 seconds for one authenticated workflow and local Mac context; up to 20 seconds for several tabs or large local project data. The pendant should stream “checking calendar/files/account effects” rather than wait silently.
- **cost:** Roughly $0.01–$0.05 per invocation, dominated by summarizing multiple extracted sources; exact field and calendar matching should be local and deterministic. No paid model is needed when there are no detected dependencies.
- **security:** This may expose more private context than the immediate action. Keep raw authenticated pages and local files on their owning surfaces; send only redacted entities and derived impact facts to judgement/relay. Label each consequence as confirmed, inferred, or unknown, include source and timestamp, and never treat an inferred consequence as a commit permission. Require explicit approval for any follow-up action.
- **missing:** A read-only counterfactual planner that accepts a proposed action without executing it; Adapters that map browser form semantics and Mac calendar/files/tasks into shared typed entities and dependency edges; A provenance-ranked impact report with uncertainty and suppression of unrelated private data; A pendant-friendly streamed progress/result format for multi-source analysis


## Changes it proposed to its own stack

### `integration` — Add a shared approval-intent envelope and atomic commit gate between faculty-judgement, Mac planner, browser bridge, and relay. On preview, each executor emits a canonical action manifest (surface, account identity, tab/session, URL, action type, field-level normalized values, DOM/source hashes, and expiry). The pendant confirmation signs/references the manifest nonce. Immediately before execution, the same executor reacquires the live state and compares the manifest; only an exact match can enter the existing execute/browser command queue. On mismatch, cancel the queued command, emit a typed stale-approval event with changed fields and a fresh preview, and make retries idempotent. Persist the manifest and final comparison in the existing job receipt/journal so undo and audit refer to the exact approved state.
- **owner gets:** An approval will mean what the owner actually saw, not merely “yes to the last description.” A changed price, recipient, appointment, account, or page cannot silently receive an old approval; the pendant tells them precisely what changed and asks again.
- effort: Medium: shared schema and canonicalization library, adapters in planner and browser bridge, atomic gate in the durable job runner, pendant event rendering, and end-to-end race tests (refresh, navigation, account switch, duplicate delivery, reconnect).  ·  risk: Overly strict canonicalization may reject harmless dynamic fields and annoy the owner; field policies need volatile-field exclusions and a clear diff. If the bridge dies after approval, the action stays pending and expires rather than executing blindly. Recovery is a fresh preview/approval; existing cancel/undo handles actions that already committed.
- cost: Negligible storage (manifest and hashes per job) and CPU; no extra model call for exact fields. Optional semantic normalization costs <$0.01 and should not be used for critical equality.  ·  latency: Adds one live read/hash pass, typically 100–500 ms locally and up to 1–2 s for a browser round trip; mismatch path is slower because it requires a new preview.
- security: Improves authorization by binding approval to account/tab/state and short-lived nonce. Keep raw sensitive values local; receipts store hashes plus redacted diffs. Prevent replay with nonce, expiry, and idempotency key.
- depends on: Durable browser job runner and command queue must expose a pre-commit hook (chg-16bc5dee, chg-14accc01 backlog).; Existing receipt/undo path must accept the manifest and comparison result (chg-5fc73ce3).; Pendant confirmation event and action-lease indicator need to be available (previously requested device skills).

### `context` — Create a read-only counterfactual impact layer between perception and action. It accepts a normalized proposed action plus source evidence, clones only the affected typed entities/relations into an ephemeral sandbox, runs deterministic dependency queries against Mac calendar/tasks/files and authenticated browser state, and returns confirmed/inferred/unknown consequences with provenance. The sandbox must be discarded after the report and be unable to call execution routes. Add adapters for browser form fields, calendar events, subscriptions, tasks, and local project metadata, with sensitivity-aware redaction before results reach relay or judgement.
- **owner gets:** The owner can make informed decisions about changes that ripple beyond the page currently visible—without trusting a vague warning and without risking an accidental commit. They see conflicts and follow-up work before approving anything.
- effort: Medium-high: typed action schema, ephemeral graph fork, dependency rules, browser/Mac adapters, provenance and redaction, plus a hard read-only boundary and adversarial tests proving no execution side effect.  ·  risk: Dependency inference can be incomplete or over-alert. Every result must distinguish confirmed from inferred and unknown, show sources, and allow the owner to proceed only with explicit acknowledgement. Sensitive unrelated entities could leak unless graph traversal is scoped to action-relevant identities and time windows.
- cost: Small temporary graph storage and local computation; approximately $0.01–$0.05 for explanation when a background model is needed. Raw browser content should not leave the browser/Mac surfaces.  ·  latency: Adds roughly 3–8 seconds for a normal action and up to 20 seconds for multi-source analysis; stream progress through the existing pipeline so the pendant does not appear stuck.
- security: Strengthens safety by making the analysis sandbox technically incapable of committing actions. Provenance, sensitivity labels, and redaction reduce cross-surface data exposure. The sandbox must use separate credentials or no credentials for execution routes.
- depends on: A typed action manifest shared by browser and Mac surfaces.; Scoped context-graph queries with provenance, TTL, and sensitivity filtering.; Read-only adapters for authenticated browser state and Mac calendar/tasks/files.; A separate non-executable planning path; do not reuse POST /execute as a side effect of analysis.
