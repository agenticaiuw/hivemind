## Capabilities it proposed

### "“Bookmark where I am. When I say resume that thread later, put me back exactly where I left off and remind me what I was doing.”"
- **useful because:** This solves the gap between the wearable conversation and the owner’s fragmented desktop work. A pendant gesture or spoken command captures the active Mac document, relevant authenticated browser tabs, unsent draft state, and the next calendar context; later, even from another room, the pendant gives a short spoken reminder and the Mac reconstructs the workspace. It is a durable handoff, not merely a summary or a one-off meeting brief.
- **path:** pendant: button/voice intent creates a bookmark and later requests resume; queues a short audio reminder when the link is unavailable → relay: creates a short-lived, encrypted continuity capsule with provenance, TTL, and an idempotency key; coordinates the return handshake → Mac planner: captures foreground app/document and approved workspace metadata, then reopens files/apps and restores the reversible parts → browser extension: records authenticated tab/session IDs, URLs, page anchors and draft-vs-submitted status without copying secrets; reattaches tabs on resume → dashboard: shows capsule contents, expiry, restore receipt, and lets the owner delete or rename it
- **model tier:** gpt-5.6-luna for ambiguous capture/restore planning and reconciliation; gpt-4.1-mini for deterministic extraction, capsule validation, and tab/file matching; gpt-realtime-2.1 only for the live spoken bookmark/resume exchange
- **latency:** Bookmark acknowledgement under 2 seconds with a local pending event; full capsule 5–10 seconds. Resume should speak the reminder in under 2 seconds, then restore Mac/browser state asynchronously within 15 seconds and report a receipt. If the link is down, the pendant retains only the intent and short reminder until reconnect.
- **cost:** About $0.01–$0.05 per bookmark/resume depending on whether reconciliation needs the expensive planner; most deterministic captures use the cheaper tier. Storage and browser/Mac round trips dominate latency, not model tokens.
- **security:** Capsules can expose work context and authenticated URLs, so default to 24-hour TTL, encrypted storage, explicit per-capsule deletion, and redacted page snippets. Never store passwords, cookies, or full mail bodies. Restore must distinguish drafts from submitted actions and must not send, delete, purchase, or overwrite without the owner’s existing confirmation policy. Show exactly which tabs/files will reopen before any high-impact mutation.
- **missing:** A first-class capsule schema with provenance, sensitivity, TTL, and idempotency; Read-only Mac foreground/workspace capture and a browser tab anchor/draft-state capture API (the newly granted schemas exist but their implementations are absent); A pendant offline bookmark/resume event and bounded queue; A restore planner that can reattach tabs and reopen files with receipts; Owner-visible capsule list/delete/rename UI

### "“If something you’re doing for me breaks halfway through, fix what can be fixed, put everything back to the last safe checkpoint, and tell me exactly what I need to decide.”"
- **useful because:** Today a Mac/browser workflow can leave partial files, open tabs, drafts, and queued jobs in an unclear state. The owner should get transactional recovery across surfaces: safe steps retry automatically, completed steps are retained as evidence, reversible mutations are rolled back when possible, and the pendant gives one concise decision instead of an opaque failure.
- **path:** relay: maintain a dependency-aware checkpoint graph and coordinate retries across the sleeping relay, Mac, and browser → Mac planner: execute compensating actions for files/apps/shortcuts and return typed receipts → browser extension: verify tab/session state and compensate only reversible draft/form changes; never resubmit an irreversible action → pendant: announce failure, recovery result, and the single unresolved choice; accept retry/abandon/continue → dashboard: show the timeline, checkpoint, compensation attempts, and exact remaining diff
- **model tier:** gpt-4.1-mini for deterministic checkpoint validation, retry classification, and compensation; gpt-5.6-luna only when the failure is ambiguous and a recovery plan needs reasoning; realtime only for the short spoken status exchange
- **latency:** Detect and classify within 2 seconds of a failed step; automatic safe recovery within 10 seconds. If a browser or Mac surface is offline, preserve the checkpoint and notify the owner rather than repeatedly spinning.
- **cost:** Usually under $0.01 per incident for typed state comparison and receipts; $0.03–$0.10 when ambiguous recovery requires the planner. Storage is dominated by compact receipts and before/after hashes, not page contents.
- **security:** A compensating action can itself be destructive or can accidentally duplicate a submission. Require idempotency keys and before/after evidence, never auto-compensate send/delete/purchase actions, redact secrets from checkpoints, and expire recovery state. The owner’s existing destructive-action confirmation policy remains authoritative.
- **missing:** A cross-surface checkpoint and compensation schema with idempotency keys; Per-action declared compensation or an explicit non-compensable marker in Mac and browser receipts; A verified state-diff endpoint for browser tabs/drafts and Mac files/apps; A durable recovery state machine that survives relay and laptop disconnects; Pendant event types for recovered, needs-decision, and abandoned


## Changes it proposed to its own stack

### `hardware` — Make the wearable’s audio path genuinely 24 kHz end to end: use a microphone/ADC and I2S clocking mode that captures 24 kHz (48 kHz wire clock with 24-bit slots), move Opus uplink to 24 kHz rather than the current 15.625 kHz capture/16 kHz stream, keep 24 kHz decode, and teach the ESP32 bridge and relay to pass 24 kHz frames without a hidden downsample. Add a small hardware DSP/codec offload or select a production MCU with enough DSP headroom; the current nRF9160 prototype spends roughly 87% of a core when encode and decode overlap.
- **owner gets:** The owner gets natural, consistent wideband speech in both directions instead of high-quality playback fed by a narrowband uplink. This directly fulfills the stated 24 kHz superwideband goal and makes queued briefings and live conversation sound like one system.
- effort: High: choose and validate a 24 kHz-capable digital microphone/codec, retune I2S clocks and DMA, update fixed-point Opus frame/rate settings, relay transcoding, bridge framing, jitter buffering, and run RF-loss/long-call tests. Keep a negotiated 16 kHz fallback for the current prototype.  ·  risk: The nRF9160’s CPU and RAM budget may cause underruns, modem contention, or battery drain; a bad clock configuration can create drift or aliasing. Recover with explicit capability negotiation, watchdog-triggered fallback to 16 kHz, frame-loss concealment, and telemetry for encode/decode occupancy. Do not silently label 16 kHz audio as 24 kHz.
- cost: Prototype firmware/relay work is modest API cost (under $0.05 per test call); production hardware likely adds roughly $3–$12 per unit for a codec/DSP or upgraded MCU plus $1–$4 for a suitable microphone/clocking solution. Power rises during active audio, likely tens of milliwatts depending on the chosen offload.  ·  latency: A 24 kHz Opus path can retain 40–60 ms frames; expect no material conversational latency increase if offloaded. On the current MCU, software-only operation risks 20–50 ms additional buffering and underruns, so it should not ship without measured headroom.
- security: No new content leaves the device beyond the existing encrypted audio stream, but audio diagnostics must report only rates, packet loss, and CPU occupancy—not raw audio. Capability negotiation should be authenticated so a peer cannot force an unsupported mode or exhaust battery.
- depends on: A production audio hardware decision based on measured nRF9160 headroom; End-to-end relay and ESP32 bridge sample-rate negotiation; A/B audio quality and battery test harness under LTE contention; Offline queued-audio format/versioning so 24 kHz clips remain playable and can downgrade safely

### `dashboard-ux` — Add a live 'audio contract' panel and pendant status event that reports negotiated uplink/downlink sample rates, codec mode, packet-loss concealment, jitter-buffer depth, and whether the call is in true 24 kHz mode or the 16 kHz fallback. Show a one-line spoken/LED indication only on transitions (for example, 'wideband restored' or 'fallback audio') and attach the same metrics to each audio receipt.
- **owner gets:** The owner can trust what they are hearing and immediately know whether a weak LTE link or prototype limitation degraded a call. It prevents the current failure mode where 24 kHz playback makes a narrowband uplink sound as if the whole conversation were wideband.
- effort: Medium: define a signed negotiated-mode event, relay metrics aggregation, a small dashboard card, and two pendant transition states; no raw audio needs to be stored.  ·  risk: Too many status announcements would be distracting, and stale metrics could mislead. Announce only mode changes, mark telemetry freshness, and make the dashboard explicit when values are estimates or unavailable.
- cost: Negligible model/API cost; a few bytes per call event and minimal dashboard storage. No meaningful hardware cost.  ·  latency: No added conversational latency; mode-change status can be emitted asynchronously.
- security: Telemetry must exclude content and identifiers beyond a short call/job ID. Authenticate mode events so a relay or browser intermediary cannot falsely claim wideband quality.
- depends on: End-to-end sample-rate negotiation and 24 kHz implementation; A signed audio receipt schema shared by pendant, bridge, relay, and Mac dashboard
