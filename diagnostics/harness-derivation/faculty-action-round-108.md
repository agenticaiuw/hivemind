## Capabilities it proposed

### "Prepare this action across my browser and Mac, show me exactly what will happen, and when I say “approve” execute it once—or tell me precisely why it was blocked."
- **useful because:** Today judgement can decide and action surfaces can execute, but there is no single handoff that binds the owner's approval to the exact evidence and action. This gives the owner a trustworthy cross-surface transaction: reversible preparation can proceed, while a stale page, changed target, offline bridge, or replayed approval cannot cause an unintended irreversible effect.
- **path:** pendant → relay → browser-extension → mac-planner → mac-vision → dashboard
- **model tier:** Use the realtime tier only to capture/confirm the short approval phrase; use the cheaper background planner for preparation, evidence collection, and receipt summarization.
- **latency:** Preparation may take seconds and continue as a durable job; approval response should be acknowledged in under 500 ms, with execution status streamed and a final spoken receipt in under 5 s when surfaces are online.
- **cost:** One background planning call plus low-cost extraction/action calls; realtime cost only for the approval turn. Dominant cost is authenticated page extraction and any vision fallback, not the approval check.
- **security:** Approval must be single-use and cryptographically/logically bound to handoffId, canonical action hash, target tab/session, and evidence freshness window. Never send secrets to the relay unnecessarily. Destructive sends, deletes, purchases, or external submissions require explicit approval; clarification is not approval. If any precondition changes, return BLOCKED with no partial irreversible effect, retain an audit receipt, and offer undo for reversible steps.
- **missing:** A durable handoff record/state machine (PREPARED, APPROVAL_REQUIRED, APPROVED, EXECUTING, COMPLETED, BLOCKED, EXPIRED) shared by relay, Mac, and browser; An atomic preflight that revalidates target identity and evidence immediately before the irreversible step; A one-shot approval token/action hash verifier and idempotency key across browser and Mac queues; Pendant-side concise approval/blocked speech and a dashboard showing evidence, exact mutations, and receipt/undo


## Changes it proposed to its own stack

### `integration` — Add a relay-owned Handoff Transaction Coordinator between judgement and action surfaces. It canonicalizes the planned action and evidence into an actionHash, stores handoffId plus target/session bindings and expiry, exposes side-effect-free preflight, accepts exactly one approval token, then dispatches idempotently to Mac and browser. Immediately before each irreversible step it rechecks evidence freshness, target identity, bridge health, and prior step receipts; any mismatch transitions to BLOCKED before the step and emits a concise pendant event. Persist append-only decision/step receipts and link existing undo/cancel operations to the same handoff.
- **owner gets:** The owner can safely say “approve” without wondering whether the agent acted on the page it saw earlier, duplicated a send, or continued after the browser changed. Failures become an actionable explanation instead of a vague “failed,” while reversible preparation remains fast.
- effort: Medium-high: new durable coordinator/state machine, canonicalization and idempotency library, adapters for Mac jobs and browser commands, plus contract tests for replay, stale evidence, offline bridge, partial reversible steps, and concurrent approvals.  ·  risk: A coordinator bug could block legitimate actions or misclassify a step. Recover with fail-closed defaults, dry-run/preflight tests, append-only receipts, operator-visible state, and existing job undo/cancel. Never infer approval from clarification or a disconnected pendant.
- cost: Small persistent relay storage and a few D1/R2 writes per handoff; negligible model cost. Extraction/vision and external API work remain the dominant costs.  ·  latency: Preparation unchanged; one local relay preflight adds tens of milliseconds, while final browser/Mac execution remains network-bound. Approval acknowledgement can be immediate before background execution.
- security: Improves security by binding approval to exact action/evidence/target and preventing replay, confused-deputy cross-tab execution, and stale destructive actions. Store hashes and minimal metadata rather than page secrets.
- depends on: A durable job runner and browser command queue must expose idempotency and typed receipts (existing backlog work chg-16bc5dee/chg-14accc01).; Judgement must emit canonical irreversible-step classification and evidence freshness requirements.; Pendant approval/blocked indication skill and actual connected pendant are still absent; voice approval can be supported first, with pendant support when the device is online.

### `relay` — Add an action-admission health gate before enqueueing any browser step: query the latest browser heartbeat/status, classify the bridge as ONLINE, STALE, OFFLINE, or NO_TAB, refuse browser dispatch immediately when not ONLINE, and cancel/expire orphaned pending commands after a bounded TTL. Return a typed BLOCKED receipt with the exact recovery instruction instead of waiting 45 seconds for a timeout. Mac-only steps may continue independently when their preconditions pass.
- **owner gets:** A request involving Safari will fail in milliseconds with a clear “open Safari and enable the bridge” message rather than hanging for nearly a minute, and stale queued commands will not execute unexpectedly when the browser reconnects. Unrelated Mac work keeps moving.
- effort: Small-medium: relay admission middleware, heartbeat freshness policy, pending-command sweeper, typed status mapping, and tests for reconnect races and mixed Mac/browser plans.  ·  risk: A false stale classification could defer a valid action. Recover with a short grace period, explicit retry, and no destructive browser dispatch while status is uncertain.
- cost: Negligible compute/storage; fewer wasted browser timeouts and model retries.  ·  latency: Adds one fast status read; saves up to the current ~45 s timeout on offline browser actions.
- security: Fail-closed behavior reduces delayed/replayed commands after a disconnected browser reconnects; do not retain page contents in health records.
- depends on: The existing browser heartbeat/status and command queue routes (/browser/heartbeat, /browser/status, /browser/poll, /browser/result/:commandId).; The durable browser job runner/idempotency work from chg-16bc5dee and chg-14accc01.

### `integration` — Add a cross-surface execution-recovery layer based on reconciliation, not blind retry. Every multi-step action records a durable checkpoint containing the intended mutation, target identity, and an idempotency key. After a crash, timeout, bridge reconnect, or Mac restart, a background reconciler queries the authoritative surface (browser page state, Mail/Calendar/Files via AppleScript, and job receipts), classifies each step as NOT_STARTED, COMPLETED, UNKNOWN, or DIVERGED, and resumes only from proven NOT_STARTED steps. UNKNOWN or DIVERGED steps become a review item with evidence; they are never replayed automatically.
- **owner gets:** If a task fails after partially completing—such as creating a calendar event, moving a file, or submitting one step of a workflow—the owner gets a truthful “what actually happened” result and safe continuation instead of duplicate events, duplicate messages, or guessing whether a send occurred. This is especially valuable when the owner walks away and the Mac or browser reconnects later.
- effort: Medium-high: checkpoint schema, per-surface state readers, reconciliation workers, crash/restart tests, and a compact spoken/dashboard explanation for UNKNOWN and DIVERGED outcomes.  ·  risk: Some external services expose incomplete or eventually consistent state, so reconciliation may remain UNKNOWN. Fail closed, preserve the original evidence and receipts, require owner review for ambiguous irreversible steps, and allow manual marking only with an audit trail.
- cost: Low background storage and API calls; reconciliation runs only after interruption or on durable jobs, using a cheaper background model only to summarize ambiguity. No realtime model needed.  ·  latency: No effect on uninterrupted actions. Recovery may take seconds while authoritative state is read; the owner receives an immediate recovery status and a later final receipt.
- security: Reduces duplicate irreversible actions and prevents replay after reconnect. Store hashes, IDs, and minimal state proofs rather than copied private page contents; respect existing confirmation requirements for sends, deletion, and purchases.
- depends on: Typed per-step receipts from POST /execute and GET /jobs/:jobId/receipts; Durable job state from GET /jobs/:jobId and GET /journal/:jobId; Browser tab/session identity and result evidence from GET /browser/sessions, GET /browser/status, and POST /browser/result/:commandId; Mac-side authoritative readers through existing AppleScript action routes and job adapters; A durable worker that survives relay and Mac process restarts
