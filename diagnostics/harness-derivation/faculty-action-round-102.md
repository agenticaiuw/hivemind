## Capabilities it proposed

### "When you have prepared something that needs my approval, say what will happen, then let me approve it with one deliberate long press on the pendant; execute it on my Mac or in my logged-in browser and tell me the result, even if I walk away."
- **useful because:** Today approval is stranded on a dashboard while the pendant can only start/end conversation. This creates a physical, auditable handoff: judgement prepares a bounded action, the relay presents a short spoken preview, the pendant's sole button confirms the exact nonce, and faculty-action executes through the appropriate Mac/browser hand. No Accessibility is required for AppleScript/declarative actions; browser-private work remains on Safari. If the link drops, the action expires rather than running later.
- **path:** faculty-judgement → relay-realtime → pendant → mac-planner → browser-extension → faculty-action → dashboard
- **model tier:** Realtime for the short spoken preview and confirmation exchange; background/local planner for preparing multi-step plans and summarizing receipts.
- **latency:** Preview under 2 seconds; confirmation-to-execution acknowledgement under 3 seconds when Mac is online. Expire unconfirmed leases after 60 seconds; do not queue an approval across a disconnect.
- **cost:** About $0.001–$0.01 per approval depending on preview length/model; most execution and receipt work is local. Small relay storage for nonce, plan hash, and outcome.
- **security:** Never transmit secrets in the spoken preview. Bind approval to an immutable plan hash, target surface, account/session, and short-lived nonce; reject stale/replayed presses and any plan mutation. Require a second confirmation in the dashboard for destructive actions (send mail, delete, purchase), consistent with owner policy. Store only hashes and redacted receipts.
- **missing:** pendant firmware button event uplink and LED confirmation state; short-lived approval lease/nonce endpoint shared by relay, Mac, and browser; device-to-relay approval acknowledgement (ideally authenticated); executor precondition gate that refuses if the approved plan changed; audio playback completion/acceptance signal

### "Make sure this actually happened: after you perform an action on my Mac or in a logged-in browser, independently verify the real-world postcondition and keep working until it is true or tell me exactly what prevented it."
- **useful because:** Today the system can execute an action and produce a receipt, but a receipt only says what the executor attempted or observed. The owner needs closure: for example, not merely 'calendar event created,' but confirmation that it appears in the authoritative calendar; not merely 'form submitted,' but a confirmation number or changed account state. A separate perception pass prevents the acting agent from certifying its own mistake and lets the relay deliver a concise success/failure outcome to the pendant.
- **path:** faculty-judgement → faculty-action → faculty-perception → mac-planner → browser-extension → relay-realtime → pendant
- **model tier:** Cheap background/local models for polling and comparing structured postconditions; realtime only for the owner's final spoken result or an urgent failure.
- **latency:** Reversible local actions: verify within 5 seconds. Browser/account changes: retry with bounded backoff for up to 10 minutes, then deliver a failure explanation and the last evidence. Never keep retrying an irreversible action; only verify or use an explicitly approved compensating action.
- **cost:** Usually under $0.01 per workflow because verification uses structured API/DOM evidence and local comparison; cost is dominated by any authenticated browser reads and optional realtime notification.
- **security:** Verification must be read-only by default and scoped to the same account/session and target named in the plan. Store redacted evidence (URL, timestamp, field names, hashes, confirmation IDs where safe), not page secrets. Do not treat a visually similar page or stale cache as proof. For destructive or financial actions, require an independent authoritative confirmation and preserve the uncertainty if it cannot be obtained.
- **missing:** first-class postcondition schema in plans (target, predicate, authority, freshness window); independent verifier route that can read Mac APIs or authenticated browser state without re-performing the action; retry/timeout state machine distinguishing verify, retry-safe action, and compensation; evidence bundle linking pre-state, action receipt, post-state, and verifier identity; pendant notification event for verified, blocked, and timed-out outcomes


## Changes it proposed to its own stack

### `interaction` — Add an approval-lease protocol spanning relay, pendant, Mac executor, and browser bridge. POST /approvals creates a 60-second lease containing immutable planHash, action IDs, target surface/session, risk class, and human-readable preview; pipeline events expose awaiting_approval. Relay pushes the lease to the pendant, which speaks/LED-signals the preview and emits one authenticated button-confirm event containing leaseId + planHash + monotonic counter. The executor verifies lease freshness, exact hash, preconditions, and counter before dispatch; it atomically consumes the lease and emits approved/rejected/expired events. Attach the leaseId to every job receipt and spoken completion. Add a simulator path for button events and replay/expiry tests. This is deliberately separate from existing receipts/undo, which currently record effects but cannot refuse execution.
- **owner gets:** The owner can approve a prepared real-world action while wearing the device, without finding a dashboard, and can trust that a delayed or changed plan will not run. Failures become explicit ('expired', 'changed', 'Mac offline') instead of silent or ambiguous.
- effort: Medium: relay schema and event plumbing, pendant firmware button/LED state machine, Mac/browser precondition gate, and end-to-end simulator tests.  ·  risk: A protocol bug could authorize the wrong action or strand approvals. Mitigate with fail-closed hash binding, one-time counters, 60-second expiry, visible preview, destructive-action second gate, and recovery via dashboard cancellation. No hardware flashing until separately approved.
- cost: Negligible API cost; roughly 1–2 KB transient relay state per pending approval and a few small event records. Firmware RAM impact should stay under 8 KB if the preview is streamed and only hashes/lease metadata persist.  ·  latency: One relay round trip plus button event, typically 0.5–3 seconds; no added latency for actions that do not require approval.
- security: Improves security by moving approval from an unauthenticated dashboard click to a one-time, device-bound, hash-bound event. Requires device identity/key provisioning and replay protection; approval metadata should be redacted in logs.
- depends on: pendant button event uplink and device identity; executor precondition/refusal gate (existing receipts do not provide this); relay approval lease route and pipeline event types; live pendant playback/ack telemetry for reliable preview delivery

### `integration` — Introduce a postcondition-carrying execution envelope and an independent verification barrier. Extend each planned action with a typed predicate (authority, selector/API, expected state, freshness, and acceptable uncertainty). After faculty-action finishes, faculty-perception—not the acting executor—must obtain fresh evidence from the authoritative Mac API or authenticated browser tab and classify the outcome confirmed, contradicted, or unknown. The relay should continue only verification-safe retries, never replay an irreversible action, and emit a pendant notification with the evidence reference and terminal state. Persist a tamper-evident before/action/after evidence chain alongside the existing receipt.
- **owner gets:** The owner gets an honest answer about whether the thing they wanted is true in the outside system, rather than a misleading success message caused by a stale page, dialog, timeout, or partial action. This is especially valuable when they walk away after asking the pendant to handle something.
- effort: Medium-high: typed plan schema, verifier adapters for Calendar/Mail/files/browser, independent evidence storage, bounded retry state machine, and relay/pendant outcome notifications.  ·  risk: A verifier can misread stale or ambiguous evidence and either claim success or waste retries. Require freshness tokens, authority allowlists, explicit unknown state, bounded attempts, and no automatic compensation unless separately approved. If verification is unavailable, preserve the action receipt but say unverified.
- cost: Low additional model cost; mostly local API/DOM reads. Storage is a small redacted evidence chain per action. Browser verification may consume authenticated-session time.  ·  latency: Adds 1–5 seconds for local verification and potentially minutes for bounded browser propagation. The owner receives an immediate 'action dispatched; verifying' status followed by a definitive or unknown result.
- security: Read-only verification reduces unsafe blind execution, but evidence can contain private account data. Keep it on the Mac/relay with redaction, access control, retention limits, and hashes rather than raw page contents.
- depends on: typed postcondition schema; faculty-perception verifier adapters; fresh authenticated browser inspection with source timestamps; relay state machine for verify/retry/unknown; pendant notification uplink
