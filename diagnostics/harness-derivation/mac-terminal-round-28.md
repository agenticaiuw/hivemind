## Capabilities it proposed

### "“Check that logged-in page for me. If my Mac or browser is unavailable, wait safely and finish when it comes back—tell me whether it is waiting, completed, or failed, and never repeat a step that already ran.”"
- **useful because:** Today a pendant request can encounter an offline browser extension, spend roughly 45 seconds timing out, and leave the owner unsure whether the site, Mac, or command failed. This gives the owner dependable cross-device continuity: the relay stays awake, the Mac owns execution, Safari contributes the private session, and the pendant reports truthful progress and completion without duplicate navigation or submissions.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** Use deterministic health checks, job state transitions, idempotency, and receipts for most of the flow; use the background tier only to summarize a completed result or explain an unusual failure. Reserve realtime for the owner's spoken status/questions.
- **latency:** Healthy requests should begin within 1–2 seconds. An unavailable browser should be reported in under 1 second rather than waiting for a 45-second action timeout. Reconnection resumes on the next authenticated heartbeat; spoken completion follows within a few seconds.
- **cost:** Usually near-zero incremental model cost: heartbeat checks, queueing, and resume are deterministic. A short background summary costs one inexpensive model call only when a completed result needs narration; storage is a few KB per pending job and receipt.
- **security:** Private page contents and cookies remain in Safari on the paired Mac. The relay stores only encrypted job state, action IDs, status, and minimal result metadata. Reconnection must not authorize an irreversible action by itself: resume only actions proven unstarted/idempotent, expire stale leases, and report any ambiguous step for owner review.
- **missing:** A paired-browser heartbeat/capability lease visible to the Mac bridge and relay; A durable waiting-for-device job state with bounded retry and dead-letter expiry; Cross-surface resume keyed by stable action IDs and existing receipts; Pendant and dashboard status events that distinguish waiting, completed, failed, and ambiguous outcomes; A browser preflight that fails fast when the extension is offline instead of waiting for the action timeout

### "“Why didn’t that work?”—give me the actual evidence from the pendant request, relay, Mac command, and browser session, explain the failure in plain language, and tell me the safest next step without rerunning anything."
- **useful because:** Today a failed cross-device task is fragmented: the pendant knows the request, the relay knows delivery, the Mac knows the job, and Safari knows whether a session was alive. The owner cannot ask one place for a causal answer and may accidentally retry a command or browser transaction that already partly ran. A cross-surface failure explanation turns raw receipts and health state into a trustworthy diagnosis before any retry.
- **path:** pendant → relay → mac-bridge → browser → dashboard
- **model tier:** Collect and correlate evidence deterministically from job receipts, shell envelopes, relay delivery events, and browser heartbeat/session state. Use the background tier to produce the concise explanation; use realtime only to speak it interactively. Never invoke the planner merely to collect evidence.
- **latency:** Evidence collection under 500 ms when devices are online; under 2 seconds if the relay must fetch recent records. A spoken explanation within 3 seconds, with a follow-up link to the detailed dashboard evidence.
- **cost:** Near-zero for correlation and classification; one short background summarization call when wording is needed. Local evidence retention is bounded and cheaper than a blind low-latency retry.
- **security:** Do not send shell stdout, URLs, page text, cookies, or environment values to the relay by default. Relay receives opaque IDs and redacted failure classes; detailed evidence stays on the Mac and is shown only through the paired dashboard or on explicit owner request. The capability is strictly read-only and must not trigger retry or undo.
- **missing:** A shared operation ID linking pendant intent, relay delivery, Mac job/receipt, and browser command/session; A normalized event schema with timestamps and causal links across relay, Mac, and browser; Shell execution envelopes containing bounded, redacted failure evidence; Browser heartbeat/session evidence that distinguishes offline bridge, closed tab, navigation failure, and page-level error; A read-only cross-surface diagnosis endpoint and concise pendant response formatter


## Changes it proposed to its own stack

### `integration` — Add a cross-surface browser availability supervisor. The relay/mac agent records extension heartbeats and a short-lived capability lease; before dispatching any browser action, the Mac performs a cheap local health read. If the lease is stale, fail the action immediately (not after the current ~45-second browser timeout), classify it as 'device unavailable' rather than action failure, retain the idempotent job in a dead-letter/waiting state, and notify the pendant. When a fresh Safari bridge heartbeat arrives, resume only unstarted action IDs and send one completion/failure receipt. Include outage start, last heartbeat, retry count, and the exact reattachment instruction in the spoken status.
- **owner gets:** A request made from the pendant will no longer burn nearly a minute per browser step or look like the account/site is broken when Safari is simply closed or the extension is offline. The owner gets a truthful spoken 'waiting for Safari' status and automatic continuation when the Mac/browser comes back, without duplicate form submissions or repeated navigation.
- effort: Medium: add lease/heartbeat state to the Mac bridge, a preflight in browser dispatch, a waiting/dead-letter job state with idempotent resume, relay event propagation, and pendant notification copy; test crash/reconnect and stale command cleanup.  ·  risk: A stale heartbeat could delay a healthy but briefly reconnecting bridge; use a short preflight timeout and explicit manual retry. A reconnect during a step could create ambiguity, so resume only after receipt says the step never started or the action ID is safely idempotent. Keep pending commands bounded and expire them with a visible reason.
- cost: Negligible API cost: deterministic health checks and event forwarding; one small D1/SQLite state record per lease/job. Saves expensive planner retries and 45-second local timeouts.  ·  latency: Healthy browser actions gain only a few milliseconds for the local preflight; offline actions return in under a second instead of ~45 seconds and reconnect jobs resume on the next heartbeat.
- security: No page contents or cookies leave the Mac. Heartbeats carry extension ID, capability state, and timestamps only; bind leases to the paired device and never treat a heartbeat as authorization to submit a pending irreversible action.
- depends on: A browser bridge heartbeat endpoint that reports online/offline and pending-command ownership; Durable action IDs/receipts already implemented in the Mac harness; Relay-to-pendant job status events and a waiting/resume state in the job tracker

### `mac-harness` — Add a shell execution envelope and recovery record around every run_shell invocation without changing the owner's unrestricted FULL_CONTROL policy. Persist command text plus SHA-256, resolved cwd, start/end monotonic times, timeout, exit code/signal, stdout/stderr byte counts and bounded tails, environment fingerprint (names and hashes only), and whether the process spawned children. For failures, deterministically classify timeout, missing executable, permission, nonzero exit, and transport crash; attach a suggested retry strategy and allow the planner to retry only transient classes with a fresh job/action ID while linking attempts under one parent operation.
- **owner gets:** When a Mac task fails, the agent can say what actually happened—wrong directory, missing tool, timeout, or a command error—and recover from transient failures instead of blindly repeating or asking the owner to diagnose. The owner can audit exactly what ran without dumping secrets such as tokens or full environment variables.
- effort: Medium: wrap computerControl.runShell's child-process result, redact/size-limit output, add parent/attempt links to existing receipts and journal, implement deterministic failure taxonomy and bounded retry policy, and expose a concise dashboard/pendant completion receipt.  ·  risk: Output can contain secrets; redact known token/key/password patterns and store only bounded tails with configurable retention. Retrying arbitrary shell is not always safe, so default automatic retry only for process launch/transport/timeouts when the command is marked retry-safe; otherwise report a one-click/manual retry. Child-process accounting is platform-specific and may be unavailable for some commands.
- cost: Near-zero model cost; a few KB of local journal storage per attempt with retention cleanup. Avoids planner calls for straightforward diagnosis and transient recovery.  ·  latency: A few milliseconds of wrapper overhead; transient retry adds bounded delay only when needed. Failure reporting becomes immediate and structured rather than requiring another low-latency model turn.
- security: Preserves unrestricted execution and no approval gates. Store command/output locally with permissions, hash the command for correlation, redact environment values, and send only the summary/error class to relay unless the owner explicitly requests diagnostic details.
- depends on: Existing action receipts and /journal observability; A bounded local retention policy for shell transcripts; A planner/executor contract that marks an action retry-safe without blocking other actions
