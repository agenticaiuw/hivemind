## Capabilities it proposed

### "“Remember this even if there’s no signal: …” — capture my spoken note on the pendant, then when it reconnects transcribe it, file it into ~/AI-Pendant-Workspace with source/time/location confidence, and tell me on the pendant exactly where it landed."
- **useful because:** The owner can safely capture thoughts while walking through LTE dead zones without keeping the thought in working memory. This is more than a voice memo: the pendant buffers only failed uploads, the relay resumes delivery, and the Mac turns the recovered utterance into a searchable, cited workspace artifact with a delivery receipt.
- **path:** pendant → relay → mac-planner → dashboard
- **model tier:** Use gpt-realtime-2.1 only for the live capture acknowledgement and a short playback receipt; use a cheaper background transcription/extraction model on reconnect, and mac-planner gpt-5.6-luna only for filing/classifying into the workspace. No browser or iOS required for the core path.
- **latency:** Local capture acknowledgement under 150 ms. Reconnect upload is opportunistic and resumable; transcription/file receipt within 2 minutes of network recovery. If classification is ambiguous, save to Inbox rather than block delivery.
- **cost:** About $0.005–$0.03 per short note, dominated by transcription and extraction; LTE airtime and SD writes dominate device energy, not inference. Background batching can reduce cost.
- **security:** Audio remains on the SD only while upload is unavailable, encrypted-at-rest with a device key if supported; relay stores an expiring ciphertext/object and deletes it after confirmed Mac receipt. Sensitive notes must not be spoken back in public. Filing and receipt need no confirmation, but any extracted action that sends mail, changes calendar, or deletes data must enter the existing confirmation gate.
- **missing:** A pendant offline-note mode with a bounded SD spool, chunk hashes, sequence numbers, and a local spoken/LED acknowledgement distinct from ordinary call audio; A reconnect upload protocol with resumable chunks and an idempotency key, plus relay-to-Mac delivery receipts and retry/dead-letter status; A Mac workspace filing endpoint that writes a markdown note plus JSON provenance sidecar under ~/AI-Pendant-Workspace/Inbox and returns the final path; A device key / key rotation policy for SD-stored audio and an owner-visible retention/delete control

### "“What am I looking at?” — use the pendant as the trigger, inspect the Mac’s current window (and the authenticated browser tab if that is the source), then answer aloud with the relevant text, controls, or next safe step without making any changes."
- **useful because:** Today the owner must stop, describe the screen, and manually bridge the wearable conversation to the Mac. This would make the pendant a genuinely hands-free context switch: a spoken question becomes an evidence-backed answer about the exact private page or app in front of them, while preserving the existing confirmation boundary for actions.
- **path:** pendant → relay-realtime → mac-vision → browser-extension → mac-planner → dashboard
- **model tier:** Use realtime only to recognize the short trigger and speak the answer. Use mac-vision gpt-4.1-mini for screenshot/UI grounding, browser-extension for DOM text and tab identity, and mac-planner gpt-5.6-luna only when reconciliation or a multi-step explanation is needed. Prefer extracted DOM text over sending screenshots to the expensive tier.
- **latency:** Acknowledge locally in under 150 ms; return a first answer in 3 seconds for a normal app or browser page, with a 6-second ceiling before saying it is still inspecting. Never wait indefinitely on a stale browser extension.
- **cost:** About $0.01–$0.06 per request, dominated by vision tokens; DOM-first routing and a short-lived screenshot reduce cost. No background calls unless the owner explicitly asks for follow-up.
- **security:** The request may expose private browser content, passwords, messages, or financial data to model processing. Require an enrolled pendant session, show the active app/tab title before capture when practical, redact password fields and tokens at the Mac harness, keep screenshots/text ephemeral, and log only provenance hashes. Reading is allowed under the owner’s standing rule; clicking, typing, sending, purchasing, or deleting still requires the existing confirmation gate.
- **missing:** A signed pendant-to-Mac context-request channel carrying request ID, freshness deadline, and cancellation; A Mac active-window capture/redaction service that can provide accessibility metadata and a screenshot without stealing focus; A browser bridge operation returning tab URL/title, selected DOM regions, and redacted text for the active tab; A unified evidence envelope (source surface, timestamp, screenshot/text hashes, confidence) and a realtime response stream; A clear owner-facing privacy indicator and policy for when private screen content is allowed to leave the Mac


## Changes it proposed to its own stack

### `integration` — Create an end-to-end offline-note delivery protocol: the pendant writes each failed-upload utterance as an append-only SD spool record (noteId, monotonic sequence, codec, byte length, SHA-256, createdAt, retry count), resumes with chunk-level acknowledgements after LTE reconnect, and the relay atomically records receipt before exposing it to the Mac. mac-planner consumes the receipt, transcribes and files a markdown note plus provenance sidecar in ~/AI-Pendant-Workspace/Inbox, then posts a signed delivered/needs-review receipt; the relay sends that compact status back to the pendant for a spoken acknowledgement. Add crash recovery, dedupe, bounded quota, and explicit purge of delivered records.
- **owner gets:** A thought captured out of coverage will not disappear, duplicate, or silently remain trapped on a memory card. The owner gets one reliable path from speech to a file they can find, with honest confirmation of whether it was uploaded, filed, or needs review.
- effort: Medium-high: firmware spool/replay and tests; Worker D1/R2 receipt state; Mac planner file writer and receipt route; dashboard status view; fault-injection tests for power loss, duplicate chunks, and reconnect during half-duplex audio.  ·  risk: Power loss or corrupted SD records could lose a note; use journaled records, per-record hashes, and quarantine rather than delete on validation failure. A compromised Mac could receive private audio; bind receipts to the enrolled device and encrypt transport/object storage. Never claim filed until the Mac fsyncs both files.
- cost: Low incremental API cost if transcription is batched with other background work; R2/D1 and LTE traffic are modest. SD wear rises with journaling, so use sequential append and periodic checkpoints.  ·  latency: Immediate local acknowledgement; delivery is network-dependent. Chunk resume avoids restarting long uploads over LTE-M.
- security: Adds sensitive offline audio persistence and a new Mac delivery endpoint; require per-device authentication, encrypted objects, short TTL after delivery, replay protection, and dashboard deletion. Do not put note contents in LED or URL query strings.
- depends on: A pendant-local offline-note trigger and bounded SD spool; A resumable chunk upload/receipt API on the relay; A Mac workspace filing endpoint with atomic write and provenance sidecar; Owner-approved SD encryption/key lifecycle

### `hardware` — Revise the wearable from the development kit to a low-power product board with a small haptic motor and a secure element connected on the currently unused I2C bus, while retaining the microSD option behind a power-gated load switch. Add a fuel-gauge IC and expose its interrupt to the MCU. Define haptic patterns for recording, queued-offline, uploaded, filed, and error states; keep spoken content off the haptic channel.
- **owner gets:** The owner can confirm—without looking at an LED or speaking aloud—that a note was captured, is still queued, or really reached the Mac. Battery warnings become trustworthy, so the pendant does not die during an important capture.
- effort: High hardware revision plus enclosure, power and EMC validation; modest firmware driver work and end-to-end state mapping. Prototype first with an I2C haptic driver, fuel gauge, and secure element breakout before committing the PCB.  ·  risk: Motor current spikes can brown out LTE or corrupt SD writes; use a load switch, current limit, reservoir capacitor, and schedule haptics outside modem TX bursts. Secure-element provisioning mistakes could strand devices; provide factory recovery and key rotation. A failed haptic must not block capture or falsely signal delivery.
- cost: Roughly $8–$20 BOM increase at low volume (haptic, fuel gauge, secure element, power components), negligible inference cost; haptic pulses add small battery drain, while the fuel gauge adds tens of microamps.  ·  latency: Haptic acknowledgement remains local and sub-100 ms; modem scheduling may defer it by a few milliseconds.
- security: Per-device keys enable authenticated spool records and encrypted SD manifests; provisioning and recovery become security-critical. No secrets should be exposed through vibration patterns.
- depends on: Offline-note spool protocol and receipt state machine; Measured LTE TX current and brownout behavior on the product power rail; Defined device enrollment/key rotation service


## What it asked for

### `s2-98pi` (skill) — offline_note_spool
- does: On a deliberate long press (or a distinct server-configured capture mode), records one short utterance locally when the uplink is absent or fails, writes a journaled hashed Opus record to the microSD failure buffer, and on reconnect replays chunks until the relay acknowledges durable receipt. It gives a local LED/audio acknowledgement and never silently treats an unuploaded note as delivered.
- must be on-device because: It must continue during LTE-M dead zones, survive a dropped WebSocket and power interruption, and access the microphone, SD, button, and LED locally. The server cannot recover audio that was never transmitted.
- trigger: Long press of the sole user button starts/stops offline-note capture; automatic fallback after an ordinary upload failure may be enabled only while explicitly in note mode. Reconnect/modem-online events trigger replay. Server push can update retention or quota policy.
- storage: microSD only while pending: append-only journal plus Opus payload and a small manifest (noteId, sequence, codec, length, SHA-256, createdAt, status). Suggested 64 MiB quota and delete-after-delivered policy; no routine cloud copy beyond the pending object.
- RAM budget: ~12–20 KiB: one 60 ms Opus frame, SD write buffer, manifest, hash state, and replay window. Reuse the existing encoder/I2S buffers; do not allocate a second audio pipeline. This fits 211,608 B application RAM but must be measured against the current ~87% CPU combined encode/decode load and half-duplex modem behavior.

## Its own summary

This round produced a new cross-surface capability: offline spoken notes that survive LTE dead zones, resume from the pendant's SD spool, get transcribed and atomically filed by the Mac into ~/AI-Pendant-Workspace with provenance, and return a truthful filed/queued/error receipt to the pendant. I proposed the resumable protocol and a product-board change (haptics, secure element, fuel gauge), and queued the firmware skill offline_note_spool. Live status confirms the relay and Mac bridge are reachable with durable audio, while the browser is offline and the Mac is not Accessibility/Screen-Recording ready.

**Biggest unknown:** The exact offline-note interaction and privacy policy still need owner/product decisions: long-press duration and maximum note length, whether failed ordinary calls may automatically enter note mode, SD quota/retention, and the device-key provisioning/recovery design. Implementation also needs a Mac atomic-file receipt endpoint and relay chunk-resume API; no further tool or permission request is useful this round.
