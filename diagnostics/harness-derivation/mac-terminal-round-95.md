## Capabilities it proposed

### "Fix the thing that just failed on my Mac."
- **useful because:** Today a failed shell or desktop job leaves the owner to repeat the request or inspect logs. This would turn a failure into a bounded incident: identify the exact failing step, collect the relevant evidence, consult documentation when useful, attempt a safe recovery or retry, and report one short spoken result. It uses the pendant for the request and notification, the always-on relay for durable state, the Mac for diagnosis and execution, and the browser only when a logged-in/private page or public documentation is needed.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use the realtime tier only to hear the owner's short command and speak the result. Run failure classification, log summarization, documentation lookup, and retry planning on a cheaper background model; reserve the expensive model for genuinely ambiguous recovery plans.
- **latency:** Acknowledge within 1 second from the pendant. Produce a diagnosis from the existing receipt and captured stdout/stderr within 5 seconds. Attempt one automatically reversible retry within 30 seconds; if diagnosis is ambiguous, speak the proposed next step instead of burning repeated retries.
- **cost:** Usually one small background-model call over a compact failure packet plus zero or one web lookup; roughly 1–3 cents per incident depending on documentation retrieval. Realtime cost is limited to the brief acknowledgement and result.
- **security:** Failure packets must redact bearer tokens, cookies, secrets, and likely personal data from environment variables and command output before leaving the Mac. Private browser pages remain on the browser/Mac path. No approval gate is added, honoring the owner's maximum-access policy, but every attempted recovery must carry the existing receipt and an explicit reason, with irreversible retries marked as such. Automatic retries should be limited by attempt count and idempotency key to prevent loops.
- **missing:** A structured failure packet on every Mac action containing actionId, argv or shell text, exit status, timeout/signal, stdout/stderr excerpts, cwd, environment fingerprint, and redaction markers.; A durable incident record and retry state machine in the relay, linked to the existing job and receipt IDs.; A recovery planner that can choose among retry, compensating undo, alternate typed action, browser documentation lookup, or handoff to the owner.; A relay-to-Mac retry route with idempotency and a hard retry budget, plus dashboard and pendant status updates.

### "When something breaks, file a complete bug report for me automatically."
- **useful because:** The owner already wants a pendant that files its own bug reports from the UART log. A useful report should correlate the pendant's local UART/audio pipeline symptoms with the Mac action receipt, relay job, browser tab (when relevant), and exact timestamps—without making the owner reproduce the failure. The owner gets a ready-to-forward report and a one-sentence spoken confirmation instead of debugging across devices.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use a cheap background model to turn structured logs into a concise reproduction summary and redact sensitive fields. Use realtime only if the owner asks follow-up questions. Do not send the report externally automatically; leave it as a local/exportable draft.
- **latency:** Start collecting evidence locally immediately. Show a draft incident in the dashboard within 3 seconds of a terminal failure or pendant watchdog event, then enrich it asynchronously within 15 seconds. UART collection must never delay audio playback or button response.
- **cost:** Near-zero for collection and correlation; typically 1–2 cents for one compact background summarization call. Storage is a bounded local/relay record plus small compressed log excerpts; no model call is needed if the owner only wants raw evidence.
- **security:** Redact bearer tokens, cookies, environment secrets, personal paths where appropriate, and private page text before relay upload. Keep raw UART logs on the pendant/Mac by default, with an owner-controlled attach action. Browser evidence should be a URL/title and DOM locator or hash, not full authenticated page content unless explicitly requested. Reports must state which fields were omitted and preserve immutable hashes for evidence integrity.
- **missing:** A pendant UART-log ring buffer with event IDs, firmware version, reset reason, and bounded export over the existing pipeline/event channel.; A shared incident schema linking pendant event IDs, pipeline IDs, Mac job/action/receipt IDs, browser command IDs, timestamps, and redaction status.; Automatic correlation in the relay that opens or updates one incident instead of producing duplicate reports during reconnects.; A dashboard incident view with raw-versus-redacted evidence, export to Markdown/JSON, and owner-controlled retention/deletion.; A local-agent hook that emits a structured failure event for every run_shell, typed action, browser action, timeout, and planner exception.


## Changes it proposed to its own stack

### `integration` — Add a cross-surface incident-correlation ledger, not another executor: on every Mac, browser, relay, or pendant failure, write a compact append-only event keyed by a shared correlationId and actionId; asynchronously join events by time window and parent job, attach the existing receipt/undo verdict, record disconnect/reconnect gaps, and expose one redacted incident bundle through the dashboard. Start with local-agent hooks around executor.js and browserBridge result handling, relay ingestion from pipeline events, and a pendant event envelope carrying boot/session sequence numbers. Deduplicate retries and reconnects by idempotency key; retain raw evidence locally and only upload redacted excerpts.
- **owner gets:** When a failure crosses devices, the owner sees one truthful timeline—what the pendant heard, what the relay dispatched, what the Mac/browser attempted, and where it stopped—instead of several incomplete job records. It directly enables the owner's requested self-filed pendant bug reports and makes support/debugging possible without asking them to reproduce the problem.
- effort: Medium: shared event schema and local hooks first, relay append/query and correlation worker second, dashboard incident panel and pendant envelope third. Add deterministic tests for dropped links, duplicate results, clock skew, and redaction.  ·  risk: Incorrect time correlation could merge two simultaneous jobs or split one across reconnects. Mitigate with parent IDs, monotonic device sequence numbers, confidence labels, and never deleting source receipts. If correlation fails, preserve separate events and show the uncertainty rather than inventing a story. UART/log volume must be capped and backpressured so audio and action latency are unaffected.
- cost: No recurring model cost for collection/correlation; optional background summarization costs about 1–2 cents per incident. Small D1/R2 growth from bounded redacted bundles; local ring buffers avoid shipping every raw log.  ·  latency: No synchronous network dependency on action execution. Hook overhead should be under 5 ms; incident joining and summarization happen asynchronously, with a draft visible in roughly 1–3 seconds.
- security: Sensitive stdout, environment variables, bearer tokens, cookies, authenticated page content, and secret UART fields are redacted before relay persistence. Preserve hashes and source locations for integrity. Raw logs stay on-device unless the owner explicitly exports them. This adds observability, not a gate or reduced access.
- depends on: A versioned event envelope shared by local-agent, relay, browser bridge, and pendant firmware; A pendant UART ring buffer and bounded event export; A relay incident storage/query route and retention policy; A local-agent failure-event hook for shell, typed actions, browser actions, timeouts, and planner errors

### `hardware` — Add a low-power wear/presence sensor and a hardware privacy state to the pendant: detect skin contact or lanyard removal, latch a local microphone/audio-capture mute and emit signed wear-state transitions over the existing radio link. Relay, Mac, and browser bridges consume that state as a shared session signal: when unworn, stop starting new capture or browser reads and mark in-flight work as paused; when worn again, resume only explicitly resumable work. Include a physical LED indication and a button override for false positives, with the state retained through brief link loss.
- **owner gets:** The owner can wear the pendant all day without wondering whether it is listening or whether a private Mac/browser task will continue after they set it down. Removing it would be an immediate, visible privacy boundary that works even when the relay or Mac is unreachable, while putting it back on restores continuity instead of losing the session.
- effort: Hardware revision for a capacitive electrode or optical/proximity sensor, firmware debounce/calibration and signed event framing, relay session-state propagation, and Mac/browser hooks that pause only resumable work. Add tests for removal during speech, radio loss, false contact, charging, and rapid wear transitions.  ·  risk: A bad fit or clothing could cause false removal and interrupt a conversation; calibration, hysteresis, LED feedback, and an explicit button override mitigate this. A sensor failure must fail closed for capture but must not erase queued work. Do not infer identity or store biometric measurements—persist only boolean state, transition time, and confidence.
- cost: Roughly $0.20–$2 for a capacitive/proximity component and PCB/layout revision, with sub-milliamp average draw. Negligible API cost; only tiny state events cross the relay.  ·  latency: Local mute/latch should take under 100 ms and must not depend on the network. Cross-surface pause notification should arrive within the normal link heartbeat, with reconnect reconciliation on return.
- security: Strengthens privacy at the device boundary: local hardware mute is authoritative and signed wear events prevent an untrusted bridge from claiming the pendant is present. It introduces no new private data beyond presence transitions and should default to unworn on ambiguous sensor state.
- depends on: A pendant firmware event type for signed wear-state transitions; A local hardware mute path that survives dropped links; Relay session-state propagation to the Mac and browser bridge; Mac/browser job semantics that distinguish resumable from non-resumable work
