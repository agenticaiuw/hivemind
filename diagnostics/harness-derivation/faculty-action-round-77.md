## Capabilities it proposed

### "“Finish the prepared action.” The system should show me the exact pending changes in a short spoken summary, let me approve from the pendant, carry out the browser and Mac steps in order, survive a dropped voice connection, and later tell me exactly which side effects happened (or safely reconcile and stop)."
- **useful because:** Today planning, browser dispatch, Mac execution, voice, and receipts are separate. This gives the owner one reliable hands-free commit path for multi-surface work: approval is unambiguous, execution resumes after disconnection, and the final answer distinguishes dispatched, verified, and not-done effects instead of claiming success from an HTTP response.
- **path:** faculty-judgement → relay-realtime → relay → pendant → browser-extension → mac-planner → mac-vision → mac-terminal → faculty-perception → faculty-action → dashboard
- **model tier:** Use the realtime model only to summarize the pending commit and speak the result; use the cheaper background/relay worker for checkpoint execution, retries, and reconciliation; use local Mac/browser agents for their respective steps.
- **latency:** Approval summary under 2 seconds; pendant acknowledgement under 300 ms; each checkpoint may take seconds. After disconnect, reconciliation can run in the background and report on reconnect or the next briefing.
- **cost:** About one realtime turn for the spoken preview and one for the final receipt; background orchestration is low-cost. Dominant cost is browser/Mac model calls for ambiguous steps, not the durable checkpoint store.
- **security:** Never infer approval from speech being heard or a stale plan: bind approval to a plan hash, expiry, owner session, and a deliberate pendant button gesture. Destructive browser/Mac steps remain individually gated. Persist only redacted before/after hashes and provenance; private page content stays on the Mac/browser bridge. If proof is missing, stop and say unknown rather than retrying a possibly non-idempotent action.
- **missing:** A durable multi-surface commit record with ordered checkpoints, idempotency keys, plan hash, expiry, and reconciliation state; A common side-effect proof schema from browser and Mac (before/after evidence, not just dispatch receipt); A pendant approval/acknowledgement transport and local pending-state indicator; Reconnect-time delivery of the final spoken receipt and a dashboard timeline

### "“Keep this situation under control until it is resolved.” The system should monitor the outcome of a decision across my logged-in browser and Mac, detect an exception, choose the next permitted reversible step, and escalate to my pendant only when judgment is needed—for example, track a support case or delivery, prepare the next response when the status changes, and stop before any irreversible action."
- **useful because:** Today the system can perform a task or watch a page, but it cannot maintain a bounded course of action whose next step depends on verified real-world changes. The owner gets continuity rather than repeated re-explanations, while irreversible decisions remain theirs.
- **path:** faculty-judgement → faculty-perception → faculty-action → relay → relay-realtime → browser-extension → mac-planner → mac-vision → mac-terminal → pendant → dashboard
- **model tier:** Use a cheaper background model for polling, state comparison, and selecting among pre-approved reversible branches. Invoke the realtime model only for a genuinely novel exception or a short pendant escalation. Keep browser/Mac execution local to their surfaces.
- **latency:** Routine checks can run on a minutes-to-hours cadence. An exception should reach the pendant within one polling interval; spoken escalation under 2 seconds once connected.
- **cost:** Low background inference and storage per monitored case; cost is dominated by authenticated page reads and occasional local-agent calls. Realtime usage occurs only for unresolved exceptions.
- **security:** The owner must define scope, expiry, allowed surfaces, and permitted reversible actions. Never send, purchase, delete, or submit without fresh confirmation. Store state fingerprints and provenance rather than private page bodies where possible. If authentication expires or evidence conflicts, pause and notify rather than improvising.
- **missing:** A bounded case/contingency object containing goal, expiry, allowed actions, escalation policy, and stop conditions; State-transition evaluation that compares verified browser/Mac observations against the case and selects a pre-approved branch; A durable exception queue that can wake the relay and deliver a pendant notification; Per-branch authorization and proof that an action changed the intended state, not merely that it was dispatched


## Changes it proposed to its own stack

### `integration` — Add a cross-surface commit coordinator between judgement and faculty-action. It materializes a versioned action graph (Mac, browser, relay, pendant), assigns each step an idempotency key and pre/postcondition, and stores append-only checkpoints. Browser and Mac workers must return typed evidence (dispatch, observed-before, observed-after, or unknown). The coordinator retries only steps declared idempotent, pauses on unknown/non-idempotent outcomes, and emits one signed receipt stream consumed by relay-realtime, the pendant, and dashboard. On reconnect, the pendant receives the pending commit state and a concise spoken result rather than a duplicate command.
- **owner gets:** A dropped call or flaky browser bridge will no longer leave the owner guessing whether an email/form/reminder happened. They get one safe approve-once workflow and an honest, auditable answer; ambiguous side effects stop instead of being repeated.
- effort: Medium-high: shared schema and state machine, adapters in Mac job runner and browser bridge, reconciliation probes, relay persistence, pendant event/audio client, and dashboard timeline; then fault-injection tests for disconnects and duplicate deliveries.  ·  risk: A coordinator bug could pause legitimate work or, worse, duplicate a non-idempotent action. Default-deny unknown outcomes, per-step idempotency declarations, short leases, explicit cancellation, and existing undo/receipt routes provide recovery. Roll out read-only shadow receipts before enabling execution.
- cost: Small storage and relay overhead; roughly one compact record per checkpoint. Background reconciliation is inexpensive. No extra realtime model call except preview/final speech; ambiguous steps still incur existing local-agent/model costs.  ·  latency: Adds tens of milliseconds to dispatch and durable writes; no added delay within a step. Final receipt may arrive later after reconnect or reconciliation.
- security: Plan hashes, owner/session binding, expiry, least-privilege surface tokens, and redacted evidence prevent stale or cross-session approvals. Private DOM/content remains on the browser bridge/Mac; only hashes and typed facts leave.
- depends on: The existing Mac job/receipt and browser command/result paths must expose stable idempotency keys and typed evidence.; A durable relay job store (the current job runner backlog item is still open).; Pendant approval and pending-state transport; the owner’s requested physical confirmation/lease skills are still unavailable this round.; A reconnect route that queues the final spoken receipt and a dashboard view of the timeline.

### `integration` — Add a bounded Contingency Case runtime, distinct from one-shot jobs and page watches. A case stores a goal, evidence assertions, expiry, stop conditions, and a finite set of owner-approved reversible branches. Each observation creates a versioned state transition; the runtime may execute only the branch whose preconditions match, records before/after evidence, and emits an exception event when no branch matches. Relay wakes the case on schedule or browser/Mac events, while the pendant receives a compact “decision needed” prompt with the relevant evidence and a one-button defer/stop response.
- **owner gets:** The owner can delegate the ongoing management of a messy situation without granting open-ended autonomy. The system keeps working when websites or statuses change, takes safe next steps automatically, and asks exactly one focused question when reality leaves the approved plan.
- effort: High: new case schema and evaluator, event/schedule wakeups, branch authorization, browser/Mac observation adapters, durable state transitions, pendant notification/defer protocol, and adversarial tests for stale evidence and repeated events.  ·  risk: A faulty precondition could trigger an unintended branch or create notification loops. Require explicit finite branches, strict expiry, monotonic transition IDs, duplicate-event suppression, dry-run simulation, and default stop on disagreement or missing proof.
- cost: Small persistent state per case and periodic observation costs; background model calls can be avoided for deterministic transitions. Novel exceptions may use a model call and authenticated browser/Mac reads.  ·  latency: No impact on ordinary voice turns. Branches run on event/schedule latency; unresolved exceptions wait for the next pendant connection or relay wakeup.
- security: Cases are scoped to named sessions/accounts and expire automatically. Secrets remain on the Mac/browser surface. Every branch carries an authorization class, and irreversible classes are unexecutable without fresh owner approval.
- depends on: A durable relay scheduler/event queue; Typed browser and Mac observation results with provenance and freshness; A branch authorization model separate from one-shot action approval; Pendant notification, defer, and stop events
