## Capabilities it proposed

### ""Carry this out, but if anything important changes while you're working, stop and tell me exactly what changed before continuing.""
- **useful because:** Today judgement can decide an action, but execution can outlive the evidence it was based on. This gives the owner a real safety boundary across Mac, authenticated browser, relay, and pendant: long jobs continue when the owner leaves, yet stale or materially changed facts cannot silently produce a send, purchase, deletion, or submission.
- **path:** faculty-judgement emits a signed action manifest with assumptions, field hashes, expiry, reversibility, and required confirmation → faculty-perception watches source tabs/files and emits invalidation events when assumptions or page state change → relay persists the manifest, checkpoints, and cancellation/invalidation state while the Mac/browser are disconnected → mac-planner routes reversible steps to mac_run_actions and multi-step work to mac_delegate → browser-extension executes authenticated tab steps with before/after evidence and idempotency keys → pendant receives a terse pause reason and offers local confirm/cancel via button/voice when the owner returns
- **model tier:** Use the cheaper background model for manifest compilation, polling, diffing, and receipt summarization; reserve realtime only for the pendant's brief spoken interruption and confirmation. Use faculty-judgement for the initial policy decision, not on every checkpoint.
- **latency:** Reversible checkpoints under 2 seconds after a detected change; browser/file watches can poll or subscribe in the background. A stale irreversible step must wait for an explicit pendant confirmation, with no more than one short spoken sentence and a detailed receipt on Mac.
- **cost:** Roughly $0.01–$0.08 per long-running job depending on checkpoint count; dominated by browser/Mac observation and background model calls, not realtime voice. Storage is small: manifests, hashes, and receipts rather than page contents.
- **security:** Private URLs, snippets, and file metadata stay on the Mac/bridge where possible; relay stores redacted hashes and minimum fields. Never auto-send mail, buy, delete, or submit after invalidation. Require explicit confirmation on the pendant for any irreversible action or changed recipient/amount/destination.
- **missing:** A shared action-manifest schema and signature/expiry verifier; Perception-to-executor invalidation events for browser tabs and Mac files; Durable checkpoint/cancel state in the relay job runner; A pendant push message plus button confirmation path; Browser and Mac adapters that report typed before/after evidence at each checkpoint

### ""If that task got halfway done, figure out what actually happened and finish only the missing parts—don't repeat anything.""
- **useful because:** Long Mac/browser work can lose connectivity after some steps succeed. Without reconciliation, retrying can duplicate calendar events, create duplicate files, or send twice. A cross-surface recovery capability turns partial failure into a trustworthy outcome and gives the owner a concise completion receipt.
- **path:** relay records per-step idempotency keys, attempts, and durable receipts even across disconnects → mac-planner/mac-terminal queries local artifacts and command receipts to establish what completed → browser-extension reattaches to the same authenticated tab/session and checks page state, confirmation banners, and submitted-record IDs → faculty-perception compares the intended manifest with current Mac/browser state and labels each step complete, missing, ambiguous, or divergent → faculty-judgement decides whether a divergent state is safe to compensate or needs owner approval → pendant speaks only the ambiguity requiring attention and accepts confirm/cancel; Mac leaves a full reconciliation report
- **model tier:** Cheaper background model for receipt normalization and state comparison; faculty-judgement for ambiguous compensation policy; realtime only for the short owner-facing question.
- **latency:** Resume/reconcile within 5 seconds for local actions and 10–30 seconds for browser reattachment and page verification. Never retry an ambiguous externally visible action automatically.
- **cost:** About $0.02–$0.10 per recovered job, dominated by browser/Mac verification calls; model use is limited to summarization and ambiguous-state classification.
- **security:** Read only the minimum artifacts/pages needed to establish state. Treat submitted IDs and confirmation banners as sensitive evidence; redact them in spoken output. Require confirmation before compensating actions that could send, purchase, delete, or alter an external record.
- **missing:** A durable per-step receipt ledger with idempotency keys and typed outcome states; Mac adapters for artifact/command reconciliation; Browser adapters for post-submit record lookup and session reattachment; A compensation-policy interface from faculty-judgement; A unified reconciliation report and pendant prompt

### ""Give this task permission to do only what I just approved, across my Mac and logged-in browser, and let me revoke that permission from the pendant at any time.""
- **useful because:** The owner can approve an individual action today, but approval is not yet a portable, independently enforceable authority shared by relay, Mac, and browser. A narrowly scoped capability token would let long-running work proceed without broad standing access while giving the owner an immediate physical revoke switch.
- **path:** pendant creates a one-time signed grant after the owner's button/voice approval, bound to task, device, destination, allowed verbs, limits, and expiry; a second button press revokes it locally and queues revocation if offline → relay is the authority registry and fan-out point, storing only token metadata and revocation state; it denies requests outside the grant and distributes revocations → mac-planner/mac-terminal present the token to action adapters, which enforce verb/path/app scope before acting and emit signed receipts → browser-extension binds the grant to an authenticated browser session/tab and enforces URL, form-field, recipient, and amount constraints before every mutation → faculty-judgement defines the grant's scope and whether a proposed step fits it; faculty-perception supplies current device/session identity and detects scope drift
- **model tier:** Use the cheaper background tier to compile and validate grants and to audit receipts. Use realtime only to explain the requested scope and receive the owner's short approval/revocation interaction.
- **latency:** Grant issuance under 1 second locally; relay propagation under 2 seconds; revocation must block new actions within 2 seconds and force a final local re-check immediately before any irreversible step.
- **cost:** Less than $0.01 per grant in relay storage/signature operations; model cost only when translating natural language into a constrained scope, typically $0.01–$0.05. Dominant cost is verification calls for browser/Mac steps.
- **security:** This is an authority system, so fail closed on unknown, expired, replayed, or offline-revoked tokens. Never place raw secrets in the token; use opaque IDs and hashes. Bind grants to the specific owner account, Mac, browser session, and task. Require a fresh physical confirmation for send, purchase, delete, or submit even if the grant appears to allow it. Keep a complete audit trail and provide emergency revoke-all from the pendant.
- **missing:** A signed capability-token format with verb/resource/field constraints and expiry; Relay-side grant registry, replay protection, and revocation fan-out; Mac and browser enforcement middleware that checks grants before every mutation; Pendant-local key storage and offline revoke queue; A judgement policy compiler that turns approval language into a least-privilege scope; Cross-device audit receipts proving which grant authorized each step


## Changes it proposed to its own stack

### `relay` — Add an Action Manifest/Checkpoint service shared by judgement, perception, and executors. Persist a versioned manifest containing action steps, assumption IDs with observedAt/validUntil, sensitivity, reversibility, idempotency key, and required confirmation. Before every irreversible or externally visible step, atomically compare current perception versions and field hashes; if any dependency is expired or invalidated, transition the job to paused_stale, cancel downstream steps, and emit a redacted pause event to the pendant. Store append-only evidence receipts and support resume only with a new manifest or explicit owner confirmation.
- **owner gets:** A request made at breakfast cannot accidentally send the wrong email, submit an outdated form, or act on a changed price while the owner is away. The owner gets a precise explanation of what changed and can resume safely instead of restarting the whole task.
- effort: Medium-high: schema, D1/R2 persistence, compare-and-swap state transitions, adapters in browser and Mac runners, and pendant notification plumbing. Build with feature flags and replay tests for disconnects/races.  ·  risk: A false invalidation may pause harmless work; recover by allowing resume from the last verified checkpoint. A missed event is more serious, so the executor must re-read critical state immediately before irreversible steps and fail closed on missing evidence. Prevent duplicate actions with idempotency keys and receipt reconciliation.
- cost: Small relay storage and background polling cost; approximately 1–5 KB manifest plus receipts per job, with model spend near zero except summarizing a pause. No new per-invocation realtime spend.  ·  latency: Adds one local/relay state check (tens of milliseconds) before each guarded step; external page/file re-read may add 0.5–2 seconds only at irreversible checkpoints.
- security: Improves safety by keeping secrets out of spoken events and storing hashes/redacted deltas. Requires authenticated device-to-relay event signing and strict tenant/job isolation; never log raw form fields or message bodies by default.
- depends on: faculty-judgement emits stable assumption IDs and required-confirmation policy; faculty-perception publishes versioned invalidation events; browser and Mac action runners return typed before/after evidence; pendant push/confirm transport; durable relay job runner

## Its own summary

Discovered the live action tools and devices: Mac bridge online; browser bridge offline. Reviewed the 64-item backlog to avoid repeats. Added two new cross-surface proposals: (1) signed temporal Action Manifests with assumption expiry, perception invalidation, relay pause, executor compare-and-swap checks, and pendant confirmation; (2) partial-task reconciliation that verifies what actually happened and resumes only missing steps using idempotency and typed receipts. These address the action agent’s core gap: judgement can decide, but execution cannot yet safely survive stale context or disconnects.

**Biggest unknown:** Whether the current relay/pendant transport supports push pause events and local confirmation, and whether Mac/browser runners already emit typed per-step before/after evidence and idempotency receipts. I asked relay-realtime, mac-planner, and browser-extension; their replies are pending. Implementation still needs the shared manifest schema, invalidation event bus, durable checkpoint ledger, reconciliation adapters, and pendant confirm transport.
