## Capabilities it proposed

### "“What am I in the middle of, and what is the next best thing to do?”"
- **useful because:** The owner often returns to a Mac session mid-task and cannot reconstruct context. A fresh, cited snapshot of the foreground app, open browser tabs, nearby files, unread mail, and the next calendar commitment—spoken briefly through the pendant—turns the whole hive into a dependable interruption-recovery system. It should distinguish observed facts from suggestions and optionally leave a review note, never silently act.
- **path:** pendant button/voice trigger → relay-realtime for the short spoken response → mac-planner using the read-only Observation Capsule API for foreground/running apps, UI snapshot, and bounded files → browser-extension for currently open authenticated tabs → mac_read_sources for Calendar and Mail → mac-planner writes a timestamped Markdown recovery note only when explicitly requested
- **model tier:** Use a cheap background/planner model to rank and summarize the compact evidence; reserve realtime only for interpreting the pendant utterance and speaking the answer. No expensive model is needed for extraction or deduplication.
- **latency:** 2–5 seconds for local/calendar/mail capture and a concise spoken answer; browser evidence should be capped at already-open tabs and may add 1–3 seconds. If a source is offline, answer with an explicit missing-source line rather than waiting indefinitely.
- **cost:** Typically <$0.01 per invocation; dominated by summarization tokens. Local inspection and tab metadata are effectively free. Do not send full mail bodies or page contents unless the owner asks.
- **security:** Private app names, tab URLs, mail subjects, and calendar details leave the Mac only as a redacted, bounded capsule. Default to snippets and host/title rather than bodies; mark each fact with source and capture time. Never infer that an empty/offline source means no work. Writing a recovery note or launching/opening anything requires a separate explicit request.
- **missing:** Working implementations for granted mac_readonly_inspect and mac_read_sources (both currently return no implementation); A typed cross-surface Observation Capsule schema with freshness and provenance; A browser-extension read operation that reliably reports current tabs when the bridge is online; A relay route to request the capsule and stream a short response to the pendant

### "“Save my place here, and bring me back to this exact work later.”"
- **useful because:** The owner loses work context whenever they close a laptop, switch projects, or get interrupted. A single pendant command should create a private, named continuation point: the Mac records the active app and relevant window/file state, the browser facet records authenticated tab identities and stable page anchors without copying secrets, and the relay stores a compact encrypted checkpoint. Later, saying “resume my design review” should reopen the safe local artifacts and reattach browser tabs, then tell the owner what changed since the checkpoint. This is a continuity primitive across the hive, not another briefing or page watch.
- **path:** pendant button or voice trigger captures the checkpoint request → relay persists the checkpoint, encryption metadata, expiry, and change journal → mac-planner records and later restores approved app/window/file state using typed actions → browser-extension records tab/session identifiers and page anchors, then reattaches tabs when the authenticated bridge is available → faculty-perception compares the checkpoint with the current Mac/browser state → faculty-judgement selects what can be restored automatically versus what must merely be described → relay-realtime gives a short spoken resume summary
- **model tier:** Use a cheap background model for checkpoint normalization and change comparison. Use the realtime tier only for the live voice exchange and final concise spoken response. Deterministic adapters should handle app/file/tab capture and restoration.
- **latency:** Saving should complete in under 2 seconds locally, with relay persistence shortly after. Resume should return a first spoken status within 3 seconds and continue nonessential comparison in the background. If the browser is offline, restore local state and report the browser portion as pending rather than pretending it succeeded.
- **cost:** Usually below $0.01 per save/resume, dominated by a small change-summary prompt. Storage is compact metadata and hashes, not page bodies or screen recordings; retention and checkpoint count should be bounded.
- **security:** Checkpoints can reveal sensitive app names, filenames, URLs, and work context. Store only opaque tab IDs/hostnames and hashed anchors by default; never persist cookies, page bodies, or credentials. Require explicit confirmation before reopening external links, restoring destructive state, or exposing checkpoint contents aloud in a shared environment. Expire checkpoints and provide a pendant command to delete one.
- **missing:** A cross-surface checkpoint schema with versioning, expiry, provenance, and per-field sensitivity labels; Mac adapters that can capture and restore window/file/app state without relying on cursor position; Browser bridge support for durable tab identity and anchor reattachment across reconnects; Relay storage and comparison jobs for checkpoint deltas; A resume orchestrator that can partially restore state and report per-surface success or failure


## Changes it proposed to its own stack

### `integration` — Implement the already-granted mac_readonly_inspect and mac_read_sources tools end to end, behind a single read-only Observation Capsule API. It should return typed records for running/foreground apps, accessibility state, UI snapshot, browser tabs, approved directory listings, Calendar/Mail snippets, and explicit unavailable/error states; attach source, capturedAt, TTL, redaction mode, and account scope to every record. The relay/planner should be able to request a capsule by task (for example “desktop triage”), merge it with browser-session evidence, and refuse to treat stale or failed observations as facts. Keep inspection separate from mac_run_actions, with no shell or mutation path.
- **owner gets:** The owner can ask the pendant what is currently happening on the Mac and get a truthful, privacy-bounded answer instead of a guessed or stale one—and the system can act on a fresh observation without stealing focus. Today the grants exist but calls return “schema but no implementation,” so this is an actual missing capability, not polish.
- effort: Medium: implement local read adapters and typed response normalization, then relay serialization, redaction tests, freshness handling, and one end-to-end pendant-to-Mac observation test.  ·  risk: UI snapshots and mail/calendar snippets may expose sensitive data; enforce approved paths, account_scope, default redaction, bounded sizes, and per-request audit receipts. If an adapter fails, return unavailable with reason and never infer empty state. No mutation risk because this API is read-only.
- cost: Low ongoing API cost: one compact observation capsule per request; local adapters add negligible compute. Storage only for short-lived capsules and audit metadata.  ·  latency: Target 0.5–2 seconds locally; browser/session merge may add 1–3 seconds. Parallelize independent adapters and cap the capsule size.
- security: Improves least privilege by making inspection explicit and separate from FULL_CONTROL execution; still requires careful redaction and no raw body by default.
- depends on: Implement the granted mac_readonly_inspect backend (currently absent); Implement the granted mac_read_sources backend (currently absent); A relay route for typed observation capsules; Browser bridge online for authenticated-tab evidence
