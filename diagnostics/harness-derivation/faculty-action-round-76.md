## Capabilities it proposed

### "“Hand this off to Alex.” From the pendant, create a safe, time-limited handoff packet containing the exact goal, relevant files or links from my Mac and logged-in browser, current status, and the one decision Alex needs to make; show me the packet before sharing, then let me revoke it or see whether Alex accepted it."
- **useful because:** Today the mind can act on the owner's Mac, browser, or pendant, but it cannot turn an interrupted personal task into a controlled delegation to another person. This would preserve context across a handoff without exposing the owner's whole account or making the owner reconstruct the work manually.
- **path:** pendant → relay-realtime → mac-planner → mac-terminal → browser-extension → dashboard
- **model tier:** Use the realtime model only to resolve the spoken target and summarize the handoff aloud. Use a cheaper background model to assemble and redact the packet, classify files/links, and generate the concise decision request. Deterministic code should enforce scope, expiry, and revocation.
- **latency:** A spoken preview in 2–4 seconds; packet assembly may take 10–30 seconds while the Mac and browser are queried. Sharing must wait for explicit owner confirmation; acceptance/revocation status should update asynchronously.
- **cost:** About $0.01–$0.08 per handoff depending on document summarization; storage and notification traffic dominate for large attachments. Avoid sending raw account pages to the model when structured extraction is sufficient.
- **security:** The packet must use scoped, expiring links or copied redacted artifacts—not live browser cookies or unrestricted account URLs. Show every included file, recipient, and permission before share; require confirmation for external sharing. Encrypt at rest, log access and acceptance, support immediate revocation, and never infer the recipient from an ambiguous name. Data leaves the Mac only for the explicitly selected packet and its audit metadata.
- **missing:** A first-class handoff object and recipient/permission model in the relay; Mac-side artifact collector that can package selected files and browser evidence without exporting session credentials; A secure external delivery/notification channel and acceptance page; Dashboard and pendant preview/revoke/status UI; Redaction and secret-scanning policy for files and extracted browser content


## Changes it proposed to its own stack

### `integration` — Add a cross-surface action transaction protocol. Before faculty-action executes a judged plan, each step must carry a typed target, precondition snapshot (device/session/tab, identity, relevant field values), intended effect, reversibility class, and verification query. The relay assigns an idempotency key and short action lease; the Mac/browser executor rechecks the precondition immediately before the mutation, refuses on drift or stale lease, then runs the verification query and emits a signed receipt containing before/after evidence. On link loss the relay keeps the transaction pending (never retries a mutation blindly), and the pendant can announce pending/succeeded/blocked when it reconnects. Extend existing receipts and undo records rather than creating a second history.
- **owner gets:** A judged instruction becomes dependable action instead of a hopeful click: the owner is told when the page, account, amount, or recipient changed underneath us, gets proof of what actually changed, and cannot suffer a duplicate or stale execution just because the Mac or voice link briefly disappeared.
- effort: Medium-high: shared transaction schema and state machine in relay plus Mac/browser adapters; precondition/verification implementations for typed Mac actions and authenticated browser mutations; receipt signing and reconnect status delivery. Start with reminders, calendar edits, and browser form drafts before irreversible sends.  ·  risk: A conservative verifier will block legitimate actions when a page has harmless cosmetic drift; recover by presenting the exact failed precondition and allowing a fresh judged plan. Never auto-retry mutations. Signing-key loss or clock skew can mark receipts unverifiable, so retain local unsigned evidence and surface 'unverified' honestly. This does not bypass macOS Accessibility/Screen Recording; AppleScript and bridge paths remain usable, while GUI steps stay blocked when reachability is false.
- cost: Small per-step relay/D1/R2 metadata and one cheap verification read; roughly 1–3 extra Mac/browser calls per mutation. No expensive model call required after judgement; use the realtime tier only to explain a block aloud.  ·  latency: Adds about 0.5–2 seconds for precondition and postcondition reads on Mac, potentially more for browser round trips; safer than speculative retries. Pending state is immediate when the link drops.
- security: Improves security: binds actions to tab/session/device and lease, prevents replay via idempotency keys, and records before/after provenance. Receipts must avoid storing page secrets; hash/redact sensitive values and require explicit confirmation for irreversible effects.
- depends on: A durable relay job record and receipt/undo store (extend the existing job and /jobs/:jobId/receipts paths); Typed action schemas in mac_run_actions and browser_run_actions; Authenticated browser session/tab affinity from the browser bridge; A physical-action confirmation and action-lease indicator on the pendant for high-impact or irreversible steps

### `hardware` — Evolve the pendant from a single-button/LED prototype into an action-confirmation interface: retain the conversation button, add a low-profile tactile confirm/cancel pair (or a two-stage thumb rocker), a coin ERM haptic motor, and a distinct amber/red/green status LED or RGB LED. Firmware should expose a small local state machine—armed, awaiting approval, executing, succeeded, blocked—with a timeout and no network dependency for cancel. The relay/action lease protocol supplies the nonce and effect summary; only a matching physical confirm event can authorize a high-impact mutation.
- **owner gets:** The owner can approve a consequential action without opening the Mac or speaking a secret aloud, and can feel/see whether an action is waiting, running, completed, or blocked in a noisy room or while the phone is away. A physical cancel gives an immediate escape when the judged plan is wrong.
- effort: High for a product revision, moderate for a dev-kit experiment: add GPIO inputs, haptic driver, LED patterns, debounce/state persistence, enclosure changes, and relay nonce binding. Prototype first with the existing button as confirm and an external I2C GPIO expander/haptic breakout; migrate to a custom board after the interaction is validated.  ·  risk: Extra controls can cause accidental presses or confuse conversation start; require a deliberate long-press/double-action and audible/haptic distinction, and fail closed on ambiguous input. A lost link must leave the lease unapproved and expire it. Hardware changes are not needed for ordinary reversible actions, so retain the current path as fallback.
- cost: Prototype breakout roughly $10–25, custom BOM increase about $3–8 per unit; haptic bursts are tens of milliamps and negligible average draw, while RGB LED current must be duty-limited. No per-call model cost.  ·  latency: Local feedback under 100 ms; confirmation waits on the owner's deliberate gesture, while relay verification remains network-bound.
- security: Strengthens authorization by requiring a local presence signal bound to a one-time lease nonce. Do not treat button presence alone as identity for financial or destructive operations; combine it with explicit spoken summary and server-side expiry.
- depends on: Cross-surface action lease/attestation transaction schema; Pendant firmware access and a final physical-action confirmation policy; A product-board revision; current nRF9160 DK has only one user button and one LED
