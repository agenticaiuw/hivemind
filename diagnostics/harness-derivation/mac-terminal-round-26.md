## Capabilities it proposed

### "“Do this and keep going even if my Mac, Safari, or connection drops; tell me when it is truly finished.”"
- **useful because:** This is the missing everyday promise: the pendant can capture intent immediately, the relay can keep the work alive, the Mac can act with the owner's local authority, and the browser can use private sessions when available. The owner gets one concise completion or an honest parked/unknown state rather than a false success or a dead request.
- **path:** Pendant captures the goal and speaks immediate acknowledgement → Relay creates a durable parent job, decomposes it into checkpointed steps, and wakes on health transitions → Mac local-agent executes shell/typed actions and emits receipts, stderr, exit status, and undoability → Browser extension executes authenticated-tab steps when online and returns tab/session provenance → Relay reconciles all receipts, retries only idempotent transient failures, and sends final audio plus a Mac review artifact
- **model tier:** Background model for decomposition, retry classification, and final summary; deterministic routing and state transitions first. Realtime only for the initial spoken acknowledgement and urgent completion alert.
- **latency:** Acknowledge from pendant in under 1 second; dispatch when a capable surface is online; no fixed completion deadline. Retry/backoff should be invisible unless it exceeds a user-configured quiet-period, then speak one status update.
- **cost:** About $0.01–$0.05 per multi-step invocation depending on decomposition and final summary; most health checks, checkpointing, and receipts are deterministic. Browser screenshots or long page extraction dominate exceptional cases.
- **security:** The relay stores intent and minimal step metadata, never shell secrets or page contents by default. Authenticated browser actions remain on the Mac bridge. Non-idempotent actions must be marked unknown after disconnect and held for owner review rather than replayed. Final audio should reveal only the minimum needed.
- **missing:** Cross-surface parent/child job and checkpoint protocol; Stable local-agent health lease and reconnect event; Durable relay queue with idempotency and unknown-outcome handling; Browser bridge online/offline wakeup integration; Pendant completion-status notification and quiet-hours policy

### "“Make sure this actually happened, not just that you clicked the button.” For example: send the prepared message, update the appointment, or change the setting, then independently verify the resulting state and tell me if reality disagrees with the intended outcome."
- **useful because:** Today the system can report that a local action or browser command returned success, but that is not proof that the external world accepted or retained the change. The owner needs outcome-level confidence for consequential everyday tasks: confirmation that the recipient/server/state reflects the requested result, with an immediate warning when it does not.
- **path:** Pendant states the intended outcome in the owner's words and speaks a concise verified/unverified result → Relay stores the intent, expected postcondition, evidence requirements, and a short-lived verification deadline → Mac agent performs local actions and reads back local state, logs, notifications, or application results → Browser bridge performs authenticated read-back in the same session, while a separate safe read path checks the resulting page/API-visible state when available → Relay compares independent evidence against the expected postcondition and sends the owner either proof, a discrepancy explanation, or a request to inspect manually
- **model tier:** Deterministic postcondition evaluation and evidence matching first; background model only translates natural-language intent into a typed expected state and explains discrepancies. Realtime is used only for the spoken result.
- **latency:** Immediate action acknowledgement, then verification within 5–30 seconds for local/browser changes. Long-running external confirmations may remain pending and notify the owner once, rather than holding the conversation open.
- **cost:** Roughly $0.005–$0.03 per invocation. Most verification is deterministic; cost is dominated by a background interpretation call and occasional authenticated page extraction or screenshot.
- **security:** Verification must not expose message bodies, account data, or credentials to the relay unnecessarily. Evidence should be hashed or reduced to the relevant fields, with sensitive read-back remaining on the Mac. Never label an action verified from the same untrusted acknowledgement that triggered it; distinguish accepted, observed, and independently confirmed states. Non-idempotent retries remain prohibited.
- **missing:** A typed expected-postcondition schema covering local apps, browser pages, and external acknowledgements; An evidence-capture API that returns minimal field-level proof with source, timestamp, and session identity; A verifier that can use a distinct read-back route and represent accepted/observed/confirmed/contradicted/unknown states; Cross-surface correlation between the original action receipt and later read-back; Pendant and relay UX for pending verification, discrepancy alerts, and manual inspection


## Changes it proposed to its own stack

### `relay` — Add a cross-surface execution health and recovery coordinator. Before dispatch, relay polls a compact Mac-agent capability lease (agent reachable, browser bridge online, accessibility/screen-recording state, pending-job count, supported action families) and chooses Mac shell, typed Mac action, browser bridge, or durable queue accordingly. Every dispatched step carries a jobId, idempotency key, checkpoint, and deadline; failures are normalized into transient (retry/backoff), unavailable (park until a health transition), or permanent (surface-specific explanation). On reconnect, resume only from the last acknowledged checkpoint and publish one signed result receipt containing attempted route, exact failure, retry history, and final state. This is observability/recovery, not an approval gate; FULL_CONTROL_MODE remains unchanged.
- **owner gets:** The owner can say one thing and leave. Instead of silently spending 45 seconds on a browser action while the extension is offline, the system immediately says what is unavailable, parks the work, resumes when Safari or the Mac returns, and avoids duplicate shell/browser mutations after a dropped link.
- effort: Medium-high: a small health lease endpoint and typed state schema in local-agent, relay-side coordinator and durable queue, idempotent checkpoint persistence, and unified spoken/result formatting. Existing /ops/snapshot, /browser/status, /jobs, receipts, and journal provide most inputs.  ·  risk: A stale lease could select the wrong route or retry a non-idempotent action. Leases need short TTLs, action idempotency classes, and an explicit 'unknown outcome' state that never retries automatically. Recovery is replayed from receipts and can be manually abandoned; no existing execution path is removed.
- cost: Low ongoing API cost: deterministic health checks and retry logic; only final explanation needs background/planner inference. Small D1/R2 or local job-store growth for checkpoints and receipts.  ·  latency: Adds tens of milliseconds for cached health; avoids long doomed attempts (currently an offline browser navigate took about 45 seconds). Reconnect work is asynchronous.
- security: Health leases must omit page content and secrets, authenticate Mac↔relay, bind results to jobId/idempotency key, and redact command env/stderr before relay storage. Existing unrestricted shell authority is preserved.
- depends on: A durable cross-surface job identity/idempotency schema; Local-agent read-only health snapshot with stable machine-readable fields; Relay-to-Mac authenticated callback or polling for parked-job wakeups
