## Capabilities it proposed

### "“What should I do next?” — and, if I have enough time, prepare the best next step for me."
- **useful because:** The owner repeatedly has a capable system but no way to turn scattered state into one useful immediate choice. A short, situational recommendation is different from a morning brief: it uses the live moment (time, calendar gap, pending jobs, open private tabs, unfinished drafts, and Mac availability), chooses one reversible action, and leaves the owner with something ready rather than another list to manage.
- **path:** pendant: capture the spoken request and available-attention hint, speak one short recommendation, and provide cancel/approve controls → relay: maintain a short-lived Now Card job and reconcile state from all surfaces without retaining unrelated private page content → mac-planner: read calendar/reminders, pending jobs, local workspace, battery/network, and prepare a reversible action or draft → browser-extension: inspect only already-open authenticated tabs relevant to the selected task and stage (never submit) a form/message if useful → faculty-perception: verify freshness and confidence of each state item and detect stale/offline surfaces → faculty-judgement: rank by deadline, expected value, effort, interruption cost, and reversibility; explain why this one wins → faculty-action: execute only preparation, then return typed before/after evidence and a resumable receipt → unified: present a single sentence plus one clear choice, not a multi-agent transcript
- **model tier:** Use the cheap background model for state normalization and candidate ranking; use realtime only for the spoken request, final one-sentence explanation, and approval turn. Escalate to the expensive tier only when candidates conflict or the action has meaningful external consequences.
- **latency:** 3 seconds for a useful spoken recommendation from cached state; up to 15 seconds to prepare the reversible step. If a source is offline, answer from fresh cached facts with an explicit age and do not block the owner.
- **cost:** About $0.005–$0.03 per invocation when ranking uses compact typed facts and cached summaries; realtime audio and any authenticated-page extraction dominate. No model call should receive full page contents unless the selected candidate requires it.
- **security:** Private calendar, reminders, workspace names, and logged-in page data leave their native surfaces only as task-scoped facts. Never infer permission to send, buy, delete, or submit from “prepare”; require an explicit approval receipt. Show source timestamps, stale/offline warnings, and a why-this-task explanation. A malicious page must not be able to inject the ranking or approval text.
- **missing:** A first-class Now Card schema with candidate facts, freshness, effort estimate, attention-window/quiet-hours policy, and expiry; A cross-surface read-only snapshot API with field-level sensitivity and source provenance; A durable prepare-only action primitive that can be resumed or discarded and cannot silently cross an irreversible boundary; Pendant-side approve/cancel affordance and a compact spoken response contract; A ranking/evaluation harness with seeded owner scenarios and tests for stale, conflicting, or offline surfaces

### "“Privacy mode.” Make sure nothing is listening, recording, or reading my private screens until I turn it back on."
- **useful because:** A wearable assistant is present in intimate and public situations where software permission settings are too slow and ambiguous. The owner should have a physical, unmistakable way to make the entire hive go quiet and prove that it did so, rather than trusting an icon or a spoken promise.
- **path:** pendant: a long physical-button press cuts microphone capture locally, gives a distinct haptic/LED/audio confirmation, and retains the privacy latch across link loss and reboot → relay: immediately revoke active audio streams, cancel queued speech generation, mark the device privacy-latched, and reject new capture or private-context jobs → mac-planner/mac-vision: stop any in-progress screen observation, terminate or quarantine private-page extraction, and show a persistent OS-level privacy banner → browser-extension: revoke page-read capability and pause authenticated-tab commands until an explicit resume handshake → faculty-perception: verify each surface has stopped observing and report any surface that failed to acknowledge → faculty-judgement: prevent all plans requiring microphone, screen, browser, or private-memory access while latched → faculty-action: cancel or safely suspend pending work, preserving only a minimal non-content receipt so it can be resumed later
- **model tier:** No expensive model is required for the latch itself. Use deterministic firmware and relay policy; use a cheap background check only to reconcile acknowledgements. Realtime is allowed to speak the confirmation before the latch completes only if the local audio path has already been cut, otherwise use the LED/haptic confirmation.
- **latency:** Local microphone mute and physical indication under 100 ms; relay and Mac/browser revocation acknowledgement within 2 seconds. If any surface does not acknowledge, the pendant must still remain locally private and clearly show partial isolation.
- **cost:** Negligible per-use model cost. A small amount of relay state and audit data; hardware cost is primarily a dedicated tactile switch or revised button/LED design, roughly $0.20–$2 depending on the enclosure and haptics.
- **security:** The privacy latch must be enforced below the model and survive dropped links, prompt injection, and server compromise. Resume must require a deliberate physical action plus an owner-authenticated handshake; speech alone must not resume capture. Do not retain audio or screen contents created before the latch beyond existing bounded-retention policy. The owner needs a visible/haptic indication when any surface remains active or unverified.
- **missing:** A hardware-enforced microphone power/capture gate and persistent privacy-latch state; A signed cross-surface privacy revocation protocol with acknowledgement deadlines and failure states; Mac and browser hooks that can stop observation rather than merely stop submitting actions; A privacy dashboard and receipt showing which surfaces are quiet, pending, or unverified; A resume handshake and tests proving the latch survives reboot, reconnect, and queued jobs


## Changes it proposed to its own stack

### `hardware` — Add a fuel-gauge IC with a thermistor input (for example, a low-power I²C gauge appropriate to the final cell), expose percentage, voltage, charging state, and estimated time-to-empty to firmware, and publish signed periodic battery beacons to the relay. Add a firmware low-power policy that reduces LTE-M reporting/audio prefetch before brownout, while retaining an emergency button path. The Mac/relay should keep a short battery trend and surface uncertainty rather than pretending a percentage is exact.
- **owner gets:** Today the pendant cannot answer a basic daily question—whether it will survive the day—and LTE-M transmit bursts make voltage alone misleading. The owner gets an honest warning before a voice interaction dies, can charge proactively, and can still trust the emergency button when the device is nearly empty.
- effort: Moderate hardware respin plus firmware driver/calibration, relay schema and a small Mac/voice status response. Validate across temperature, cell aging, LTE-M burst load, and charging transitions.  ·  risk: Gauge drift or an incorrect cell profile could create false confidence; mitigate with calibration, voltage/impedance sanity checks, explicit unknown state, and a conservative reserve threshold. I²C or thermistor faults must fail safe and never disable the button. Recovery is continued operation with unknown battery state and a visible service diagnostic.
- cost: Roughly $1–$3 BOM increase at volume (more for prototype board changes), negligible steady-state power but a small measurement current; one tiny telemetry record per interval and no meaningful model cost.  ·  latency: Battery state is local and immediate; relay trend updates within one beacon interval. No added voice latency except when the owner explicitly asks for a trend.
- security: Battery telemetry is low sensitivity but still device-linked; authenticate beacons and retain only coarse history with bounded retention. Do not include location or microphone data in the battery packet.
- depends on: Choose the final battery/cell and enclosure before gauge selection; Firmware telemetry schema and relay device-authentication path; Mac/pendant status response that can report unknown/stale values honestly

### `interaction` — Define a cross-surface degraded-mode contract driven by verified device health: when the pendant is offline, low-confidence audio, or below a conservative battery reserve, relay-realtime immediately hands the conversation to the Mac/browser where possible, marks the handoff in the spoken response, and queues a resumable pendant notification for later. If no alternate surface can reach the owner, it stores a compact offline handoff marker rather than repeatedly retrying or claiming completion.
- **owner gets:** A dead or disconnected pendant should not turn a simple request into a silent failure. The owner hears “I can do this on your Mac; the pendant is low/offline” and gets continuity instead of having to repeat the request later.
- effort: Moderate protocol work: health predicates, explicit handoff state, Mac/relay routing, and a small set of audio/UI acceptance tests. This is policy and protocol, not a new model.  ·  risk: A handoff could expose private content on a shared Mac or create duplicate actions. Restrict fallback to the owner-authenticated Mac session, keep preparation read-only by default, use one idempotency key across surfaces, and require confirmation for external effects. If health is stale, say so and remain on the current surface.
- cost: Negligible model cost; a few relay state records and occasional Mac/browser calls. Hardware cost is none beyond the fuel-gauge proposal.  ·  latency: Adds at most one health lookup (~100–300 ms) on requests whose device state is uncertain; healthy interactions remain unchanged.
- security: Handoff packets must carry sensitivity labels and expiry, and must not be broadcast to arbitrary devices. Browser private data stays in the authenticated extension; relay receives only the minimum result needed to continue.
- depends on: Reliable pendant health/battery telemetry or an explicit stale-health state; Durable idempotency and receipt protocol across relay, Mac, and browser; Owner-authenticated Mac session and a clear degraded-mode spoken contract
