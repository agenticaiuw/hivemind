## Capabilities it proposed

### "If something I asked you to do fails while I'm away, figure out why, try the safest equivalent route on the Mac or in my logged-in browser, and tell me only what worked and what still needs me."
- **useful because:** Today a failed shell/browser step becomes a vague failed job: /ops/snapshot shows 14 failed actions and 112 actions without tier attribution, while five browser commands remain pending and the extension is offline. A wearable request should survive transient bridge/browser outages and executor-specific failures rather than making the owner repeat the whole task. This is genuinely hive-only: the relay retains the job, the Mac has local alternatives, the browser owns authenticated sessions, and the pendant delivers a concise outcome.
- **path:** pendant → relay → mac-planner → browser-extension → mac-vision → dashboard
- **model tier:** background for failure classification and recovery planning; deterministic rules first, planner-tier escalation only when the error or fallback is ambiguous; realtime only to acknowledge receipt on the pendant.
- **latency:** Acknowledge immediately; classify within 2 seconds; retry deterministic/transient failures within 10 seconds; background recovery can run for minutes while the owner is away; never block a later independent job.
- **cost:** Usually zero model calls for exit-code/timeout/bridge-offline signatures. Roughly 2k–5k input tokens to gpt-4.1-mini for an ambiguous failure, with planner escalation only for multi-surface recovery; dominant cost is retained error/output context, not transport.
- **security:** Shell remains unrestricted per owner policy and no new gate is proposed. Store only bounded, redacted stderr/stdout and typed error metadata; never send environment variables, cookies, page bodies, or secrets to the relay/model. Browser retries must preserve tab/session affinity and stop before irreversible submission. Show the exact fallback and changed inputs in the receipt; require owner confirmation only where the existing action semantics already require it.
- **missing:** A durable cross-surface recovery state machine with attempt lineage, failure taxonomy, bounded redacted diagnostics, and retry budgets; A capability map describing equivalent Mac, browser, and relay executors plus idempotency/undo semantics; A background worker that can wake when the Mac bridge or browser extension reconnects and resume pending attempts; A single receipt schema joining pendant request, relay job, Mac job/action receipt, browser command, and final evidence; A small dashboard/pendant summary for recovered, waiting, and permanently failed work


## Changes it proposed to its own stack

### `mac-harness` — Add a lossless-but-bounded execution ledger around every run_shell, typed Mac action, and browser command. Before dispatch, assign a correlation/attempt ID and executor fingerprint; after dispatch, persist start/end timestamps, argv or action type, cwd, timeout, exit code, signal, stdout/stderr hashes plus redacted tails, network/bridge state, idempotency key, undoability, and evidence references. Link retries and alternate-surface attempts into one DAG. Add deterministic classifiers for timeout, bridge-offline, missing permission, unavailable app, stale tab, invalid input, and unknown failure. Expose filtered views and a 'next recovery' recommendation through /journal, /ops/snapshot, and a new read-only /recovery endpoint; wake the durable runner on bridge/browser heartbeat and record whether recovery was automatic or abandoned.
- **owner gets:** When the owner asks from the pendant and walks away, they get a truthful answer later instead of 'something failed'. The agent can distinguish a disconnected browser from a bad form, resume after the Mac returns, avoid repeating successful steps, and explain exactly which surface completed the work. It also makes the current 14 failures and 112 unattributed actions actionable without reducing the owner's deliberately unrestricted access.
- effort: Medium-high: shared ledger schema and writer in executor/jobTracker/browserBridge, classifier and retry planner, reconnect hooks, retention/redaction tests, and dashboard/receipt rendering. Start with read-only instrumentation and replay tests, then enable automatic retries for explicitly idempotent actions.  ·  risk: Ledger corruption or duplicated retries could repeat mutations. Mitigate with append-only attempt records, idempotency keys, bounded retry budgets, pre/post evidence, and only auto-retry actions already marked idempotent/reversible; preserve the existing unrestricted execution behavior. If the ledger is unavailable, execute normally and emit a degraded receipt rather than blocking the action.
- cost: Small local disk growth (bounded retention, roughly tens of KB per job plus capped output); negligible API cost for deterministic classification. Occasional background mini-model call for ambiguous failures; planner escalation is rare.  ·  latency: Under 10 ms local write overhead per attempt; no added model latency for normal execution. Recovery retries happen asynchronously and do not delay the initial response.
- security: Improves auditability without gates. Redact env/cookies/tokens and cap output before relay upload; retain full raw diagnostics locally only if the existing job policy permits. Cross-surface receipts contain hashes/locators rather than authenticated page bodies.
- depends on: Durable job runner and browser command queue (chg-16bc5dee/chg-14accc01); Existing receipts/undo records (chg-5fc73ce3); Bridge/browser reconnect heartbeat handling; A shared correlation ID propagated by relay, Mac, and browser surfaces

### `hardware` — Add a low-power I²C fuel-gauge IC and a guarded battery-voltage divider to the pendant, with firmware exposing coarse battery percentage, charging/USB state, and low-battery interrupts to the bridge/relay. Persist a tiny last-known power record in flash and include it in pipeline telemetry. At critical level, the relay should finish/serialize the current job state and move audio/results to durable storage before the pendant powers off; on reconnect, the pendant resumes its queued spoken receipt.
- **owner gets:** The pendant is the always-with-you surface but currently has no battery gauge, so the system cannot tell whether silence means a dead wearable, a broken link, or no response. The owner would get graceful handoff and a reliable 'your task completed while the pendant was charging' experience instead of losing a conversation or background result.
- effort: Medium hardware/firmware change: select a tiny fuel gauge compatible with the existing board and battery, route I²C and interrupt, update board layout, add calibration and charge-state firmware, then add relay power-state handling and reconnect tests. Validate battery safety with the actual cell and charger before production.  ·  risk: Incorrect calibration or charger interaction could misreport state; a bad divider can waste power or affect ADC readings. Keep the gauge read-only, use conservative thresholds, brownout-test it, and fall back to 'unknown' rather than making shutdown decisions when telemetry is stale. The relay must never delete a job solely on a low-power signal.
- cost: Roughly $1–$3 BOM increase in volume, plus PCB revision and validation; gauge draw typically tens of µA, with negligible API cost. Firmware flash/RAM impact is small (target under 8 KB flash and 2 KB RAM).  ·  latency: One low-rate telemetry packet per minute and an interrupt-driven critical event; no noticeable conversational latency. Durable handoff may add a few seconds before power loss.
- security: Battery state is non-sensitive local telemetry. Do not include location, microphone data, or task contents in the low-power packet; only send device ID, coarse state, and the job correlation ID needed for handoff.
- depends on: Pendant-to-relay pipeline telemetry (existing); Durable relay job/audio storage; A reconnect/resume protocol linking pendant correlation IDs to Mac/browser receipts; Battery and charger electrical review

### `integration` — Introduce a local-first privacy boundary compiler for multi-surface jobs. Before a relay/planner call, compile the task into typed claims and opaque references: authenticated page contents, local files, shell output, cookies, and account identifiers stay on the Mac/browser; the cloud receives only the minimum redacted excerpts, hashes, capability results, and an explicit request for the next operation. The compiler should enforce per-field sensitivity labels, support local model execution for high-sensitivity classification, and emit a machine-verifiable disclosure receipt showing exactly what crossed the Mac boundary. The pendant can display a short 'kept on Mac' versus 'sent to relay' summary.
- **owner gets:** The owner could ask the hive to work across private browser accounts and local documents without having to choose between usefulness and sending raw personal data to the cloud. Today the surfaces can act, but there is no unified guarantee or proof of what private page text, shell output, or account metadata was exposed during a combined task. This gives them a meaningful privacy mode that preserves authenticated automation instead of merely disabling it.
- effort: High integration effort: define sensitivity labels and claim schemas, add local redaction/classification and reference resolution to Mac/browser bridges, update relay request validation, propagate disclosure receipts through jobs and the pendant, and test against credential leaks, prompt injection, screenshots, and shell output. It should be opt-in initially and support a strict local-only mode.  ·  risk: Over-redaction can make a task fail or produce incorrect conclusions; under-redaction can expose sensitive data. Use conservative defaults, secret-pattern detection plus DOM/file metadata labels, bounded excerpts, fail-closed for credentials and session tokens, and a visible degraded result when the cloud cannot receive enough context. Prompt injection in private pages must never alter the disclosure policy.
- cost: Moderate local CPU/storage overhead for scanning and receipt generation; generally zero additional API cost, with occasional small local/background classification calls. Relay payloads and planner token costs should decrease because only relevant claims cross the boundary.  ·  latency: Add roughly 50–300 ms for local labeling on ordinary jobs; large files/pages may take seconds to scan. High-sensitivity jobs may be slower if they require local extraction before a planner call.
- security: Strongly improves confidentiality and auditability. Credentials, cookies, raw screenshots, and unneeded page/file content remain device-local; disclosure receipts contain hashes and field categories, not secrets. Must protect the local policy store and prevent any unrestricted fallback from silently bypassing it.
- depends on: A shared typed context/claim schema across relay, Mac, and browser; Local authenticated browser and Mac action bridges; Durable job receipts that can carry disclosure records; A user-selectable privacy policy exposed in the pendant and dashboard
