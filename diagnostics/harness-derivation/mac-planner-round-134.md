## Capabilities it proposed

### "“Read the key number or sentence from the private page I’m looking at, say it to me once through the pendant, and forget it afterward.”"
- **useful because:** Today the browser can hold an authenticated page and the pendant can speak, but there is no deliberate one-shot private handoff: the owner must expose the page to another surface, risk leaving sensitive text in durable research/session history, or read it themselves. This would let them retrieve a balance, deadline, tracking number, or short instruction hands-free while preserving a clear ephemeral boundary.
- **path:** browser-extension → mac-planner → relay-realtime → pendant → unified
- **model tier:** Use a cheap background/text extraction model for selecting the requested field and redacting surrounding content; use realtime only for the owner’s live request and one short spoken response. No model should summarize beyond the requested field.
- **latency:** Under 3 seconds after the browser bridge responds; one browser read and one short TTS/audio delivery. If the bridge is unavailable, say so immediately rather than substituting a public or stale page.
- **cost:** Typically a few cents or less per invocation; browser extraction and a short realtime/TTS turn dominate, with no need for a long context resend.
- **security:** The browser extension must return only the requested semantic field, not a full page. Redact secrets by default, display the source tab/domain and capture time in the response metadata, keep the spoken payload in volatile memory/audio buffers only, and delete the associated capsule/session transcript immediately after successful delivery. Require an explicit spoken confirmation for values classified as authentication secrets, payment credentials, or one-time codes; never read those automatically. If audio is routed through the relay, the selected phrase leaves the Mac briefly, so the owner needs a privacy setting that permits or forbids relay transit.
- **missing:** An ephemeral, non-persisting browser extraction contract with a field-size limit and source-domain receipt.; A relay audio delivery mode that acknowledges playback and then cryptographically/transactionally purges text, audio, and trace payloads.; A cross-surface privacy classification/redaction service that distinguishes ordinary private facts from credentials and one-time secrets.; A pendant response primitive for one-shot playback with no replay/history affordance.; A durable deletion receipt proving the handoff payload and derived audio were purged without retaining the sensitive value.


## Changes it proposed to its own stack

### `browser-harness` — Add a browser-bridge liveness watchdog and queue quarantine layer, distinct from the command protocol itself. Track each device heartbeat lease and each command claim lease; when the lease expires, atomically move processing commands to `orphaned` (not immediately runnable), stop claiming new commands while the device is offline, and mark sessions whose lastUsedAt exceeds a configurable TTL as stale. On reconnection, require a fresh heartbeat and device/session identity before offering quarantined commands; replay only idempotent commands with the original request/idempotency key, while non-idempotent commands remain held for review. Emit one durable incident/receipt linking the command, attempts, last heartbeat, and reason, and let the pendant/relay announce a compact “browser bridge offline; N queued, M held” status rather than timing out for 45 seconds.
- **owner gets:** Today a dead or stale browser bridge can leave ten commands queued and a command stuck `processing` for hours with 18 attempts, while a browser action burns ~45 seconds before failing. The owner would get an honest immediate status, no accidental duplicate navigation/form action after reconnect, and automatic continuation of safe reads when the browser returns.
- effort: Medium: browserBridge queue state machine plus a small periodic reaper/lease table, session TTL handling, and relay-facing status projection; add crash/reconnect integration tests for offline, duplicate poll, and reconnect cases.  ·  risk: A too-short lease could quarantine a slow but healthy tab; use heartbeat-derived TTL with generous grace and an explicit operator replay endpoint. A crash between state transition and receipt write must be recovered by an idempotent transaction. Never auto-replay submit/click/form mutations.
- cost: Negligible API cost; one small D1/local state record per lease and occasional watchdog work. Reduces wasted planner/bridge retries and 45-second timeout traffic.  ·  latency: Offline browser requests fail/status-return in milliseconds instead of waiting for bridge timeout. Healthy polling adds only a lease check; safe queued reads resume after one fresh heartbeat.
- security: Improves safety for authenticated sessions by preventing stale-tab actions and cross-device claims. Persist only command metadata, not page contents; bind leases to extension/device and session identity.
- depends on: A heartbeat payload must include a stable extension/device identity and server-observed lease timestamp.; Existing request IDs/idempotency keys and typed action results from the browser queue work must be retained.; Relay/pendant needs a read-only bridge-health status projection and compact notification path.

### `mac-harness` — Add an accessibility-aware execution truth layer (observability, not an approval gate). Before and after every ui_* / synthesized-input action, attach the latest `/observe` inputReachability and accessibility probe to the receipt. If eventsPost=false or uiActionsWillReachTheScreen=false, label the action `unverified_no_input_path` rather than `ok`, preserve the requested action and failure reason, and automatically suggest/route an equivalent AppleScript or high-level action when the target app is in the granted Automation list. For actions with no equivalent, report “not executed” immediately instead of claiming success. Expose a compact capability matrix per app (automation available, accessibility available, screen recording available) so faculty-action can choose a truthful route.
- **owner gets:** Right now the Mac reports that clicks, typing, and keypresses succeeded while doing nothing because AI Pendant Agent lacks Accessibility; the owner can be told a false success and lose trust. This change makes receipts honest and still lets Calendar, Mail, Notes, Finder, Safari, Chrome, and other already-authorized apps work through AppleScript without waiting for a manual TCC fix.
- effort: Medium: enrich executor receipts and journal derivation, add an action-equivalence registry for common app intents, and add tests with accessibility trusted/untrusted and secure-input states.  ·  risk: An app may accept an AppleScript command but produce an unexpected UI result; retain before/after app-level evidence and mark semantic completion separately from dispatch. Some actions genuinely require Accessibility and must remain unexecuted/unverified until the owner grants it.
- cost: No meaningful model/API cost; a small local probe and receipt metadata per action.  ·  latency: Adds a local probe (sub-second). High-level AppleScript fallback can be faster than a no-op UI loop.
- security: Does not broaden permissions. It makes existing Automation grants explicit and avoids silently pretending input reached the screen; receipt metadata should omit page contents and secrets.
- depends on: Keep `/observe` read-only and make its inputReachability result available to executor receipts.; Preserve the owner’s maximum-capability policy: this is truthful classification and fallback, not a confirmation or refusal policy.; Accessibility/Screen Recording remain owner-installed TCC grants for vision/UI tasks; no server-side substitute exists.

### `integration` — Create an ephemeral-private data lane spanning browser extraction, relay speech, and pendant playback. A request creates a short-lived handoff ID bound to the authenticated tab and owner device, returns only one bounded field plus source metadata, streams it to the pendant, and then performs an atomic purge of extracted text, generated audio, research/session references, and temporary receipts. The purge receipt retains only hashes, timestamps, domain, byte counts, and success/failure—not the sensitive value. Make this lane separate from ordinary `/research` briefings so it cannot accidentally enter durable briefings, memory, or the conversation transcript.
- **owner gets:** The owner could ask for one private fact while moving around—such as a deadline or balance—and hear it once without creating a durable copy of the page or forcing a full authenticated-page summary. Today the component routes exist independently, but there is no trustworthy boundary proving the sensitive handoff was erased.
- effort: Medium-high: define a volatile handoff record and lifecycle across the Mac bridge and relay, add streaming playback acknowledgement and crash cleanup, then test relay loss, pendant disconnect, duplicate requests, and purge verification.  ·  risk: A crash or logging path could retain the value; use memory-only buffers where possible, scrub structured logs, encrypt any unavoidable short-lived relay storage, and run a TTL sweeper. Delivery acknowledgement must not imply purge success; report those separately. Never permit credentials or one-time codes through the ordinary path.
- cost: Small per-request relay/storage overhead and one short TTS turn; lower than a full research run. Cleanup metadata is tiny and contains no page content.  ·  latency: One bounded extraction plus streaming audio, target 2–3 seconds; purge occurs immediately after playback acknowledgement and has a hard TTL fallback.
- security: Adds a strict data-minimization boundary and auditable deletion without weakening browser authentication. It requires an explicit owner privacy policy for whether selected text may transit the relay.
- depends on: A browser command that supports bounded semantic extraction from the current authenticated tab.; Relay/pendant playback acknowledgement and a volatile audio queue.; A purge-capable handoff store and log scrubber; ordinary research/session persistence must be bypassed.; A privacy classifier that refuses credentials and one-time secrets by default.
