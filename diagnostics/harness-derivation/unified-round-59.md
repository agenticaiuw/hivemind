## Capabilities it proposed

### "“Handle this while I’m away, but let me approve the final step from the pendant.”"
- **useful because:** The owner can start a logged-in browser task by voice, walk away, and later approve the exact irreversible action from the device they are wearing. The Mac/browser gather evidence in the background; the relay keeps the job alive; the pendant presents a short spoken diff and a single bound approval. No private page content needs to be spoken until the owner requests it, and a changed page forces a fresh preview instead of risking a stale send.
- **path:** pendant → relay → mac-planner → browser-extension → dashboard
- **model tier:** Use the cheap background planner for research/extraction and reconciliation; use realtime only for the brief spoken preview, approval acknowledgement, and interruption handling.
- **latency:** Start acknowledgement under 1 s. Background gathering may take minutes while the owner is away. Final preview should be ready within 30 s of the last page load; approval-to-execution receipt under 3 s on a healthy link.
- **cost:** One background planner invocation per job plus cheap extraction calls; roughly $0.03–$0.20 depending on page count. Realtime cost is limited to a few short turns. Dominant cost is authenticated-page context and evidence re-sent during retries.
- **security:** Private page data stays in the authenticated browser/Mac path and is reduced to field-level hashes and a minimal diff for the pendant. Approval is single-use, expires, and is bound to account, tab/session, URL, field hashes, and action plan. Sending mail, deleting files, purchases, and submissions always require explicit approval; stale DOM or changed hashes invalidate it. Store receipts and allow undo where possible.
- **missing:** Durable cross-surface job state with pause/resume and expiry; Shared approval-intent envelope plus an atomic pre-execution revalidation gate; A pendant-local approval/deny interaction that works offline until the next link opportunity; Field-level redaction and compact spoken preview generation; End-to-end tests covering browser disconnect, Mac sleep, duplicate delivery, and stale-page rejection

### "“What did I decide about this, and did it actually happen?”"
- **useful because:** Today the owner can receive a spoken answer, take a browser action, or create a reminder, but cannot reliably reconstruct the chain from an earlier pendant conversation through Mac/browser work to the real-world outcome. This gives them a private, evidence-backed decision ledger: the original spoken intent, the relevant page or document, what the Mac/browser changed, whether the action was completed, and what remains unresolved. It can answer follow-ups months later without pretending that a draft, a queued job, and a sent transaction are the same thing.
- **path:** pendant → relay → mac-planner → mac-vision → browser-extension → dashboard
- **model tier:** Use a cheap background model to normalize events and link entities; use realtime only to answer the owner's short spoken query. Use no model for cryptographic receipt validation or status transitions.
- **latency:** Record event links asynchronously within seconds. A normal query should return a one-sentence answer in under 3 seconds, with the dashboard opening the detailed evidence timeline afterward.
- **cost:** Low ongoing cost: compact event normalization and embeddings only for new decisions, roughly $0.01–$0.05 per decision thread. Query cost is small because the model receives a compact evidence graph rather than full transcripts or pages.
- **security:** The ledger may contain sensitive speech, mail, financial, and account metadata. Keep raw audio and page contents under existing retention policies; store redacted claims, hashes, timestamps, actor/surface, and permission scope by default. Never infer completion from intent alone. Mark uncertainty explicitly, require owner confirmation before promoting an inferred commitment to a reminder, and allow deletion of an entire thread.
- **missing:** A first-class decision/commitment event schema shared by pendant, relay, Mac, and browser; Causal links between speech turns, plans, browser mutations, job receipts, and external confirmations; A completion verifier that can distinguish drafted, queued, submitted, accepted, failed, and unknown; User-visible provenance and correction controls in the dashboard; Retention, redaction, and deletion rules for linked evidence


## Changes it proposed to its own stack

### `integration` — Implement a durable Transaction Continuation Protocol joining relay jobs, Mac/browser work, and the pendant: a typed state machine (collecting → preview-ready → awaiting-owner → executing → receipt/failed), append-only evidence manifest, idempotency key, and approval-intent token. The relay owns the state; Mac/browser workers lease steps and heartbeat; a worker restart or link loss resumes from the last checkpoint. Immediately before execution, the worker re-reads the bound tab/session and compares field hashes; any mismatch atomically returns to preview-ready. The pendant receives only a redacted preview plus token and can approve/deny; execution and receipt are delivered back as a short spoken status and dashboard detail.
- **owner gets:** A task no longer silently dies when the Mac sleeps, Safari changes, or LTE drops. The owner can safely say “handle this,” leave, and approve later with confidence that the action still matches what they saw.
- effort: Medium-high: shared schema and D1 migrations, relay lease/heartbeat worker, browser/Mac adapters, pendant command/ack path, and failure-injection tests. Reuse existing jobs, receipts, browser sessions, pipeline, and execute routes rather than creating another queue.  ·  risk: A split-brain worker could duplicate an action or an old approval could be replayed. Mitigate with unique action keys, compare-and-swap state transitions, single-use expiry-bound tokens, lease fencing, and preflight hash revalidation. If any invariant is uncertain, stop at preview-ready and notify the owner; receipts remain auditable and existing undo endpoints handle reversible actions.
- cost: Small D1/R2 and relay overhead; one heartbeat per active lease and a few compact evidence records. Model cost is unchanged or lower because retries resume from checkpoints instead of resending full context.  ·  latency: Adds roughly 100–500 ms to final execution for token validation and live re-read; no added latency while background work runs.
- security: Improves security by making approval scoped and auditable, minimizing pendant data, and rejecting stale or cross-account actions. Requires careful redaction so hashes and previews cannot leak secrets.
- depends on: A durable job runner (the existing browser runner work must finish); Shared approval-intent envelope and atomic pre-commit gate; Pendant-local approval/deny event and link-aware delivery; Field-level evidence/redaction contract between browser bridge and relay

### `hardware` — Add a discrete secure element (for example an ATECC608-class device) on the currently unused I2C bus, provisioned at manufacture with a non-exportable pendant identity key. Firmware signs approval acknowledgements and job receipts with a monotonic counter; the relay verifies the signature and binds it to the paired owner, job id, action hash, and expiry. Keep private keys out of nRF9160 flash and out of the Mac/browser bridge.
- **owner gets:** A stolen or cloned pendant session cannot approve a purchase or send a message just by replaying a captured button event. The owner gets a trustworthy, auditable “this approval came from my paired wearable” boundary while still being able to use the Mac/browser for the actual work.
- effort: Moderate hardware and firmware security work: add the IC, provisioning fixture and recovery/re-pair flow, implement secure-element signing and monotonic counters, and update relay pairing/verification. Include fault-injection and clone/replay tests.  ·  risk: Lost or damaged hardware can make the identity unrecoverable, and provisioning errors could brick a batch. Use a documented re-pair ceremony, never store owner secrets on-device, support revocation and replacement in D1, and fall back to dashboard approval rather than silently accepting unsigned events.
- cost: Approximately $0.70–$2.50 BOM at volume, under 1 mA active and near-microamp standby draw; modest engineering/provisioning cost.  ·  latency: Usually tens of milliseconds per signature; approval acknowledgement remains under roughly 1 s on LTE-M.
- security: Strongly improves anti-replay and device authenticity, but does not replace scoped approval tokens, live page revalidation, or owner confirmation. Key attestation and pairing metadata must be treated as sensitive.
- depends on: Production pendant constraints and secure provisioning process; Shared approval-intent envelope and atomic pre-commit gate; Pendant approval event protocol; Replacement/revocation flow in relay storage

### `memory` — Create a tamper-evident Decision Ledger distinct from the existing context graph and job journal. Each event is an append-only, redacted claim with eventId, actor surface, source hash, timestamp, confidence, and explicit causal links: spoken intent → plan → browser/Mac mutation → external acknowledgement. Add a verifier that periodically rechecks outcome-bearing claims against receipts or authenticated page state, changing status to completed, failed, or unknown rather than allowing stale success. Expose a compact query projection for the pendant and a correction/deletion UI in the dashboard; corrections append a superseding event instead of rewriting history.
- **owner gets:** The owner can ask whether a decision became reality and get an honest answer with the exact evidence, instead of relying on a transcript, an optimistic agent response, or a stale reminder.
- effort: High integration effort: event schema and migrations, adapters in pendant relay, planner, computer-use, and browser bridge, outcome verifiers, redaction/retention jobs, and dashboard timeline plus correction controls.  ·  risk: Incorrect causal links could make unrelated actions appear connected, and a ledger could become a sensitive surveillance archive. Require source references for every claim, confidence thresholds, human-correctable links, per-thread deletion, short raw-data retention, and fail closed to “unknown” when evidence is missing.
- cost: Small storage overhead for redacted events and hashes; background verification adds occasional cheap planner calls and browser reads. Query prompts become materially smaller because only the relevant evidence projection is sent.  ·  latency: No user-facing delay for recording; normal spoken queries add roughly 0.5–2 seconds for projection and verification lookup.
- security: Improves auditability while reducing raw-content exposure, but requires strict access control and redaction. Never expose secret values merely because they are linked evidence.
- depends on: A shared cross-surface event schema; Reliable browser/Mac receipts with source hashes; Authenticated outcome verification; Retention and deletion policy; Dashboard provenance and correction UI
