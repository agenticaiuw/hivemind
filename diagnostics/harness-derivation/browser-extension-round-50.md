## Capabilities it proposed

### "I'm looking at this page—tell me what it means for my day, and make me a short plan."
- **useful because:** This is a uniquely cross-surface request: the browser can see the owner's authenticated page, the Mac can see local Calendar/Reminders/files, and the pendant is the natural hands-free interface. It turns a private web page into a grounded personal plan without asking the owner to copy links or expose credentials. The result should cite the page facts, distinguish them from local facts, and stop at a reviewable plan rather than silently changing anything.
- **path:** browser-extension: capture the active authenticated tab's URL, title, selected/visible text, and page evidence cards → mac-planner: fetch overlapping Calendar/Reminders and relevant local files, then reserve no time and mutate nothing → relay-realtime: accept the pendant request, stream a concise spoken answer and follow-up questions → faculty-perception: normalize page and local evidence with freshness and source labels → faculty-judgement: reconcile conflicts, identify deadlines, and produce a 3–5 item plan → mac-planner: write a timestamped review artifact containing citations, assumptions, and suggested actions
- **model tier:** Use a cheaper background text model for extraction, deduplication, and plan synthesis; use realtime only for the live pendant turn and short spoken delivery. Escalate to the expensive tier only when page semantics are ambiguous or sources conflict.
- **latency:** Acknowledge on the pendant in under 1 second; browser capture and local reads in 3–8 seconds; speak a first useful summary within 10 seconds. If a source is slow, deliver the page-only summary first and append local-calendar context when ready.
- **cost:** Roughly $0.01–$0.05 per invocation depending on page length and local-file extraction; most cost is model context for extracted page text, not browser control. Cache evidence hashes for follow-up questions so unchanged page text is not resent.
- **security:** Only the active tab and explicitly requested local sources leave their surfaces; do not upload screenshots when structured text suffices. Redact credentials, tokens, hidden form values, and unrelated tabs. Keep source URLs and snippets in a local encrypted artifact with short retention. Never create events, send messages, submit forms, or make purchases in this mode; show suggested mutations separately for approval.
- **missing:** A reliable browser heartbeat/command bridge: Safari currently reports offline with three pending commands and no live tab, despite durable session records in /observe.; An active-tab capture contract that returns bounded visible text plus stable evidence locators and freshness, rather than an unbounded page dump.; A cross-surface job schema carrying source-labeled evidence and a resumable review artifact between browser, Mac, relay, and faculty agents.; A clear local-source selector (calendar only versus calendar plus reminders/files) so the owner controls how much context is joined.

### "Read the section I'm pointing at in Safari, explain it in plain language, and let me ask follow-ups about that exact section without losing my place."
- **useful because:** The owner can currently ask for a page read, but cannot maintain a precise, hands-free reference to the paragraph or control currently under their attention. This capability makes the pendant a spatial companion to the authenticated browser: it reads only the bounded DOM/accessibility subtree around Safari's current selection or focus, explains it, and keeps that same evidence anchor for follow-up questions. It is especially useful for dense contracts, forms, account notices, and technical documentation where a whole-page summary is too broad.
- **path:** browser-extension: report the active tab's focused/selected element, bounded accessible subtree, nearby heading path, scroll position, URL, and a stable locator; highlight the referenced region locally without changing form values → relay-realtime: receive the pendant's short request, provide immediate spoken acknowledgement, and stream the explanation and follow-up answers → faculty-perception: normalize the DOM/accessibility evidence and detect when the anchor has changed or gone stale → faculty-judgement: explain, define terms, and answer follow-ups constrained to the anchored region; explicitly say when context outside it is required
- **model tier:** Use a low-cost text model for DOM cleanup, section detection, and plain-language explanation; reserve realtime for the live pendant exchange and only invoke the expensive tier for genuinely ambiguous legal/technical language.
- **latency:** Acknowledge in under 500 ms; capture and explain the focused region in 2–5 seconds; follow-up answers in 1–3 seconds from cached evidence. If the page changes, say so immediately instead of silently answering from stale text.
- **cost:** Approximately $0.005–$0.03 per section and follow-up sequence; bounded DOM text and cached evidence keep context cost low. Browser extension work and accessibility-tree serialization dominate engineering effort, not API spend.
- **security:** Send only the focused/selected subtree and minimal page metadata, never hidden inputs, password fields, unrelated tabs, or full-page screenshots. Redact tokens and account identifiers. Keep the anchor evidence ephemeral unless the owner explicitly asks to save it. This is read-only: no clicking, typing, navigation, or submission.
- **missing:** A Safari extension command/result contract for focused-element and selection capture with a stable locator and DOM revision hash.; A local anchor lease that invalidates cached evidence when the tab navigates, DOM revision changes, or the selection moves.; A pendant interaction cue (for example, a short button press or double tap) that requests the current browser anchor and distinguishes it from a general page read.; A browser-to-relay evidence envelope with field-level redaction and bounded-size guarantees.


## Changes it proposed to its own stack

### `browser-harness` — Add a browser bridge lease/reconciliation layer that treats extension heartbeat, durable session records, and queued commands as separate truth sources. On every heartbeat, reconcile tab IDs and URLs; when the extension disappears, mark affected sessions stale, quarantine the three pending commands, cancel their waiters with an explicit offline receipt, and rehydrate only idempotent navigations after a fresh heartbeat. Expose a small diagnostic showing last heartbeat, command age, session freshness, and whether a tab is actually controllable.
- **owner gets:** The owner should never hear that a private page was read or an action succeeded when Safari is offline. Today the system can simultaneously report offline/no tab and retain apparently live durable tabs, which risks hanging requests or trusting stale browser state. This makes browser work fail clearly and recover automatically when Safari returns.
- effort: Medium: lease timestamps and state machine in browserBridge/browserSessions, an idempotent command classifier, stale-queue sweeper, and dashboard/receipt fields; add tests for restart, duplicate result, and offline-to-online recovery.  ·  risk: A legitimate Safari sleep or extension restart may mark a session stale and defer work. Recovery is automatic for reads/navigation after a new heartbeat; any mutation remains quarantined and is never replayed. Keep the existing durable session records for manual reattachment.
- cost: Negligible API cost; one small D1/local state update per heartbeat and a periodic local sweep. No new hardware.  ·  latency: Adds milliseconds to enqueue and avoids 45-second dead waits by failing immediately when the lease is expired. Rehydration waits for the next heartbeat.
- security: Improves safety by preventing stale tab IDs and late results from being accepted; bind results to command ID, device lease, and session generation. No new data leaves the device.
- depends on: A functioning Safari extension heartbeat/result path; A typed command state machine distinguishing reads from mutations; Existing browser session and request-ID infrastructure
