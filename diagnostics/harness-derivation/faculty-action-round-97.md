## Capabilities it proposed

### "“Do this for me, and keep going until you can prove whether it actually happened.” The pendant should capture my intent, the judgement agent should turn it into a bounded action bundle, the Mac or private browser should execute it, and perception should independently verify the resulting state before telling me it is done."
- **useful because:** Today an action can be reported as successful even when the UI did nothing, or a browser command can sit pending while the owner assumes it ran. This gives the owner one honest answer: completed with evidence, safely queued with an expiry, or failed with the exact handoff that broke. It works across the pendant, always-on relay, Mac automation, and authenticated browser rather than being another Mac-only feature.
- **path:** pendant → relay-realtime → faculty-judgement → faculty-action → faculty-perception → mac-planner → mac-vision → browser-extension → dashboard
- **model tier:** Use realtime only to capture/confirm the short owner utterance; use a cheaper background model for plan normalization, retries, and evidence reconciliation. No expensive model is needed for routine status polling.
- **latency:** Acknowledge intent on the pendant in under 2 seconds; execute when a surface is available; verify within 10 seconds for Mac actions and up to 60 seconds for browser actions. If unavailable, persist a queued state rather than spinning or claiming completion.
- **cost:** Roughly one short realtime turn plus 1–3 background calls per action; dominant cost is evidence reconciliation and any vision fallback, which should run only when typed/API verification fails.
- **security:** The relay stores only a signed action bundle, expiry, sensitivity class, and receipts—not page contents by default. Irreversible effects require an explicit owner confirmation bound to the exact final parameters; stale approvals, changed targets, and browser-session changes invalidate the bundle. Never treat a relay_result or UI success alone as proof.
- **missing:** A durable two-phase action-bundle state machine (prepared/approved/dispatched/verified/failed/expired) shared by relay and Mac; Typed precondition and postcondition probes for common Mac and browser actions; Independent verification route that can refuse the word done when no authoritative state change is observed; Pendant delivery acknowledgements once a real pendant is connected; Browser extension availability and owner-granted Accessibility/Screen Recording for vision-only actions

### "“Before you send or change anything irreversible, make sure the final target still matches what I originally meant—even if the task crossed apps or took an hour.” The system should detect semantic drift in recipient, amount, account, attachment, destination, or scope across the pendant, relay, Mac, and browser, and interrupt only when the final operation differs materially from the owner’s captured intent."
- **useful because:** Today an approval can become stale or detached from the exact operation after a long workflow, a page refresh, a changed tab, or a handoff between agents. This protects the owner from sending to the wrong person, paying the wrong amount, modifying the wrong account, or approving a broader action than they requested without forcing confirmation for every harmless step.
- **path:** pendant → relay-realtime → faculty-judgement → faculty-action → faculty-perception → mac-planner → mac-vision → browser-extension → dashboard
- **model tier:** Use a cheap background model to normalize and compare structured intent fields. Use realtime only to ask the owner a short clarification when a material mismatch is detected; deterministic hashes and policy rules should handle ordinary matches.
- **latency:** No noticeable delay for reversible steps. For an irreversible step, compare the final parameter capsule in under 500 ms; if ambiguous, pause and ask one concise question rather than executing.
- **cost:** Usually a small structured comparison with negligible model cost; one realtime turn only for genuine mismatches. The dominant cost is extracting final fields from an unstructured page when typed browser evidence is unavailable.
- **security:** Store a minimized intent capsule rather than raw speech or page contents, with sensitivity labels and expiry. Bind confirmation to the exact normalized parameters, session/tab identity, and destination. A changed recipient, amount, or scope invalidates approval. Never silently broaden an action because an agent inferred more context.
- **missing:** A canonical intent capsule schema shared by judgement, action, Mac, and browser; Field-level semantic diffing with materiality policies by action type; A mandatory pre-commit hook that can pause every executor, including AppleScript and browser commands; Final-state extraction for recipients, amounts, attachments, and scopes from each supported app; A concise pendant/dashboard clarification and resume protocol


## Changes it proposed to its own stack

### `integration` — Add a durable, idempotent action-bundle protocol spanning relay and Mac agent. Each bundle contains a requestId, normalized target, exact parameters hash, preconditions, postconditions, expiry, confirmation token (if needed), and preferred executor. Dispatch must first re-check readiness and preconditions; execution emits receipts; faculty-perception independently probes the postcondition through typed APIs/AppleScript/browser inspection. Only a verified postcondition transitions the bundle to completed. Offline browser, missing permissions, absent pendant, timeout, or ambiguous UI transitions to queued/blocked/unknown with a retry policy and never to done. Surface the same state and evidence capsule in relay speech and dashboard, and make retries/undo use the same idempotency key.
- **owner gets:** The owner stops having to guess whether “done” means done. Long or cross-device requests survive leaving the house, avoid duplicate sends, and explain exactly why work is waiting or unverifiable.
- effort: Medium-high: shared schema and D1/local persistence, executor adapters, postcondition probes, and dashboard/relay rendering; then fault-injection tests for offline and timeout cases.  ·  risk: A strict verifier may mark real work unknown when a site has no readable confirmation, so provide a safe “needs review” state and never auto-retry irreversible actions. Recovery is manual review or a bounded retry with the same idempotency key.
- cost: Small D1/local storage and polling cost; background model only for ambiguous evidence. Vision calls are exceptional. No new hardware cost.  ·  latency: Adds one verification round trip after execution; fast typed probes remain under seconds, while browser verification may take tens of seconds.
- security: Improves safety by binding approval to exact parameters and expiry, minimizing replay and duplicate execution. Evidence should be redacted by sensitivity class before relay storage.
- depends on: A durable job runner and existing receipt/undo records; A typed verification/proof tool (currently requested but not yet available); Browser extension recovery/online polling for private pages; Actual pendant connection before spoken delivery acknowledgements can be trusted

### `hardware` — Add a low-power haptic actuator and a three-color status LED (or an RGB LED) to the next pendant revision, with a tiny event protocol from relay: accepted, waiting-for-device, executing, verified, needs-owner, and failed. Keep the existing single button semantics. The firmware should render these states locally from signed short events and fall back to a distinct error pattern when the link drops; it must not imply completion until the relay sends the verified state.
- **owner gets:** The owner can tell at a glance or by touch whether a request was merely heard, is waiting for the Mac/browser, or was actually verified—without opening a phone or trusting a possibly stale spoken response in a noisy place.
- effort: Low-to-medium hardware revision plus firmware event/state handling and relay mapping; validate visibility, haptic distinctness, and battery impact in real wear tests.  ·  risk: Extra notifications could become distracting or reveal sensitive activity in public. Make haptics opt-in per sensitivity class, use neutral patterns by default, and ensure loss of connectivity never freezes the device in a false success state. Recovery is a reboot-safe neutral/unknown pattern.
- cost: Approximately $1–4 BOM increase for actuator, driver/passives, and RGB LED; roughly 5–20 mA only during short haptic/LED pulses, near-zero idle draw. No model/API cost.  ·  latency: Local indication is immediate after relay delivery; verified indication still waits on the real execution and probe path.
- security: Use opaque patterns for sensitive jobs and do not encode message content. Signed event type plus expiry prevents spoofed completion indications.
- depends on: A real pendant hardware revision (current board is a prototype with one LED and no connected device); Relay action-bundle states and authoritative postcondition verification; Firmware update path and power-budget measurement

### `integration` — Implement an intent-drift firewall at the final-commit boundary. Faculty-judgement emits a canonical, expiring intent capsule with typed fields (actor, recipient, destination, amount, object, scope, attachments, side effects, and allowed alternatives). Every Mac, AppleScript, and browser executor must submit its final mutation capsule to the firewall before committing. The firewall performs deterministic field comparisons plus a policy-driven semantic comparison, invalidates stale approvals when tab/session/page identity or material fields change, and returns allow, block, or ask-owner-with-diff. Resume tokens must be single-use and parameter-bound; retries cannot bypass the firewall.
- **owner gets:** The owner gets protection against a subtle but costly failure: the system completes the workflow it inferred rather than the action the owner actually authorized. They see only a short exception when something materially changed, not repetitive approval prompts.
- effort: High integration effort: define the shared schema, instrument every executor, build field extractors and policy tests, then fault-test changed recipients, amounts, tabs, attachments, and partial retries.  ·  risk: Overly strict comparison may interrupt legitimate edits, while weak extraction may miss drift. Default uncertain cases to ask-owner for irreversible effects, allow only explicitly safe alternatives, and retain a human-readable before/after diff for recovery.
- cost: Small persistent capsules and deterministic comparisons; occasional cheap semantic-model calls and rare realtime clarification. No hardware cost.  ·  latency: Sub-second for typed fields; roughly 1–3 seconds when semantic extraction is required, before an irreversible commit.
- security: Reduces replay, confused-deputy, wrong-recipient, and stale-approval risk. Capsules must be encrypted or minimized, expire quickly, and exclude raw private page content unless needed for the diff.
- depends on: A shared action protocol across relay and local Mac agent; Typed final-value extraction from browser and app adapters; An owner confirmation/resume channel on the pendant or dashboard
