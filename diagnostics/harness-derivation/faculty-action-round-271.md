## Capabilities it proposed

### "“Prove what you changed in that last action.”"
- **useful because:** A completion message is not enough for a consequential action. The owner can ask for a compact, privacy-safe audit that ties the intent, executor receipt, fresh postcondition check, and exact surface touched together—especially useful when they are away from the Mac and cannot inspect the screen.
- **path:** pendant sends an opaque operation reference (or resolves “that last action” to the latest acknowledged operation) and receives a spoken summary plus a short haptic status → relay assembles the operation ledger, executor receipt, verifier provenance, timestamps, and terminal state → Mac agent re-runs only the read-only postcondition check against current app/file/browser state when the original evidence is stale → browser extension supplies a redacted field/URL fingerprint or browser-state proof for owner-private pages, never raw credentials or page bodies
- **model tier:** Deterministic aggregation first; use a cheaper background model only to turn typed evidence into a short owner-readable explanation. Realtime is unnecessary unless the owner asks follow-up questions.
- **latency:** Return cached proof in under 1 s; if a fresh check is required, under 5 s. If evidence cannot be obtained, say exactly which link or postcondition is missing rather than filling gaps.
- **cost:** No model call for structured proof; bounded ledger/provenance storage. A short summarization call is typically <$0.01 and only when evidence has multiple steps.
- **security:** Operation IDs are opaque and session-bound. Evidence defaults to hashes, URLs/origin, app names, and field labels; secrets, message bodies, tokens, and page contents are excluded unless the owner explicitly asks for a sensitivity-scoped snippet. Never treat proof generation as permission to mutate state.
- **missing:** A read-only audit aggregation route that joins operation ledger, POST /execute receipts, and verify_operation_step provenance.; A freshness policy distinguishing cached proof from a newly rechecked postcondition.; A pendant command/voice intent resolver for “that last action” that cannot cross session boundaries.

### "“Preview this before you do it.”"
- **useful because:** The owner can see the exact consequence of a multi-surface action before committing—recipients, files, browser fields, and irreversible side effects—without trusting a vague plan or accidentally performing it. This is the safest way to use the system for high-stakes tasks while away from the Mac.
- **path:** pendant captures the spoken goal and renders pending/preview-ready status through the existing outcome beacon; it never receives secrets or executes → relay creates a non-mutating preview transaction with an expiry and joins the plan to the later approval nonce → Mac agent uses AppleScript, read-only app/file inspection, and browser snapshot/inspect to construct a typed before/after diff; all mutation actions are prohibited in preview mode → browser extension returns only redacted target summaries and normalized field diffs for authenticated pages → faculty-action presents the preview over audio and stores its digest so a later physical approval can be bound to exactly this preview, not to a changed page
- **model tier:** Use a cheaper background/planning model for decomposition and explanation; deterministic surface adapters produce the actual diff. Realtime is only needed if the owner asks follow-up questions while previewing.
- **latency:** Simple previews under 3 s; multi-app/browser previews under 8 s. If a surface cannot be inspected, label that portion unknown and refuse to claim a complete preview.
- **cost:** One planning call plus bounded read-only probes; roughly $0.01–$0.05 depending on task complexity. No cost for the eventual execution beyond normal action calls.
- **security:** Preview mode has a hard no-write capability token enforced by the Mac agent and browser bridge, not merely a prompt instruction. Secrets are redacted; preview digests expire quickly and are session-bound. Approval is required again if the target fingerprint or proposed effect changes.
- **missing:** A capability-scoped no-write token enforced by every action adapter, including AppleScript and browser actions.; Typed preview diff schema covering app_state, file_state, browser_field, browser_url, and message_draft.; A binding from preview digest to the existing physical_transaction_approval_latch and verified commit protocol.

### "“Why did that stop?”"
- **useful because:** When a task stalls across LTE, relay, Mac, or a logged-in browser, the owner needs a causal explanation—not “still working.” This capability identifies the first failed handoff, distinguishes blocked, expired, cancelled, verifier-unknown, and offline states, and gives a safe next action without retrying blindly.
- **path:** pendant sends the operation reference or resolves the most recent pending operation; it receives a concise spoken diagnosis and a safe-retry/cancel haptic pattern → relay correlates operation timeline, lease expiry, queue state, and delivery acknowledgements across the cellular conversation and Mac job → Mac agent contributes read-only GET /observe, GET /browser/status, job receipts, and current app/browser reachability without performing a retry → browser bridge reports session/device heartbeat age, pending command age, and whether the target tab/session still matches the operation fingerprint → faculty-action classifies the terminal cause and offers exactly one reversible recovery (resume, re-prepare, or cancel), never silently retries an irreversible step
- **model tier:** Deterministic cause classification over typed events; a cheap background model may phrase the timeline. Realtime is reserved for an interactive follow-up, not diagnosis itself.
- **latency:** Cached diagnosis under 1 s; fresh cross-surface checks under 5 s. If evidence conflicts, report “unknown cause” and preserve the timeline rather than guessing.
- **cost:** Usually no model cost; bounded event joins and read-only probes. Optional explanation costs <$0.01. Storage is a compact event timeline per operation with expiry.
- **security:** Expose only owner-authorized operation metadata, redacted URLs/app names, and error classes; never relay browser contents or credentials. A diagnosis cannot authorize mutation. Recovery requires the existing physical approval latch when risk is irreversible.
- **missing:** A normalized cross-surface failure taxonomy and event schema (lease_expired, offline, cancelled, verifier_unknown, target_changed, executor_failed).; A read-only correlation route joining relay jobs, Mac receipts, browser status, and audio delivery ACKs.; A policy that selects one safe recovery and binds it to the original operation/preview digest.

### "“If the price drops below $X before Friday, buy one—but only if shipping is free, and tell me exactly what you found.”"
- **useful because:** The owner gets bounded, conditional delegation instead of either babysitting a browser or granting an unconstrained agent permission. The system can wait while the owner is asleep, evaluate a private logged-in page when it changes, and act only inside explicit limits, with a verifiable explanation of both the decision and the purchase.
- **path:** pendant captures the condition, ceiling, expiry, and notification rule; a deliberate physical approval establishes the delegation but does not expose credentials → relay persists a signed delegation capsule, wakes the workflow on schedule or browser events, and revokes it automatically at expiry or on owner cancellation → browser extension watches the authenticated shopping session and returns only normalized product, price, shipping, availability, and checkout-state fields → Mac agent performs read-only comparison and prepares the exact checkout manifest; it must stop if target identity, total, shipping, or seller changes → faculty-action submits only when every predicate and risk policy passes, then faculty-perception independently verifies order confirmation, total, and item identity before reporting success; otherwise it reports expired/unknown and never improvises
- **model tier:** Cheaper background model for extracting and evaluating conditions; deterministic predicate evaluation and risk gates for execution. Realtime only for clarifying an ambiguous condition before the delegation is armed.
- **latency:** Event reaction within 30 seconds of a browser update; scheduled polling according to the owner's cadence. Checkout verification within 10 seconds. No action after expiry, stale session, or missing evidence.
- **cost:** Background evaluation is a few cents per active delegation depending on polling; browser/Mac reads dominate. One execution and verification pass costs roughly <$0.05 excluding external purchase charges.
- **security:** Delegations are least-privilege, session-bound, signed, expiring, and revocable. Never store or relay payment credentials. Require a second physical confirmation for purchases above the owner's configured threshold or whenever a predicate is underspecified. If a page changes, fail closed rather than silently broaden the authorization.
- **missing:** A first-class signed conditional-delegation capsule with predicates, expiry, budget, allowed domains/actions, and revocation state.; An event/schedule trigger that can wake a dormant workflow and a durable evaluator for typed predicates.; A checkout-specific adapter that emits a redacted manifest and a post-submit proof object; generic browser clicks are insufficient for truthful purchase verification.; Owner-configurable thresholds and action policy data; defaults must remain conservative until the owner chooses them.

### "“For the next hour, keep everything on-screen private: you may act, but do not speak page contents or play them aloud.”"
- **useful because:** The owner can wear the pendant in public or around other people without choosing between disabling the system and leaking private browser or message content. This is a temporary, owner-visible privacy mode enforced across every output path, not a prompt preference that one agent may forget.
- **path:** pendant accepts a physical gesture and gives a distinct haptic acknowledgement; it stores only the mode, expiry, and policy ID → relay distributes a signed privacy lease with an absolute expiry to realtime conversation, Mac jobs, and audio delivery → Mac agent and browser extension classify and redact spoken/displayed evidence, replacing private values with typed summaries or silence → ESP32 audio bridge enforces an output class tag, refusing payloads marked private while still permitting minimal status tones → faculty-action blocks any action whose required confirmation would reveal protected content, and emits a compact “blocked by privacy lease” result
- **model tier:** Deterministic policy enforcement; no model should decide whether a value is safe after the lease is active. A cheap classifier may label untrusted content before it reaches the policy boundary.
- **latency:** Mode activation and propagation under 1 second when connected; queued devices apply it on reconnect before accepting content. Expiry is local-clock enforced so a delayed packet cannot extend the lease.
- **cost:** Negligible runtime model cost; small signed lease and classification metadata. One-time engineering across relay, Mac/browser, and bridge firmware.
- **security:** Fail closed on missing, invalid, or expired leases for sensitive output. The lease must not contain page contents or credentials, and its state must be visible through haptics. Emergency status and owner-requested deactivation remain explicit exceptions; every exception is logged.
- **missing:** A cross-surface signed privacy lease and policy vocabulary for output classes.; Browser/Mac redaction enforcement before model/audio handoff, rather than only after generation.; An ESP32 output gate that understands privacy classes and can suppress queued playback.; A local monotonic expiry implementation on the pendant and bridge, independent of the unsourced pendant wall clock.

### "“During this call, listen for the appointment details, quietly summarize them to me, and only send a reply after I approve it with the pendant.”"
- **useful because:** The owner can handle a real phone call while keeping hands and eyes free: the system extracts dates and commitments, privately gives a concise haptic/audio summary, drafts a reply, and prevents an accidental text or booking. It combines the pendant, real iPhone, Mac control, and approval boundary in a way no single surface can provide.
- **path:** pendant captures the session start/stop gesture, delivers private summaries through the owner's chosen audio path, and accepts a deliberate approval or cancellation gesture → relay maintains a short-lived call-session state, routes low-latency audio/events, and expires all transcripts and drafts at session end → Mac iPhone Mirroring / ios control observes the live call and Messages/Calendar context, extracts only requested appointment fields, and prepares but does not send a draft → faculty-action binds the draft to the exact conversation/session and waits for the physical approval latch before sending; faculty-perception verifies the sent-message state and calendar result independently → browser/Mac surfaces remain excluded unless the owner explicitly adds them, preventing an incidental logged-in tab from receiving call content
- **model tier:** Realtime model for low-latency speech extraction and concise summaries; cheaper background model for draft polishing and calendar normalization. Deterministic policy controls sending and expiry.
- **latency:** Haptic acknowledgment under 300 ms; summary updates within 1–2 seconds of a detected commitment; approved message verification within 5 seconds. If recognition is uncertain, ask rather than infer.
- **cost:** Realtime inference dominates, roughly $0.05–$0.30 per short call depending on audio duration; transcripts and drafts are short-lived and bounded.
- **security:** Explicit session gesture and visible/haptic recording indicator are mandatory. Do not retain call audio by default; keep only owner-approved structured fields. Never send or create a calendar event without a fresh physical approval tied to the displayed/spoken draft. Unknown iPhone state must fail closed.
- **missing:** A privacy-preserving live call audio bridge from the real iPhone/Mac to relay-realtime without opening an uncontrolled microphone.; A typed iOS call/message observation and draft API with session identity and redacted fields.; A pendant session indicator and stop gesture that works offline or during a dropped relay link.; A policy and verifier integration for message send and calendar creation postconditions.


## Changes it proposed to its own stack

### `integration` — Make verified commit the mandatory boundary for every externally visible mutation: POST /execute or browser actions first record an operation/step intent and executor receipt, then faculty-action calls verify_operation_step against fresh Mac/browser state; only a passing postcondition may emit the signed tactile_action_outcome_beacon success. A failed or unavailable verifier commits UNKNOWN (never success), preserves the receipt and evidence provenance, and routes reversible steps to an explicit retry/undo state rather than silently continuing. Carry operation_id, step_id, attempt_id through action ledger, job receipts, and the pendant outcome envelope.
- **owner gets:** The owner can trust that “sent,” “changed,” or “done” means the outside world was actually checked—not merely that our Mac agent returned. When a browser or app is stale, they get an honest unknown and a safe retry path instead of a dangerous false success.
- effort: Medium: add correlation fields and a commit state machine in the existing action ledger/policyRouter, invoke the already granted verifier after each mutation, and map states to the existing pendant beacon.  ·  risk: Some actions have no observable postcondition and will become UNKNOWN until a generic verifier locator is supplied; retries must be idempotent to avoid duplicate sends. Recover by retaining executor receipts and requiring explicit owner approval for an unverified continuation.
- cost: One read-only verifier call per mutation step; low storage for IDs, hashes, and compact provenance. More latency (typically one Mac/browser round trip) and modest model context for interpreting verification failures.  ·  latency: Adds roughly 0.5–3 seconds per mutating step, but avoids costly and harmful false completion.
- security: Improves security: verifier receives only typed postconditions and sensitivity-scoped evidence, and the pendant receives outcome metadata—not page secrets or form contents. Unknown is fail-closed.
- depends on: verify_operation_step (t21-8d1c); POST /execute action receipts; GET /jobs/:jobId/receipts; tactile_action_outcome_beacon; existing actionLedger.js and approvalHandoff.js

## Its own summary

Round 271 produced three new recorded capabilities/changes: (1) mandatory verified commit after every mutation, with UNKNOWN rather than false success; (2) owner-requested privacy-safe audit proof tying intent, receipts, fresh state, and provenance; (3) preview-before-execute with a hard no-write capability and approval bound to the preview digest; plus a fourth capability, causal “Why did that stop?” diagnosis across relay/Mac/browser/audio. I also told faculty-perception to use verify_operation_step as the evidence fence. The recorder rejected exact-answer replay because it already exists; I did not rephrase it.

**Biggest unknown:** The system still needs implementation decisions, not another proposal: a no-write enforcement token across every Mac/browser adapter, a normalized cross-surface event/failure schema, and the owner's policy for which recovery actions may run automatically versus require physical approval. The owner also still needs to choose the future wheel/second-button mapping; today's two buttons are already assigned.
